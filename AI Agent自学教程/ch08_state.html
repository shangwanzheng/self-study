第 8 章 · 方法

状态机、持久化与人工确认

档案助理查到上限 200 元以后，要能拿着这次观察回到规划，把观察存进检查点；算出超出 150 元时先停下来等人确认，确认之后才给出最终回答。

预计学习 90 分钟前置：第 3、4、7 章交互演示 2 个离线可打开
  • 能说明链式流程为什么只能向前，以及有环的状态图怎样让观察回到规划。
  • 能在回环里守住 maxSteps 4，第 5 步不发起。
  • 能把工具观察（上限 200 元）写进检查点，并在刷新后原样读回。
  • 能让超出 150 元的情况先进入等待确认，确认前最终回答为空。

这一章：观察能回去，观察要存下，超出就等人

第 4 章的循环最多走 4 步，第 7 章说明模型本身不记事。本章把这两件事落到流程上：教学句「上周报销超了：上限 200 元，这单填了 350 元。」进来后，规划先决定调用 lookupClause，观察拿到第 3 条的上限 200 元并写进检查点，再回到规划算出 \(350 - 200 = 150\) 元。超出大于 0，流程停在「等待确认」，人确认后回答节点才写出 200 和 150。图框架里检查点、中断、恢复用什么参数名，以该框架文档原文为准，本章不写死任何菜单或参数。

可以回到规划

链式只能向前。图里有一条「观察 → 规划」的边，才能拿着 200 回去改计划。回环仍受 maxSteps 4 限制。

观察要留下

观察（上限 200）写进检查点。刷新后从检查点读回；没有检查点，这次观察就没了，不能再报 200。

超出先等人

超出 150 元时转入等待确认。确认前最终回答为空；确认后回答同时写出 200 和 150。

8.1 链式走完就回不去

先看最朴素的写法：把规划、行动、观察、回答排成一条链，每一环只知道下一环是谁。

问题：规划在观察之前就做完了。它决定「调用 lookupClause 查第 3 条，然后回答」。观察拿回上限 200 元以后，链上的下一环只有回答，没有一条边能把 200 送回规划。于是「这单 350 元是否超出、超出了要不要等人」这类要看到观察才能定的决定，链式流程做不出来。

符号与单位：节点用英文名 plan（规划）、act（行动）、observe（观察）、answer（回答）。金额一律用整数元。

// 链式：只有向前的边，观察之后没有路回到规划
const chain = ['plan', 'act', 'observe', 'answer'];

function nextInChain(node) {
  const i = chain.indexOf(node);
  return chain[i + 1] || null;
}

console.log(nextInChain('observe')); // answer，回不到 plan

示例代码：examples/ch08/chain.js

链式不是错，是不够

步骤固定、不需要看结果再决定的任务，链式足够。报销这句要先看到上限 200 才知道超出 150，决定依赖观察，所以需要能往回走的边。

可操作对象：在 chain.js 里对每个节点调用 nextInChain，确认没有任何返回值是 'plan'。

8.2 有环：观察之后可以回到规划

8.1 的链缺一条往回的边。把流程改成状态图：节点是状态，边是允许的转移，其中一条边从观察指回规划。

状态图：规划可以去行动、去等待确认或去回答；行动之后一定是观察；观察之后回到规划。第二次进入规划时，状态里已经有观察到的 200，规划就能算出 \(350 - 200 = 150\)，并据此选下一条边。这条「观察 → 规划」的边就是环。

// 有环：观察之后可以回到规划
const edges = {
  plan: ['act', 'waitHuman', 'answer'],
  act: ['observe'],
  observe: ['plan'],
  waitHuman: ['answer'],
  answer: []
};

console.log(edges.observe); // [ 'plan' ]

示例代码：examples/ch08/graph.js

链式

规划 → 行动 → 观察 → 回答。观察的 200 只能被回答节点照抄，规划看不到它。

有环

规划 → 行动 → 观察 → 规划 → 等待确认 → 回答。第二次规划拿着 200 改计划。

状态图画成不能回去的直线

画图时把节点从左到右排成一行、只画向右的箭头，就又退回了链式。检查办法：在图里找有没有一条从观察出发、指向规划的边。找不到，这张图就不能拿着观察回去改计划。

只向前 / 观察后可回到规划切换分段 · 点「下一步」逐步走
观察要点：① 「只向前」走到观察以后只能去回答，回答里没有超出 150 的判断，也没有等人。② 「观察后可回到规划」在观察之后回到规划，第 3 步算出超出 150 元，转入等待确认，已用步数停在 3。③ 两种模式的已用步数都不超过 4。④ 观察到的 200 在回环模式里写进了检查点。

8.3 仍只能走 4 步

有了环，流程就可能一直绕下去。第 4 章的 maxSteps 4 在这里照样生效。

计步约定：与第 4 章同一套四步。第 1 步规划，决定调用 lookupClause。第 2 步行动并观察，拿到上限 200 元，写入检查点。第 3 步回到规划，用 350 减去 200 得到超出 150 元，转入等待确认。第 4 步在人确认之后写出回答。等待确认停在第 3 步之后、第 4 步之前，确认本身不调用模型。第 5 步不发起。

// 回环不放宽上限：与第 4 章同一套四步，第 5 步不发起
// 1 规划；2 行动并观察；3 算出超出并等待确认；4 确认后回答
const maxSteps = 4;

function nextStep(state) {
  if (state.step >= maxSteps) {
    return { ...state, status: 'stopped' };
  }
  return { ...state, step: state.step + 1, status: 'running' };
}

console.log(nextStep({ step: 3 }).step);   // 4
console.log(nextStep({ step: 4 }).status); // stopped

示例代码：examples/ch08/step-guard.js

为了回环把步数放到 4 以上

「多绕几圈总能做完」不是理由。环让流程可以回去，不等于可以无限回去。maxSteps 是 4，回环版和链式版用同一个上限；用满 4 步还没结果，状态转为停止并如实报告。

可操作对象：把 nextStep 从 { step: 0 } 开始连续调用 5 次，前 4 次步数依次变为 1、2、3、4，第 5 次返回 stopped。

8.4 检查点记下这次观察

8.3 的状态里已经有步数和观察。第 7 章说过模型不记事，状态如果只放在内存里，进程一断就没了。所以每走完一步，把状态写进检查点。

检查点里放什么：步数、当前状态、观察。观察要带上来源：工具名 lookupClause、条款号 3、上限 200 元。之后任何一步要用上限，都从这里读，不再让模型重新说一遍。检查点按线程标识（本例 demo-thread）分开存放，一个会话一份。

// 观察写进检查点：上限 200 元来自 lookupClause 的结果
// store 只是教学替身；真实持久化在服务端，用所选框架文档规定的检查点接口
function saveCheckpoint(store, threadId, state) {
  store[threadId] = JSON.stringify(state);
}

const store = {};
saveCheckpoint(store, 'demo-thread', {
  step: 2,
  status: 'observed',
  observation: { tool: 'lookupClause', clauseNo: 3, limitYuan: 200 }
});

console.log(store['demo-thread']);

示例代码：examples/ch08/checkpoint.js

把持久化说成把密钥写进前端页面

持久化存的是流程状态：步数、状态、观察。它落在服务端的存储里，存储方式和接口按所选框架文档原文配置。访问模型或存储所需的凭据由服务端持有，不进检查点，也不进前端页面。本课所有示例里都没有凭据值。

可操作对象：运行 checkpoint.js，打印出的字符串里应能找到 "limitYuan":200，找不到任何凭据字段。

8.5 刷新后读检查点，上限仍是 200

8.4 把观察存下了。现在模拟页面刷新或进程重启：内存清空，流程从检查点接着走。

有检查点：按 demo-thread 读回状态，observation.limitYuan 仍是 200，步数仍是 2，下一次进入规划是第 3 步。没有检查点：读回 null。这时这次观察已经没了，流程只能从头重新调用 lookupClause，不能凭印象报「上限 200」。

// 刷新后从检查点读回观察，原样使用，不改写上限
function loadCheckpoint(store, threadId) {
  const raw = store[threadId];
  return raw ? JSON.parse(raw) : null;
}

const saved = {
  'demo-thread': '{"step":2,"status":"observed","observation":{"tool":"lookupClause","clauseNo":3,"limitYuan":200}}'
};

const restored = loadCheckpoint(saved, 'demo-thread');
console.log(restored.observation.limitYuan); // 200

const lost = loadCheckpoint({}, 'demo-thread');
console.log(lost); // null：没有检查点，这次观察就没了

示例代码：examples/ch08/resume.js

没有检查点就认为刷新后还看得见 200

刷新前屏幕上出现过 200，不代表刷新后流程还拿得到它。状态只在内存里时，刷新就丢了。读回为 null 就重新查，不能把记忆里的数当作观察。

检查点里改写上限

恢复时只读、不改观察。不要在读回后把 limitYuan 换成别的数、四舍五入或按「常识」补一个值。上限的唯一来源是那次 lookupClause 的观察；要更新它，就重新调用工具得到新的观察。

8.6 超出 150 元必须等人

8.5 读回的观察进入第 3 步规划。规划现在拿着 200，可以对这单 350 元做判断了。

判断：\[\text{超出} = 350 - 200 = 150\ \text{元}\] 超出大于 0，规划走「等待确认」这条边，状态写成 waitHuman，confirmed 为 false，步数记为 3，并且把这份状态也写进检查点。流程停在第 4 步之前，不调用模型。超出为 0 时才直接走向回答。

// 回到规划后先算超出；超出就转入等人，不往回答走
function planAfterObserve(state, claimedYuan) {
  const overYuan = claimedYuan - state.observation.limitYuan;
  const next = { ...state, step: state.step + 1, overYuan: overYuan };
  if (overYuan > 0) {
    return { ...next, status: 'waitHuman', confirmed: false };
  }
  return { ...next, status: 'answer' };
}

const s = planAfterObserve({ step: 2, observation: { limitYuan: 200 } }, 350);
console.log(s.step, s.status, s.overYuan); // 3 waitHuman 150

示例代码：examples/ch08/interrupt.js

超出了仍直接回答

算出 150 以后顺手把「超出 150 元」回给用户，看起来更快，但跳过了这一步的意义：超出的单子要人来定。状态是 waitHuman 时，下一条边只能是等人，不能是回答。

暂停要靠框架的中断机制

「停在这里、之后接着走」在图框架里通常叫中断与恢复。具体怎样声明中断点、怎样带着人的输入恢复，参数名和用法以该框架文档原文为准。

8.7 未确认不出最终回答

8.6 让流程停在等待确认。停着的时候，最终回答必须是空的，不能先给一个「草稿答案」。

门槛：回答节点只认 confirmed === true。状态还是 waitHuman，或者 confirmed 不是 true（包括 false、缺失、未定义），一律返回空字符串。

// 未确认不出最终回答：只认 confirmed === true
function finalAnswer(state) {
  if (state.status === 'waitHuman' || state.confirmed !== true) {
    return '';
  }
  return '报销上限 ' + state.observation.limitYuan + ' 元，这单超出 ' + state.overYuan + ' 元。';
}

const waiting = { status: 'waitHuman', confirmed: false, overYuan: 150, observation: { limitYuan: 200 } };
console.log(JSON.stringify(finalAnswer(waiting))); // ""

示例代码：examples/ch08/answer-gate.js

确认按钮隐藏就当成已经同意

界面上没显示确认按钮、按钮被折叠、用户没点就关了页面，都不是同意。同意只能是一条明确写进状态的 confirmed: true。没有这条记录，流程就一直停在等待确认。

直接回答 / 先等确认切换分段 · 在「先等确认」下点「人工确认」
观察要点：① 「直接回答」一算出超出就给了回答，读数标红，这是本章要避开的做法。② 「先等确认」下，未确认时停在第 3 步，最终回答为空。③ 点「人工确认」后进入第 4 步，最终回答才出现，并同时写出 200 和 150。④ 确认前后检查点里的上限都是 200。

8.8 确认后回答同时写出 200 和 150

最后一环：人的确认写回状态，流程从等待确认恢复，走到回答节点。

确认是什么：它是来自流程外部的一条输入，把 confirmed 改为 true、状态改为 answer，并进入第 4 步。确认本身不调用模型。确认前停在第 3 步，最终回答为空；确认后已用步数是 4。回答节点从检查点里取上限 200 和超出 150，两个数一起写进最终回答：「报销上限 200 元，这单超出 150 元。」只写其中一个数，读的人就没法核对。

// 人工确认是外部输入，写回状态后才进入第 4 步回答；确认本身不是模型调用
function confirmByHuman(state) {
  return { ...state, confirmed: true, status: 'answer', step: state.step + 1 };
}

function finalAnswer(state) {
  if (state.status === 'waitHuman' || state.confirmed !== true) {
    return '';
  }
  return '报销上限 ' + state.observation.limitYuan + ' 元，这单超出 ' + state.overYuan + ' 元。';
}

const waiting = { step: 3, status: 'waitHuman', confirmed: false, overYuan: 150, observation: { limitYuan: 200 } };
const done = confirmByHuman(waiting);
console.log(done.step, finalAnswer(done)); // 4 报销上限 200 元，这单超出 150 元。

示例代码：examples/ch08/confirm.js

把人工确认当成另一次模型调用

让模型「再想一下这单要不要放行」不是人工确认。模型的回答仍是模型的输出，只是又走了一步。人工确认必须由人给出，经界面或接口写回状态。

整条链对一遍

第 1 步规划 → 第 2 步行动 lookupClause，观察上限 200，写检查点 → 第 3 步回到规划，算出超出 150，转入等待确认（最终回答为空）→ 人工确认 → 第 4 步回答写出 200 和 150。第 5 步不发起。

本章避坑清单

  1. 没有检查点就认为刷新后还看得见 200；读回为空就重新调用 lookupClause。
  2. 超出了仍直接回答；超出 150 元时状态必须是等待确认。
  3. 为了回环把步数放到 4 以上；回环仍受 maxSteps 4 限制，第 5 步不发起。
  4. 把人工确认当成另一次模型调用；确认是人写回状态的外部输入。
  5. 在检查点里改写上限；恢复时观察只读，上限仍是 200。
  6. 确认按钮隐藏就当成已经同意；只认明确的 confirmed: true。
  7. 把状态图画成不能回去的直线；图里要有从观察指回规划的边。
  8. 把持久化说成把密钥写进前端页面；检查点只存流程状态，凭据留在服务端。

本章小结与延伸阅读

链式只能向前，有环才能拿着观察回去改计划。回环仍受 maxSteps 4 限制，基准流程走满四步：规划、行动并观察、算出超出并等待确认、确认后回答。工具观察（上限 200 元）在第 2 步写进检查点，刷新后原样读回；没有检查点，这次观察就没了，不能再报 200。第 3 步算出 \(350 - 200 = 150\) 元超出，流程停在等待确认，确认前最终回答为空；人工确认后第 4 步同时写出 200 和 150。
