4.1 Worker 碰不到 DOM

订单表先在渲染进程的主线程上。Web Worker 是另一条线程，先看它能不能碰到这棵 DOM。

问题：计算挪进 Web Worker 之后，能不能直接改订单表上的格子？

约定：这一节的 Worker 指页面用 new Worker 创建的 Web Worker。它有自己的全局，跑在渲染进程里的另一条线程上，没有这份文档的 document，也没有页面的 window。订单表的 DOM 只在渲染进程主线程。Worker 想告诉页面一个结果，就 postMessage；页面收到消息之后，仍由主线程改 DOM。规范上的全局、消息和脚本加载以 WHATWG HTML 里 Workers 一节的原文为准。

线程 主线程

订单表 DOM 在这里。stock 与 amountFen 的格子由这里读写。

线程 Web Worker

没有这棵 DOM。它只能收到消息、做完计算，再把结果发回来。

消息 postMessage

两边交换的是消息。下一节写这份消息怎样被拷走。

用教学订单页走一遍：表在主线程。主线程用 document.getElementById 能读到 stock 和 amountFen。同一句查询放进 Worker，document 不存在，读数是碰不到。字段仍是基准：stock 为 8，amountFen 为 19950。碰不到 DOM 不会把这两个数改掉，也不会把表搬进 Worker。

var table = document.getElementById('order-table'); var stock = table.querySelector('[data-field="stock"]').textContent; var amountFen = table.querySelector('[data-field="amountFen"]').textContent; var canRead = !!table;

示例代码：examples/ch04/read-table.js

self.onmessage = function () { var canRead = typeof document !== 'undefined' && !!document.getElementById('order-table'); self.postMessage({ canRead: canRead }); };

示例代码：examples/ch04/worker-dom.js

主线程那一份里，表在文档中，canRead 为真。Worker 那一份里 typeof document 为 "undefined"，后面的 getElementById 不会执行，canRead 为假。页面收到的消息是 { canRead: false }。

在 Worker 里改订单表 DOM

在 Worker 脚本里写 document、改表格节点或改格子的文本，碰不到这棵订单表。要改显示，把结果发回主线程，由主线程改 DOM。

把消息当成共享了同一棵表

postMessage 过去的是消息，不是订单表节点的别名。Worker 里没有一份可以赋值的 DOM。下一节会看到，普通行对象还会被拷成另一份。

可操作对象：切换下面的分段。主线程应读出「能读到」，Worker 应读出「碰不到」。两段的表上 stock 都是 8，amountFen 都是 19950。再在纸上把 DOM 画在主线程，Worker 一格写「没有 document」。

订单表 DOM 谁读得到切换分段
观察要点：① 分段停在主线程时，读数是能读到，订单表节点在这份文档里。② 分段停在 Worker 时，读数是碰不到。Web Worker 没有这棵 DOM。③ 两种分段下表上 stock 仍是 8，amountFen 仍是 19950。读不到 DOM 不会把字段改掉。④ 切换分段只改变这一侧能不能读，不把表格节点搬进 Worker。

4.2 结构化克隆传 10000 行

DOM 的边界定了。消息要进 Worker，就看 listN 那 10000 行怎样被拷走。

问题：主线程把整表行数据发给 Worker，两边是同一份数组，还是各持一份？

约定：worker.postMessage(list) 按结构化克隆把消息拷到另一侧。算法以 HTML 规范里的 structured clone 为准。普通对象、数组、数字和字符串会得到一份新的副本。structuredClone 是同一套算法在主线程上的入口，用来把副本留在身边看。函数和 DOM 节点不能克隆，会得到 DataCloneError。可转移的是 ArrayBuffer 这类对象；订单行是普通对象，传过去的是拷贝，所有权不会从主线程挪走。

function buildRows(n, stock, amountFen) { var list = []; var i; for (i = 0; i < n; i++) { list.push({ stock: stock, amountFen: amountFen }); } return list; } var list = buildRows(10000, 8, 19950); var copied = structuredClone(list); copied[0].stock = 7;

示例代码：examples/ch04/clone-rows.js

跑完之后 list.length 与 copied.length 都是 10000。copied[0].stock 是 7，list[0].stock 仍是 8，list[0].amountFen 仍是 19950。发给 Worker 时写 worker.postMessage(list)，Worker 收到的是又一份克隆，不是 list 这个引用。

用教学订单页走一遍：listN 的基准是 10000，每行带着基准 stock 8 和 amountFen 19950。克隆完成时主线程上会同时有原列表和副本。发送这一侧要走完这份克隆，Worker 省下的是它接下来的计算，不是这 10000 行克隆本身占掉的时间。这段时间仍用第 3 章的 frameBudgetMs 和 longTaskMs 去量，本章不另设一个毫秒门槛。接口一页的 size 是 20。真要少传数据，就传这一页，而不是先把 listN 行克隆进 Worker 再在那边切片。

改副本时以为原列表一起变了

Worker 里把收到的行的 stock 写成 7，主线程上的 list[0].stock 仍是 8。要让表格变成 7，Worker 得再发一条消息，由主线程写 DOM。

把订单表节点传进 Worker

DOM 节点克隆不了。postMessage(table) 不会让 Worker 拿到这棵树，只会失败。4.1 的边界在这里是同一件事：表留在主线程，消息里只放能克隆的数据。

可操作对象：在控制台跑示例里的 buildRows 和 structuredClone。把副本第一行的 stock 改成 7，读原列表第一行，应为 8。再把行数记成 listN，也就是 10000。

4.3 SharedWorker 与多 Tab 一条连接

一条消息是一次拷贝。多个 Tab 要共用的是连接，不是这棵 DOM。

问题：两个订单页 Tab 都要听同一条订单连接时，连接开在每一页里，还是开在一处？

约定：SharedWorker 可以被同一源上的多个浏览上下文连接，例如多个 Tab。每个 Tab 用 new SharedWorker 得到自己的 port，并调用 port.start()。Worker 脚本在 onconnect 里拿到 e.ports[0]。上游那一条连接只在 SharedWorker 里创建一次，后来的 Tab 只把自己的 port 登记上去。port 上的消息仍然按结构化克隆传递。SharedWorker 也没有各个 Tab 的 document。脚本全局和 connect 事件以 HTML 规范原文为准。某个 Tab 关掉之后，这条 SharedWorker 还会留多久，以这一版浏览器的行为为准，不把 connectTimeoutMs 写成它的寿命。

Tab 页面 A

自己的 DOM，自己的 port。stock 仍是这一页上的 8。

一处 SharedWorker

多个 port 登记在这里。名为 orders 的那条连接只创建一次。

Tab 页面 B

另一棵 DOM，另一个 port。它不和页面 A 共用节点。

var worker = new SharedWorker('orders-shared.js'); worker.port.start(); worker.port.onmessage = function (e) { // e.data 来自 SharedWorker 里那一条连接的转发 }; worker.port.postMessage({ apiPath: '/api/orders', page: 1, size: 20 });

示例代码：examples/ch04/page-connect.js

var ports = []; var connection = null; onconnect = function (e) { var port = e.ports[0]; ports.push(port); if (!connection) connection = { name: 'orders' }; port.onmessage = function (ev) { var i; for (i = 0; i < ports.length; i++) { ports[i].postMessage({ via: connection.name, body: ev.data }); } }; port.start(); };

示例代码：examples/ch04/orders-shared.js

两个文件都在 examples/ch04/。页面里的地址写成同目录的 orders-shared.js。第二个 Tab 再连上时，connection 已经有了，不会再创建第二条；ports 里则有两个 port。

用教学订单页走一遍：请求路径是 apiPath，也就是 /api/orders。页码 page 为 1，每页 size 为 20。两个 Tab 把这份查询发给同一个 SharedWorker，由那一条名为 orders 的连接去取。回来的消息按 port 分发。每个 Tab 的主线程收到之后，各自改自己的订单表。stock 8 和 amountFen 19950 仍是各页文档上的字段。SharedWorker 写不了其中任何一棵 DOM。

多个 Tab 被当成一棵 DOM

共用 SharedWorker 只说明连接和 Worker 全局是一处。每个 Tab 仍有自己的文档。在 Worker 里改表格，仍然是 4.1 的那件事：碰不到 DOM。

每个 Tab 再开一条上游连接

onconnect 里若总是新建连接，两个 Tab 就是两条连接，SharedWorker 只剩转发壳子。if (!connection) 把上游留成一条。Tab 关掉后还留在 ports 里的 port，留到 4.5 和监听一起卸。

可操作对象：画两个 Tab，各自一个 port，中间一个 SharedWorker，上面只画一条名叫 orders 的连接。两棵订单表画在两个 Tab 里，不画进 Worker。

4.4 闭包钉住旧列表

连接可以离开当前这一屏。内存里还可能留着上一份列表。

问题：页面改成只拿一页 20 行之后，原来的 10000 行还会留在内存里吗？

约定：函数记住的是它引用到的那个数组对象。把这个数组放进参数再返回一个读取函数，后来的变量可以改去指向另一份数组，读取函数仍返回当初那一份。只要这个函数还被定时器、监听或模块级变量留着，那份数组就还有引用，回收不会把它收走。

function buildRows(n, stock, amountFen) { var list = []; var i; for (i = 0; i < n; i++) { list.push({ stock: stock, amountFen: amountFen }); } return list; } function pin(list) { return function () { return list; }; } var oldList = buildRows(10000, 8, 19950); var readOld = pin(oldList); var pageList = buildRows(20, 8, 19950); var held = readOld();

示例代码：examples/ch04/pin-list.js

held 就是 oldList，长度 10000。pageList.length 是 20。两份数组的第一行 stock 都还是 8，amountFen 都还是 19950。短的那份出现了，并不改写长的那份。

用教学订单页走一遍：整表行数是 listN，基准 10000。接口一页是 size，基准 20。滚动或翻页之后，界面持有的是 pageList。若之前有人把整表交给了 pin，readOld 仍指向那 10000 行。每一行仍带着 stock 8 和 amountFen 19950。界面只画 viewportRows 行，也就是 12 行，并不等于其余行已经可以回收。回收看引用还在不在。

换了变量就当成已经释放

页面上的当前列表变量改指向 20 行之后，闭包里的参数仍是原来的数组。要释放，就丢掉 readOld 这份函数，而不是只换掉外面的变量名。

闭包仍指向 listN 那 10000 行

readOld() 的长度是 listN。这 10000 行和后来的一页同时活着。堆里会看见一大份订单数组还被函数留着。下一节的定时器若调用的就是这个函数，人离开订单页之后它还在。

可操作对象：写下 readOld() 的长度 10000，以及 pageList 的长度 20。标出仍被闭包指着的是 oldList。

4.5 监听和定时器没卸

闭包钉住的是对象。监听和定时器若还登记着，离开订单页之后还会改 stock。

问题：视图已经离开，文档还在。原先的点击监听和定时器还会跑吗？

约定：监听和定时器登记在这份还活着的文档上。离开订单页若只是卸下视图，文档还在，就要在离开时 removeEventListener，并 clearTimeout 或 clearInterval。清理函数两个都做。只卸监听，定时器仍会跑；只清定时器，下一次点击仍会跑。中级课已经讲过副作用的清理，这里把清理接到 stock 上。SharedWorker 那一侧也一样：Tab 关闭时从 ports 里拿掉对应 port，否则 Worker 还按着一条已经不用的通道。

function mount(order) { var button = document.getElementById('order-refresh'); var timer = setTimeout(function () { order.stock = 7; }, 0); function onClick() { order.stock = 7; } button.addEventListener('click', onClick); return function cleanup() { clearTimeout(timer); button.removeEventListener('click', onClick); }; }

示例代码：examples/ch04/leave-stock.js

离开前调用返回的 cleanup，定时器不会把 order.stock 写成 7，点击也不会。amountFen 不在这两个回调里，始终是 19950。不调用 cleanup 就离开，定时器到点仍会把 stock 写成 7。

用教学订单页走一遍：基准 stock 是 8。定时器和点击都把它写成 7，也就是 8 减 1。离开页面本身不会替你点按钮，所以没卸时先发作的是定时器。演示把这次回调当场结算：卸掉之后读数停在 8，没卸则是 7。amountFen 两段都是 19950。这是视图卸下、文档还在时的行为。整个标签页被关掉时，这份文档上的定时器会随文档一起拆掉，那是另一段生命周期。

离开页面后定时器仍改 stock

清理没跑，setTimeout 的回调仍把 stock 从 8 写成 7。界面已经不在订单页，这份数据还是被改了。离开时要清掉定时器。

只卸掉其中一个

只 removeEventListener，定时器仍会把 stock 写成 7。只 clearTimeout，按钮上的监听还在，之后的点击也会写成 7。两个一起卸，stock 才停在 8。

可操作对象：切换下面的分段。卸掉监听，离开后 stock 应是 8。没卸，离开后 stock 应是 7。两段的 amountFen 都写 19950。

离开页面之后的 stock切换分段
观察要点：① 分段在「卸掉监听」时，离开页面后 stock 仍是 8。② 分段在「没卸」时，离开页面后定时器把 stock 改成 7。③ 两段的 amountFen 都是 19950。定时器改的是 stock。④ 分段表示离开时有没有执行清理。清理同时卸掉监听和定时器。

4.6 脱离文档的 DOM

数据会被闭包钉住。节点本身也可能已经不在文档里，却还被变量留着。

问题：行已经从表格里拿掉，这笔订单的节点还占内存吗？

约定：remove 让节点离开文档树。document.contains 对它为假。若变量、闭包或监听还指着它，节点和它的子树仍可达，回收不会收走。这种节点称为脱离文档的 DOM。它不在订单表上，也不等于已经释放。丢掉最后的引用，并且卸掉指着它的监听，它才可以回收。

var table = document.getElementById('order-table'); var row = document.createElement('tr'); row.textContent = 'stock 8'; table.appendChild(row); var keep = row; row.remove(); var inDocument = document.contains(keep);

示例代码：examples/ch04/detached-row.js

inDocument 为假。keep 仍是那一行。keep.textContent 仍是 stock 8。表格上看不见它，变量还看得见它。

用教学订单页走一遍：订单表画的是当前这一屏，大约 viewportRows 行。换页时若用新行替换旧行，旧的 tr 会离开文档。只要翻页回调、缓存数组或没卸的监听还把旧行放在 keep 里，这行就还在。行上的文本仍是当时的 stock 8。它和 4.4 的 10000 行数组是两类对象：一个是数据，一个是节点。两类都可以在界面已经换页之后还活着。

remove 之后就当成已经释放

离开文档只说明 document.contains 为假。还有变量指着它时，这行 DOM 仍在堆里。内存面板里会把它标成脱离文档的节点。

监听还挂在已经拿掉的行上

行被 remove 之后，若没有 removeEventListener，监听和行互相留着。4.5 的清理要在拿掉节点时一起做。否则离开订单页之后，这行既不在树上，也收不掉。

可操作对象：对示例里的 keep 写两句。document.contains(keep) 为假。变量还在，所以这行还在。再标一句：它已经不是订单表上的可见行。

4.7 两次堆快照

闭包、没卸的定时器和脱离文档的节点，都要靠两次堆快照对。看一眼当时还活着的对象，下不了「已经释放」的结论。

问题：快照里看见订单数组，就能说它泄漏了吗？

约定：一次堆快照只回答「这一刻谁还活着」。订单页本来就要拿着当前这一页，快照里有订单对象是预期。要判断某次清理有没有生效，就在动作前拍 A，做完动作再拍 B，用 B 相对 A 的比较看谁还在、谁多出来。比较能看的名字包括：长度为 listN 的数组、仍被函数留着的那份列表、脱离文档的表格行。开发者工具的内存面板可以拍堆快照并做比较；菜单和命令面板都是入口，以这一版的说明为准。不要把某一次点击路径写成唯一做法。

动作前 快照 A

记下此刻还活着的 10000 行、监听和节点。此时看见它们，只说明它们当时该在。

动作 丢掉引用并清理

丢掉钉住旧列表的函数，卸掉监听和定时器，不再保留已经离开文档的行。

动作后 快照 B

和 A 比。还在的那 10000 行、还在的脱离文档节点，才是这次没收掉的。

比较里还在对应哪一节界面上你以为已经发生的事
长度为 listN 的数组4.4 闭包页面已经改拿 20 行
定时器或监听仍可到达订单4.5 没卸人已经离开订单页
脱离文档的行节点4.6这行已经从表格里 remove

用教学订单页走一遍：A 拍在整表还被 readOld 按住的时候，数组长度是 listN，10000。动作是丢掉 readOld、调用 4.5 的 cleanup、丢掉 4.6 的 keep。B 若还看见这 10000 行，闭包还在；若还看见脱离文档的 tr，节点引用还在。当前这一页 20 行可以仍在 B 里，那是页面正在用的数据，不和旧的 10000 行写成同一笔。stock 8 和 amountFen 19950 出现在行上，只说明这是教学订单的字段，不说明这份对象该不该还活着。

看见订单对象就叫泄漏

正在显示的那一页本来就该在快照里。泄漏要看动作之后仍多出来的那份：被闭包留下的 listN 行，或已经不在文档里的节点。

快照只打一次就下结论

只有 A 或只有 B 时，你只能说这一刻它还在或这一刻没看见。看不见可能是还没分配，看见可能是本来就要用。结论写在两次的差上。

可操作对象：在纸上写三行：快照 A、动作、快照 B。关于 10000 行还在不在的那句结论，只许写在 B 与 A 的差上。

4.8 transition、Suspense、错误边界

内存边界看完了。更新这一侧改的是优先级和失败边界，订单字段仍是 stock 8、amountFen 19950。

问题：把一次列表更新标成 transition，或给订单表套上 Suspense 和错误边界，金额分会变吗？

约定：并发渲染改变的是更新能不能被打断、哪一次先画到屏幕上。transition 用 startTransition 把一次更新标成可以让路的那一类，紧急更新先画。Suspense 在子树还没就绪时给出后备界面，就绪之后仍渲染原来的订单字段。错误边界划出失败时替换哪一支子树；它接住的是子树渲染期间的失败。点击回调里的异常，以及边界自己渲染时的异常，不在这个边界里。这三处的精确范围以 React 文档里 startTransition、Suspense、Error Boundaries 的原文为准。四者都不负责改写订单字段。

var order = { stock: 8, amountFen: 19950 }; var pendingList = null; function renderOrders(list) { startTransition(function () { pendingList = list; }); return { stock: order.stock, amountFen: order.amountFen }; } function OrderList(suspended) { if (suspended) return { view: 'fallback' }; return { view: 'table', stock: order.stock, amountFen: order.amountFen }; } function OrderPage() { return { failureNote: '失败说明留在错误边界外面', boundary: OrderList(false) }; }

startTransition 由页面里的 React 提供。示例只写出调用和返回值，不在这个文件里另写一套调度器。renderOrders 返回的 stock 是 8，amountFen 是 19950。pendingList 换成新列表，并不给 order 赋值。OrderList(true) 的 view 是后备界面 fallback。OrderList(false) 仍带原来的两个字段。OrderPage 把失败说明放在 boundary 外面。

用教学订单页走一遍：账上的金额是 amountFen，基准 19950。展示文本用 Course.orderMath.yuanText 得到 199.50。transition 里若只是推迟画出 listN 行，这次更新的优先级变了，分没有变。Suspense 在订单表还没就绪时先显示后备界面，就绪后格子上仍是 stock 8 和 amountFen 19950。错误边界包住 OrderList 这一支。这一支渲染失败时，替换停在边界上，外面的失败说明还在。中级课已经讲过组件，这里不再把状态钩子讲一遍。

把 transition 当成会改金额分

放进 startTransition 的是列表那次更新的优先级。它不会把 amountFen 从 19950 改成 199.5，也不会把 stock 改成 7。金额仍以整数分记账。展示要用 yuanText，不要拿 199.5 做加减。

错误边界把整页白屏包进去，连失败说明也没了

边界若包住整页，后备界面又是空白，失败时整页换成空白。失败说明若写在边界里面，会和订单表一起被换掉，页面上就没有这句说明。说明留在边界外面，边界只包订单表这一支。

可操作对象：给订单页画一个框。框外写失败说明，框内写订单表，并写上 stock 8、amountFen 19950。框旁标 transition：这一次可以让路，金额分不改。

本章避坑清单

  1. 闭包仍指向 listN 那 10000 行。页面改拿 20 行，不会改写闭包里的那份数组。
  2. 错误边界把整页白屏包进去，连失败说明也没了。失败说明留在边界外面，边界只包订单表。
  3. 快照只打一次就下结论。动作前拍一次，动作后再拍一次，用比较看谁还在。
  4. 在 Worker 里改订单表 DOM。Web Worker 没有这棵 DOM，改表留在主线程。
  5. 离开页面后定时器仍改 stock。监听和定时器一起卸，stock 才停在 8；没卸会被写成 7。
  6. 把 transition 当成会改金额分。transition、Suspense 和错误边界不改 amountFen 19950。
  7. 结构化克隆会拷走 10000 行。Worker 里改副本，主线程上的 stock 仍是 8，直到主线程自己改 DOM。
  8. 脱离文档的节点只要还有引用就收不掉。remove 只是离开这棵树。

本章小结与延伸阅读

订单表的 DOM 在渲染进程主线程。Web Worker 碰不到这棵 DOM，postMessage 按结构化克隆把 listN 那 10000 行拷走，主线程上的 stock 仍是 8，直到主线程自己改表。SharedWorker 给多个 Tab 共用一条连接，每个 Tab 仍用自己的 port 和自己的 DOM。内存看三处：闭包还指着旧的 10000 行，监听和定时器没卸时离开页面仍会把 stock 写成 7，脱离文档的节点还有引用就收不掉。这三处用两次堆快照对。并发渲染、transition、Suspense 和错误边界改变的是优先级和失败边界。amountFen 仍是 19950，失败说明留在错误边界外面。
