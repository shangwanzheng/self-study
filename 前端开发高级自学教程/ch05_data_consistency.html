这一章：一次打开 /orders，两层缓存再写回同一份列表

第 4 章看过内存里的对象会不会被钉住。这一章仍用 Course.data.order 这一笔教学订单，把一次打开 /orders 上的缓存和列表写成一条链。

打开页面时，HTTP 缓存头决定两件发布物：入口 HTML 按 htmlMaxAgeSec 复用，基准 60 秒；带内容 hash 的 js 与 css 按 assetMaxAgeSec 复用，基准 31536000 秒。文档起来之后，页面内存里的请求缓存才管 apiPath（/api/orders）的列表。发布新脚本和作废列表是两次失效，分开写。同一页上的重复点击合并成一次在途请求。用户先要第 2 页、再回到地址栏上的第 1 页时，两次请求都会发出；后到的旧响应丢掉，列表停在第 1 页。扣库存先把界面上的 stock 从 8 改成 7，失败要回到 8。列表和详情读这一份 stock。响应就算是 HTTP httpOk（200），业务 code 为 businessCodeFail（40001）仍是失败，列表不更新。

HTTP 缓存头

5.1。入口 HTML 60 秒，带 hash 的资源长缓存。列表不在这一层。

内存与失效

5.2–5.3。/api/orders 的请求缓存跟这份文档走。两层失效各写一次。

列表怎样写回

5.1 HTTP 缓存头管哪一层

沿着一次打开往下走。先看响应头能复用的是哪两件发布物。

问题：入口 HTML、带 hash 的脚本、以及 /api/orders 的列表，谁走 HTTP 缓存头？

约定：HTTP 缓存看响应头。本章把这一层收成两个秒数，都在 Course.data.order 上。入口 HTML 用 htmlMaxAgeSec，基准 60，单位是秒。带内容 hash 的 js 与 css 用 assetMaxAgeSec，基准 31536000，单位是秒。按每天 86400 秒计，\(31536000/86400 = 365\)，也就是 365 天。带内容 hash 指文件名里有内容摘要：内容变了，地址也变，长缓存留着旧地址上的那份文件。Cache-Control 里 max-age 的具体指令以 HTTP 缓存文档原文为准。调用下面的函数时，kind 只接受 html 与 asset。

HTTP · 入口 HTML · 60 秒

htmlMaxAgeSec。用户在这个秒数之内可以继续用已经下载的入口文档。

HTTP · 带 hash js / css · 31536000 秒

assetMaxAgeSec。文件名里的 hash 变了，才是另一份资源。

function cacheMaxAgeSec(order, kind) { if (kind === 'html') return order.htmlMaxAgeSec; if (kind === 'asset') return order.assetMaxAgeSec; return null; }

示例代码：examples/ch05/http-layer.js

用教学订单页走一遍：把 Course.data.order 传进 cacheMaxAgeSec。kind 为 html 时得到 60。kind 为 asset 时得到 31536000。kind 为 api 时得到 null：apiPath 没有第三个秒数。页面源是 pageOrigin 加上路由 route（/orders），接口源是 apiOrigin。两件发布物的秒数都写在页面这一侧要遵守的响应头上，列表行留到 5.2 的内存对象里。

接口列表跟着带 hash 脚本的长缓存走

带 hash 的脚本还在，只说明那份 js 的 HTTP 缓存还留着。/api/orders 的列表不使用 assetMaxAgeSec。脚本文件还在，列表仍要按 5.2 的键去内存里找，找不到就重新请求。

入口 HTML 套用带 hash 资源的秒数

两个秒数各管各的文件。入口 HTML 写成 assetMaxAgeSec，60 秒就变成 365 天。带 hash 的脚本保持 31536000 秒，入口保持 60 秒。回滚时怎样更换入口，第 8 章再写。

可操作对象：对同一笔 order 调用三次 cacheMaxAgeSec，kind 依次为 html、asset、api。前两次记下 60 和 31536000，第三次记下 null。纸上不要给 /api/orders 再写一个 max-age。

5.2 内存缓存管接口数据

发布物的秒数已经分开。列表数据放在这份文档自己的对象里。

问题：/api/orders 的某一页，第二次读取时从哪里拿？

约定：页面内存里的请求缓存是这份文档上的一个对象。键由 apiPath、page、size 拼出，值是该页列表。寿命跟这份文档的 window 走。刷新后文档重建，这个对象是空的，列表要重新请求 apiPath。草稿键 storageKey（order.draft）在 localStorage，Cookie 名 cookieName（sid）是会话名。这两处都不拿来当这一次列表请求的缓存。写入发生在 5.8 判定成功之后；这一节先把取出、放下、作废三步的位置定下来。

function createRequestCache() { var box = {}; return { key: function (order, page) { return order.apiPath + '?page=' + page + '&size=' + order.size; }, get: function (key) { return box[key]; }, set: function (key, rows) { box[key] = rows; }, drop: function (key) { delete box[key]; } }; }

示例代码：examples/ch05/memory-cache.js

用教学订单页走一遍：order.page 是 1，order.size 是 20，order.apiPath 是 /api/orders。键就是 /api/orders?page=1&size=20。get 还没有这份值时，才向 apiOrigin 发请求。成功之后的 set 留到 5.8。listN 是 10000，缓存里放的是当前这一页的行，整表 10000 行不因此变成已经在内存里的一张表。刷新这一份文档之后，box 随文档一起拆掉，下一页仍从 get 未命中开始。

刷新后还读上一份文档里的列表

筛选条件和这一份请求缓存都在页面内存里。刷新会重建文档。get 在新文档里没有旧的第 1 页。要看到列表，就再请求一次 /api/orders。

把列表写进草稿键或带 hash 的文件

order.draft 只放草稿。带 hash 的 js 是 5.1 的发布物，秒数是 assetMaxAgeSec。列表行只进入 createRequestCache 的 box。写进草稿键的页码会在刷新后回来，盖住地址栏里当前的 page。

可操作对象：用 Course.data.order 生成第 1 页的键，写到纸上。再写两列：刷新后这一键在不在，localStorage 的 order.draft 在不在。第一列写「要重新请求」，第二列保持草稿，不把列表放进去。

5.3 两层失效不能写成同一次

两层各自有了位置。失效也要各写一次，不能并成一次调用。

问题：换了带 hash 的脚本，内存里的列表算不算一起失效？

约定：HTTP 这一层读两个秒数：入口 HTML 仍是 htmlMaxAgeSec，带 hash 的资源仍是 assetMaxAgeSec。内容变了就换文件名里的 hash，长缓存留在旧地址上。内存这一层只对 5.2 的键调用 drop。读秒数的函数不接收缓存对象，删键的函数不改这两个秒数。扣库存成功之后要作废的是列表键；发布新脚本要更新的是入口在 60 秒内指向的那个 hash。两次原因各调用一次。

function readHttpLayer(order) { return { htmlMaxAgeSec: order.htmlMaxAgeSec, assetMaxAgeSec: order.assetMaxAgeSec }; } function dropMemory(cache, key) { cache.drop(key); }

示例代码：examples/ch05/invalidate-apart.js

用教学订单页走一遍：readHttpLayer(Course.data.order) 得到 60 和 31536000。它不调用 drop。列表键仍是 /api/orders?page=1&size=20。库存已经在服务端从 8 变成 7 时，调用 dropMemory(cache, key)，下一次 get 未命中，再请求 /api/orders。这次 drop 不改入口的 60 秒，也不把 assetMaxAgeSec 改成 60。反过来，只换了脚本的 hash、库存仍是 8 时，不必为了新脚本去删这个列表键。

换了 hash 就当作列表已经作废

新的脚本地址只说明浏览器会去取另一份 js。内存里的第 1 页还在这份文档中时，get 仍会命中旧行。列表要作废，就再调用一次 dropMemory。

两层失效写成同一次

一个函数里又改入口秒数、又 drop 列表键，两次原因就绑在一起。发布脚本会清掉还有效的第 1 页，扣库存成功又会去动 htmlMaxAgeSec。保持 readHttpLayer 与 dropMemory 两次调用。

可操作对象：在纸上写两行。第一行是 readHttpLayer，填 60 和 31536000。第二行是 dropMemory，填 /api/orders?page=1&size=20。两行都填完，再标出这一次是「发布脚本」还是「库存已变」。

5.4 重复点击合并

失效已经分开。同一页上连点时，在途的那一次请求只发出一次。

问题：第 1 页的请求还没回来，又点了一次加载，/api/orders 发出几次？

约定：合并看的是同一个键。键仍是 apiPath、page、size。send 代表真正发往 apiOrigin 的那一次，它返回 Promise。第一次 load 在同步部分里调用 send，并把任务放进 inflight。响应回来之前的再次 load 发现这个键已经在 inflight 里，就返回同一次任务，sent 不再增加。任务结束时删掉这个键，下一次点击可以再发。第 1 页和第 2 页的键不同，不会在这里并成一次请求；那是 5.5 的两次发出。

function createLoader() { var inflight = {}; var sent = 0; return { sent: function () { return sent; }, load: function (order, page, send) { var key = order.apiPath + '?page=' + page + '&size=' + order.size; if (inflight[key]) return inflight[key]; sent += 1; var task = send(key).then(function (body) { delete inflight[key]; return body; }, function (err) { delete inflight[key]; throw err; }); inflight[key] = task; return task; } }; }

示例代码：examples/ch05/coalesce-clicks.js

用教学订单页走一遍：两次点击都是 page 1、size 20。键都是 /api/orders?page=1&size=20。第一次 load 调用 send，sent() 为 1。响应回来之前的第二次 load 命中 inflight，sent() 仍是 1。两次点击拿到的是同一次 /api/orders。若先 load 第 2 页再 load 第 1 页，键不同，sent() 为 2，两份响应都可能回来，写回规则在 5.5。

按钮已经灰了，请求函数仍各走一遍

按钮不可点，只减少用户再次触发。处理函数若对每次调用都执行 send，灰掉的按钮挡不住已经排队的那两次。合并写在 load 里：相同的键在 inflight 中就返回已有任务。

合并点击仍发两次 /api/orders

同键的第二次点击若又执行 send，sent() 会变成 2。检查时看 sent()：第 1 页连点两次、响应尚未回来，这个数是 1。第 2 页和第 1 页各点一次，这个数是 2，那两下不叫重复点击。

可操作对象：准备一个会计数的 send。对 page 1 连续 load 两次，读 sent()，应为 1。再对 page 2 load 一次，读 sent()，应为 2。两次读数都对上，再进入 5.5 看后到的那一份写不写进列表。

5.5 后到的旧响应丢掉

同键的点击已经并成一次。不同页的两次请求都发出之后，写列表之前要看地址栏。

问题：先发第 2 页、再发第 1 页，第 2 页的响应后到，列表停在哪一页？

约定：地址栏里的页码是当前页。教学订单页的基准是 page，值为 1。每一份响应带着自己的页码。到达时用 applyArrival：响应页码与地址栏相同，列表写成这一页，dropped 为 null；响应页码与地址栏不同，列表保持地址栏那一页，dropped 为这份响应的页码。比较发生在写列表之前。后到的那一份不会因为后到就覆盖。5.4 已经说明这两页的键不同，所以会有两次 send；这一节决定哪一次可以写进列表。

function applyArrival(addressPage, responsePage) { if (responsePage !== addressPage) { return { shown: addressPage, dropped: responsePage }; } return { shown: responsePage, dropped: null }; }

示例代码：examples/ch05/drop-stale-page.js

用教学订单页走一遍：发出顺序固定为先 page 2，再 page 1。地址栏随后停在 Course.data.order.page，也就是 1。applyArrival(1, 2) 得到 shown 1、dropped 2。applyArrival(1, 1) 得到 shown 1、dropped null。第 2 页先到时，它在到达的这一刻就被丢掉，列表仍对着地址栏的 1。第 2 页后到时，丢掉的就是这份后到的旧响应，列表不被盖成 2。两种到达顺序下，列表应显示的 page 都是 1，被丢弃的 page 都是 2。

旧响应把第 1 页盖成第 2 页

地址栏已经是 1，后到的第 2 页若直接 set 进 5.2 的缓存并画上列表，用户看到的就是第 2 页。写之前先过 applyArrival。dropped 为 2 的那一份不调用 set。

谁后到就用谁的 page 覆盖列表

到达顺序只决定哪一份先进入 applyArrival。后到的页码与地址栏不同时，shown 仍是地址栏的 1。用「最后返回的 JSON」直接替换表格，就会在第 2 页后到时把第 1 页盖掉。

可操作对象：下面先固定发出顺序：第 2 页，然后第 1 页，地址栏停在 1。切换谁后到，读三格：后到的 page、列表应显示的 page、被丢弃的 page。后两格应一直是 1 和 2。

两次请求谁后到切换到达顺序
观察要点：① 发出顺序固定为先 page 2、再 page 1，地址栏停在 page（1）。切换分段只改变谁后到。② 列表应显示的 page 一直是 1，与后到的是 2 还是 1 无关。③ 被丢弃的 page 一直是 2。第 2 页后到时，丢掉的就是这份旧响应；第 1 页后到时，第 2 页在先到的那一刻已经丢掉。④ 若按后到覆盖，只有第 2 页后到才会把列表写成 2。读数不采用这种覆盖。

5.6 乐观更新失败回滚

列表页码已经能停在地址栏上。扣库存时，界面可以先动，失败要回到原来的 8。

问题：界面先把 stock 从 8 改成 7，请求失败后两处各是多少？

约定：乐观更新先把界面上的库存写成 stock - 1。基准 stock 是 8，所以界面先显示 7。响应到达后用 settleStock 结算，函数不改写 Course.data.order。成功时返回的界面 stock 与订单 stock 都是 7。失败时两格都回到 order.stock，也就是 8：订单侧一直持有 8，界面从提前显示的 7 写回 8。下一次扣减仍从基准 8 起算。成功与失败的判定在 5.8；这一节先把结算后的两个数写对。列表和详情怎样读这一个数，放在 5.7。

function settleStock(order, ok) { var next = order.stock - 1; if (ok) return { ui: next, orderStock: next }; return { ui: order.stock, orderStock: order.stock }; }

示例代码：examples/ch05/optimistic-stock.js

用教学订单页走一遍：读 Course.data.order.stock，得到 8。点击扣库存后，界面先显示 7，订单 stock 仍是 8。请求成功时 settleStock(order, true) 得到界面 7、订单 7。请求失败时 settleStock(order, false) 得到界面 8、订单 8。失败分支没有把订单 stock 写成 7，也没有把界面留在 7。amountFen 仍是 19950，扣的是库存件数，不动金额分。

乐观失败后界面停在 7

7 是响应回来之前的提前显示。失败结算必须把界面写回 order.stock。界面停在 7、订单仍是 8 时，用户看到的件数已经离开服务端仍持有的库存。

失败时把订单 stock 改成 7

失败说明服务端没有接受这次扣减，订单 stock 保持 8。只把界面回滚、却把订单结果写成 7，下一轮会从错误的基数再减。成功才让返回值里的两格一起是 7。

可操作对象：先选成功或失败，再点扣库存。看视图里的乐观那一行，再读结算后的界面 stock 与订单 stock。失败时两格都是 8；成功时两格都是 7。再点一次，仍从基准 8 起算。

乐观更新的两个库存选择结果 · 点击扣库存
观察要点：① 点击之后，视图第一行是乐观瞬间：界面 stock 为 7，订单 stock 仍为 8。② 选择成功时，读数里界面 stock 与订单 stock 都是 7。③ 选择失败时，界面 stock 回到 8，订单 stock 仍是 8。④ 每次点击都从基准 stock 8 起算，不会从 7 再减成 6。列表和详情读界面这一份，5.7 不再各写一个字段。

5.7 列表与详情共用一份库存

结算后的两个数已经有了。页面上的列表和详情还要读同一份界面库存。

问题：详情已经显示 7 的时候，列表上的件数从哪里读？

约定：界面上的库存只有一份对象。createStock 用 order.stock 做初值。readList 与 readDetail 都调用 get。乐观时 set(order.stock - 1)，两处一起变成 7。失败时 set(order.stock)，两处一起回到 8。成功时停在 7，两处仍读这个 get。没有名为列表库存、详情库存的第二个字段。5.6 的订单 stock 是服务端这一侧的结算结果，写进这一份界面库存只发生在你决定采用该结算的时候。

一份 get 列表与详情

两处都调用 get()。写成 7 时一起是 7，写回 8 时一起是 8。

要避开的写法 两个字段

列表一个数、详情另一个数。回滚只赋值给其中一处时，另一处会停在 7。

function createStock(order) { var stock = order.stock; return { get: function () { return stock; }, set: function (next) { stock = next; } }; } function readList(stock) { return stock.get(); } function readDetail(stock) { return stock.get(); }

示例代码：examples/ch05/shared-stock.js

用教学订单页走一遍：createStock(Course.data.order) 之后，readList 与 readDetail 都是 8。乐观 set(7) 之后，两次读取都是 7。失败再 set(8)，两次读取都是 8。成功则停在 set(7)，两次读取都是 7。订单侧的 8 或 7 来自 5.6 的 orderStock，不在 readList 里再保存一份拷贝。

详情先写成 7，列表仍显示 8

两次读取若来自两个变量，详情可以先被乐观更新改掉，列表还留着旧的 8。用户在同一页上会看到两个件数。readList 和 readDetail 都应返回同一次 get()。

列表和详情各写 stock

各写一个字段时，失败回滚常常只写回详情，列表停在 7；或只写回列表，详情停在 7。共用 set 之后，5.6 的失败结算只赋值一次，两处读到的都是 8。

可操作对象：从基准 8 出发，依次做三步并各读两次：初始、set(7)、失败时 set(8)。每一步的列表读数和详情读数写成同一个数。纸上若出现两个赋值目标，就还没有共用这一份。

5.8 成功之后才更新列表

库存已经共用一份。列表行要等这一次响应既是 HTTP 成功、又是业务成功，才写进缓存。

问题：HTTP 状态是 200，正文里的业务 code 是 40001，列表更新吗？

约定：更新列表要同时满足两件事：HTTP 状态等于 httpOk（200），正文里的业务 code 等于 businessCodeOk（0）。commitList 只在这时调用缓存的 set，并返回新的行。businessCodeFail 是 40001。状态已经是 200 而 code 为 40001 时，函数返回缓存里原有的行，不调用 set。状态不是 200 时同样不 set。库存结算跟这一次判定走：通过时用 5.6 的成功分支，界面与订单 stock 都是 7；不通过时用失败分支，界面回到 8，订单 stock 仍是 8。失败正文里就算带了行，也不进入 5.2 的 box。

HTTP 状态业务 code列表库存结算
httpOk 200businessCodeOk 0写入缓存并显示新行成功，界面与订单都是 7
httpOk 200businessCodeFail 40001保持原列表失败，界面回到 8，订单仍是 8
其他不论 code保持原列表失败，界面回到 8，订单仍是 8
function commitList(order, cache, key, status, code, nextRows) { if (status === order.httpOk && code === order.businessCodeOk) { cache.set(key, nextRows); return nextRows; } return cache.get(key); }

示例代码：examples/ch05/commit-on-success.js

用教学订单页走一遍：键仍是第 1 页的 /api/orders?page=1&size=20。第一次成功之后，缓存里已有这一页。随后一次扣库存返回状态 200、code 40001：commitList 不调用 set，返回的仍是缓存里的原行；settleStock(order, false) 让界面回到 8。另一次返回状态 200、code 0：set 写进新行，settleStock(order, true) 让界面与订单 stock 都是 7，列表和详情通过 5.7 的 get 一起显示 7。状态不是 200 时，即使正文里写了 0，也不更新列表。

正文里的 40001 被 HTTP 200 盖过去

200 只说明 HTTP 这一层拿到了正文。业务 code 仍要和 businessCodeOk 比较。40001 留在正文里，就是这次业务失败。列表保持 get 的旧值，库存走失败回滚。

HTTP 200 就更新列表

只判断 status === order.httpOk 就 set，40001 的正文会盖掉当前第 1 页，界面也会停在乐观的 7。commitList 里的条件是状态与 code 同时成立。40001 不进入缓存。

可操作对象：用 5.2 的缓存先放入一页旧行。再调用两次 commitList：一次状态 200、code 40001，一次状态 200、code 0。第一次读到的应是旧行，第二次才是新行。两次旁边各标一次 settleStock 的界面 stock：8，然后 7。

本章避坑清单

  1. 接口列表跟着带 hash 脚本的长缓存走。/api/orders 不使用 assetMaxAgeSec。
  2. 两层失效写成同一次。入口 60 秒与内存里的列表键分开处理。
  3. 合并点击仍发两次 /api/orders。相同的键在响应回来之前只 send 一次。
  4. 旧响应把第 1 页盖成第 2 页。地址栏已是 page 1 时，后到的第 2 页丢掉。
  5. 乐观失败后界面停在 7。失败时界面回到 stock 8，订单 stock 仍是 8。
  6. 列表和详情各写 stock。两处都读同一份 get()。
  7. HTTP 200 就更新列表。业务 code 40001 仍是失败，不写入列表缓存。
  8. 入口 HTML 使用带 hash 资源的秒数。入口用 htmlMaxAgeSec，带 hash 的资源用 assetMaxAgeSec。

本章小结与延伸阅读

一次打开教学订单页，HTTP 缓存头管入口 HTML 的 60 秒和带 hash 资源的 31536000 秒。页面内存里的请求缓存管 /api/orders，键带着 page 与 size，刷新后重新请求。两层失效分成 readHttpLayer 与 dropMemory。同一页的重复点击在响应回来之前只发出一次。先发第 2 页再发第 1 页时，地址栏停在 1，后到的第 2 页丢掉，列表应显示的 page 是 1。乐观更新把界面从 8 改成 7；失败时界面回到 8，订单 stock 仍是 8。列表和详情读同一份库存。HTTP 200 且业务 code 40001 不写入列表缓存。

  • HTTP 缓存的 max-age 以 RFC 9111 原文为准。本章只用 htmlMaxAgeSec 与 assetMaxAgeSec，不把 /api/orders 写进这两个秒数。
  • 内存里的请求缓存是这份文档上的对象。它随 window 重建，不在 HTTP 缓存的秒数里。
  • 相同键的在途请求合并成一次 send。页码不同的两次请求都要发出，写列表前用地址栏页码丢掉对不上的那一份。
