8.1 Cache-Control 与协商缓存

先把一次取文件分成新鲜、协商和重新下载。后面的回滚和旧包都从这三档读。

问题：Network 里同一条脚本，什么叫还新鲜，什么叫协商过，什么叫重新下载？

约定：Cache-Control 的 max-age 给出新鲜期，单位是秒。新鲜期内浏览器可以不向服务器发请求，直接使用已保存的响应。新鲜期的计算以 RFC 9111 为准，本章用响应里写明的 max-age，不靠启发式新鲜期。过了新鲜期，可以用验证器再问一次。本章的验证器用 ETag，条件请求头是 If-None-Match。服务器认为表示未变，就返回 304，正文不重新传送，这是协商缓存。表示变了，就返回 200 并带上新正文，这是重新下载。验证器还可以是 Last-Modified；本章的协商只读 ETag。指令的完整名单以 HTTP 文档原文为准。

1. 新鲜，可以不请求 2. 过期，带上 ETag 3. 304 协商，或 200 重新下载
Network 里看见的判断
大小列为 (memory cache)内存缓存。这次没有重新下载
大小列为 (disk cache)磁盘缓存。这次没有重新下载
状态 304协商缓存。条件请求对上了 ETag，正文没有重新下载
状态 200，大小列是传输体积重新下载。新正文经过了网络

用教学订单页走一遍：入口 HTML 的新鲜期按 htmlMaxAgeSec 读，是 60 秒。带内容 hash 的 JavaScript 和 CSS 按 assetMaxAgeSec 读，是 31536000 秒。同一地址上的 hash 文件在这一年里保持新鲜，浏览器不必为了 ETag 再问一次。入口过了 60 秒可以再验证：ETag 未变则 304，入口正文没变；ETag 变了则 200，入口被重新下载，里面的脚本地址以新正文为准。已经打开的标签页不会因为服务器上的 ETag 变了，就把正在执行的函数换成新文件。

新鲜期内把内存缓存读成重新下载

大小列已经是 (memory cache)，说明这次没有把正文再传一遍。把它记成重新下载，后面会误判用户已经拿到新包。304 同样没有重新下载正文，它只是协商之后继续用已保存的那一份。

改掉 hash 文件的字节，指望 ETag 换掉仍新鲜的缓存

带 hash 的地址在 assetMaxAgeSec 内是新鲜的。新鲜期内浏览器可以不发条件请求，服务器上新的 ETag 没有机会被问到。内容变了就应使用新的文件名。同一地址上的字节保持不变。

可操作对象：拿一条脚本在纸上填四格：大小列原文、状态码、ETag 有没有参与、结论是内存缓存、磁盘缓存、协商缓存还是重新下载。四格填完再进入下一节的两个秒数。

8.2 入口短缓存、hash 长缓存

新鲜期的读法已经固定。订单页把两个秒数分给入口和带 hash 的文件。

问题：入口 HTML 和带内容 hash 的 JavaScript、CSS，各用哪一个 max-age？

约定：入口 HTML 的文件名通常不变，Cache-Control 的 max-age 使用 htmlMaxAgeSec。它里面写着这一次要加载的脚本地址和样式地址。带内容 hash 的 JavaScript 和 CSS，文件名随内容变化，同一地址上的字节在发布之后保持不变，max-age 使用 assetMaxAgeSec。两行都显式写出 max-age。hash 文件名本身就是内容的身份，不靠事后改字节来换包。

资源字段max-age新鲜期内
入口 HTMLhtmlMaxAgeSec60 秒可以不请求这份入口
带内容 hash 的 JavaScript、CSSassetMaxAgeSec31536000 秒这一地址可以在 365 天内不重新下载
var order = { htmlMaxAgeSec: 60, assetMaxAgeSec: 31536000 }; function entryMaxAge(policy) { if (policy === 'short') return order.htmlMaxAgeSec; return order.assetMaxAgeSec; } function afterRollback(policy) { if (entryMaxAge(policy) === order.htmlMaxAgeSec) return '新入口'; return '旧脚本'; } console.log(entryMaxAge('short')); console.log(entryMaxAge('long')); console.log(afterRollback('short')); console.log(afterRollback('long'));

示例代码：examples/ch08/cache-policy.js

四行输出是 60、31536000、新入口、旧脚本。afterRollback 比较的是同一次回滚之后、已经超过 60 秒、尚未超过 31536000 秒的那一次打开。短缓存的新鲜期已经结束，读数是新入口。把入口写成一年时，新鲜期还在，读数是旧脚本。60 秒之内再次打开，短缓存的入口也还是新鲜的旧文档。8.4 的演示用的是同一个时刻。

用教学订单页走一遍：页面源是 pageOrigin，路由是 route，也就是 http://localhost:5173/orders。用户打开订单页时先取入口 HTML。入口新鲜时，脚本地址仍是上一次写进 HTML 的那个 hash。入口过了 60 秒再取，新 HTML 若指向 app.goodhash.js，随后加载的就是这个新地址。该地址若浏览器里还没有，脚本是重新下载；若回滚指向的那一版 hash 曾经加载过，脚本可以来自内存缓存或磁盘缓存。决定地址的是入口正文。带 hash 的文件自己的 max-age 保持 31536000 秒。

入口 HTML 也缓存一年，回滚后仍是旧包

把入口的 max-age 写成 assetMaxAgeSec，新鲜期变成 31536000 秒。服务器上的入口已经换成新文档，浏览器仍可以一直使用旧 HTML，于是继续请求旧 HTML 里的旧脚本。回滚后用户拿到的仍是旧包。

两个秒数写反

入口用 31536000 秒、带 hash 的脚本用 60 秒，文件名的分工就反了。不变的入口被长期留下，内容一变就会换地址的脚本却被反复重新下载。订单页的两行是入口 60 秒、hash 文件 31536000 秒。

可操作对象：在纸上写两行 Cache-Control：入口 HTML 的 max-age 填 htmlMaxAgeSec，app.goodhash.js 与对应的 CSS 填 assetMaxAgeSec。再标一句：已经超过 60 秒、尚未超过 31536000 秒的那一次打开，短缓存读「新入口」，把入口写成一年则读「旧脚本」。

8.3 用户仍在跑上一版

两个秒数已经分开。发布完成之后，先确认这位用户的文档正在执行哪一个 hash。

问题：新包已经在服务器上，为什么这位用户的订单页还是上一版？

约定：先看文档正在使用的脚本地址，再看 Network 里这一行的大小列。地址仍是上一版的 hash，并且大小列是 (memory cache)，这次就是内存缓存，没有重新下载新包。大小列是 (disk cache) 时同样没有重新下载，记成磁盘缓存。只有状态 200 且大小列是传输体积，才是重新下载。已经打开、还没有重新加载的标签页，继续执行加载时的那份脚本；Cache-Control 不替换正在运行的程序。开发者工具里若关掉了缓存，这次看到的重新下载不能当成线上用户的行为。面板名称用 Network，大小列的字样以 Chrome DevTools 文档中的 memory cache、disk cache 为准。

function networkKind(sizeText, status) { if (sizeText === '(memory cache)') return '内存缓存'; if (sizeText === '(disk cache)') return '磁盘缓存'; if (status === 304) return '协商缓存'; return '重新下载'; } console.log(networkKind('(memory cache)', 200)); console.log(networkKind('(disk cache)', 200)); console.log(networkKind('0.3 kB', 304)); console.log(networkKind('180 kB', 200));

示例代码：examples/ch08/network-kind.js

四行输出是 内存缓存、磁盘缓存、协商缓存、重新下载。最后一行的 180 用主包 bundleMainKb 当作一次传输体积的教学数字，真实大小列以那一次为准。

用教学订单页走一遍：上一版入口写着 app.badhash.js。用户这次打开仍取到那份入口时，Network 里这一行若是内存缓存，订单页执行的就是上一版，新地址 app.goodhash.js 还没有出现。入口若已过 60 秒并被重新下载，脚本地址改成新 hash 之后，才谈得上新包。第 5 章的内存缓存指 /api/orders 的列表停在页面内存里，刷新文档后要重新请求；本章大小列上的内存缓存只说明这份静态文件没有重新下载。接口 JSON 的业务 code 不由这一列解释。首屏体积仍由 firstScreenKb() 计算，那是包体，不是缓存档位。

发布完成就当成这位用户已在新包上

服务器换了入口，只说明新的 HTML 已经可以被取到。新鲜期内的入口、尚未重新加载的标签页、以及大小列上的内存缓存，都还在跑上一版。判断要落在这位用户的脚本地址和这一行 Network 上。

用关掉缓存的那一次重新下载代表线上

开发者工具关闭缓存时，脚本会重新下载。线上用户的浏览器仍按 max-age 使用已保存的文件。要看用户是否仍在上一版，保留缓存，读大小列是内存缓存还是重新下载。

可操作对象：对一位仍打开 /orders 的用户记三行：脚本地址里的 hash、大小列原文、networkKind 的结论。地址是上一版且结论是内存缓存时，这一单仍算上一版。

8.4 回滚改入口

上一版怎么被认出来，已经能从 Network 读到。回滚时改的是入口里的地址。

问题：要回到上一版可用的订单页，改入口，还是改已经缓存的 hash 文件名？

约定：回滚更换入口 HTML，让其中的脚本地址和样式地址指向要恢复的那一版 hash。那些 hash 文件留在原地址上，文件名和字节都不变，max-age 仍是 assetMaxAgeSec。用户若曾经加载过这一版，回滚后的新入口可以再次命中内存缓存或磁盘缓存，那是恢复后的文件，不是「没换入口所以仍是坏的那一版」。已经写进旧入口、并被长缓存留下的地址，不会因为服务器把文件改了名就跟着改口。

var good = 'app.goodhash.js'; var bad = 'app.badhash.js'; function rollbackByEntry() { return { entryPointsTo: good, hashFileName: good }; } function rollbackByRename() { return { entryPointsTo: bad, hashFileName: 'app.rolled.js' }; } console.log(rollbackByEntry().entryPointsTo); console.log(rollbackByEntry().hashFileName); console.log(rollbackByRename().entryPointsTo); console.log(rollbackByRename().hashFileName);

示例代码：examples/ch08/rollback-entry.js

前两行都是 app.goodhash.js：入口和文件名一起指向要恢复的那一版。后两行是 app.badhash.js 与 app.rolled.js：入口仍要旧名字，服务器上的文件名却改成了另一个。缓存里的旧入口继续请求 app.badhash.js。

用教学订单页走一遍：坏的一版把订单列表指到 app.badhash.js。回滚时发布一份新的入口 HTML，脚本地址写成仍留在服务器上的 app.goodhash.js。已经超过 60 秒时，短缓存用户取到这份新入口，读数是新入口。若入口的 max-age 是 31536000 秒，同一次回滚之后新鲜期还在，用户继续使用旧入口，读数是旧脚本，Network 里 app.badhash.js 是内存缓存，不是新包的重新下载。删掉 app.badhash.js 而旧入口还指着它，这些用户会拿到脚本失败；要改变他们的地址，仍是换入口。

服务器换了入口就以为 60 秒内的人都已换包

htmlMaxAgeSec 的 60 秒是新鲜期，不是「回滚指令到达浏览器的延迟」。这 60 秒里再次打开，短缓存的入口仍可以是旧文档。演示把读数放在已经超过 60 秒、尚未超过 31536000 秒的那一次打开。

回滚去改已缓存的 hash 文件名

把 app.badhash.js 改名为 app.rolled.js，不会改写用户已经缓存的入口。旧入口继续要原来的名字。回滚改的是入口，不是已缓存的 hash 文件。

可操作对象：切换入口是短缓存还是长缓存。读数回答：已经超过 60 秒、尚未超过 31536000 秒的那一次打开，用户拿到的是新入口还是旧脚本；长缓存时这一行是不是内存缓存。

入口短缓存或长缓存切换后看回滚读数
观察要点：① 这一次打开已经超过 htmlMaxAgeSec（60 秒），尚未超过 assetMaxAgeSec。入口短缓存时读数是新入口。② 入口长缓存时 max-age 为 assetMaxAgeSec，读数是旧脚本；入口正文来自内存缓存，不是重新下载。③ 旧脚本那一行的大小列是内存缓存。带内容 hash 的 JavaScript 和 CSS 的 max-age 仍是 assetMaxAgeSec。④ 回滚改的是入口里的地址。已缓存的 hash 文件名保持不动。

8.5 TLS 失败时日志里没有这条请求

静态文件的新旧已经能分开。订单接口若在 TLS 上失败，业务接口日志里还没有这条请求。

问题：列表出不来时，先在业务日志里找 code 40001，还是先确认请求有没有进到业务接口？

约定：HTTPS 先完成 TLS，再发送 HTTP 请求。证书不受信任、主机名对不上或证书过期时，握手失败，HTTP 响应不存在，正文里的业务 code 也不存在。业务接口日志记录的是进入订单接口处理函数的那一条。握手停在 TLS 时，这条还没有进入处理函数，业务接口日志里没有它。边缘或证书层可以另有握手记录，那一份不是业务接口日志。businessCodeFail 只出现在已经到达的响应正文里。教学订单页上它的值是 40001，并且与 HTTP httpOk 200 同时出现时，才是业务失败。

现象业务接口日志业务 code
TLS 握手失败没有这条请求没有
页面是 HTTPS，接口写成 http没有这条请求没有
HTTP 200，正文 code 为 40001有这条请求40001
var order = { httpOk: 200, businessCodeFail: 40001 }; function businessLog(kind) { if (kind === 'tls' || kind === 'mixed') { return { present: '没有', http: null, code: null }; } return { present: '有', http: order.httpOk, code: order.businessCodeFail }; } console.log(businessLog('tls').present); console.log(businessLog('tls').code); console.log(businessLog('mixed').present); console.log(businessLog('code').present); console.log(businessLog('code').http); console.log(businessLog('code').code);

示例代码：examples/ch08/request-log.js

六行输出是 没有、null、没有、有、200、40001。tls 与 mixed 的 code 都是 null，因为没有业务正文。code 这一档 HTTP 是 200，业务 code 是 40001，日志读数是有。

用教学订单页走一遍：本地页面源 http://localhost:5173 与接口源 http://localhost:8080 都是 http，这一对不是混合内容。apiPath 是 /api/orders。线上页面若以 HTTPS 提供，接口仍写成 http:// 开头，浏览器按混合内容阻止这次请求，它到不了 8080 上的处理函数，业务接口日志里没有这条。TLS 握手失败时同样没有。只有处理函数返回了 HTTP 200 且 code 为 40001，日志里才有这条，列表按业务失败保持原样。连接超时 connectTimeoutMs、读超时 readTimeoutMs 和浏览器侧等待 browserTimeoutMs 是另外三列时间，不把它们写成 40001。

TLS 失败当成业务 code 40001

40001 写在已经返回的正文里。TLS 没有完成时，不存在这段正文，也不能把 HTTP 记成 200。业务接口日志里还没有这条请求。

混合内容把接口打到 http

页面文档是 HTTPS，接口地址却是 http。浏览器阻止这次请求，订单接口看不到它。修的是接口地址的协议，使它与页面同为 HTTPS。不要到业务 code 里找这一次。

可操作对象：在 TLS 失败和业务 code 40001 之间切换，读出业务接口日志里有没有这条请求，以及 code 一栏是空还是 40001。

TLS 失败或业务 code 40001看业务接口日志
观察要点：① 选 TLS 失败时，业务接口日志的读数是没有。业务 code 一栏没有 40001。② 选业务 code 40001 时，HTTP 为 httpOk，业务接口日志的读数是有。③ 40001 来自已经到达处理函数的响应正文，字段是 businessCodeFail。④ TLS 失败停在握手。业务接口日志里还没有这条请求。

8.6 脚本错误与未处理拒绝

请求有没有进业务接口，已经能分开。页面自己抛出的错误走另外两条记录。

问题：订单页白了，监控里该记脚本错误，还是未处理的 Promise 拒绝？

约定：脚本运行时错误走 error。没有被接住的 Promise 拒绝走 unhandledrejection。两条都要记下，并且带上发布版本。发布版本就是栈或文件名里的那一个 hash，和 8.3 里文档正在执行的脚本是同一个名字。已经被 catch 接住的拒绝，不进入未处理拒绝。业务 code 40001 若由请求层接住，它是业务失败记录，不是未处理拒绝。跨源脚本若只剩下一句 Script error、又没有文件名，这一条对不上版本；先让栈带回脚本地址，再交给 source map。事件名以 WHATWG HTML 为准。

var release = 'app.goodhash.js'; var seen = []; function noteScriptError(message, file) { seen.push({ kind: '脚本错误', message: message, file: file, release: release }); } function noteUnhandledRejection(reason) { seen.push({ kind: '未处理拒绝', reason: reason, release: release }); } noteScriptError('yuanText is not a function', release); noteUnhandledRejection('orders rejected'); console.log(seen[0].kind); console.log(seen[0].file); console.log(seen[0].release); console.log(seen[1].kind); console.log(seen[1].release); console.log(seen.length);

示例代码：examples/ch08/watch-errors.js

六行输出是 脚本错误、app.goodhash.js、app.goodhash.js、未处理拒绝、app.goodhash.js、2。文件名和发布版本是同一个 hash。本课的 course.js 也在听 error 与 unhandledrejection，把消息放进 Course.errors。订单页的监控同样听这两类，并多记发布版本和栈的文件名。

用教学订单页走一遍：展示金额调用 Course.orderMath.yuanText()，整数分 amountFen 是 19950，文本是 199.50。若这一调用在脚本里抛出，记录种类是脚本错误，文件是当前 hash。列表请求的 Promise 若被拒绝且没有 catch，记录种类是未处理拒绝，发布版本仍是这个 hash。TLS 失败若被请求层接住并误写成 40001，监控里会同时缺业务日志、又多一条假的业务失败；未被接住时则是未处理拒绝，reason 属于网络或 TLS，code 仍不是 40001。两种记录都不要改记成 HTTP 200。

把已接住的 40001 记成未处理拒绝

请求层已经按业务失败处理了 40001，Promise 有归属。未处理拒绝只留给没有 catch 的那一条。两类计数分开，发布版本都写当前脚本的 hash。

栈里没有脚本地址

只有一句「出错了」、没有 hash 文件名，就无法对上 8.3 的那一版。Script error 且文件名为空时，先补回脚本地址。没有地址的栈，不能开始对 source map。

可操作对象：准备两条记录：一条脚本错误，一条未处理拒绝。每条都写下种类、文件名里的 hash、发布版本。三者里的 hash 是同一个字符串。

8.7 source map 与版本号

错误已经带着 hash。还原栈时，map 必须是这一版的，公网能否下载则另判一次。

问题：混淆后的栈已经上报，用哪一份 source map 还原？这份 map 能不能放在公网？

约定：source map 把混淆后的行列对回这一次构建的源码。栈里的脚本地址属于哪个 hash，就只用同一次构建产出的那份 map。下一版的 map 会指到另一套行列。脚本末尾的 sourceMappingURL 只说明浏览器或监控去哪里找 map。找得到，并且版本一致，才可以还原。这份 map 是否上传到公网静态目录，是另一次判断：公网可下，意味着拿到脚本的人也能拿到源码映射。交给错误监控的私有存储，和放到与 JavaScript 相同的公网目录，是两条目的地。格式以 Source Map 的修订说明为准。

function canSymbolicate(stackRelease, mapRelease) { return stackRelease === mapRelease; } function mapOnPublicWeb(uploadedToPublicWeb) { return uploadedToPublicWeb === true; } console.log(canSymbolicate('app.goodhash.js', 'app.goodhash.js')); console.log(canSymbolicate('app.goodhash.js', 'app.badhash.js')); console.log(mapOnPublicWeb(false)); console.log(mapOnPublicWeb(true));

示例代码：examples/ch08/map-release.js

四行输出是 true、false、false、true。第一行版本一致，可以还原。第二行栈是 app.goodhash.js，map 却是 app.badhash.js，不能还原。后两行只回答公网：false 表示没有上传到公网，true 表示公网可下。版本对得上时，公网这一问仍然要单独作答。

用教学订单页走一遍：用户仍在跑 app.badhash.js 时，栈里的文件名就是这个 hash。还原要用当时随这一文件一起构建的 map。发布系统里最新的 app.goodhash.js 已经在服务器上，也不能把新 map 套到旧栈上。入口 60 秒只影响下一次取 HTML，不改已经上报的那条栈所属的版本。第 9 章再写构建产物和测试范围；本章先把「能否还原」和「公网能否下载」分成两个布尔值。

source map 公网可下

map 跟带 hash 的脚本放在同一公网目录，并且 sourceMappingURL 指向它，这份映射就可以被下载。监控能还原栈，只说明监控那一侧有 map。公网是否可下，要单独判断。

用下一版的 source map 还原上一版的栈

用户仍在 app.badhash.js 上时，新包的 map 对不上这些行列。先用 8.3 的脚本地址确认发布版本，再选同一次构建的 map。

可操作对象：对一条脚本错误写两个判断：栈的 hash 与 map 的 hash 是否相同；这份 map 的目的地是监控的私有存储，还是公网静态目录。两个判断都写完才算对上版本。

8.8 埋点对齐发布版本

栈能对上版本之后，订单页的埋点也要带上正在跑的那一版。

问题：订单页的指标掉了，掉的是仍在跑的上一版，还是刚刚发布的这一版？

约定：埋点对齐发布版本：每条事件带上这条页面加载时的脚本 hash。关键路径可以采样，采样之后的事件仍带着这个版本。发布系统里「当前线上版本」是服务器此刻的入口所指向的 hash；已经打开的标签页、以及入口仍新鲜的用户，事件上的版本可以仍是上一版。没有版本字段的曲线，会把这两拨人画在一起。路由用订单页的 route。

function orderView(release) { return { route: '/orders', release: release }; } var aligned = orderView('app.goodhash.js'); var missing = { route: '/orders' }; console.log(aligned.route); console.log(aligned.release); console.log(missing.release);

示例代码：examples/ch08/release-event.js

三行输出是 /orders、app.goodhash.js、undefined。第三条没有 release，读出来是 undefined，对不上任一版订单页。

用教学订单页走一遍：事件的路由是 /orders。用户文档里的脚本若是 app.badhash.js，事件的发布版本就写这个名字，即使服务器上的新入口已经指向 app.goodhash.js。入口短缓存只保证新鲜期结束之后的下一次打开会取到新入口；这一次会话在重新加载之前仍报旧 hash。把 qpsTeach 的 50 写进这条曲线，并不能分开两版。50 仍是教学数量级。金额、库存和分页继续用 amountFen、stock、page 与 size，它们不是发布版本。

用刚发布的版本给仍开着的标签页记账

标签页加载时执行的是上一版 hash。发布完成后，这条页面不会自动改报新版本。事件上的版本取自这次加载的脚本地址，和 Network 里仍显示内存缓存的那一版是同一个名字。

埋点没有版本，对不上一版的订单页

曲线上只有路由 /orders，没有 hash。上一版仍在内存缓存里运行时，它的订单页和新包的订单页落在同一条线上，无法判断掉量属于哪一版。

可操作对象：写一条订单页事件，字段只有两个：route 为 /orders，release 为当前脚本文件名。再写一条故意不带 release 的，确认它读出来是 undefined，不能用来对上一版。

本章避坑清单

  1. 入口 HTML 也缓存一年。max-age 写成 assetMaxAgeSec 之后，回滚后仍是旧包。
  2. 回滚去改已缓存的 hash 文件名。旧入口继续请求原来的地址。
  3. 在仍新鲜的 hash 地址上改字节，指望 ETag 让浏览器换掉旧文件。
  4. 把 Network 大小列上的内存缓存读成重新下载，并据此认为用户已经在新包上。
  5. 用开发者工具关掉缓存之后的重新下载，代表线上用户。
  6. TLS 失败当成业务 code 40001。业务接口日志里当时还没有这条请求。
  7. 混合内容把接口打到 http。页面是 HTTPS 时，这次请求到不了业务接口。
  8. 把已经接住的业务 code 40001 记成未处理的 Promise 拒绝。
  9. source map 公网可下。监控能还原栈，不代替「公网是否可下载」这一次判断。
  10. 用下一版的 source map 还原上一版栈里的行列。
  11. 埋点没有版本，对不上一版的订单页。仍在跑旧 hash 的会话和新包落在同一条曲线上。

本章小结与延伸阅读

入口 HTML 的 Cache-Control 使用 htmlMaxAgeSec，60 秒。带内容 hash 的 JavaScript 和 CSS 使用 assetMaxAgeSec，31536000 秒。用户仍在跑上一版时，先看脚本地址，再看 Network 大小列是内存缓存还是重新下载。回滚改的是入口，已缓存的 hash 文件保持原文件名。已经超过 60 秒、尚未超过 31536000 秒的那一次打开，短缓存读到新入口；入口若也缓存一年，则仍是旧脚本。TLS 失败时业务接口日志里还没有这条请求，不能记成业务 code 40001。页面是 HTTPS 而接口写成 http，混合内容同样使请求到不了业务接口。错误监控分开记录脚本错误和未处理的 Promise 拒绝，栈与 source map 属于同一个 hash。source map 能否还原，和它是否公网可下，是两次判断。埋点带上这次加载的发布版本，才能对上一版订单页。
