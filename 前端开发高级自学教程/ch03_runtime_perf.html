3.1 路由懒加载与代码分割

章首把首屏算成 600 KB。这一节看路由块的 40 KB 怎样才停在这次加载之外。

问题：打开 /orders 时，路由块要不要和主包、第三方一起下载？

约定：代码分割把路由单独打成一块，字段是 bundleRouteKb，基准 40 KB。首屏只加两笔：bundleMainKb 与 bundleVendorKb。Course.orderMath.firstScreenKb() 做的就是这一次加法，结果是 600。懒加载指导航到路由 /orders 之后再取这 40 KB。入口若仍然同步引用这块，文件虽然切开了，字节仍算进首屏，读数是 \(600 + 40 = 640\)。

\[ \mathrm{firstScreenKb} = 180 + 420 = 600 \]

\[ 600 + 40 = 640 \]

本课页面按普通脚本加载。示例里用一个布尔表示「路由块算不算进首屏」，布尔为真就加上 bundleRouteKb。打包器通常靠动态导入把目标切出去；入口里若写成同步引用，切出去的文件仍会跟着首屏走。

var bundleMainKb = 180;
var bundleVendorKb = 420;
var bundleRouteKb = 40;

function firstScreenKb(routeInFirstScreen) {
  var kb = bundleMainKb + bundleVendorKb;
  if (routeInFirstScreen) {
    kb = kb + bundleRouteKb;
  }
  return kb;
}

console.log('不进', firstScreenKb(false));
console.log('进首屏', firstScreenKb(true));

示例代码：examples/ch03/route-split.js

控制台两行是 不进 600 与 进首屏 640。页面上的演示改读 Course.orderMath，不把 600 和 640 写死在分支里。

用教学订单页走一遍：订单路由是 route，即 /orders。主包 180 KB 放壳和这段路由之外的公共代码，第三方 420 KB 放依赖，两者相加由 firstScreenKb() 给出 600。订单列表这一块若等路由匹配之后再取，首屏保持 600。演示默认停在「不进」。

文件切开，仍可能在首屏

网络面板里能看见单独的路由文件，只说明分割成功。它若和入口同一波下载，首屏按 640 KB 记。下一节的预加载就是把这一波提前。

可操作对象：切换分段。读「首屏 KB」：不进是 firstScreenKb() 的 600，路由块进首屏是 640。

路由块进不进首屏切换分段
观察要点：① 分段「不进」时，首屏 KB 等于 Course.orderMath.firstScreenKb()，即主包 180 加第三方 420，读数 600。② 分段「路由块进首屏」时，在 firstScreenKb() 上加 bundleRouteKb 40，读数 640。③ 第三方 420 两档都在首屏里；这一档开关只搬动路由块那 40。④ 这里的单位是 KB。12 与 10000 是行数，不出现在这一栏。

3.2 预加载与第三方库是否进了首屏

40 KB 已经可以留到路由匹配之后。预加载会把它取回首屏。第三方的 420 KB 要从入口引用看，不从「是不是第三方」看。

问题：给路由块加预加载之后，首屏还是 600 KB 吗？第三方库算不算在这 600 里？

约定：预加载是在首屏阶段就去取某个 URL。文档里用 link，rel 为 preload、as 为 script，并指向路由块时，路由块的请求和主包排在同一次加载。块文件仍然单独存在，计时却回到了首屏。firstScreenKb() 不含这 40 KB，预加载之后要自行加上 bundleRouteKb，得到 640。第三方库只要被首屏入口引用，就记在 bundleVendorKb，420 KB 已经加进 firstScreenKb()。看网络面板里它是否和入口同一波，不看包名里有没有 vendor 这几个字母。

var bundleMainKb = 180;
var bundleVendorKb = 420;
var bundleRouteKb = 40;

function firstScreenKb(preloadRoute) {
  var kb = bundleMainKb + bundleVendorKb;
  if (preloadRoute) {
    kb = kb + bundleRouteKb;
  }
  return kb;
}

console.log('不预加载', firstScreenKb(false));
console.log('预加载路由块', firstScreenKb(true));

示例代码：examples/ch03/preload-route.js

用教学订单页走一遍：订单页希望 /orders 的列表代码晚一点到，于是做了分割。若又在文档头部预加载这块，3.1 的分段应拨到「路由块进首屏」，读数从 600 变成 640。被入口直接引用的依赖，体积在 420 KB 里，两档分段都还在。

预加载把路由块又拉回首屏

懒加载决定「何时取」，预加载把「何时」改回首屏。分割文件还在，首屏字节已经是 \(600 + 40 = 640\)。要晚取，就不要在首屏文档里预加载这块路由。

可操作对象：回到上一节的分段，把「路由块进首屏」当成预加载之后的那一档，核对首屏 KB 是否成为 640。再在纸上把 420 KB 标成「入口已引用，两档都在」。

3.3 包体积从哪来

600 与 640 的差已经能读出来。这一节把三笔字节的来源摊开，避免和行数混用。

问题：首屏的 600 KB 里，主包和第三方各占多少？40 KB 又是哪一块？

约定：教学订单页只使用这三笔，不另造一个「优化后」的体积。业务壳与路由之外的公共代码进主包，bundleMainKb 为 180。依赖进第三方包，bundleVendorKb 为 420。订单路由自己的代码进路由块，bundleRouteKb 为 40。首屏默认是前两笔之和。

块字段KB默认是否进首屏
主包bundleMainKb180进。加进 firstScreenKb()
第三方bundleVendorKb420进。入口引用了就在 600 里
路由块bundleRouteKb40不进。懒加载；预加载后改记 640

\[180 + 420 = 600\]

用教学订单页走一遍：打开 /orders 时，先下载的是主包和第三方。列表路由的 40 KB 等匹配到 route 再取。把 12 当成 KB，或把 40 当成一屏行数，都会把后面的虚拟列表和这次加载加错。12 是 viewportRows，40 是 bundleRouteKb。

三笔字节分开记

主包 180、第三方 420、路由块 40。首屏函数只加前两笔。压缩、去掉未引用代码和分割，都要落回这三笔再相加，不另报一个对不上 firstScreenKb() 的整数。

可操作对象：在纸上画三格：180、420、40。前两格圈进首屏，第三格写「懒加载 / 预加载后并入」。用 3.1 的读数核对圈内是 600 还是 640。

3.4 长任务占住主线程

字节下完之后，脚本仍在渲染进程的主线程上跑。这一节只拆两道时间门槛。

问题：主线程上的一段脚本超过 16.7 ms，能不能就叫做长任务？

约定：帧预算按假设的 60Hz 估算，\(\frac{1000}{60} \approx 16.7\)，存在 frameBudgetMs。它表示这一帧大约能装下的时间，不是显示器的保证，也不是长任务的定义。长任务看主线程上的一次任务是否达到 longTaskMs，门槛是 50 ms。耗时大于 16.7 且尚未达到 50，只说明这一帧装不下。达到 50，才称为长任务。两道门槛不要写成同一个毫秒数。

脚本耗时与 frameBudgetMs 16.7 比与 longTaskMs 50 比
16.7 ms未大于帧预算未达到长任务
20 ms超过帧预算未达到长任务
50 ms超过帧预算达到长任务
 
var frameBudgetMs = 16.7;
var longTaskMs = 50;

function classify(ms) {
  return {
    overFrame: ms > frameBudgetMs,
    isLongTask: ms >= longTaskMs
  };
}

console.log('20', classify(20));
console.log('50', classify(50));
console.log('16.7', classify(16.7));

示例代码：examples/ch03/long-task.js

20 这一行是超过帧预算、尚未达到长任务。50 这一行两栏都为真。16.7 用的是大于，而不是大于等于，所以刚好等于帧预算时，overFrame 为假。

用教学订单页走一遍：订单列表有 listN 行。若在一次任务里同步走完 10000 行的样式读写，主线程在这段时间不回到事件循环。耗时先和 frameBudgetMs 比，再和 longTaskMs 比。接口超时 browserTimeoutMs（3000 ms）、连接超时 connectTimeoutMs（500 ms）是请求的等待，不拿来当帧预算，也不拿来当长任务门槛。

把 16.7 和 50 写成同一个毫秒数

帧预算来自 \(1000/60 \approx 16.7\)（假设 60Hz），长任务门槛是 50。合成一个「超过 16.7 即长任务」，或把两栏都填成 50，性能轨迹里的标记会对不上。大于 16.7 回答「这一帧装不装得下」；达到 50 才回答「这是不是长任务」。

可操作对象：把 20 ms 与 50 ms 代进 classify。20 只勾「超过帧预算」，50 两栏都勾。纸上写下 frameBudgetMs 与 longTaskMs 两个字段名。

3.5 强制同步布局

长任务的毫秒数已经分开。这一节看脚本怎样把布局从一帧的后半提前到自己这段任务里。

问题：循环里先改行高、再读 offsetHeight，主线程上多出来的是什么？

约定：一帧里脚本在样式计算、布局、绘制之前。脚本若在改过样式之后读取几何量，例如 offsetHeight 或 getBoundingClientRect()，引擎会在这次读取时把尚未完成的布局同步算完，以免读到旧尺寸。紧接着的下一行若再改样式，刚算完的布局作废，下一次读取再算一遍。这样读写交错的循环，称为强制同步布局。次数跟着行数走：全量是 listN 的 10000 次量级，一屏是 viewportRows 的 12 次。工作量记在主线程这段脚本上，先对照 frameBudgetMs，达到 longTaskMs 才叫长任务。

function paintAll(rows) {
  var i = 0;
  var height = 0;
  while (i !== rows.length) {
    rows[i].style.height = '48px';
    height = rows[i].offsetHeight;
    i = i + 1;
  }
  return height;
}

function thrashCount(rowCount) {
  var writes = 0;
  var reads = 0;
  var i = 0;
  while (i !== rowCount) {
    writes = writes + 1;
    reads = reads + 1;
    i = i + 1;
  }
  return { writes: writes, reads: reads };
}

console.log('全量', thrashCount(10000));
console.log('一屏', thrashCount(12));

示例代码：examples/ch03/sync-layout.js

paintAll 里每一次写 style.height 之后都读 offsetHeight。行高字符串 48px 对应 rowHeightPx。thrashCount(10000) 给出 10000 次写和 10000 次读；thrashCount(12) 给出 12 对。paintAll 要有真实元素才读得到布局，页面演示不创建这 10000 个节点。

用教学订单页走一遍：订单行高是 48 px。若对接口返回的一页 size（20 行）尚且交错读写，次数还小；若对内存里的 listN 行各写一次再读一次，主线程按 10000 对来回。先把需要的高度读完，再集中写；或者只对可见的 12 行读一次。行高已知时，直接用 rowHeightPx，不必为了确认 48 而去读布局。

读写次数跟着行数

全量循环的交错次数是 10000 量级，一屏是 12。把读集中到循环外，或只读可见行，主线程上的布局计算就不再按 listN 重复。

可操作对象：在 paintAll 的循环体旁标两笔：写样式、读几何。再写一行替代：行高用 rowHeightPx，循环内不再读 offsetHeight。

3.6 长列表虚拟化，DOM 只留 12 行

布局被 10000 次读写提前之后，节点本身也不该有 10000 个。这一节把 DOM 行数和两笔高度分开。

问题：10000 行都放进 DOM，高度是多少？只保留一屏的节点时，DOM 行数和节点高度又是多少？

约定：全量 DOM 为 listN 的每一行创建一个节点，基准 10000。这些节点叠起来的高度是 Course.orderMath.fullListPx()，即 \(10000 \times 48 = 480000\) px。虚拟列表只为当前视口创建 viewportRows 个行节点，教学基准是 12，不另加缓冲区行数。这些节点的高度是 Course.orderMath.visiblePx()，即 \(12 \times 48 = 576\) px。滚动要能走到最后一行，用占位把可滚动范围留在 fullListPx()；占位不是行节点。演示里的「高度」读节点这一侧：全量 DOM 用 fullListPx，虚拟列表用 visiblePx。

\[\mathrm{visiblePx} = 12 \times 48 = 576\]

\[\mathrm{fullListPx} = 10000 \times 48 = 480000\]

var listN = 10000;
var viewportRows = 12;
var rowHeightPx = 48;

function listView(virtual) {
  if (virtual) {
    return {
      domRows: viewportRows,
      heightPx: viewportRows * rowHeightPx
    };
  }
  return {
    domRows: listN,
    heightPx: listN * rowHeightPx
  };
}

console.log('全量 DOM', listView(false));
console.log('虚拟列表', listView(true));

示例代码：examples/ch03/virtual-rows.js

全量 DOM 打印 domRows: 10000、heightPx: 480000。虚拟列表打印 domRows: 12、heightPx: 576。与 fullListPx()、visiblePx() 相同。

用教学订单页走一遍：接口一页是 size 行，基准 20，那是请求的分页，不是 DOM 里该创建的节点数。视口大约 12 行，行高 48 px，可见 576 px。整表逻辑高度仍是 480000 px，供滚动占位使用。占位元素是一个空盒子，里面不要再塞 10000 个行。演示「全量 DOM」只画一条示意图，不创建 10000 个节点。

虚拟列表仍把 10000 行放进 DOM

函数名叫虚拟列表，若仍为 listN 创建行节点，DOM 行数是 10000，节点高度落到 fullListPx() 的 480000 px，和全量 DOM 是同一对读数。虚拟列表这一档应读出 12 与 visiblePx() 的 576。

可操作对象：切换「全量 DOM / 虚拟列表」。读 DOM 行数是 10000 还是 12，高度是 fullListPx 还是 visiblePx。

全量 DOM 与虚拟列表切换分段
观察要点：① 「全量 DOM」的 DOM 行数是 listN 10000，高度调用 Course.orderMath.fullListPx()，读数 480000 px，高度来自 fullListPx。② 「虚拟列表」的 DOM 行数是 viewportRows 12，高度调用 visiblePx()，读数 576 px，高度来自 visiblePx。③ 两笔都用行高 48：\(576 = 12 \times 48\)，\(480000 = 10000 \times 48\)。④ 视图里的横条最多 12 条。虚拟列表这一档不会把 10000 行放进 DOM；全量一档也只用示意图，不创建 10000 个节点。

3.7 memo 只在测量后用

首屏字节、长任务门槛和 DOM 行数都有了读数。这一节规定 memo 排在这些读数之后。

问题：列表一卡，要不要先把每一行包进 memo？

约定：memo 记住上一份输入。输入同为这一行时，跳过这次渲染函数，沿用上一次的输出。它不改 bundleMainKb，不改 bundleVendorKb，因此不改 firstScreenKb() 的 600。它也不把 DOM 节点从 listN 改成 viewportRows。测量先看三处：首屏是不是仍是 600 KB，主线程任务有没有达到 50 ms，DOM 行数是 10000 还是 12。三处已经指出字节、长任务或节点个数时，先处理那一处。测量指出同一行因无关状态反复执行渲染函数时，再对那一行使用 memo。

var bundleMainKb = 180;
var bundleVendorKb = 420;

function firstScreenKb() {
  return bundleMainKb + bundleVendorKb;
}

function memo(render) {
  var prev;
  var prevOut;
  return function (row) {
    if (row === prev) return prevOut;
    prev = row;
    prevOut = render(row);
    return prevOut;
  };
}

function renderRow(row) {
  return row.amountText;
}

var MemoRow = memo(renderRow);
console.log(MemoRow({ amountText: '199.50' }));
console.log('没测量也包了 memo，首屏仍是', firstScreenKb());

示例代码：examples/ch03/memo-after-measure.js

金额文本 199.50 与订单金额分 amountFen 经 Course.orderMath.yuanText() 得到的展示一致。第二行日志的首屏仍是 600。包了 memo，加法仍是 \(180 + 420\)。

用教学订单页走一遍：订单行展示金额时调用 yuanText()。父级每次翻页都新建行对象时，memo 的引用比较对不上，渲染函数仍会跑。即便比较命中，下载的主包与第三方也不变，DOM 里有多少行节点也不变。先读 3.1 的首屏 KB、3.4 的两道毫秒数、3.6 的 DOM 行数，再决定这一行要不要包。

没测量就 memo，首屏仍是 600 KB

未测量就给订单行包 memo，firstScreenKb() 仍是主包 180 加第三方 420，即 600 KB。路由块是否懒加载、DOM 是 10000 行还是 12 行，都不因这层缓存改变。memo 只回答「同一输入要不要再执行渲染函数」。

可操作对象：在纸上先写三个测量栏：首屏 KB、是否达到 50 ms、DOM 行数。三栏都填完，并且热点确是重复渲染，再在第四栏写 memo。只填了第四栏时，把首屏改回 600。

3.8 LCP、INP、CLS

加载和主线程都有了本课的数。这一节把三个体验指标的「一次」和「分布」分开，并把缺行高的挪动记成 48 px。

问题：实验室跑出一次 LCP 之后，能不能把这个数当成用户侧的 LCP？缺了行高，页面挪了多少像素？

约定：LCP（Largest Contentful Paint）是视口里最大的那块文字或图片完成绘制的时间。订单页上它常落在表头或首屏主内容。首屏 600 KB 会推迟它的下载和执行，LCP 的单位仍是时间，不是 KB。INP（Interaction to Next Paint）是交互到下一次绘制的延迟。主线程上达到 longTaskMs 50 ms 的任务会推迟这次绘制，INP 因此变长；INP 的读数仍是时间，不是把 50 填进去。CLS（Cumulative Layout Shift）是布局偏移分数，由影响比例和距离比例相乘得到。分数不是像素。

三个指标都各有两种数。实验室一次是一次运行、一次环境里的一个样本。用户侧是多次访问上的分布；对外常用第 75 百分位做一条汇总，汇总来自分布，不代替分布本身。用实验室那一次填进用户侧的栏目，两套数就并成了一个。

行上没有预留 rowHeightPx 时，这一行的内容插入后，后面的内容下移一行。教学订单页把这次挪动的距离记为 clsShiftPx，与行高同为 48 px。预留 48 px 之后，这一次挪动的像素是 0。48 填在「挪了多少像素」，不填进 CLS 分数。

var rowHeightPx = 48;
var clsShiftPx = 48;

function shiftPx(hasRowHeight) {
  if (hasRowHeight) return 0;
  return clsShiftPx;
}

用教学订单页走一遍：订单表若先渲染空行、图片或金额晚到，且行上没有 48 px 的高度，后续行下移 clsShiftPx。虚拟列表的 12 个节点同样要带上 rowHeightPx，否则一屏内部也会挪 48 px。实验室对 http://localhost:5173 上的 /orders 跑一次，得到的 LCP 是那一次的样本。用户从各自的网络打开同一页，LCP 铺成分布。报告里两栏都留着。

缺行高导致 CLS 48 px

行高未预留时，插入内容把后面的订单行挪动 48 px，即 clsShiftPx，与 rowHeightPx 相同。CLS 分数是比例的乘积，像素记在挪动距离上。给行预留 48 px 后，shiftPx(true) 为 0。

用一次实验室 LCP 代替用户侧分布

实验室一次 LCP 是一个样本。用户侧是多次访问的分布，常用第 75 百分位做汇总。把样本写进分布那一栏，INP 和 CLS 若同样只留一次实验室结果，三指标都会并成一个数。本课要求两个数分开记。

可操作对象：画两列：实验室一次、用户侧分布。LCP、INP、CLS 各写一行。在 CLS 行旁加一笔像素：缺行高为 48，已预留行高为 0。

本章避坑清单

  1. 预加载把路由块又拉回首屏。懒加载时首屏是 firstScreenKb() 的 600 KB；预加载后再加 bundleRouteKb，成为 640 KB。
  2. 把 16.7 和 50 写成同一个毫秒数。帧预算是 \(1000/60 \approx 16.7\)（假设 60Hz），长任务门槛是 50 ms。大于 16.7 只说明这一帧装不下。
  3. 虚拟列表仍把 10000 行放进 DOM。虚拟列表的 DOM 行数是 12，高度用 visiblePx() 得 576 px。10000 行与 fullListPx() 的 480000 px 属于全量 DOM。
  4. 没测量就 memo，首屏仍是 600 KB。memo 不减少主包 180 与第三方 420，也不把 DOM 从 10000 行改成 12 行。
  5. 缺行高导致 CLS 挪动 48 px。clsShiftPx 与 rowHeightPx 都是 48。这是像素距离，不是 CLS 分数。
  6. 用一次实验室 LCP 代替用户侧分布。实验室一次是一个样本；用户侧是分布。INP、CLS 同样分开记。

本章小结与延伸阅读

订单页首屏是 Course.orderMath.firstScreenKb()，即主包 180 KB 加第三方 420 KB，共 600 KB。路由块 40 KB 懒加载时不进这 600；预加载或打进入口后，首屏为 640 KB。主线程上，帧预算按 \(\frac{1000}{60} \approx 16.7\)（假设 60Hz）估算，长任务另看 50 ms。强制同步布局让读写按行数交错。全量 DOM 是 10000 行、fullListPx() 480000 px；虚拟列表的 DOM 是 12 行、visiblePx() 576 px。memo 不改变 600 KB，只在测量之后用。LCP、INP、CLS 的实验室一次和用户侧分布分开记。缺行高时挪动 clsShiftPx 48 px。

  • web.dev，《Largest Contentful Paint》《Interaction to Next Paint》《Cumulative Layout Shift》：实验室一次是一个样本，用户侧是分布，常用第 75 百分位做汇总。CLS 分数由影响比例与距离比例相乘，与挪动像素不是同一个数。
  • 长任务：主线程任务达到 50 ms 才记入长任务，与 longTaskMs 一致。帧预算另按 \(1000/60 \approx 16.7\)（假设 60Hz）估算。
  • web.dev 关于避免大规模布局与布局抖动的说明：写样式之后立刻读几何量，会把布局提前到脚本阶段。次数按行数算，全量对照 listN，一屏对照 viewportRows。
