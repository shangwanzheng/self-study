这一章：订单页从哪一次请求，到金额只留一处

先回答订单页的数据在哪一次请求里拿到。页面在 http://localhost:5173 打开 /orders，接口在 http://localhost:8080 的 /api/orders。MPA 由服务端在这次导航的文档里写入订单表。SPA 的首屏 HTML 是壳，浏览器再请求接口。SSR 在用户打开时由服务端写入 HTML。SSG 的表在构建那一次写好，和 SSR 不是同一次请求。

2.1 多页、单页、SSR、SSG 的数据各在哪一次请求

章首把数据、发布边界和分层串成一条。先走数据：订单表落在哪一次请求。

问题：订单表的数据，在浏览器这一次请求里，还是在服务端那一次里？

约定：多页记作 MPA，单页记作 SPA。四种形态各有一次固定的数据落点，本章的基准按下表，不随框架菜单改口。「浏览器这一次请求」指浏览器拿到文档之后，再去请求 apiOrigin 上的 apiPath。SPA 的订单表走这一次。「服务端那一次」指订单表写进 HTML 的那一次发生在服务端：MPA 与 SSR 的写入和用户打开是同一次文档请求；SSG 的写入在构建时，早于打开。所以 SSG 也读作服务端那一次，却和 SSR 不是同一次请求。具体注册参数、构建命令以所用框架的文档原文为准。

形态数据在哪一次具体是哪一次与打开是否同一次
MPA服务端那一次这次导航的文档请求，表写进 HTML是
SPA浏览器这一次请求拿到壳之后请求 /api/orders否
SSR服务端那一次打开时渲染 /orders是
SSG服务端那一次构建时写入，不是打开时否

基准算例：页面源是 http://localhost:5173，路由 /orders。接口源是 http://localhost:8080，路径 /api/orders，查询用 page 1、size 20。总行数 listN 是 10000，首屏表只带当前这一页。金额事实 amountFen 是 19950，库存 stock 是 8。下面的函数把四种形态收成与上表相同的四列。页面上的演示改读 Course.data.order 的路径，不另抄一套地址。

function whereOrderData(shape) {
  if (shape === 'MPA') {
    return {
      where: '服务端那一次',
      which: '这次导航的文档请求，表写进 HTML',
      table: '有',
      sameOpen: '是'
    };
  }
  if (shape === 'SPA') {
    return {
      where: '浏览器这一次请求',
      which: '拿到壳之后请求 /api/orders',
      table: '没有',
      sameOpen: '否'
    };
  }
  if (shape === 'SSR') {
    return {
      where: '服务端那一次',
      which: '打开时渲染 /orders',
      table: '有',
      sameOpen: '是'
    };
  }
  if (shape === 'SSG') {
    return {
      where: '服务端那一次',
      which: '构建时写入，不是打开时',
      table: '有',
      sameOpen: '否'
    };
  }
  return null;
}

console.log('SSR', whereOrderData('SSR').which);
console.log('SSG', whereOrderData('SSG').which);

示例代码：examples/ch02/where-data.js

控制台两行是 SSR 打开时渲染 /orders 与 SSG 构建时写入，不是打开时。两行都来自「服务端那一次」，具体哪一次已经分开。

SSR 和 SSG 当成同一次请求

两份首屏 HTML 里都可以有订单表，读数却差一次。SSR 的 19950 写在用户打开 /orders 的那一次里。SSG 的 19950 写在构建那一次里。把两行的「具体是哪一次」合成一句「服务端渲染过」，库存 8 就会被当成打开瞬间的现算值。

打开后又请求了接口，就改记首屏来源

SSG 的页面打开后，浏览器仍可再请求 /api/orders 看当前库存。那一次更新的是打开之后的数。首屏表的来源仍是构建那一次，sameOpen 仍是「否」。不要因为后来有一次接口，就把 SSG 改记成 SPA。

可操作对象：在纸上抄四行：形态、数据在哪一次、具体是哪一次、与打开是否同一次。SSR 与 SSG 的第一列都写「服务端那一次」，第三列必须不同。下一节的分段用同一张表核对首屏 HTML。

2.2 首屏 HTML 里有没有订单表

四次请求已经分开。这一节看同一次打开的首屏 HTML 里有没有订单表。

问题：打开 /orders 时，首屏 HTML 里有没有订单表？

约定：首屏 HTML 指浏览器为这次打开拿到的第一份文档，还没等后续的 JavaScript 把表格插进去。MPA、SSR、SSG 的基准是这份 HTML 里已经有订单表。SPA 的基准是这份 HTML 只有壳，表要等浏览器请求 /api/orders 之后才出现。表里的行数是当前页的 size，不是 listN。

基准算例：第 page 页是 1，每页 size 是 20。总行数 listN 是 10000，pageCount() 为 500。有表的那三行，首屏 HTML 里是这一页的 20 行，金额展示由 yuanText() 写成 199.50，库存是 8，金额事实仍是 19950。SPA 这一行的首屏 HTML 里没有这些单元格。切换下面的分段，读数与 2.1 的函数一致。

壳页面也写成首屏已有订单表

SPA 的文档响应里若只有导航和空容器，订单表还不存在。把「脚本稍后会画出来」记成「首屏 HTML 里有表」，检索和首屏看到的就是壳，20 行要等 http://localhost:8080/api/orders 返回。

把 10000 行写进首屏 HTML

listN 是 10000，接口一页是 size 20。首屏表按第 1 页的 20 行写。把 10000 行都放进第一份 HTML，文档体积和这一次请求的工作量都会离开本页的分页基准。

可操作对象：切换 MPA、SPA、SSR、SSG。读「数据在哪一次」和「首屏 HTML 有订单表」两栏。SSR 与 SSG 的表都是「有」，「与打开是否同一次」一栏必须一是一否。

四种形态的数据落点切换 MPA / SPA / SSR / SSG
观察要点：① MPA：数据在服务端那一次，就是这次文档请求，首屏 HTML 有订单表。② SPA：数据在浏览器这一次请求，地址是 apiOrigin 加上 /api/orders，首屏 HTML 没有订单表。③ SSR：数据在服务端那一次，而且与打开是同一次，首屏 HTML 有订单表。④ SSG：数据也在服务端那一次，但是构建时；「与打开是否同一次」为否。首屏 HTML 仍有订单表。和 SSR 不是同一次请求。

2.3 SEO 与部署方式为什么不能混用

表在不在文档里已经能读出来。SEO 看这份 HTML，部署看上线的是请求时生成还是构建产物，两列各记各的。

问题：文档能被检索，是不是就该部署成静态文件？

约定：SEO 这一列只回答：首次拿到的 HTML 里有没有订单表的文本。部署这一列只回答：上线的是请求到达时生成的 HTML，还是构建好的文件。两列分开填。检索行为以搜索引擎当时的文档为准，本章只用「HTML 里有没有表」作为教学对照，不把某一家爬虫的菜单写成定论。

形态SEO：HTML 里有没有表文本部署
MPA有。表在这次文档响应里每次导航由服务端给出整份文档
SPA没有。壳里还没有 20 行可以部署静态壳，数据在 http://localhost:8080
SSR有。表在打开时那一次里打开时有服务处理 /orders 并写入 HTML
SSG有。文本是构建当时的 19950 与 8部署构建好的文件，打开时不再现算这张表

基准算例：要让检索看到金额 199.50 和库存 8，对应的 HTML 里得有这张表，也就是 MPA、SSR 或 SSG。其中只有 SSR 的这张表和用户打开是同一次。SSG 能被检索到的是构建时写入的 19950，部署物是静态文件。SPA 把壳部署成静态文件之后，检索列仍然是「没有」。页面源 5173 与接口源 8080 只说明两个监听，不代替这两列。

能检索就改成静态文件

SSG 的 HTML 里有表，检索能看到构建时的文本。打开时的金额和库存仍是构建当时的 19950 和 8。要打开时现算，部署的是 SSR 那种请求时渲染。把 SSG 的文件再叫成 SSR，两列就合成了一个词。

用部署方式填写数据在哪一次

静态托管回答的是文件放在哪。数据在哪一次请求，仍回到 2.1 的四行。SPA 也可以把壳部署成静态文件，首屏 HTML 里还是没有订单表，数据仍在浏览器对 /api/orders 的这一次请求里。

可操作对象：拿 2.2 里当前选中的形态，在纸上另画两列：HTML 里有没有表文本、部署的是请求时生成还是构建产物。两列用不同的词，不互相代替。

2.4 微前端解决发布和团队边界

形态的请求和文档对齐了。微前端划的是谁发布、哪个团队拥有订单页。

问题：两个团队要分开发布订单页，拆的是前端发布，还是后端服务？

约定：微前端把订单页收成可以单独发布的子应用，团队边界跟发布走：谁改订单表、何时发布，可以和壳分开。后端按服务拆分回答的是进程、数据和接口所有权。库存从 8 怎么扣、金额 19950 谁说了算，仍是一处业务规则。子应用的个数不增加事实的份数。接入框架的注册参数以该框架文档原文为准。

基准算例：壳和订单子应用可以分开发布，路由仍是 /orders，接口仍是 /api/orders。发布拆开之后，stock 仍是 8，amountFen 仍是 19950，yuanText() 仍是 199.50。分页仍是第 1 页、每页 20 条，总行数仍是 10000。这些字段不因为多了一个前端发布单元就各写一份。

把微前端当成后端服务拆分

两个团队各发一版订单页，解决的是发布节奏和代码所有权。库存扣减、金额 19950 仍留在原来的那一处规则里。按后端服务的边界去划子应用，页面上会以为每个子应用都拥有一份订单数据。

每个子应用各写一套从 8 扣到 7 的规则

子应用只负责自己的发布。扣减若在订单子应用里写一遍、在别的子应用里再写一遍，界面会看到两套库存。事实仍只有 Course.data.order.stock 这一处，基准是 8。

可操作对象：画两个框：发布框里写「壳」和「订单子应用」；规则框里只写一行 stock 8 和一行 amountFen 19950。发布框可以有两格，规则框保持一格。

2.5 路由接管与公共依赖

发布和团队已经分开。路由要把 /orders 交给一个子应用，公共依赖仍只占首屏里的一份。

问题：/orders 交给子应用之后，公共依赖要不要再打进它的首屏？

约定：路由接管表示 /orders 只由一个子应用渲染订单表。壳不再为同一条路由画第二张表。公共依赖是 bundleVendorKb，基准 420 KB，已经加进首屏。首屏由 firstScreenKb() 计算，等于主包 bundleMainKb 180 KB 加上这一份 420 KB。路由块 bundleRouteKb 40 KB 在懒加载时不进这 600 KB，那一笔放到第 3 章。公共依赖再打进子应用的首屏时，加上的是又一份 420 KB，不是把 40 KB 当成这一份。

\[ \mathrm{firstScreenKb} = 180 + 420 = 600 \]

再叠一份公共依赖时，加上的是 bundleVendorKb。主包 180 KB 不在这一次加法里，路由块 40 KB 也不在。

\[ 600 + 420 = 1020 \]

基准算例：只计一份公共依赖时，首屏是 600 KB，这是基准。每个子应用的首屏再打包一份公共依赖，读数变成 1020 KB。基准首屏仍是 600 KB，1020 只出现在「再叠一份」这一支。示例里的两个布尔与这两式对应。

var bundleMainKb = 180;
var bundleVendorKb = 420;

function firstScreenWithVendor(extraCopy) {
  var kb = bundleMainKb + bundleVendorKb;
  if (extraCopy) {
    kb = kb + bundleVendorKb;
  }
  return kb;
}

console.log('一份公共依赖', firstScreenWithVendor(false));
console.log('再叠一份', firstScreenWithVendor(true));

示例代码：examples/ch02/shared-dep.js

控制台两行是 一份公共依赖 600 与 再叠一份 1020。页面上的基准仍读 Course.orderMath.firstScreenKb()，结果是 600。

壳和子应用同时接管 /orders

两处都渲染订单表，/api/orders 会按第 1 页、每页 20 条各打一次。路由只交给一个子应用。这和公共依赖叠成 1020 KB 是两件事：前者是谁画表，后者是首屏里有几份 420 KB。

公共依赖打进每个子应用的首屏，首屏从 600 KB 再叠一份

基准首屏 \(180+420=600\) KB，里面已经有一份 bundleVendorKb。再打进子应用，首屏从 600 KB 再叠一份，成为 \(600+420=1020\) KB。不要把第 3 章的 \(600+40=640\) 拿来当作这一份。640 是路由块进了首屏，1020 是公共依赖有了第二份。

可操作对象：在纸上写两行：600 与 1020，并注明第二行多出来的是 420 KB 的公共依赖。旁边另写 40 KB，标成「路由块，懒加载时不在这两行里」。再标出 /orders 只有一个子应用接管。

2.6 样式隔离，全局 CSS 会互相盖

路由和体积分开了。样式若还是全局 CSS，后加载的规则会盖住订单表。

问题：壳和订单子应用都写了全局 CSS，订单表还看得见吗？

约定：全局 CSS 的选择器作用在整份文档上。壳和子应用若共用类名，后出现的规则盖住先出现的规则，订单表的金额单元格会跟着壳的声明走。样式隔离让选择器停在子应用边界内，例如单独的样式根，或影子树。影子树和具体框架的配置键以相应文档原文为准，本章只定边界：订单表用的类名不能和壳的全局规则撞在同一个选择器上。

壳把 .amount 设成透明。订单表若用同一个类名，199.50 被盖住。

199.50
选择器停在订单表边界内

类名不再跟壳共用。展示仍是 yuanText() 的 199.50。

全局 CSS 盖住订单表

壳的全局规则作用到子应用的 table 上，订单表会被盖住或改掉字号、颜色。选择器要停在订单子应用自己的样式根里，不写进整份文档的全局 CSS。

可操作对象：在订单表的金额格上标类名。若与壳的全局选择器相同，把这一格圈进「会被盖住」，并改到子应用自己的前缀下。对照上面两块：左边是被盖住的 199.50，右边是边界内仍能读到的 199.50。

2.7 分层：页面、组件、请求、状态、桥

子应用的边界画完了。页面内部再分成页面、组件、请求、状态、桥。

问题：金额和库存写在页面、组件、请求、状态、桥的哪一层？

约定：五层各做一件事。页面负责路由 /orders 上放哪一块。组件负责表格和金额的展示，展示调用 yuanText()。请求层是发出接口调用的 JavaScript，只在这一层访问 /api/orders。状态层保存这一份 amountFen 和这一份 stock，列表和详情读同一份。桥只传与客户端往来的消息，消息里可以带已经准备好的展示字段。桥的配对、超时和版本放到第 7 章，本章不在桥上写第二份金额规则。各层的目录名以仓库约定为准。

页面

组装 /orders。决定这里放表格还是空态。

组件

画出金额 199.50。不另存一份 19950。

请求

只在这一层请求 /api/orders，参数是第 1 页、每页 20 条。

状态

amountFen 19950 与 stock 8 各一份。

桥

和客户端往来的消息。规则不写在桥上。

基准算例：请求层带上 page 1、size 20，向 http://localhost:8080/api/orders 取当前页。状态层记下 amountFen 19950、stock 8。组件把 19950 格式化成 199.50。总行数 10000 留在状态里作为列表规模，不要求组件一次画出 10000 行。桥若把 199.50 传给客户端，传的是展示文本，金额事实仍留在状态层的 19950。

在组件里再存一份 19950

组件为了少传一次参数，把 amountFen 再抄进自己的字段。状态层一份、组件一份，金额事实变成两份。组件只接收 19950 并调用 yuanText()，不保留第二份。

页面和组件各自请求 /api/orders

页面按 page 1、size 20 请求，组件又按另一组分页请求。后返回的那一次会盖住订单表。请求只留在请求层，分页参数只用这一套 page 与 size。

可操作对象：给订单页的五个目录各写一句话：谁组装 /orders、谁画 199.50、谁请求 /api/orders、谁保存 19950 和 8、谁和客户端说话。金额事实只出现在状态那一句里。

2.8 BFF 聚合时业务规则仍只有一处

五层分开之后，聚合可以放到 BFF。金额事实 19950 仍然只有一处。

问题：列表在 BFF 聚合成一次响应之后，19950 还有几份？

约定：BFF 把这一页要展示的字段收成一次响应，例如当前页的行、金额、库存。聚合减少的是往返次数。金额规则仍只有一处：事实是 amountFen 19950。浏览器用 yuanText() 得到 199.50，这是展示，不另计一份事实。子应用、页面脚本若再写一份 19950，份数就是 2。BFF 的路径与字段以接口文档原文为准，本章不另造一套金额。

基准算例：规则只在 BFF 时，份数是 1，数值是 19950，展示是 199.50，库存仍是 8。分段拨到「每个子应用各写一份」时，BFF 一份、子应用一份，份数是 2，两份里的数都还写着 19950。示例单独在控制台跑，对 19950 得到 199.50；页面演示改用 Course.orderMath.yuanText()，两处展示文本相同。

var amountFen = 19950;

function yuanText(fen) {
  var sign = fen < 0 ? '-' : '';
  var v = Math.abs(Math.trunc(fen));
  var whole = Math.floor(v / 100);
  var frac = String(v % 100);
  if (frac.length < 2) {
    frac = '0' + frac;
  }
  return sign + whole + '.' + frac;
}

function amountFactCopies(mode) {
  if (mode === 'each-app') {
    return 2;
  }
  return 1;
}

console.log('只在 BFF', amountFactCopies('bff'), amountFen, yuanText(amountFen));
console.log('各写一份', amountFactCopies('each-app'), amountFen, yuanText(amountFen));

每个子应用各写一份 19950

BFF 已经给出 amountFen 19950，子应用再写一份同样的 19950。分段读数从 1 变成 2。两份以后若有一处改成别的分，订单表和接口会对不上。展示文本 199.50 不参与这个计数。

规则写在浏览器和 BFF 两边

浏览器里用 JavaScript 再实现一遍金额规则，BFF 里留着原来的 19950。聚合没有减少事实，只是多了一次往返上的拼装。规则留在 BFF 这一处，浏览器只调用 yuanText() 做展示。

可操作对象：切换「规则只在 BFF」和「每个子应用各写一份」。读金额事实的份数，只能是 1 或 2。两档的 amountFen 都是 19950，展示都是 199.50，stock 都是 8。

金额事实有几份切换规则放在哪
观察要点：① 「规则只在 BFF」时，金额事实份数是 1。② 「每个子应用各写一份」时，份数是 2，视图里同时有 BFF 和子应用两张卡片。③ 两档的 amountFen 都是 19950，yuanText() 都是 199.50。199.50 是展示，不另计一份。④ stock 保持 8，不随份数变成第二份金额。

本章避坑清单

  1. SSR 和 SSG 当成同一次请求。两份首屏 HTML 都可以有订单表；SSR 写在打开时，SSG 写在构建时。
  2. 把微前端当成后端服务拆分。微前端划的是发布和团队边界，stock 8 和 amountFen 19950 仍各只有一处。
  3. 每个子应用各写一份 19950。规则只在 BFF 时份数是 1，再写一份就是 2。
  4. 公共依赖打进每个子应用的首屏，首屏从 600 KB 再叠一份，成为 \(600+420=1020\) KB。基准首屏仍是 600 KB。
  5. 全局 CSS 盖住订单表。壳的 .amount 会把 199.50 盖住，选择器要停在子应用边界内。
  6. 规则写在浏览器和 BFF 两边。浏览器只做 yuanText() 的展示，金额事实留在 BFF 的 19950。
  7. 壳和子应用同时接管 /orders，同一页会打出两次 /api/orders。
  8. 把 listN 10000 行写进首屏 HTML。这一页只有 size 20 行。

本章小结与延伸阅读

订单页的数据先落到一次请求上。MPA 与 SSR 由服务端在打开时的文档请求里写入订单表，首屏 HTML 有表。SPA 的首屏 HTML 是壳，浏览器再请求 http://localhost:8080/api/orders。SSG 的表在构建时写入，和 SSR 不是同一次请求。SEO 看 HTML 里有没有表文本，部署看上线的是请求时生成还是构建产物。微前端划发布和团队边界，/orders 只交给一个子应用。公共依赖再打进子应用首屏，会从 600 KB 再叠一份 420 KB，成为 1020 KB。全局 CSS 会盖住订单表。分层是页面、组件、请求、状态、桥。聚合放在 BFF 时，金额事实仍是 19950 这一处，yuanText() 的 199.50 只用于展示。

  • web.dev 文章《Rendering on the Web》：MPA、SPA、SSR、SSG 在文档响应和数据请求上的差别。具体行为以所引用的原文为准。
  • Martin Fowler 上 Cam Jackson 的《Micro Frontends》：子应用对应独立发布和团队边界。注册参数以所用框架的文档原文为准。
  • Sam Newman 与 Phil Calçado 关于 BFF 的文章：聚合放在面向页面的这一层，领域规则仍留在一处。
