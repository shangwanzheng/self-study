高级要守住的边界

学完中级课，你已经能交付教学订单页 /orders。这一章不讲新框架，用同一笔订单把高级要守的四条判断定下来：形态、性能、安全、发布。

这一章：同一笔订单，四条判断

中级已经能交付 /orders：表格分页、金额按分算、接口失败有提示。高级不是把这张页再写一遍，而是在它变大、变多人用、要反复发布时，守住四条判断：形态（数据在哪一次请求里拿、页面怎么切）、性能（首屏多大、主线程多忙）、安全（什么不能信前端）、发布（新旧包怎样替换和回滚）。

整章只用一笔订单。首屏 firstScreenKb() 是 600 KB，路由块 40 KB 按需再取。一屏 viewportRows 是 12 行。入口 HTML 的 htmlMaxAgeSec 是 60 秒，带 hash 的资源用 assetMaxAgeSec 长缓存。乐观更新先把界面显示成 order.stock - 1（7），请求失败回到确认值 8；Course.data.order.stock 仍是 8。菜单里藏起按钮只是体验，接口照样要鉴权。

1.1 中级已经能交 /orders，高级接着守什么

先把起点摆出来：中级课交付的那张订单页，已经有哪些东西是对的。

问题：页面能打开、能翻页、金额显示对了，还缺什么？

约定：中级的交付以“这张页在我这台机器上按需求跑通”为界：路由 route 是 /orders，列表接口 apiPath 是 /api/orders，第 page 页、每页 size 条，金额用整数分 amountFen 计算，展示时才转成元。高级在这个基础上多守一层：页面变大以后首屏还撑不撑得住，换人、换端以后哪些判断不能交给前端，发布十次以后旧包怎么退场。本课把这些归成四条判断：形态、性能、安全、发布。每条判断都要能落到 Course.data.order 里的一个量上，不靠“感觉慢”“感觉不安全”。

基准算例：页面源 pageOrigin 是 http://localhost:5173，接口源 apiOrigin 是 http://localhost:8080。一次成功的列表请求同时满足 HTTP 状态 httpOk（200）和业务 code businessCodeOk（0）。金额 amountFen 是 19950，Course.orderMath.yuanText() 给出展示文本 199.50。这些在中级已经对了，高级不重新定义它们，只在它们上面加判断。

HTTP 200 就当业务成功

接口返回 httpOk（200），正文里的业务 code 却是 businessCodeFail（40001），这一次仍是失败。只看状态码就把列表标成“已加载”，失败提示永远不会出现。两个字段要一起看。

拿 199.50 元去做加减

展示文本 199.50 是 yuanText() 的输出，只给人看。合计、优惠、退款都用 amountFen（19950）这样的整数分去算，最后一步再格式化。拿小数元去累加，误差会在对账时才冒出来。

可操作对象：在纸上列出 /orders 已经交付的五件事：路由、接口路径、分页参数、金额按分、HTTP 状态与业务 code 一起判断。每件后面留一格，标上它以后最可能牵涉形态、性能、安全、发布中的哪一条。

1.2 为什么这门课不换一套订单数字

起点定了。后面九章都在这笔订单上推，所以数字只能有一套。

问题：每章换一组更“典型”的数字，不是更好讲吗？

约定：这门课的基准算例只来自 Course.data.order 和 Course.orderMath，与中级课、Java 服务课同一笔教学订单。一章得出的结论，下一章要能拿同一个数核对；换了数字，就分不清是结论变了，还是例子变了。章内需要推导的值用函数算，例如 pageCount()、visiblePx()、firstScreenKb()，不在正文里另抄一份常量。

类别字段基准值
标识userIdText、snowflakeText10001；9007199254740993（只以字符串存放）
金额与库存amountFen、stock19950 分（展示 199.50）；8
分页page、size、listN1；20；10000，共 pageCount() = 500 页
超时connectTimeoutMs、readTimeoutMs、browserTimeoutMs500；2000；3000（毫秒）
结果httpOk、businessCodeOk、businessCodeFail200；0；40001

基准算例：雪花 id snowflakeText 是 9007199254740993，超过了 JavaScript 能精确表示的最大安全整数。Course.orderMath.jsonNumberRoundTrip('9007199254740993') 先按 JSON 数字解析再序列化，得到 9007199254740992，末位变了。isSafeId() 对它返回 false，对 userIdText（10001）返回 true。所以 id 在接口里按字符串传，前端也按字符串存和比较。

用 userIdText 10001 演示精度丢失

10001 远小于最大安全整数，按数字解析再序列化仍是 10001，什么也演示不出来，反而让人以为“id 当数字没问题”。精度丢失要用 snowflakeText：9007199254740993 往返后是 9007199254740992。

雪花 id 按 JSON 数字传

接口把 9007199254740993 写成 JSON 数字，前端 JSON.parse 之后已经是 9007199254740992。再拿它去查详情，查到的是另一笔订单，或者查不到。id 在协议里就写成字符串，不要指望前端事后补救。

可操作对象：在浏览器控制台里对两个文本各跑一次 Course.orderMath.jsonNumberRoundTrip() 和 Course.orderMath.isSafeId()：一个是 '10001'，一个是 '9007199254740993'。把四个结果抄在表格旁边。

1.3 一个现象先落在形态、性能、安全、发布的哪一条

数字只有一套。接下来给每个线上现象先找一个归属，再去查数。

问题：用户说“订单页有问题”，第一步先问什么？

约定：四条判断各自回答一个问题。形态：页面怎么切、数据在哪一次请求里拿到，是浏览器拿到 HTML 之后再请求 /api/orders，还是服务端那一次请求里已经把订单写进 HTML。性能：首屏要下载多少、主线程一次被占多久、一屏画多少行。安全：哪些输入不能当代码执行，哪些判断不能交给前端。发布：新包怎么替换旧包、缓存多久、回滚改什么。一个现象先落到一条，再去找那一条的量；同一个现象可以牵涉第二条，但第一步只选一条作为入口。

形态

数据在哪一次请求里拿；单页、多页、服务端渲染怎么切。

性能

首屏 firstScreenKb()、主线程门槛、一屏 viewportRows。

安全

备注不当 HTML；鉴权在服务端；密钥不进前端包。

发布

入口 htmlMaxAgeSec 短，带 hash 资源 assetMaxAgeSec 长。

基准算例：首屏下载 600 KB 才可交互，落在性能，先看 \(180+420=600\) 里哪一块能拆。订单备注里有人写了一段标签，被当成 HTML 插进表格，落在安全。回滚之后用户报告仍是旧脚本，落在发布，先看入口 HTML 的 60 秒。订单数据要在服务端处理 /orders 的那一次请求里就写进 HTML，落在形态。

回滚后仍是旧脚本，先去压包

用户还在跑旧脚本，和脚本大小无关。去拆 vendor、压首屏，读数不会变。这个现象落在发布：先看入口 HTML 有没有换、缓存还剩多久。

把备注拼进 innerHTML

订单备注是用户输入。用字符串拼进 innerHTML，备注里的标签和事件属性就成了页面的一部分。备注按文本插入；确实要富文本时，交给第 6 章的过滤与 CSP，而不是在拼接处补几个替换。

可操作对象：在下面的演示里依次点四个现象。每点一次，读数给出它落在哪一条、先看哪个量、后面哪一章展开。

现象先落在哪一条切换分段
观察要点：① 每个现象只点亮四张卡片中的一张，第一步只选一条入口。② 首屏过大落在性能，先看的量是 firstScreenKb()，与入口缓存秒数无关。③ 备注被当 HTML 落在安全，和首屏大小无关。④ 回滚后仍是旧脚本落在发布，先看入口 HTML 的 htmlMaxAgeSec。⑤ 数据在服务端那一次请求里拿，落在形态，问的是数据在哪次请求，不是快慢。

1.4 首屏 600 KB、一屏 12 行、入口 60 秒，各自约束什么

四条判断有了。三个最常用的量分别属于性能和发布，各管一件事。

问题：600、12、60 这三个数，能不能互相换算？

约定：三个数各管一件事，不能互相换算。首屏 600 KB 约束打开 /orders 时必须先下载的 JavaScript：firstScreenKb() 等于主包 bundleMainKb 加依赖包 bundleVendorKb；路由块 bundleRouteKb（40 KB）只在进入对应路由时才取，不算进首屏。一屏 12 行 约束一次要画多少 DOM：可见高度 visiblePx() 是 viewportRows 乘 rowHeightPx。入口 60 秒 约束发布：入口 HTML 的缓存上限 htmlMaxAgeSec，决定新入口最晚多久被用户拿到。主线程另有两道时间门槛：帧预算 frameBudgetMs 和长任务 longTaskMs。

基准算例：首屏 \(180+420=600\) KB，路由块 40 KB 另算。可见高度 \(12 \times 48 = 576\) px；整表 listN 是 10000 行，fullListPx() 是 \(10000 \times 48 = 480000\) px。接口分页一页 20 条，共 500 页。入口 HTML 60 秒，带 hash 资源 31536000 秒。帧预算按 60Hz 估算是 \(1000/60 \approx 16.7\) ms，长任务门槛是 50 ms。

把 frameBudgetMs 16.7 和 longTaskMs 50 当成同一个门槛

16.7 ms 是一帧的估算预算，超过它只说明这一帧装不下；任务达到 50 ms 才叫长任务。把两个数并成一个，要么把每次掉帧都报成长任务，要么等到 50 ms 才承认卡顿。两道门槛分开记、分开报。

把 qpsTeach 50 当成容量承诺

qpsTeach 的 50 只是教学用的数量级，用来说明“每秒几十次请求”这个量级下的现象。它不是压测结果，也不是接口能扛住的上限。容量要在真实环境里测，以测得的数为准。

一次画完 10000 行

一屏只看得见 12 行（576 px），却把 listN 行全部建成 DOM，整表高 480000 px。样式计算、布局都按整表算，主线程很容易超过 50 ms。只画可见范围附近的行，滚动时再换，第 3 章展开虚拟列表。

可操作对象：画三栏表：首屏、一屏、入口。每栏写一个数、一个算式、一条它约束的事。首屏栏写 \(180+420=600\) KB，并在旁边注明 40 KB 路由块不算进来。

1.5 菜单里藏起按钮，请求还要不要鉴权

性能和发布的量记住了。安全这一条，先看最常见的一个误会。

问题：没有权限的用户看不见“改库存”按钮，接口还需要再校验吗？

约定：前端代码全部下载到用户机器上，用户能读、能改、能绕过。菜单隐藏、按钮置灰是体验：让没有权限的人少走一步弯路。鉴权在服务端：每一次到 apiOrigin 的请求，服务端都根据会话（例如 Cookie sid）判断这个人能不能做这件事。凡是“不能让用户做”的规则，服务端必须再判一次。同理，密钥只留在服务端进程；secretName 的值 ORDER_API_SECRET 是名字，不是密钥本身，这个名字和它的值都不该出现在前端包里。本地存储键 storageKey（order.draft）只放草稿，不放凭据。

基准算例：运营隐藏了“改库存”菜单。一个没有权限的用户在控制台直接向 http://localhost:8080/api/orders 发修改请求，浏览器照样带上 Cookie sid。如果服务端只认“前端不会发这个请求”，库存 8 就被改了。服务端校验权限后返回失败，前端按 HTTP 状态和业务 code 显示失败，stock 仍是 8。

以为隐藏的按钮就发不出请求

请求不一定从按钮发出。控制台、抓包重放、改过的脚本，都能直接打到 /api/orders。按钮在不在页面上，只决定普通用户的路径，不决定接口能不能被调用。

菜单隐藏当成鉴权

只在前端按角色隐藏菜单，接口不判权限，等于没有权限控制。按角色隐藏可以保留，但它只是体验；每个改数据的接口都在服务端按会话判一次。第 10 章的灰度开关也一样，开关不代替鉴权。

把 ORDER_API_SECRET 打进前端包

构建时把环境变量里的 ORDER_API_SECRET 注入到页面脚本，密钥就随着每一次打开 /orders 下载到用户机器上。压缩、混淆都藏不住。需要密钥的调用由服务端发起，前端只调用自己的接口。

可操作对象：列出订单页上所有会改数据的操作，每一行写两列：前端怎么让它“看不见”，服务端怎么让它“做不成”。第二列有空格的那一行，就是要补的鉴权。

1.6 乐观把库存改成 7，失败时界面停在哪

安全这一条要求服务端说了算。乐观更新先改界面，结果仍以服务端为准。

问题：点“减一”后界面先显示 7，请求失败了，界面应该显示几？

约定：乐观更新是在请求返回之前先把界面改成预期结果，让用户不用等。它要同时留着服务端确认过的值：成功时以服务端返回为准，失败时回到确认过的值。界面上的 7 写成 order.stock - 1，是从确认值算出来的显示值；不要直接改 Course.data.order.stock，否则失败时就没有可以回去的 8。失败时还要给出提示，让用户知道这一次没有成功。

var order = { stock: 8 };

function optimisticStock(order, ok) {
  var shown = order.stock - 1;
  if (!ok) shown = order.stock;
  return shown;
}

console.log(optimisticStock(order, true));   // 7
console.log(optimisticStock(order, false));  // 8，不停在 7
console.log(order.stock);                    // 8

示例代码：examples/ch01/optimistic-stock.js

基准算例：确认值 stock 是 8。点“减一”后界面显示 order.stock - 1，即 7。请求成功，服务端确认 7，界面保持 7。请求失败（例如 HTTP 200 但业务 code 40001，或浏览器侧等满 3000 ms 超时），界面回到 8，并提示失败。无论哪种结果，演示都不改写 Course.data.order.stock，它始终是 8。

乐观时直接改共享的订单对象

把 Course.data.order.stock 或列表与详情共用的那份库存直接减成 7，失败时手里已经没有 8 了，只能再加回去，而“加回去”在并发点击下很容易加错。显示值从确认值算出来，确认值只在服务端成功后才更新。

乐观失败后界面停在 7

请求失败只弹了提示，界面没有回滚，用户看到 7，库存其实还是 8。用户据此再下单或再改，后面的每一步都建立在错的数上。失败分支必须把显示值回到确认值 8。

可操作对象：在下面的演示里切换请求中、成功、失败三种结果，看界面库存和教学基准里的 order.stock 各是几。

乐观减一：界面库存与订单库存切换分段
观察要点：① 请求中，界面先显示 order.stock - 1，即 7。② 成功时界面保持 7，以服务端确认的结果为准。③ 失败时界面回到 8，并显示失败提示，不停在 7。④ 三种结果下，教学基准 Course.data.order.stock 都读出 8，演示从不改写它。

1.7 用户还在跑旧脚本时，回滚改哪一个文件

数据回滚靠确认值。发布回滚靠入口：换掉入口，旧脚本才会退场。

问题：新版有问题要回滚，是改 JavaScript 文件，还是改入口 HTML？

约定：构建产物分两类。入口 HTML 文件名固定，缓存要短，htmlMaxAgeSec 是 60 秒。JavaScript 与 CSS 文件名里带内容 hash，内容变了文件名就变，可以长缓存，assetMaxAgeSec 是 31536000 秒（一年）。入口 HTML 写着这一版要加载哪些带 hash 的文件。所以发布和回滚改的都是入口：回滚就是让入口重新指向上一版的 hash 文件。旧版的带 hash 文件要在服务器上留着，不要覆盖，也不要发布后立刻删。已经打开的页面在刷新之前一直跑它加载过的脚本，回滚管不到它。

基准算例：回滚在某一时刻把入口换回上一版。没打开过页面的用户，下一次请求拿到新入口。60 秒内打开过的用户，浏览器里的入口最多还能用 60 秒，之后重新取入口，拿到上一版的 hash 文件名；这些文件早就在缓存里，不用重新下载。已经打开着 /orders 的用户，在刷新前仍跑旧脚本。

回滚去改带 hash 的文件

带 hash 的文件被浏览器缓存一年，覆盖同名文件的内容，已经缓存的用户拿不到新内容，还会让同一个文件名对应两份内容，排查时对不上版本。回滚只改入口，hash 文件只增不改。

入口 HTML 也缓存一年

把 assetMaxAgeSec 套到入口 HTML 上，用户的浏览器在一年里都不再取入口，新版和回滚都到不了他。入口用 htmlMaxAgeSec 的短缓存，长缓存只给文件名带 hash 的资源。

可操作对象：画一条时间线：发布新版、发现问题、回滚。在线上标出三类用户：没打开过的、60 秒内打开过的、一直开着页面的。给每类用户写一句他什么时候回到上一版。

本章避坑清单

  1. 乐观更新失败后界面停在 7。失败分支要把显示值回到确认值 8，并提示失败。
  2. 入口 HTML 也缓存一年。入口用 htmlMaxAgeSec（60 秒），长缓存 assetMaxAgeSec 只给文件名带 hash 的资源。

  5. 雪花 id 按 JSON 数字传，9007199254740993 往返后变成 9007199254740992。id 按字符串传。
  6. 订单备注拼进 innerHTML。用户输入按文本插入。

本章小结与延伸阅读

中级已经能交付 /orders，高级接着守四条判断：形态、性能、安全、发布。整门课只用一笔教学订单，数字来自 Course.data.order，雪花 id 9007199254740993 按字符串存，往返成数字会变成 9007199254740992。首屏 \(180+420=600\) KB 管下载，路由块 40 KB 另算；一屏 12 行管一次画多少；入口 60 秒管新入口多久到用户。帧预算 16.7 ms 和长任务 50 ms 是两道门槛，qpsTeach 50 只是数量级。菜单隐藏不代替鉴权，ORDER_API_SECRET 不进前端包。乐观更新把界面先改成 order.stock - 1，失败回到 8。回滚改入口 HTML，带 hash 的资源只增不改。

  • ECMAScript 规范与 MDN：Number.MAX_SAFE_INTEGER、Number.isSafeInteger、JSON.parse 对大整数的处理。
  • IETF RFC 9111《HTTP Caching》：Cache-Control 的 max-age，以及入口与带 hash 资源分开设置缓存的依据。
  • OWASP Cheat Sheet Series：Cross Site Scripting Prevention、Authorization。前者对应备注不当 HTML，后者对应鉴权放在服务端。
  • W3C Long Tasks API 与 web.dev 上关于长任务的文章：50 ms 门槛的来源。帧预算另按 \(1000/60 \approx 16.7\)（假设 60Hz）估算。
  • semver.org 与所用包管理器关于 lock 文件的文档：为什么 1.4.2 锁住而未锁定的安装可能拿到 1.5.0。
