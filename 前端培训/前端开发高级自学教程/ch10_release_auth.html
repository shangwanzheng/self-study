10.1 静态站点与缓存头

发布从产物目录开始。目录里已经有入口和带 hash 的资源，先把两条缓存头分开。

问题：静态目录交给谁，入口和 hash 资源各缓存多久？

约定：构建得到的目录由 Nginx 或对象存储提供。入口 html 的 Cache-Control max-age 取 htmlMaxAgeSec，基准 60 秒。文件名带内容 hash 的 js 与 css 取 assetMaxAgeSec，基准 31536000 秒。协商缓存和 ETag 的具体指令以 HTTP 缓存文档原文为准，本章不另写一套秒数。页面内存里的接口数据有自己的失效，不写进这两条响应头。

资源字段基准发布时交给
入口 htmlhtmlMaxAgeSec60 秒Nginx 或对象存储
带内容 hash 的 js / cssassetMaxAgeSec31536000 秒同一处静态站点
/api/orders 的 JSON内存缓存与上面两行分开接口源，不靠这两条 max-age
 
入口 html 的 Cache-Control max-age 取 htmlMaxAgeSec，基准 60 秒。
带内容 hash 的 js 与 css 的 max-age 取 assetMaxAgeSec，基准 31536000 秒。
这两条交给 Nginx 或对象存储。
接口数据不写在这两条缓存头里。

示例代码：examples/ch10/cache-headers.txt

用教学订单页走一遍：页面源是 pageOrigin 加上路由 /orders。第一次打开拿到入口文档，文档再引用带 hash 的脚本。60 秒内再次打开，入口仍可能命中短缓存。hash 文件名不变时，脚本按长缓存命中。列表 JSON 来自 apiOrigin 加上 apiPath，成功与否看 HTTP 状态和业务 code，不看静态资源的 max-age。

把入口的 max-age 写成 hash 资源那一档

入口若取 assetMaxAgeSec，短缓存的 60 秒窗口就没了。后面的回滚要等的是长缓存那一档，用户仍拿着旧入口。

可操作对象：在发布清单上写两行缓存：入口 htmlMaxAgeSec，hash 资源 assetMaxAgeSec。第三行写接口数据另记。两行秒数都从 Course.data.order 读，不手写第三个数。

10.2 回滚到上一入口

两条缓存头分开之后，回滚才有可替换的对象。对象是入口，不是已经长缓存的 hash 文件。

问题：要回到上一版订单页，替换哪一份文件？

约定：回滚用上一份入口替换当前入口，让入口指向要恢复的那一版 hash。已经按 assetMaxAgeSec 长缓存的 hash 文件留在 Nginx 或对象存储上。用户手里的当前入口，在 htmlMaxAgeSec 这段短缓存结束之后会拿到换过的入口。Network 里先看文档类型的入口是重新下载还是缓存命中，再看它引用的脚本文件名。

回滚用上一份入口替换当前入口。
上一入口指向要恢复的那一版 hash 资源。
已经长缓存的 hash 文件留在原地。
只改 hash 文件、不换入口时，旧入口仍引用旧名字。

示例代码：examples/ch10/rollback-entry.txt

用教学订单页走一遍：当前入口引用这一版带 hash 的订单脚本，上一入口引用上一版的 hash 名字。两份脚本都可以留在静态站点上。回滚只换入口文档。60 秒内仍可能看到换之前的入口；60 秒后入口指向要恢复的脚本。库存、金额和超时都不因为回滚而改字段。

回滚改 hash 文件而不改入口

只覆盖或删除服务器上的 hash 文件时，已缓存的入口仍引用旧名字。用户要么继续跑旧脚本，要么旧名字已经不在。上一版要靠上一份入口指回去。

可操作对象：写下两行文件名：当前入口指向的 hash，上一入口指向的 hash。回滚动作只替换入口那一行。hash 两行保持原样。

10.3 流水线制品是静态资源

入口和 hash 文件从流水线来。先把流水线的顺序和制品的形态写死。

问题：这一条流水线交出去的是什么？

约定：顺序是安装、检查、测试、构建、制品、环境晋升。安装消费已提交的 lockfile，教学依赖锁在 semverLocked 1.4.2；未锁定时可能解析到 semverUnlocked 1.5.0，构建机不执行那次安装。检查和测试对着这一笔订单页。构建产出静态目录。制品就是这个目录：入口 html，以及带内容 hash 的 js 与 css。环境晋升把同一目录向前送。

流水线制品当成 jar

10.4 环境晋升

制品目录已经是静态资源。下一步是把它晋升到下一环境，而不是另打一份带新数字的包。

问题：测试环境通过之后，生产用的还是这一份目录吗？

约定：环境晋升移动同一次构建得到的静态目录。入口缓存仍取 htmlMaxAgeSec，hash 资源缓存仍取 assetMaxAgeSec。金额仍取 amountFen。三个超时仍取 connectTimeoutMs、readTimeoutMs、browserTimeoutMs。各环境的域名以部署文档原文为准，本章不新增页面源或接口源。pageOrigin 与 apiOrigin 仍是教学订单里的那两个源。

环境晋升移动的是同一次构建得到的静态目录。
入口缓存仍取 htmlMaxAgeSec。
hash 资源缓存仍取 assetMaxAgeSec。
金额仍取 amountFen。
超时仍取 connectTimeoutMs、readTimeoutMs、browserTimeoutMs。

10.5 灰度按用户或版本放量

同一份制品可以先给一部分人。放量的条件是用户或版本，开关只决定谁先看见新界面。

问题：新入口先给谁？

约定：灰度按用户或按版本放量。按用户时，对照教学订单的 userIdText，基准是字符串 10001。按版本时，对照这一次入口所指向的构建标记；标记来自这次制品，本章不另编版本号。命中则露出新按钮或新入口；未命中则保持当前界面。放量不改服务端对 /api/orders 的鉴权，也不改业务 code。

按用户

规则里的用户 id 与 order.userIdText 相同则命中。10001 仍是用户标识，不能当作密钥或权限证明。

按版本

规则里的构建标记与这次入口所指向的标记相同则命中。标记跟着制品走，不在晋升时新写一个数。

function hitGray(order, buildLabel, rule) {
  if (rule.kind === 'user') return order.userIdText === rule.userIdText;
  if (rule.kind === 'version') return buildLabel === rule.buildLabel;
  return false;
}

示例代码：examples/ch10/gray-by-user.js

用教学订单页走一遍：用户 10001 命中「按用户」时，订单页可以画出这次要放量的按钮。另一位用户未命中时，按钮不出现。按版本放量时，只有拿到这次入口的会话才命中。两种命中都不表示接口已经返回 businessCodeOk 0。

为灰度另写一个百分比

本章没有放量百分比。命中或未命中，只按用户或版本判断。另写一个比例，就会引入课程数据里没有的数。

可操作对象：选一条规则：要么写用户 10001，要么写这次制品的构建标记。在订单页旁注明命中后露出的是按钮，接口仍走 apiPath。

10.6 开关不代替鉴权

放量开关已经能决定按钮出不出现。接口成功与否仍看 HTTP 状态和业务 code。

问题：灰度开关打开，服务端返回 HTTP 200 且业务 code 40001，订单列表还显示吗？

约定：开关打开只表示这次放量命中。showOrderList 在此之后仍要求 HTTP 状态等于 httpOk 200，且业务 code 等于 businessCodeOk 0。业务 code 为 businessCodeFail 40001 时，函数返回假，界面不显示订单列表。40001 留在业务失败这条分支，不送去 10.7 的登录刷新。TLS、证书或混合内容失败时，业务日志里还没有这条响应，也不要记成 40001。

function showOrderList(grayOn, status, code, order) {
  if (!grayOn) return false;
  if (status !== order.httpOk) return false;
  if (code !== order.businessCodeOk) return false;
  return true;
}

示例代码：examples/ch10/business-code-gate.js

用教学订单页走一遍：开关对用户 10001 打开。响应的 HTTP 状态是 200，正文里的业务 code 是 40001。列表保持不显示，金额 199.50 和库存 8 都不从这次响应写上界面。code 为 0 时，列表才可以显示这一笔订单。

灰度开关打开就显示订单数据

服务端已经返回 40001。开关只说明界面准备好了，不说明这张列表可以画。把 19950 分和库存 8 画出来，等于把失败响应当成了成功。

开关打开，业务 code 为 40001切换分段
观察要点：① 灰度开关保持打开，HTTP 状态来自 httpOk，业务 code 来自 businessCodeFail。② 分段在「先看业务 code」时，读数「界面是否仍显示订单列表」为否。③ 切到「开关打开就显示」时，读数变为是；服务端已经是 40001，列表仍被画出来。④ 40001 不发起登录刷新。刷新次数留在后面的 401 演示里。

可操作对象：先看演示读数。列表为「否」时，在接口日志旁写下 HTTP 200 与业务 code 40001。列表为「是」时，记下这是开关越过了业务 code。

10.7 过期与 401

业务 code 40001 已经按失败留在界面之外。登录态过期是另一条路径，状态是 401，处理放在一处。

问题：访问令牌或会话过期之后，订单请求在哪里接手？

约定：HTTP 401 表示登录态过期或未授权，由一处统一处理：调用同一次刷新，成功后再重放原来的请求。业务 code 40001 即使带着 HTTP 200，也不进入这处刷新。handleResponse 先看状态是不是 401；不是 401 时，只有状态等于 httpOk 且 code 等于 businessCodeOk 才让列表显示。凭据放在第 6 章已经分开的位置：HttpOnly 的 Cookie 脚本读不到，cookieName 只是名字 sid；内存 token 随刷新页面消失。secretName 的 ORDER_API_SECRET 不进这次静态制品。

function handleResponse(res, order, refreshOnce, replay) {
  if (res.status === 401) {
    return refreshOnce().then(replay);
  }
  var httpOk = res.status === order.httpOk;
  var bizOk = res.code === order.businessCodeOk;
  if (httpOk && bizOk) {
    return { ok: true, showList: true };
  }
  return { ok: false, showList: false, code: res.code };
}

示例代码：examples/ch10/session-401.js

用教学订单页走一遍：打开 /orders 时若拿到 401，页面不把库存改成 7，也不把列表写成空数据冒充成功。它把这次请求交给统一的刷新，刷新完成后再重放 apiPath。若拿到的是 HTTP 200 和 40001，重放不会发生，列表保持不显示。

每个调用点各自处理 401

列表、详情和扣库存若各写一段刷新，同一次过期会打出多次刷新。40001 若也被送进这段刷新，业务失败会变成一次多余的会话写入。

可操作对象：在请求层标出唯一的 401 入口。旁边写上：40001 不进这个入口。下一节把并发的两个 401 接到同一次刷新上。

10.8 并发刷新只打一次

401 已经收进一处。两个请求同时过期时，这一处只允许打出一次刷新。

问题：列表和详情同时收到 401，刷新请求打几次？

约定：createRefreshOnce 记住正在进行的那一次 Promise。后来的 401 若看见它还在，就等待同一次结果，不再调用 sendRefresh。两次都完成后，各自重放自己的请求。刷新次数是 1。这个 1 是合并的次数，不替换 connectTimeoutMs、readTimeoutMs 或 browserTimeoutMs。

function createRefreshOnce(sendRefresh) {
  var inflight = null;
  return function refreshOnce() {
    if (inflight) return inflight;
    inflight = Promise.resolve()
      .then(function () { return sendRefresh(); })
      .then(function (session) {
        inflight = null;
        return session;
      }, function (err) {
        inflight = null;
        throw err;
      });
    return inflight;
  };
}

示例代码：examples/ch10/refresh-once.js

用教学订单页走一遍：同一时刻，订单列表和订单详情都因为过期收到 401。第一次调用开始刷新，第二次调用拿到同一个进行中的 Promise。会话只写一次。两次原请求再用这次结果重放。重放之后若业务 code 仍是 40001，对应的那一块列表仍不显示。

并发 401 打了多次刷新

两个 401 各打一次时，读数是 2。两次刷新会并发写同一会话，后完成的那次可能盖住先完成的登录态。合并之后读数应为 1。

并发两个 401切换分段后再发一次
观察要点：① 一次动作同时遇到两个 401，请求记为 A 与 B。② 分段在「合并成一次」时，读数「刷新请求次数」为 1，B 等待 A 已经发起的那一次。③ 切到「各刷一次」时，次数为 2，这是并发打了多次刷新。④ 次数 1 只表示合并后的刷新次数，三个超时字段保持原值。

可操作对象：先读「合并成一次」的次数，再切到「各刷一次」对照。发布前把请求层的刷新入口收成演示里次数为 1 的那种。

10.9 前端权限只是体验

会话能续上之后，还要分开两件事：界面上有没有按钮，服务端让不让调用接口。

问题：菜单里不画订单按钮，/api/orders 还要鉴权吗？

约定：菜单和按钮隐藏是这一页的体验。paintOrdersMenu 只返回按钮是否可见。requestOrders 仍标明 authorizeOnServer。直接请求 apiPath 时，允许或拒绝发生在服务端。灰度开关、隐藏菜单、隐藏按钮，都不代替这次鉴权。没有按钮时，用户仍可能构造请求；服务端按会话和权限处理，前端不把「看不见」写成「已拒绝」。

function paintOrdersMenu(experienceAllowed) {
  return { visible: !!experienceAllowed };
}

function requestOrders(order) {
  return { path: order.apiPath, authorizeOnServer: true };
}

示例代码：examples/ch10/menu-is-ux.js

用教学订单页走一遍：未命中灰度时，订单按钮可以不画。用户 10001 若直接访问 apiOrigin 加上 apiPath，服务端仍要鉴权。鉴权失败不靠前端再藏一次按钮来表达。业务 code 40001 与 401 仍按前面两节各自处理。

菜单隐藏就不再鉴权

按钮从菜单消失，只说明这个界面没有入口。接口若因此去掉服务端校验，隐藏就变成了唯一的门槛。门槛应留在服务端对 /api/orders 的鉴权上。

可操作对象：画两列。左列是菜单可见性，右列是服务端鉴权。右列在按钮隐藏时仍写「要鉴权」。灰度命中与否只改左列。

10.10 用同一笔订单做发布前检查

发布、灰度和会话都对着同一笔订单。发布前把字段原样读出来，避免为了这一章新写超时或金额。

问题：上线前对照哪一组数，才能确认没有另造一套订单？

约定：检查只读 Course.data.order 与 Course.orderMath。releaseCheck 取出入口缓存、hash 资源缓存、HTTP 成功状态、业务成功码、业务失败码、金额分和三个超时。展示金额用 yuanText()，得到 199.50。雪花 id 仍用 snowflakeText 这串文字，不写成数字字面量。本章不增加字段，不把 401 的「一次」写成新的毫秒数。

function releaseCheck(order) {
  return {
    entryMaxAgeSec: order.htmlMaxAgeSec,
    assetMaxAgeSec: order.assetMaxAgeSec,
    httpOk: order.httpOk,
    businessCodeOk: order.businessCodeOk,
    businessCodeFail: order.businessCodeFail,
    amountFen: order.amountFen,
    connectTimeoutMs: order.connectTimeoutMs,
    readTimeoutMs: order.readTimeoutMs,
    browserTimeoutMs: order.browserTimeoutMs
  };
}

本章避坑清单

这是全课清单。先写下现象，再对其中一条，再回到对应章。数字仍只来自 Course.data.order 与 Course.orderMath。本章不另造超时或金额。

  1. 离开教学订单另造数字。id、金额分、库存、分页、三个超时、首屏体积和缓存秒数都读 Course.data.order。
  2. 微前端按后端服务拆分来做。它解决的是发布和团队边界；stock 的规则仍只留一处。
  3. 说不清列表出现在哪一次请求。多页、单页、服务端渲染、静态生成的数据不在同一次响应里。
  4. 把 bundleRouteKb 算进首屏，或用预加载代替代码分割。首屏用 firstScreenKb()，基准是 600 KB。
  5. 长任务和帧预算并成一个毫秒数。超过 frameBudgetMs 只说明这一帧装不下；达到 longTaskMs 才叫长任务。
  6. 虚拟列表的总高度改成 visiblePx()。只画 viewportRows 行，整表高度仍是 fullListPx()。
  7. 实验室的一次 LCP、INP、CLS 测量写成用户侧分布。行高缺失时的位移对照 clsShiftPx。没测量就加 memo。
  8. 在 Web Worker 里操作这份文档的 DOM。消息按结构化克隆传递。多个 Tab 共用的连接才是 SharedWorker 那一条。
  9. 只拍一次堆快照就判断泄漏。要有进入 /orders 的一次，以及离开并卸掉监听之后的一次。
  10. 用 transition、Suspense 或错误边界包住整个订单壳。它们改变的是更新优先级和失败边界，等待和失败落在列表这一块。
  11. HTTP 缓存和页面内存缓存共用一条失效。缓存头管静态资源，内存缓存管接口数据。
  12. 后返回的旧响应写回列表。乐观更新失败要回到 stock 8。列表和详情共用这一份库存。
  13. 把订单备注当 HTML 插入。CSP 与开放重定向按各自文档原文配置，文本呈现仍要先做。
  14. 把 cookieName sid 当成安全属性。HttpOnly 表示脚本读不到该值；Cookie 会带上凭据时仍要防 CSRF。内存 token 随页面刷新消失。
  15. ORDER_API_SECRET 进入前端包或仓库。userIdText 10001 不能当密钥。
  16. 不提交 lockfile，或让构建机执行未锁定的安装。锁定版本是 semverLocked 1.4.2，未锁定可能解析到 semverUnlocked 1.5.0。
  17. WebView 的注入对象没挂在这个 window 上。嵌入页的存储、证书和刷新生命周期与独立浏览器不同。
  18. Bridge 的请求与回调不配对。客户端版本和页面版本被并成一个兼容条件。
  19. 多 Tab 把旧 token 写回共享存储。一条长连接挂在错误的全局对象上。
  20. 入口 html 使用 assetMaxAgeSec。入口短缓存是 htmlMaxAgeSec 60 秒，带 hash 的资源才用长缓存。
  21. TLS、证书错误或混合内容失败时去查业务 code。这一层失败时，业务日志里还没有这条请求。
  22. 错误监控不带发布版本。source map 放到公网可下载的静态目录。旧包和新包画在没有版本的同一条曲线上。
  23. 端到端测试打到真实的 apiOrigin，或覆盖关键路径以外的整站。组件测试仍用假请求。要支持的浏览器范围不写明，就把视觉差异都当成缺陷。
  24. 一次改动不看公共组件的影响面。业务页复制一套基础控件。设计系统里的 token 和登录凭据混用。文案宽度写进布局。
  25. 流水线制品当成 jar。前端制品是静态目录。顺序是安装、检查、测试、构建、制品、环境晋升。
  26. 回滚改 hash 文件而不改入口。回滚替换的是上一入口，已经长缓存的 hash 文件留在原地。
  27. 灰度开关打开就显示订单数据。HTTP 200 且业务 code 40001 仍是失败，界面不显示订单列表。
  28. 并发的 401 各自刷新。401 统一处理，只打一次，其余请求等这一次的结果再重放。
  29. 菜单或按钮隐藏之后不再鉴权。隐藏是体验，接口鉴权在服务端。界面开关同样不能代替这次鉴权。
  30. 本章引入新的超时或金额。发布前检查仍用 amountFen 19950，以及 500、2000、3000 这三个原来的超时字段。

本章小结与延伸阅读

同一次发布把静态目录交给 Nginx 或对象存储。入口缓存 htmlMaxAgeSec 60 秒，带 hash 的资源缓存 assetMaxAgeSec。回滚替换上一入口。流水线按安装、检查、测试、构建、制品、环境晋升进行，制品是静态资源。灰度按用户或版本放量。开关打开且 HTTP 200、业务 code 40001 时，订单列表不显示。401 在一处处理，并发的两个 401 只刷新一次。菜单隐藏是体验，接口鉴权在服务端。发布前仍用这一笔订单的金额和三个超时。
