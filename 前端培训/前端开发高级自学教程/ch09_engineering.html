9.1 构建缓存与产物分析

从这一次交付的构建看起。缓存和产物分析回答的是两件不同的事。

问题：构建很快结束，能不能说明订单页的路由块已经不在首屏里？

约定：构建缓存按输入复用上次产物。输入包括这次参与编译的源文件、锁住的依赖和所选环境。订单页源码变了，路由块重做；主包和第三方库的输入没变，这两块可以命中缓存。产物分析看打出来的文件：主包 bundleMainKb、第三方库 bundleVendorKb、路由块 bundleRouteKb。首屏体积是前两块之和，路由块留在首屏之外。CSS 与脚本分开看；本章的体积基准只用这三个字段，不另写一个 CSS 的 KB 数。配置键以所用构建工具的文档原文为准。

\[ \mathrm{firstScreenKb}=\mathrm{bundleMainKb}+\mathrm{bundleVendorKb} \]

基准是 180 与 420 相加，等于 600。路由块是 40。Course.orderMath.firstScreenKb() 与这个和相同。

产物字段基准这次交付里它回答什么
主包bundleMainKb180 KB计入首屏
第三方库bundleVendorKb420 KB计入首屏
订单路由块bundleRouteKb40 KB不计入首屏
function bundleReport(order) { var firstKb = order.bundleMainKb + order.bundleVendorKb; return { mainKb: order.bundleMainKb, vendorKb: order.bundleVendorKb, routeKb: order.bundleRouteKb, firstKb: firstKb, routeInFirst: false }; }

示例代码：examples/ch09/bundle-report.js

在本章页面的控制台把 Course.data.order 传进去。firstKb 应等于 Course.orderMath.firstScreenKb()。routeInFirst 为 false，表示教学订单页的路由块不在首屏里。若某一次真实产物把路由块打进了主包，要改的是这次分析结论，这三个基准数字仍留在订单数据里。

用教学订单页走一遍：这一次只改了 /orders 的页面源码。路由块的缓存失效并重做。主包 180 KB 与第三方库 420 KB 的输入未变，可以命中缓存。构建日志写成功之后，仍打开产物分析，核对首屏是 600 KB，路由块 40 KB 单独存在。CSS 是否被打进首屏，看这次分析列出的样式文件，不把 40 改写成别的数来凑。

缓存命中就当成产物已核对

命中只说明这块输入没变、复用了上次产物。它不回答路由块在不在首屏里。订单页这一次交付仍要看 bundleMainKb、bundleVendorKb、bundleRouteKb 三行。

只看构建成功

成功只说明这次命令跑完。路由块若被打进主包，首屏就不再是 firstScreenKb() 的 600 KB。产物分析要单独打开。

可操作对象：在纸上画两列。左列写「缓存：路由块重做，主包与第三方库命中」。右列写「分析：首屏 600 KB，路由块 40 KB，routeInFirst 为 false」。

9.2 按环境打包

产物的三块已经分开。同一份订单页源码还要按环境各打一份。

问题：开发服务器上能打开的订单页，是不是这次要交付的那一份产物？

约定：按环境打包使用同一份订单页源码。开发环境由 pageOrigin 上的开发服务器提供页面，接口源是 apiOrigin。交付环境打开的是构建产物里的路由 /orders。两个环境可以不同的，是公开配置，以及 source map 放在监控系统还是公网目录。命令示例的 Node 主版本按 nodeMajor 写，基准是 20。secretName 的值是名字 ORDER_API_SECRET，留在服务端；两个环境的前端包都不包含它。环境的配置键以所用构建工具的文档原文为准。

环境浏览器打开的是可以不同仍然相同
开发pageOrigin 上的开发服务器公开的接口源订单页源码；前端包不含 ORDER_API_SECRET
交付产物里的 /orders公开配置，以及 source map 放哪同一份订单页源码；前端包仍不含该名字

用教学订单页走一遍：开发时页面在 http://localhost:5173，接口在 http://localhost:8080。交付时浏览器打开的是已经生成的静态文件，路由仍是 /orders，列表请求仍走 apiPath。公开的接口源可以按环境换成交付环境的地址。source map 在下一节决定是否进入公网目录。无论哪一个环境，前端包里都不出现 ORDER_API_SECRET。

开发服务器能开，就当成这次交付

开发服务器按源码现给 /orders。这次交付要打开的是构建产物里的同一条路由。入口、哈希资源和缓存头随产物一起看，那是第 8 章的发布物；本章先确认打的是哪一个环境。

按环境把密钥打进前端包

为了让交付环境能连上订单接口，把 ORDER_API_SECRET 写进该环境的构建变量。秘密会进浏览器下载到的脚本。公开配置只放接口源这类地址，秘密留在服务端。

可操作对象：写两行环境。开发行写 pageOrigin 与 apiOrigin。交付行写「产物中的 /orders」。两行的密钥栏都写「前端包中无 ORDER_API_SECRET」。

9.3 source map 是否公网可下

环境已经分开。这一次交付还要决定订单页的 source map 会不会跟着静态文件公开。

问题：监控要还原混淆后的订单页栈。公网能不能下载到这份源码映射？

约定：source map 把混淆后的栈对回订单页源码，交给错误监控，并带上这一次发布的版本。映射文件不放进公网可下载的静态目录。放进去之后，任何人都能下到订单页的源码映射。监控系统另收的那一份，用来还原栈，不出现在公网目录的文件列表里。上传字段以所用监控文档的原文为准。

function sourceMapGate(uploadPublic) { var onPublicWeb = !!uploadPublic; return { onPublicWeb: onPublicWeb, canDownload: onPublicWeb ? '能' : '不能' }; }

示例代码：examples/ch09/source-map-gate.js

sourceMapGate(true) 的 canDownload 是「能」。sourceMapGate(false) 是「不能」。下面的读数用同一条规则。

用教学订单页走一遍：交付产物里有订单页的脚本。映射若随脚本放在公网静态目录，打开该目录就能下到订单页源码映射，混淆后的栈可以被还原成页面源码的位置。映射只交给监控系统时，公网目录没有这个文件，公网上下不到。订单路由仍是 /orders，公开与否不改变这条路由。

source map 上传公网

为了线上能点开栈，把 source map 和订单页脚本放进同一个公网目录。公网就能下到订单页源码映射。还原栈用监控系统里的那一份。

映射和脚本放进同一个公网目录

脚本要公开，映射不公开。两个文件放在一起之后，下载脚本的人可以继续下载映射。第 8 章的错误监控仍要版本号；版本号不能代替「映射不在公网」这一条。

可操作对象：切换公开或不公开，读出公网能否下到订单页源码映射。

source map 公开或不公开切换后读公网能否下载
观察要点：① 选「不公开」时，公网能否下到订单页源码映射，读数是「不能」，映射交给监控系统。② 选「公开」时，读数是「能」，映射在公网静态目录。③ 路由始终是 /orders，公开与否不改这条路径。④ 读数来自 sourceMapGate：上传为真则「能」，否则「不能」。

9.4 多包与一次改动的影响面

这一次交付的产物边界已经清楚。仓库若是多包，还要看这一次改动打到哪些页。

问题：公共订单表只改了一个文件。哪些页面会跟着变？

约定：多包仓库里，订单表是公共组件，自己有包，被页面引用。影响面按「谁引用了这份订单表」来列。教学订单页的路由是 /orders。每多一个页面引用它，影响面就多一页。行高读取 rowHeightPx，基准是 48。公共组件里写成另一个像素时，所有引用页的行高一起离开 48。本章不把那个另一个像素写进 Course.data.order。

改动落在影响面行高
订单页自己的文案路由 /orders 这一页仍是 rowHeightPx，48
公共订单表组件所有用到订单表的页组件仍读 rowHeightPx 时是 48；写成另一个数则这些页一起离开 48

用教学订单页走一遍：列表行高是 rowHeightPx。可见高度是 Course.orderMath.visiblePx()，即 viewportRows 乘 48。整表高度是 Course.orderMath.fullListPx()，即 listN 乘 48。公共组件若不再读 rowHeightPx，这两次计算用的 48 会在所有引用页上变成另一个数。/orders 在影响面里；其余引用同一组件的页面也在。只打开当前这个文件，列不全这些页。

只看正在改的那一个文件

文件树里高亮的是公共组件那一个路径。引用它的订单页在别的包里。影响面按引用关系列，不按编辑器当前打开的文件列。

改公共组件不看影响面

订单表行高从 48 变成另一个数。公共组件一改，所有用到订单表的页一起离开 rowHeightPx。先列出这些页，再改行高的来源。另一个像素不写进课程数据。

可操作对象：列两行。第一行是 /orders，标「引用订单表」。第二行留给仓库里其余引用方，暂时写「待列出」，不要留空就合并代码。行高栏写 rowHeightPx。

9.5 公共组件的版本

影响面按引用来列。公共组件还有自己的版本，这一次交付要能读出锁住的是哪一版。

问题：公共订单表从 1.4.2 到 1.5.0，行高是不是自然还是 48？

约定：公共组件的版本用 SemVer，按主版本、次版本、修订版本理解。锁住时的版本是 semverLocked，基准 1.4.2。不锁时，同一条允许更新的声明可能解析到 semverUnlocked，基准 1.5.0。1.5.0 的主版本仍是 1，次版本从 4 到 5，表示作者声称这是兼容范围内的变化。声称兼容之后，影响面仍要看：行高是否还读 rowHeightPx，引用页是否仍是所有用到订单表的页。本章只比较这两个版本，不另造第三个版本号。lock 文件名以仓库的包管理器文档为准。

字段版本在这一次交付里
semverLocked1.4.2lock 锁住的公共组件版本
semverUnlocked1.5.0不锁时可能解析到的版本

用教学订单页走一遍：订单页依赖的订单表停在 1.4.2。有人放宽声明，安装结果变成 1.5.0。SemVer 的次版本说明作者声称兼容，引用方仍是所有用到订单表的页。核对行高：组件继续读 rowHeightPx 时，这些页仍是 48。组件在 1.5.0 里写成另一个像素时，版本号仍是次版本，行高已经离开 48。版本号和影响面各记各的。

次版本号升高就不再看行高

1.5.0 相对 1.4.2 是 SemVer 的次版本。作者的兼容声称不代替打开订单表，核对高度是否仍来自 rowHeightPx。

公共组件不锁在 1.4.2

不提交 lock 时，下一次安装可以解析到 semverUnlocked 1.5.0。同一条订单页在两台机器上会用到两个版本。要升级时，让安装器改写 lock，再提交锁住的结果。

可操作对象：写下公共组件的两栏：锁住写 semverLocked，不锁写 semverUnlocked。旁边加一栏「行高来源」，填 rowHeightPx。版本栏填完之后，这一栏仍要填。

9.6 设计系统与 token

公共组件的版本能读出来。订单页上的控件从设计系统来，不在业务页再画一套。

问题：订单页需要一个输入框。它从哪一层来？

约定：设计系统分四层。基础组件提供输入框、按钮这类控件。业务组件提供订单表这类带订单语义的块，由基础组件组合而成。token 是设计变量，承载颜色、间距、字号和行高；本章的 token 与登录凭据不是同一个词。主题切换的是这组 token。基础组件通过 CSS 读取 token，业务页使用基础组件，不复制控件，也不复制一套 CSS。行高这一项若进入 token，值仍来自 rowHeightPx。

基础组件

输入框、按钮。业务页直接使用。

业务组件

订单表。组合基础组件，被 /orders 引用。

token

颜色、间距、字号、行高。设计变量，不是登录凭据。

主题

切换 token。CSS 把 token 交给基础组件。

function orderPageControl(copied) { return { layer: copied ? '业务页自绘' : '基础组件', copied: !!copied }; }

示例代码：examples/ch09/order-page-control.js

orderPageControl(false) 的 layer 是「基础组件」，copied 为 false。orderPageControl(true) 的 layer 是「业务页自绘」。订单页这一次交付取 false 这一支。

用教学订单页走一遍：筛选框使用设计系统的基础输入框，订单表使用业务组件。主题更换时，基础组件的 CSS 改读另一组 token，业务页不跟着抄一份输入框样式。行高仍是 rowHeightPx 的 48。登录凭据的存放在安全那一章；这里出现 token 这个词，指的是设计变量。

业务页复制一套输入框

订单页为了改一处颜色，把基础输入框的标记和 CSS 复制进业务页。主题再切换 token 时，复制出来的那一套不跟着变。业务页调用基础组件。

设计 token 当成登录凭据

看见 token 就把它放进请求头或 cookieName 所指的会话。设计系统里的 token 是颜色、间距、字号、行高。会话凭据仍按安全章的约定放置。

可操作对象：给订单页的筛选框写一行：orderPageControl(false)。主题栏写「切换 token」。凭据栏不要写这个 token。

9.7 文案与布局分开，语义与键盘

控件来自设计系统。页面上的句子和格子还要分开，键盘能否到达对照文档原文。

问题：改一句订单文案，要不要改列宽？键盘能不能到这张表的按钮？

约定：文案与布局分开。金额展示用 Course.orderMath.yuanText()，由 amountFen 得到文本；这是文案和格式。列宽、行高是布局，行高用 rowHeightPx。句子的字数不写进列宽。语义标签、键盘操作、焦点和对比度，对照项目采用的无障碍文档原文。订单表使用表格的语义标签，按钮使用按钮，键盘能到达关键路径上的这些控件，当前焦点在页面上可见。对比度是否达标，以该文档列出的要求为准。本章不把某一个对比度数写进 Course.data.order，正文也不写死一个比值。

用教学订单页走一遍：金额 19950 分，展示文本是 Course.orderMath.yuanText() 的结果。列宽按布局留出，不按「199.50」这五个字符的宽度写死。换一句状态文案或换一种语言时，改文案资源，行高仍是 48。筛选和翻页使用按钮的语义标签，可以用键盘到达，焦点停在上面时看得见。对比度拿项目写明的那份无障碍文档去对，不从课程数据里读一个度数。

对比度写死成课程里的一个度数

无障碍文档里的对比度要求留在文档原文。把某一个比值抄进订单数据或写成全课常数之后，文档更新了，页面仍拿旧度数当结论。本章不提供这个度数。

文案写进布局宽度

列宽按当前这句中文的字数写成像素。文案一换，格子装不下，或者空出一大块。金额文本来自 yuanText()，宽度来自布局，行高来自 rowHeightPx。

可操作对象：画两列。文案列写 yuanText(amountFen) 和状态句子。布局列写列宽与 rowHeightPx。下面再写四行核对：语义标签、键盘、焦点、对比度；对比度那一行写「以文档原文为准」，不写数字。

9.8 端到端只覆盖关键路径，兼容范围写明浏览器

页面的控件和文案已经分开。测试范围收到一条关键路径，兼容范围写成具体的浏览器。

问题：端到端要点完 10000 行吗？某个浏览器上字距不一样，算不算缺陷？

约定：端到端只覆盖关键路径，路由是 route，基准 /orders。这条路径记 1 条用例：打开订单页并看到列表。整表 listN 行不逐行点击；若每一行一个用例，用例数等于 listN。选择器保持稳定，用这条路径上的稳定标记，不用行号去点第 10000 行。组件测试仍用假请求，不去打真实的 apiOrigin。兼容范围写明要支持的浏览器名称和版本。视觉差异先对照这份已经写明的范围：范围之外的差别不自动记成缺陷，范围之内也不是每一处像素差都记成缺陷。

function e2eCaseCount(scope, listN) { if (scope === 'route') return 1; return listN; }

示例代码：examples/ch09/e2e-scope.js

e2eCaseCount('route', listN) 得到 1。e2eCaseCount 的其他范围得到 listN。1 是这一条关键路径的条数，不是订单数据里的另一个字段。下面的读数用同一条规则。

用教学订单页走一遍：关键路径打开 /orders，列表一页是 size 行，基准 20，数据总量仍是 listN。端到端停在这条路径上，用例数是 1。去点整表时，用例数变成 10000。兼容范围单独写一行，例如写明这一次交付要支持的浏览器；课程首页建议用新版 Edge 或 Chrome 来阅读教程，那一行不代替订单页的兼容范围。字距、滚动条外观这类差别，先对照已经写明的浏览器，再决定是否记成缺陷。

端到端去点整表 10000 行

关键路径是 /orders。把 listN 行各点一次，用例数等于 10000，选择器还会绑在行号上。端到端停在这一条路径，行的渲染交给组件测试和列表本身的约定。

把所有浏览器视觉差异当缺陷

兼容范围没有写明浏览器时，任何一台机器上的像素差都会变成缺陷。先写下要支持的浏览器。范围内的差别也不都是缺陷：对照订单页已经写明的行为，字距不同而路径仍能完成时，单独记录，不自动开缺陷。

可操作对象：切换「只有 /orders」或「整表 10000 行」，读出用例数。再在纸上写一行兼容范围，填浏览器名称，不填「所有看起来不同的都算」。

观察要点：① 选「只有 /orders」时，用例数是 1，路由是 /orders。② 选「整表 10000 行」时，用例数等于 listN。③ 1 是这一条关键路径的条数；10000 来自订单的 listN，不另造第三个数。④ 用例数不代替兼容范围。浏览器名称要另写一行。

本章避坑清单

  1. 构建缓存命中之后就不再做产物分析，路由块在不在首屏里不知道。
  2. 按环境把 ORDER_API_SECRET 打进前端包。
  3. 把 source map 上传公网，公网能下到订单页源码映射。
  4. 改公共组件不看影响面，订单表行高从 rowHeightPx（48）变成另一个数，所有用到订单表的页一起变。
  5. 用 SemVer 的次版本代替影响面：1.5.0 仍要核对行高是不是还读 rowHeightPx。
  6. 业务页复制一套输入框。
  7. 把文案写进布局宽度。
  8. 把某一个对比度数写进课程数据，代替无障碍文档原文。
  9. 端到端去点整表 listN（10000）行。
  10. 兼容范围不写浏览器，并把所有视觉差异当成缺陷。

本章小结与延伸阅读

订单页这一次交付先看构建缓存，再看产物：首屏是 bundleMainKb 加 bundleVendorKb，路由块 bundleRouteKb 不在其中，CSS 的体积以这次产物分析为准。按环境打包仍是同一份源码，ORDER_API_SECRET 不进前端包。source map 不公开时，公网不能下到订单页源码映射；公开时则能。多包里改公共订单表，影响面是所有用到订单表的页；行高离开 rowHeightPx 的 48，这些页一起变成另一个数。公共组件的版本用 SemVer，锁住是 1.4.2，不锁可能是 1.5.0，次版本不代替影响面。设计系统分基础组件、业务组件、token、主题，业务页不复制输入框。文案与布局分开。语义标签、键盘、焦点、对比度以文档原文为准。端到端只覆盖 /orders，用例数是 1；整表 10000 行的用例数是 listN。兼容范围写明浏览器。
