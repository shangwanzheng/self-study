这一章：订单页嵌在 WebView 里，从存储走到多 Tab

订单页嵌在 WebView 里时，存储、证书和刷新生命周期都和独立浏览器不同。独立浏览器刷新后，同一源的 localStorage 还在。嵌入页的存储以宿主文档为准，这一档可以和独立浏览器不同。证书握手若没有完成，两边都还没有业务 code；错误页可以出现在宿主一侧。刷新会拆掉当前这份文档。

注入对象挂在这份文档的 window 上，不是另一个全局袋子。一条长连接放在宿主进程里。当前文档的全局对象仍是 window，取用点是 window.OrderBridge.socket。页面内存里的变量会随刷新拆掉，连接不能只放在那里。新文档加载后，宿主把 OrderBridge 再注入到新的 window 上。

JS Bridge 要有消息域，要有请求与回调的配对。超时用浏览器超时 browserTimeoutMs 这一档，基准 3000 ms，不另造超时数。客户端版本和页面版本分开兼容。旧客户端不去读、不去填新页面才有的字段。

多 Tab 的登录态看 cookie 名 cookieName（sid）和 storage 事件。另一张标签换了登录时，本页采用当前 cookie 里的 sid，不把内存中的旧 sid 写回去。

7.1 嵌入页与独立浏览器的存储

章首把嵌入页和独立浏览器分开了。先看草稿键在刷新之后还在不在。

约定：独立浏览器里，localStorage 按源保存。教学订单页的页面源是 pageOrigin，即 http://localhost:5173。同一源刷新文档，键 storageKey（order.draft）还在。WebView 的存储落在宿主为这个视图准备的目录里。刷新文档，或宿主拆掉 WebView 再新建，这份存储还在不在，以宿主文档为准。本章演示把嵌入页这一档显示为刷新后不在，用来和独立浏览器对照。真实宿主可以保留，也可以清掉。演示这一档不是所有 WebView 的通则。

7.2 证书与刷新生命周期

存储这一档已经分开。证书停在哪一层、刷新拆掉什么，接着看。

问题：嵌入页遇到证书错误，或宿主把文档重新加载，页面里已经拿着的对象还在吗？

约定：走到 HTTPS 时，证书和握手完不成，就没有 HTTP 响应。业务 code 只出现在已经拿到的正文里。这次失败不记成 businessCodeFail（40001），也不记成 httpOk（200）。独立浏览器用自己的证书界面。WebView 可以由宿主的 WebView 客户处理证书错误，订单页不一定看得到独立浏览器那张错误页。界面在哪一侧，都不改变“握手未完成就没有业务 code”。

刷新会新建文档。当前这份 window、页面脚本里的变量、尚未触发的定时器，以及页面自己创建的连接，随旧文档拆掉。独立浏览器刷新仍保留同一源的 localStorage，7.1 已经把这条写明。WebView 刷新是否保留存储，仍以宿主文档为准。

长连接的取用点

长连接放在宿主进程里。当前文档的全局对象是 window。页面通过 window.OrderBridge.socket 取用。刷新拆掉这份 window 和页面内存里的变量。新文档由宿主重新注入 OrderBridge，socket 仍指向宿主那条连接。宿主进程若退出，连接随宿主结束。

用教学订单页走一遍：订单页从 pageOrigin 打开，接口在 apiOrigin。部署改成 https 后，握手失败停在证书这一层，列表接口的正文还没到，businessCodeOk（0）和 businessCodeFail 都还不存在。若此时宿主刷新 WebView，页面变量里的草稿副本和页面自己 new 出来的连接一起结束。草稿键是否还在，回到 7.1 的那一档，不从“页面变量没了”推出“localStorage 也没了”。长连接要继续用，就从新文档的 window.OrderBridge.socket 再取。

把证书失败记成业务 code

40001 和 HTTP 200 都要等响应已经到达。证书失败时这两栏都空着。嵌入页没有独立浏览器那张错误页，只说明宿主接过了界面，不说明业务 code 已经返回。

长连接放在会被刷新拆掉的页面内存里

把连接句柄只放在页面脚本的变量里，这次刷新就把它拆掉。下一份文档的 window 是新的，旧变量不在了。连接放在宿主进程，取用点写在当前 window 的 OrderBridge.socket 上。

可操作对象：在纸上分三行：证书失败、页面变量、宿主里的长连接。第一行写“无业务 code”。第二行写“刷新后不在”。第三行写“window.OrderBridge.socket”。

7.3 注入对象挂在 window

刷新会换一份文档。注入对象要出现在新文档的 window 上。

问题：宿主交给页面的 Bridge，写在哪个全局对象上？

约定：这份文档的全局对象是 window。宿主把 OrderBridge 设成这个 window 的属性。页面用 window.OrderBridge 取它，再用它上面的 socket 取长连接。它不是 Node 的 process，也不是与 window 平级的另一份全局袋子。宿主注册注入对象的 API 以该端文档为准；页面侧只认当前这份 window。刷新之后旧 window 已经不存在，要读的是新文档上重新注入的那一个。

用教学订单页走一遍：订单页脚本跑在当前文档里。currentBridge(window) 应等于 window.OrderBridge。currentSocket(window) 取的是宿主放在这个对象上的连接。只放在页面内存里、没有挂到 OrderBridge 上的对象，函数返回 null。下面用一个普通对象代替真的宿主，避免改动本页正在使用的 window。

function currentBridge(win) { return win.OrderBridge || null; } function currentSocket(win) { var bridge = currentBridge(win); if (!bridge) return null; return bridge.socket || null; } var hostWindow = { OrderBridge: { socket: { name: 'host-socket' } } }; var pageMemory = { socket: { name: 'page-socket' } }; console.log(currentBridge(hostWindow) === hostWindow.OrderBridge); console.log(currentSocket(hostWindow).name); console.log(currentSocket(pageMemory));

示例代码：examples/ch07/order-bridge.js

三行输出是 true、host-socket、null。true 表示注入对象就是这份 window 的属性。host-socket 从注入对象上取。null 表示页面内存里的那份没有挂到 OrderBridge 上，刷新时也会随文档拆掉。

到另一份全局袋子里找注入对象

在订单页里找 process，或假设有一个与 window 平级的袋子专门放 Bridge，都找不到宿主注入的对象。取用点是当前文档的 window.OrderBridge。

刷新后仍读旧 window 上的注入对象

刷新新建了文档，旧 window 上的 OrderBridge 已经随那份文档结束。新页面要等宿主注入到新的 window 之后再读。把刷新前闭包里的引用留到新文档里，拿到的是已经拆掉的那一页。

可操作对象：写下两格。左格是当前 window，里面有 OrderBridge。右格写“另一份全局袋子：无”。长连接写在左格的 socket 上，并注明由宿主持有。

7.4 消息域

注入对象可能被多个页面用到。订单页先看消息域。

问题：回调已经到达 window.OrderBridge，里面的库存就能改订单吗？

约定：从页面向宿主、再从宿主回到页面的每条 Bridge 消息都带 domain。教学订单页的 domain 使用 route，即 /orders。domain 不是 /orders 的消息，不读取它的 stock，页面库存保持 stock（8）。消息域先看，请求编号再看。域对不上时，后面的配对和超时都还没轮到。

用教学订单页走一遍：订单页只处理自己的路由。另一张嵌入页若共用同一个注入对象，它的消息要带自己的域。域是 /other、库存却写着 8 的回调，仍然不改教学订单页的库存。7.6 的 acceptThisStock 第一行做的就是这件事：message.domain 必须等于 route。

不看消息域就改这份库存

看见回调里的库存是 8，就把它当成 /orders 这一次，别的页面的消息会改到教学订单上。先对 domain 和 route。

用路径以外的字符串另造一个域

教学订单页的消息域就是 route（/orders）。另造一个新名字，再和回调里的 /orders 去比，对得上的消息会被丢掉，对不上的消息又可能被收进来。

可操作对象：拿一条回调，先写 domain 一栏。栏里不是 /orders 就停笔，库存一栏保持 8，不往下改。

7.5 请求与回调配对

域对上之后，还要看这次请求和回调是不是同一对。

问题：回调里的库存是 8，页面就要把这一次订单收下来吗？

约定：页面发出这次 Bridge 请求时带上 requestId。回调里的 requestId 必须等于这一次。不相等，就不改库存，库存保持 stock（8）。requestId 是这一次调用的配对记号。订单的雪花 id 仍是字符串 snowflakeText，配对记号不写成 JS 数字，也不拿雪花 id 代替这对编号。到达的先后不能代替编号：先到的、对不上号的回调，仍然不改库存。

检查对不上时
domain 等于 route（/orders）不改库存，保持 8
回调的 requestId 等于这次请求不改库存，保持 8
到达时刻不大于 browserTimeoutMs不采纳为这一次，见 7.6

用教学订单页走一遍：这一次请求的 requestId 是 1。回调若带着 2，即使 stock 写着 8，也是另一对。页面库存留在 8，不去采用那条回调。下一节的函数里，requestId 不一致就返回 false。示例的第三行 console.log 就是这对编号对不上的情况。

回调不配对就改库存

上一次订单、另一张页面的回调若先到达，编号不同。用它改写当前库存，这一次订单的 8 会被别的回调换掉。编号一致之前，库存保持 stock。

用到达先后代替 requestId

先到达只说明它先回到主线程。配对看的是回调里的 requestId 与这次发出的是否同一个。没有编号的回调，不拿来改库存 8。

可操作对象：写两列编号：发出的 requestId，回调里的 requestId。两列不同，在库存列写“保持 8”。

7.6 超时用 3000 ms 这一档

配对之后，回调还要落在浏览器超时这一档里。

问题：这条配对的回调过了 3000 ms 才到，库存字段仍是 8。还算这一次订单吗？

约定：课程里已经有三档超时，Bridge 用最后一档，不另造第四个毫秒数。

字段基准用在哪
connectTimeoutMs500 ms连接建立
readTimeoutMs2000 ms连接之后等待响应数据
browserTimeoutMs3000 ms浏览器侧整段等待。Bridge 回调用这一档

到达时刻小于或等于 browserTimeoutMs，并且消息域、配对和库存都对得上，采纳这次库存 8。到达时刻大于 3000 ms，这次请求已经按超时结束。后到的回调即使 requestId 相同、stock 仍是 8，也不采纳为这一次订单。500 和 2000 继续管连接和读取，不拿来替换 Bridge 这一档。

用教学订单页走一遍：页面发出 requestId 为 1 的请求，域是 /orders，等待的库存是 stock（8）。3000 ms 整点到达，函数返回 true，采纳。3001 ms 到达，返回 false，不采纳。编号是 2 或域是 /other，即使只过了 100 ms，也返回 false。文件里的 3000、8 和 /orders 就是 browserTimeoutMs、stock 和 route 的基准。

var route = '/orders'; var browserTimeoutMs = 3000; var stock = 8; function acceptThisStock(message, requestId, elapsedMs) { if (!message || message.domain !== route) return false; if (message.requestId !== requestId) return false; if (elapsedMs > browserTimeoutMs) return false; return message.stock === stock; } var requestId = '1'; console.log(acceptThisStock({ domain: '/orders', requestId: '1', stock: 8 }, requestId, 3000)); console.log(acceptThisStock({ domain: '/orders', requestId: '1', stock: 8 }, requestId, 3001)); console.log(acceptThisStock({ domain: '/orders', requestId: '2', stock: 8 }, requestId, 100)); console.log(acceptThisStock({ domain: '/other', requestId: '1', stock: 8 }, requestId, 100));

示例代码：examples/ch07/bridge-stock.js

四行输出是 true、false、false、false。第一行是 3000 ms 内的配对回调，采纳库存 8。第二行是超时后。第三行是编号不配对。第四行是消息域不对。

为 Bridge 另造一个超时数

连接 500 ms、读取 2000 ms、浏览器 3000 ms 已经是三档。再写一个 4000 ms 或别的毫秒数，同一次订单会有两个截止时刻。Bridge 回调用 browserTimeoutMs。

Bridge 超时后仍把后到的回调当成这一次订单

大于 3000 ms 的回调可以带着相同的 requestId 和库存 8。它属于已经超时的那一次，页面不再采纳。后到的 8 不把超时结果改回去。

观察要点：① 这一演示的回调已经配对，消息域是 route，库存是 stock（8）。② 到达时刻小于或等于 browserTimeoutMs（3000 ms）时，采纳这次库存 8。③ 大于 3000 ms 的后到回调不采纳，即使编号相同、库存仍是 8。④ 条上的刻度是这一档的位置。连接超时和读取超时仍是 500 ms 与 2000 ms，不另造 Bridge 超时。

7.7 客户端版本与页面版本

超时数已经落在 3000 ms 这一档。客户端和页面仍各有各的版本。

问题：宿主应用还是旧的，订单页已经更新。新字段谁来填？

约定：客户端版本是包住 WebView 的宿主应用。页面版本是这次加载的订单页资源。两套分开兼容。旧客户端不读取、不填写新页面才有的字段。新页面看出客户端是旧版本时，只使用旧客户端已经会回传的字段。库存是否采纳，仍只走消息域、requestId、browserTimeoutMs 和 stock。缺了新字段，不把库存改成别的数。

semverLocked（1.4.2）、semverUnlocked（1.5.0）是依赖锁定，nodeMajor（20）是终端里 Node 的主版本。这三个数不是宿主客户端版本，也不是订单页版本。版本说明由宿主放在注入对象上，字段名以宿主文档为准。本章不另写一个版本号码。

客户端版本页面版本
指什么包住 WebView 的宿主应用这次加载的订单页

用教学订单页走一遍：新页面若多了一个展示字段，旧客户端的回调里没有它。页面继续用 acceptThisStock 判断库存 8，不要求旧客户端补上这个新字段，也不让旧客户端去读它。新客户端遇到仍会发出旧字段的页面时，按旧字段把这次订单走完。两套版本各看各的，不合成一个号码。

把两套版本合成一个号码

宿主应用的发布和订单页资源的发布可以错开。合成一个号码之后，旧客户端会去对新页面的字段，新页面也会去等旧客户端没有的回传。

客户端旧版本仍调新页面的字段

旧客户端去读、去填只有新页面才有的字段，回调里就会缺字段。页面若把缺字段当成库存更新，8 会被改掉。旧客户端只走它已经有的字段；新字段留在认得出该客户端版本的页面路径上。

可操作对象：画两列：客户端版本、页面版本。在旧客户端那一格写下“不调用新字段”。在库存那一格写下“仍按 8 和 3000 ms 判断”。

7.8 多 Tab 与 storage 事件

同一份订单页可以开着多个标签。登录态看 sid，也看 storage 事件。

问题：两个标签都打开着 /orders。一边重新登录，另一边内存里还是旧的 sid。要不要把旧值写回去？

约定：登录态 cookie 的名字是 cookieName，即 sid。这些标签若落在该 cookie 的范围内，cookie 罐是共享的。改 cookie 不会发出 storage 事件。完成登录的那一页再写 localStorage，键用 sid，用来通知其他标签。其他标签收到事件：key 是 sid 时，采用当前 cookie 里的 sid，不把本页内存中的旧 sid 写回 cookie，也不写回 localStorage。key 是 order.draft 时，登录态不动。写出通知的那一页自己收不到这条 storage 事件，它已经持有新的 sid。

storage 事件的 key本页登录态
sid（与 cookieName 同名）改用当前 cookie 的 sid，不把旧值写回
order.draft（storageKey）不改 sid，也不写回

用教学订单页走一遍：标签 A 内存里的 sid 是 old-sid。标签 B 登录完成后，cookie 里的 sid 已是 new-sid，并写入了同名的 localStorage 键。标签 A 的 sidAfterStorage 在键为 sid 时返回 new-sid。返回值不等于 old-sid，因为函数没有把旧值交回去写。键若是草稿 order.draft，返回的仍是内存里的 old-sid，登录态不跟着草稿事件改，函数里也没有写 cookie 的语句。第 6 章把凭据放在 cookie 或内存里；这里只使用 cookie 名 sid，不用草稿键保存会话。

var cookieName = 'sid'; var storageKey = 'order.draft'; // 键是 sid：采用当前 cookie，不返回旧的 memorySid。 // 键是 order.draft：登录态不动。函数里没有把 sid 写回 cookie。 function sidAfterStorage(event, memorySid, cookieSid) { if (event && event.key === cookieName) return cookieSid; return memorySid; } var fromSid = sidAfterStorage({ key: cookieName }, 'old-sid', 'new-sid'); var fromDraft = sidAfterStorage({ key: storageKey }, 'old-sid', 'new-sid'); console.log(fromSid); console.log(fromSid === 'old-sid'); console.log(fromDraft);

三行输出是 new-sid、false、old-sid。false 表示键为 sid 时没有采用旧值。old-sid 只出现在草稿键那一次，登录态保持原样，没有写回。

多 Tab 把旧 sid 写回

本页内存里的 old-sid 是加载时的副本。另一张标签已经换成新的 cookie。把旧副本写回 cookie 或 localStorage，会盖住新的登录。收到键为 sid 的 storage 事件后，采用当前 cookie 里的值。

在写出 sid 的那一页等待 storage 事件

storage 事件发给其他文档，不发给这次写入的文档。写出新 sid 的标签已经持有新值。它再等事件、再用内存里的旧值写一次，就把新登录盖掉。

可操作对象：假定本页收到一条 storage 事件。先看 key。是 sid 就写下当前 cookie 的值，并在“写回旧 sid”一栏写“否”。是 order.draft 就写下“登录态不动”。

本章避坑清单

  1. 长连接放在会被刷新拆掉的页面内存里。它放在宿主进程，取用点是当前文档 window 上的 OrderBridge.socket。
  2. Bridge 超时后仍把后到的回调当成这一次订单。大于 browserTimeoutMs（3000 ms）就不采纳，即使库存仍是 8。
  3. 客户端旧版本仍调新页面的字段。旧客户端只走它已经有的字段，库存仍按消息域、配对、3000 ms 和 8 判断。
  4. 把独立浏览器的 localStorage 寿命套到 WebView。独立浏览器刷新后 order.draft 还在；嵌入页以宿主文档为准，演示这一档可能不同。
  5. 回调不配对就改库存。requestId 不一致时，库存保持 8。
  6. 多 Tab 把旧 sid 写回。收到键为 sid 的 storage 事件后，采用当前 cookie，不把内存里的旧值写回去。
  7. 不看消息域就改这份库存。域要等于 route（/orders）。
  8. 把证书失败记成业务 code 40001 或 HTTP 200。握手未完成时，这两栏都还不存在。

本章小结与延伸阅读

订单页嵌在 WebView 里时，存储、证书和刷新都要单独看。独立浏览器刷新后，order.draft 还在；WebView 以宿主文档为准，本章演示的那一档可以不同。证书握手未完成时没有业务 code。注入对象挂在当前文档的 window 上。长连接放在宿主进程，取用点是 window.OrderBridge.socket。Bridge 先看消息域 /orders，再看 requestId，超时用 browserTimeoutMs（3000 ms）。3000 ms 内且配对，采纳库存 8；超时后的回调不采纳。客户端版本和页面版本分开，旧客户端不调用新页面的字段。多 Tab 看 cookie 名 sid 和 storage 事件，不把旧 sid 写回。

  • MDN，Window.localStorage：独立浏览器里，同一源的数据在刷新后还在。配额和抛错以该文档为准。
  • MDN，Web Storage 的 storage 事件：其他文档改 localStorage 时通知同域文档。发出改写的那个文档自己不收到事件。
  • MDN，Document.cookie：本章登录态 cookie 的名字用 cookieName，即 sid。改 cookie 本身不发出 storage 事件。
  • WebView 的存储目录、证书错误交给谁、重新加载是否新建文档，以宿主应用的文档为准。本章演示把嵌入页这一档显示为刷新后草稿不在，只说明它可以和独立浏览器不同。
  • 超时只使用教学订单页已有的三档：connectTimeoutMs 500 ms、readTimeoutMs 2000 ms、browserTimeoutMs 3000 ms。Bridge 回调用最后一档。证书失败时业务日志里还没有这条请求，放到第 8 章。
