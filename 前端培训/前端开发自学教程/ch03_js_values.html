这一章：订单字段进了 JavaScript 之后怎么读

订单页上的格子已经有了数。这一章看这些数进 JavaScript 之后，按值和绑定来读，而不是按「看起来像不像同一个数」。

先分清原始值和对象引用。stock 抄到一个数字里再减 1，订单库存仍是 8；两个名字指向同一对象，改字段会一起变。比较用 ===。控件输入 0 时，|| 会退回库存 8，?? 会留下 0。雪花 id 保持字符串；金额运算用 19950 分，展示用 199.50。

函数接着决定自己看见哪一份。闭包记下的是绑定：remember(order.page) 留下参数 1，后来把订单改成第 2 页，这个函数仍读到 1；同一个 let 再写成 2，读到的就是 2。普通函数的 this 由这次调用决定，row.read() 得到库存 8；箭头函数用外层的 this。对象沿原型找方法。拷贝要分清是不是仍共享嵌套的那一块。

3.1 原始类型与对象、引用

从字段的存放看起。数字抄出来再改，和两个名字指向同一对象，结果不同。

问题：改一处库存，为什么另一处也变了？

约定：原始值按值持有，包括 string、number、bigint、boolean、undefined、symbol。对象、数组和函数按引用传递：两个变量可以指向同一份对象。null 表示有意留空，它没有字段。typeof null 的结果是 "object"，这是语言里留下来的结果，判断空值时用 === null。相等和运算符的精确定义以 ECMAScript 规范原文为准。

基准算例：Course.data.order.stock 是数字 8。把它读进局部变量 shown 再写成 7，shown 变成 7，订单上的库存仍是 8，因为数字是原始值。若 alias 与 order 指向同一对象，alias === order 为 true；字段内容看起来一样的两个不同对象，=== 为 false。用户标识用字符串字段 userIdText，值是 10001。

const order = Course.data.order; let shown = order.stock; shown = shown - 1; // shown 为 7，order.stock 仍为 8 const alias = order; // alias === order 为 true，两边是同一张订单

3.2 == 与 ===、null 与 undefined、真值与假值

存放方式定了。下一步是比较：null 和 undefined、真值和假值会把分支带偏。

问题：件数是 0 的时候，页面会把它当成没填吗？

约定：=== 同时比较类型和值，不做转换。== 会做转换，并且 null == undefined 为 true，null === undefined 为 false。假值有 false、0、''、null、undefined、NaN。数字 0 是假值，同时可以是一次明确的输入或一个成功码。

基准算例：userIdText 与字符串 '10001' 用 === 比较为 true，与数字 10001 用 === 比较为 false，用 == 比较为 true。库存 8、page 1 都是真值。businessCodeOk 是 0，真值判断进不去成功分支；成功要写成与 0 严格相等。businessCodeFail 是 40001，httpOk 是 200，这两个数都是真值，不能靠“有没有值”区分业务失败和 HTTP 成功。

易错：== 把 null 和 undefined 放行

missing == null 在 missing 为 undefined 时也为 true。字段没出现和字段明确写成 null 走进同一分支，后面的检查被放行。missing === null 为 false，missing === undefined 为 true，两路才能分开。

可操作对象：写条件前先列出三态：字段缺失（undefined）、明确的 null、明确的 0。id 文本和数字 10001 用 === 分开。业务成功只认与 0 严格相等。

3.3 ?? 与 ||

相等已经分开。控件上的 0 还要看默认值用的是 || 还是 ??。

问题：件数控件读到 0 时，页面该采用 0，还是回退到订单库存？

约定：|| 在左侧是假值时取右侧，0、''、null、undefined、NaN、false 都会换到右侧。?? 只在左侧是 null 或 undefined 时取右侧，0 和空字符串会留下。用 === 手写回退时，条件写成“严格等于 null 或严格等于 undefined”，0 同样留下。默认参数的空值范围留到第 3.7 节。

基准算例：控件输入只有两种：0 或 8。0 只出现在控件上。默认回退值是 order.stock，值为 8。订单上的库存保持 8。输入 0 时，|| 采用 8，?? 和 === 回退都采用 0。输入 8 时三种写法都采用 8，看不出差别。输入 null 或 undefined 时三种写法都采用 8。

3.4 安全整数、雪花 id、金额分

比较规则够用了。雪花 id 和金额分是这份订单上两个不能换单位的字段。

问题：雪花 id 写成数字会怎样？

约定：在 IEEE 754 双精度这个假设下，JavaScript 的 Number 能连续表示的整数满足 \( |n| \le 2^{53}-1 \)。超出上界之后，相邻整数会落到同一个 Number。JSON number 进入 JavaScript 时走这条 Number 路径。雪花 id 在课程数据里只以字符串存放，比较和展示都用字符串字段，并交给 orderMath.isSafeId 与 orderMath.jsonNumberRoundTrip。金额的业务加减用最小货币单位的整数；展示时才格式化成元。精确定义以 ECMAScript 规范原文为准。

基准算例：userIdText 是 10001。isSafeId(userIdText) 为 true，jsonNumberRoundTrip 之后仍是原串，所以它不能用来演示丢精度。maxSafeText 是 \(2^{53}-1\) 的十进制文本。snowflakeText 超过这个上界；jsonNumberRoundTrip(snowflakeText) 得到的字符串等于 snowflakeRoundedText，与原串相差 1。两段都是字符串。amountFen 是 19950，orderMath.yuanText() 得到 199.50。两件是 19950 的两倍，即 39900 分，yuanText(39900) 得到 399.00。amountYuan 是 199.5，这个元值单次换成二进制看不出误差，加减仍只发生在 amountFen 上。

避坑：雪花 id 进 Number，金额用小数相加

可操作对象：切换 userIdText 与 snowflakeText，读出 isSafeId 和往返后的字符串。审查接口时，id 字段保持字符串，金额字段名带着“分”。

3.5 词法作用域与闭包

值本身已经能读准。函数若把页码记下来，要看它记下的是哪一份绑定。

问题：地址已经翻到第 2 页，订单请求为什么还带着第 1 页？闭包留住的是那个数字，还是那个变量？

约定：函数按它写在哪里决定能看见哪些绑定，这层记录叫做词法环境（lexical environment）。调用发生在哪里，不改这组绑定。闭包是函数加上它仍能到达的那些词法绑定。外层函数返回之后，只要内部函数还在，这些绑定就还在。闭包记下的是绑定，不是把当时的数字复印一份冻住。查找从内层向外层走；内层再声明同名的 page，读到的是内层那一个。精确定义以 ECMAScript 规范原文为准。

同一个名字，读到的页码可以不同，差在绑定是不是同一份：

怎么写绑定后来改到第 2 页之后
remember(order.page)参数是一次新绑定，传入时是 1load() 仍是 1。改的是订单上的另一份
内部函数直接读 let page外层和内部函数是同一个绑定把这个 page 写成 2，load() 就是 2
内部函数读 row.page闭上的是对象引用，字段在调用时再读调用前把 row.page 写成 2，load() 就是 2
同一个调用里返回 read 和 next两个函数共用参数那一份绑定next() 把 1 改成 2，read() 也是 2

基准算例：order.page 是 1，order.size 是 20。下面四段都不修改 Course.data.order，局部对象上的页码才改成 2。总页数仍用 orderMath.pageCount() 现算。请求若在初次渲染时执行了 remember(order.page)，它留下的是参数绑定 1，和当前页相差 1 页；size 没有进这个绑定，仍是 20。若内部函数读的就是后来被写成 2 的那个 let，或者读的是对象上的 page，调用时得到 2。

function remember(page) { return function load() { return page; }; } const row = { page: order.page }; const load = remember(row.page); row.page = 2; // load() 仍是 1。参数绑定和 row.page 不是同一份。 let page = order.page; const live = function () { return page; }; page = 2; // live() 是 2。赋值改的就是它闭上的那个绑定。 const current = function () { return row.page; }; // row.page 已经是 2，current() 是 2。字段在调用时读取。 function pair(page) { return { read: function () { return page; }, next: function () { page = page + 1; return page; } }; } const box = pair(order.page); box.next(); // next 把这份绑定从 1 改成 2，read() 也是 2。

易错：凡是闭包都冻住创建时的 1

3.6 this 与箭头函数

闭包看的是词法环境里的绑定。this 反过来，由这次调用决定。

问题：读库存的函数，为什么有时得到 8，有时又读不到这张订单？this 跟着函数走，还是跟着这次调用走？

约定：普通函数的 this 由这次调用决定，不由函数写在哪里决定。这和上一节的词法环境相反。调用点写成 row.read() 时，this 是 row。call、apply、bind 可以给普通函数指定这次的 this。bind 交出的是新函数，以后调用仍用绑定时传入的对象。箭头函数没有自己的 this，它使用外层词法环境里的那一个；call、apply、bind 改不了箭头的 this。对象字面量不建立 this。class 字段里的箭头在构造时创建，外层 this 是正在构造的实例。调用规则以 ECMAScript 规范原文为准。

3.7 默认参数与剩余参数

调用点定了 this。参数缺省和剩余参数决定这次调用收下哪些实参。

问题：默认库存是 8，传入 0 时用的是哪一个？

约定：默认参数只在该实参是 undefined 时填入。null、0 和空字符串都会原样进入函数体。默认值表达式在每次需要填入时求值。剩余参数把形参列表里没被点名的实收进一个真正的数组。它和 arguments 是两份数据。语法细节以 ECMAScript 规范原文为准。

基准算例：setQty(0) 的参数是 0，默认的 order.stock 不会替掉它。setQty() 与 setQty(undefined) 得到 8。setQty(null) 得到 null。这和上一节的 || 不同：0 || order.stock 得到 8，默认参数在传入 0 时得到 0。分页函数的默认页码用 order.page（1），默认每页条数用 order.size（20）。describe(order.snowflakeText, order.amountFen, order.stock) 的剩余参数有 2 个：19950 和 8。id 仍是字符串。

function setQty(qty = order.stock) { return qty; } setQty(0); // 0 setQty(undefined); // 8 setQty(); // 8 function describe(id, ...parts) { return parts.length; } // describe(snowflakeText, amountFen, stock) 的长度是 2

示例代码：examples/ch03/default-rest.js

易错：以为默认参数会把 0 换成库存

setQty(0) 采用 0。若期望“0 就换回 8”，那是 || 的行为，默认参数不会这么做。件数要保留 0 时，默认参数和 ?? 一致；要小心的是另外写成 || 的那一行。

避坑：默认值里发请求，或改 arguments

默认值表达式会在实参为 undefined 时执行。把拉订单的请求写在默认参数里，缺参的那次调用就会发请求。剩余参数才是函数体内该使用的数组；改 arguments 不会改剩余参数里的 19950 和 8。

可操作对象：给页码和件数写默认值时，用 order.page、order.size、order.stock。用 0 调用一次，确认参数仍是 0，再决定空值该交给默认参数、?? 还是显式 === undefined。

3.8 原型链与 class

函数侧的规则齐了。对象上找不到的方法，沿原型继续找。

问题：多行共用一段读库存的方法，改一行会改到别的行吗？

约定：属性查找沿原型链向上：实例，然后构造函数的 prototype，然后 Object.prototype，直到 null。class 的方法放在原型上，实例字段放在每个对象上。class 是原型的写法，每行订单会各自持有自己的 stock，方法仍是共享的那一个。查找规则以 ECMAScript 规范原文为准。

基准算例：两行分别用库存 8 和 7 构造。8 来自 order.stock，7 是 order.stock - 1，只存在于这个局部实例上，订单数据里的库存仍是 8。a.text() 得到 8，b.text() 得到 7。a.text === b.text 为 true，因为方法在原型上是同一份。stock 在实例上，text 在原型上。

function OrderLine(stock) { this.stock = stock; } OrderLine.prototype.text = function () { return this.stock; }; const a = new OrderLine(order.stock); const b = new OrderLine(order.stock - 1); // a.text() 为 8，b.text() 为 7，a.text === b.text class OrderCard { constructor(stock) { this.stock = stock; } text() { return this.stock; } }

示例代码：examples/ch03/prototype.js

易错：改一行的方法，以为所有行都变了

给 a.text 重新赋值，新函数只出现在实例 a 上。b.text 仍走原型，b.text() 仍是 7。要让所有行一起换方法，改原型上的那一个，并先确认这是你自己的构造函数。

避坑：改内置原型给订单列表开洞

往 Array.prototype 或 Object.prototype 上加“订单专用方法”，页面上别的数组和对象都会沿着原型链看见它。订单行的方法放在自己的 OrderLine.prototype 或 class 上。字段 stock 放在实例上，各行互不影响。

可操作对象：读一行订单时分开两问：stock 在不在实例上，text 在不在原型上。可以用 Object.hasOwn 核对，具体返回值以当前运行环境的文档原文为准。

3.9 浅拷贝、深拷贝、不可变更新

原型链解决查找。列表和详情若要各持一份，还要看拷贝是否仍共享嵌套字段。

问题：改了详情里的库存，列表为什么也变了？

约定：浅拷贝只复制第一层。第一层上的原始值因此各有一份；第一层上的对象仍是同一个引用。深拷贝要让嵌套对象也各自独立。不可变更新是交出一张新对象：改到的每一层都新建，没改的层可以沿用。JSON 文本往返会丢掉值为 undefined 的字段，也会丢掉函数和 symbol，日期会变成字符串。它适合检查“文本里还剩什么”，不适合当作通用深拷贝。

基准算例：局部的列表项含有字符串 id（snowflakeText）、amountFen 19950，以及嵌套的 draft.stock 8。浅拷贝之后把详情的 draft.stock 写成 7，列表的 draft.stock 也是 7，两处相差 0，因为嵌套对象是同一份。把详情自己的 amountFen 改成另一个整数，列表的 19950 不变，因为分是原始值。不可变更新新建 draft：新对象的库存是 7，列表仍是 8，相差 1。整个过程不修改 Course.data.order.stock，订单库存保持 8。

const list = { id: order.snowflakeText, amountFen: order.amountFen, draft: { stock: order.stock } }; const detail = { id: list.id, amountFen: list.amountFen, draft: list.draft }; detail.draft.stock = order.stock - 1; // list.draft.stock 也变成 7。order.stock 仍是 8。 const fresh = { id: order.snowflakeText, amountFen: order.amountFen, draft: { stock: order.stock } }; const next = { id: fresh.id, amountFen: fresh.amountFen, draft: { stock: order.stock - 1 } }; // fresh.draft.stock 仍是 8，next.draft.stock 是 7。 const payload = { page: order.page, remark: undefined, amountFen: order.amountFen }; const cloned = JSON.parse(JSON.stringify(payload)); // cloned.page 为 1，cloned.amountFen 为 19950，cloned 上没有 remark

示例代码：examples/ch03/copy.js

易错：浅拷贝后列表和详情改同一块嵌套字段

Object.assign 或对象展开只复制第一层。draft 仍是同一个对象。详情把嵌套库存改成 7 时，列表上的嵌套库存也是 7。订单原始数据里的 stock 若没有被赋值为 0，就仍然是 8；一起变的是这份嵌套草稿。

避坑：JSON 往返当成深拷贝

JSON.parse(JSON.stringify(payload)) 会丢掉 remark: undefined。页码 1 和金额 19950 还在，备注这个键没有了。雪花 id 若本来就是字符串，文本里可以保留；一旦先被放进 Number，往返还会碰上上一节的差 1。需要留下 undefined 时，按字段自己复制。

可操作对象：更新草稿时新建被改的那一层 draft，让列表继续持有库存 8，详情编辑持有自己的那一份。提交前看 payload：缺了的键是不是当初值为 undefined 的备注。

3.10 标准库里的日期和正则先点到为止，细节在第 4 章

值和对象这条链到这里。日期和正则只点明它们在标准库里，细节交给下一章的数据结构。

问题：订单日期和单号，这一节要定到什么程度？

约定：Date 和正则是标准库的一部分。本章只定边界：三个超时是三个毫秒数，雪花 id 保持字符串。解析步骤、时区、正则标志、以及 Array、Map、Set、URL 的用法在第 4 章展开。库的参数表以语言文档原文为准，这里不列成操作手册。

基准算例：教学订单没有单独的日期字段。连接超时 connectTimeoutMs 是 500，读取超时 readTimeoutMs 是 2000，浏览器等待 browserTimeoutMs 是 3000。三者相差分别是 1500 毫秒和 1000 毫秒，它们是三个数字，可以各自放进定时逻辑，不先收成一个 Date。雪花 id 用 isSafeId 判断是否还能安全地当整数看；格式检查可以发生在字符串上。

易错：三个超时收成一个日期

把 500、2000、3000 收成同一个 Date 或同一个毫秒数之后，连接、读取和浏览器等待就无法分开核对。页面上先记下这三个数各自是哪一层的等待。

避坑：正则取出雪花 id 再交给 Number

正则可以检查字符串的形状。检查通过后，值仍放在 snowflakeText 里，并用 isSafeId 与 jsonNumberRoundTrip 核对。交给 Number 会得到和第 3.4 节相同的差 1。

可操作对象：读到日期比较、时区或正则贪婪时，先记在第 4 章的标准库一节，再查文档原文。本章的订单字段仍然是：id 用字符串，金额用 amountFen，件数的 0 用 ?? 或 === 保留。

本章避坑清单

  1. 用 == 比较 null 和 undefined 时，字段缺失和明确留空会走进同一分支。
  2. 用 || 给件数做回退时，控件输入 0 会被换成 order.stock 的 8。订单库存保持 8。
  3. 雪花 id 保持字符串。交给 Number 或写成 JSON number 后，往返字符串与原串相差 1。
  4. userIdText 在安全整数内，isSafeId 为 true，不能用来演示丢精度。
  5. 金额加减用 amountFen（19950）。展示用 yuanText() 得到 199.50。199.5 不做加减。
  6. remember(page) 留下的是参数绑定 1。同一个 let page 再写成 2，闭包读到的是 2。
  7. var 循环里的多个回调共用一个 page 绑定，离开循环后读到的是同一个值。
  8. 浅拷贝之后，列表和详情的嵌套 draft 仍是同一份。详情改到 7，列表也是 7。
  9. JSON.parse(JSON.stringify(...)) 会丢掉值为 undefined 的字段。
