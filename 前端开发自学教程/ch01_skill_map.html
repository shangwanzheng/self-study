这一节解决什么问题：技能模型里的“中级”要落到一个可以交出去的页面上。中级的要求是：JavaScript 和浏览器基础扎实，能用 TypeScript 和组件框架独立完成页面、样式和接口联调，并熟悉常见前端规范和工程化工具。高级全表（架构、性能、安全、跨端、发布）在第 9 章建立地图，标成碰到再展开。本章先钉住交付物的名字和两条路径。

符号或约定：全课只有一笔基准算例，名字写在 Course.data.order.name，就是「教学订单页」。页面路径读 order.route，接口路径读 order.apiPath。运行时全局名只用 Course。派生数字调用 Course.orderMath，不另写一套公式。

1.3 教学订单页的字段与单位

这一节解决什么问题：后面每一章都会引用同一批数字。这一节把字段名、单位和“哪个函数负责现算”一次定下来。标识用字符串，金额运算用整数分，分页用页码和页大小，成功与失败同时看 HTTP 状态和业务 code。

1.4 页面全局对象是 window

这一节解决什么问题：订单数据放进页面之后，要有一个说得清的全局对象。技能模型把这件事写成：浏览器里没有 JVM，也没有进程级全局袋子，页面全局对象是 window。本章的脚本是经典脚本，Course 挂在这个 window 上。

符号或约定：在浏览器页面里，window.Course 与 Course 指同一个对象。Course.data.order 是这一页的基准数据，Course.orderMath 是这一页的计算。window 的生存期跟这一份文档走：刷新后文档重新建立，内存里的绑定重新建立。Node 主版本 nodeMajor 的值是 20，留给第 2 章写命令示例；项目实际版本以仓库约定和文档为准。开发者工具从哪里打开，以浏览器文档原文为准。

用教学订单走一遍：在页面脚本里读取 window.Course.data.order.stock，得到 8；读取 window.Course.data.order.route，得到 /orders。这两个值住在这份文档的 window 上。草稿键 storageKey（order.draft）和 Cookie 名 cookieName（sid）也只是订单上的字符串，把它们赋给 window 的一个自造属性，只是又多了一个内存绑定。它们要真正留下，得按 1.5 节的存储种类去写。第 2 章会说明页面里找不到名为 process 的运行时；本章先把全局对象的名字定成 window。

易错：以为页面里有进程级全局袋子

多个请求、多个 Tab 若各自打开教学订单页，各有自己的 window。库存数字仍以订单字段 stock 的 8 为基准。不存在一个进程级袋子，让所有页面共享同一块内存里的订单。

避坑：把草稿键和 Cookie 名当成进程级全局变量

把 order.draft 或 sid 挂到 window 上，刷新后这个属性随文档重建。草稿要进 localStorage，会话名要进 Cookie。存储种类在下一节按刷新和关 Tab 分开点亮。

可操作对象：在页面里执行的脚本，用 window.Course.data.order 读取基准，用 window.Course.orderMath 做现算。排查“全局变量丢了”时，先确认自己读的是 window，再按 1.5 节判断该不该刷新后还在。

1.5 刷新后内存、localStorage、sessionStorage、Cookie、已下载的包各留下什么

这一节解决什么问题：刷新教学订单页之后，用户会问草稿还在不在、筛选条件还在不在、登录用的 Cookie 还在不在、脚本是不是仍是上一份下载。五处位置的答案不同。技能模型的原句是：内存变量没了；localStorage 还在；sessionStorage 关 Tab 才没；Cookie 按域和过期时间；已下载的包可能还是旧的。

符号或约定：草稿的键是 order.storageKey，文字为 order.draft，放在 localStorage。筛选条件放在页面内存，刷新后不在。第 10 章核对页时仍用这句话。Cookie 的名字是 order.cookieName，文字为 sid。本章不另写一个 Cookie 过期秒数，过期与域以浏览器和 HTTP 文档原文为准。带内容 hash 的脚本属于已下载的包，缓存秒数在 1.7 节与入口 html 分开。浏览器里查看存储的菜单位置以该浏览器文档原文为准。

1.6 三个超时

这一节解决什么问题：教学订单页上的一次等待，在不同位置有不同的毫秒数。连接还没建立、连接已经建立但响应还没读完、浏览器这一侧放弃等待，是三段。排错时要能指出当前看的是哪一段。

符号或约定：三个字段都在 Course.data.order 上，单位都是毫秒。connectTimeoutMs 是建立连接可等待的时间。readTimeoutMs 是连接建立之后、等待响应数据的时间。browserTimeoutMs 是浏览器这一侧的等待。客户端设置界面里的菜单项叫什么，以所用 HTTP 客户端的文档原文为准。本章只用这三个字段名。

用教学订单走一遍：读 order.connectTimeoutMs，得到 500。读 order.readTimeoutMs，得到 2000。读 order.browserTimeoutMs，得到 3000。三个数同时出现在同一笔订单上，就是为了避免并成一个“网络超时”。请求从 pageOrigin 发往 apiOrigin 时，浏览器侧的预算用 3000。服务端或客户端库若再区分连接与读取，连接用 500，读取用 2000。旁边还有 qpsTeach，值是 50。它表示数量级，用来记住“这一页的教学流量大概在这个量级”。它不是超时，不是压测结论，也不是容量承诺。orderMath 不为超时提供函数，这三个数直接读字段。

连接 500 msconnectTimeoutMs。还在建立到接口源的连接。
读取 2000 msreadTimeoutMs。连接已经建立，在等 /api/orders 的响应数据。
浏览器 3000 msbrowserTimeoutMs。页面这一侧等待的上限。
易错：把浏览器超时 3000 当成读超时 2000

页面上的加载指示停在 3000 毫秒，只说明浏览器这一侧的等待到了。读超时仍是 2000 毫秒。把 3000 填进读取配置，或把 2000 当成浏览器放弃的时刻，两段日志会对不上。

避坑：三个超时合成一个数

检查表上写三行：连接 500、读取 2000、浏览器 3000。菜单里若只有一个叫“超时”的输入框，先对照文档原文确认它改的是哪一段，再填写对应字段。qpsTeach 的 50 不参与这三行。

可操作对象：一次失败请求记下三格毫秒数，并写上当时看的是浏览器、连接还是读取。第 8 章排错、第 10 章核对都沿用这三格。

1.7 接口数据缓存和 html/js 的 HTTP 缓存

这一节解决什么问题：教学订单页有两层缓存。一层是页面内存里的接口数据：列表、金额、库存来自 /api/orders 的响应。另一层是浏览器对入口 html 和 js/css 的 HTTP 缓存。两层的失效对象、失效时间都不同。写成同一条策略，刷新后的现象会对不上。

符号或约定：接口数据的位置是页面内存，寿命跟这份文档的 window 走。HTTP 缓存看响应头；头的具体写法以 HTTP 文档原文为准。订单上与 HTTP 缓存直接对应的两个数是：htmlMaxAgeSec 管入口 html，assetMaxAgeSec 管带内容 hash 的 js/css。带内容 hash 的意思是文件名里带上内容摘要，内容变了，地址也变。

用教学订单走一遍：接口侧：listN 是 10000，当前页 page 是 1，页大小 size 是 20，金额分 amountFen 是 19950。这些一旦只放在内存里，刷新后要重新请求 apiPath。静态资源侧：读 order.htmlMaxAgeSec，得到 60，单位是秒，入口 html 短缓存。读 order.assetMaxAgeSec，得到 31536000，单位是秒，带内容 hash 的 js/css 长缓存。回滚时改的是入口，已缓存的 hash 文件留在 1.5 节说的“可能仍是旧文件”那一格，第 9 章再展开做法。第 9 章还会把首屏体积算出来：orderMath.firstScreenKb() 等于 bundleMainKb + bundleVendorKb，懒加载时 bundleRouteKb 不进首屏。那一层是包体积，和这里的两层缓存用不同的字段。

易错：用脚本还在不在判断接口列表还在不在

带 hash 的脚本可能仍是已下载的那一份，这只说明 HTTP 缓存还留着那个文件。接口列表在页面内存里。刷新后内存重建，列表要重新向 /api/orders 请求。脚本文件还在，不能代替这次请求。

避坑：两条缓存写成同一条失效策略

失效要写两行。接口数据：刷新文档即丢，下次进入页面重新请求。静态资源：入口 html 使用 60 秒，带内容 hash 的 js/css 使用 assetMaxAgeSec。把接口列表也套上 31536000 秒，或把入口 html 套上同一长缓存，回滚和刷新都会看到错的那一层。

可操作对象：在设计笔记上画两行：一行写“内存 / /api/orders / 刷新后重请求”，一行写“HTTP / html 60 秒 / hash 资源 assetMaxAgeSec”。两行的秒数和触发条件都填完，才算把两层分开了。

1.8 类型打包后会被擦掉，先记住这句话

这一节解决什么问题：第 5 章才系统讲 TypeScript。在那之前，订单字段已经要穿过 JSON。先记住一句：类型在打包后会被擦掉。页面上跑的是脚本，运行时看不到类型标注。和姊妹课里「类型留在字节码里」只做这一句对照，不展开 Java 的反射、泛型和字节码。

符号或约定：契约上，订单 id 用字符串，金额用整数分。这是写法约定，由人在源码里标注。打包完成后，这些标注不留在页面里。运行时能用的是 orderMath.isSafeId 和 orderMath.jsonNumberRoundTrip。钩子名字 useState、useEffect 从第 6 章才进入页面，语义以 React 文档原文为准；它们也不把类型留在打包产物里。

用教学订单走一遍：设想接口约定把雪花 id 标成字符串，把金额标成整数分。isSafeId(order.userIdText) 在运行时为真，isSafeId(order.snowflakeText) 在运行时为假。把雪花文本交给 jsonNumberRoundTrip，得到的字符串等于 snowflakeRoundedText，和原文字差 1。类型标注即使写过 string，也不会在浏览器里把这 1 加回去。amountFen 的 19950 同样要在运行时当整数用，展示再调用 yuanText()。业务成功看 businessCodeOk 的 0，失败看 businessCodeFail 的 40001；类型里的联合类型在打包后也不替你做这次判断。第 5 章会把缺字段、断言和运行时校验接上同一笔数。

易错：以为打包后的页面里还留着类型

源码里写了字符串和整数分，检查器能在编译时提意见。打包后的教学订单页只剩脚本。运行时的 id 是不是字符串，要看 JSON 里它是带引号的文本，还是一个 JSON number。

避坑：雪花 id 以 JSON number 解析少 1

雪花 id 以 snowflakeText 这个字符串进入契约。若响应里把它写成 JSON number，jsonNumberRoundTrip 得到 snowflakeRoundedText，少 1。类型写过 string 也拦不住。1.3 节的演示可以来回切换，确认 userId 保持原样、雪花 id 不保持。

可操作对象：审一份订单响应时，先看雪花字段在 JSON 里有没有引号，再调用 isSafeId 与 jsonNumberRoundTrip。类型文件留到第 5 章，不代替这两次运行时读取。

1.9 路由表不是后端 Controller

这一节解决什么问题：教学订单页在浏览器里有一条路径，在服务端有一个接口。路由表记录的是浏览器里哪条路径打开哪一页。后端 Controller 是服务端接收 HTTP 的入口，属于姊妹课。两套名字若叠在一起，页面路径和接口路径会被写成同一个字符串。

符号或约定：order.route 是页面路径。order.apiPath 是接口路径。order.page 与 order.size 会在第 6 章变成路径上的参数，页数用 orderMath.pageCount() 现算。页面源 pageOrigin 与接口源 apiOrigin 端口不同。路由表里放路径和页面的对应关系。业务规则、金额分和密钥名字不写进路由表。

用教学订单走一遍：用户打开的地址由 pageOrigin 加上 route 组成，路径部分是 /orders。列表数据向 apiOrigin 加上 apiPath 去要，路径部分是 /api/orders。当前基准页码是 1，页大小是 20，pageCount() 给出总页数（格子在 1.3 节，由函数现算，基准是 500）。翻到第 2 页时，变的是页面路由上的 page，请求也带着这个页码；旧响应怎么丢，放在第 7 章。路由表的一行写成：路径 /orders 打开教学订单页。它不写成一个 Java 类，也不写成 ORDER_API_SECRET。框架如何声明这行路由，以该框架文档原文为准。

易错：把路由表写成后端 Controller

Controller 负责在服务端接收 /api/orders。浏览器路由表负责打开 /orders。两行可以同时存在，字段名保持 route 与 apiPath。把 Controller 的类名抄进前端路由表，页面路径就和接口路径缠在一起。

避坑：把两条路径收成同一个字符串

/orders 与 /api/orders 都要保留。http://localhost:5173 与 http://localhost:8080 端口不同，第 2 章用它们讲同源。路由表里也不写 secretName。密钥仍只是名字，不进前端包。

可操作对象：画两行地址：一行是页面源加 route，一行是接口源加 apiPath。检查路由配置时只改第一行的路径对应关系；接口契约改第二行。页码和页大小从 order.page、order.size 读，总页数调用 pageCount()。

1.10 后面九章各自接这条订单页的哪一段
