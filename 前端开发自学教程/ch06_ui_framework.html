第 6 章 · 方法

组件、状态、副作用与路由

这一章用函数组件看教学订单页：列表怎样认出每一行，库存字段怎样才会重画，以及 page 怎样进入请求。示例都是函数组件。useState 与 useEffect 的精确语义以 React 文档原文为准，不把某一小版本的调度写成唯一行为。

  • 能说明列表 key 用雪花 id 而不用下标；
  • 能说明直接改字段不会重画、要用新对象替换；
  • 能说明请求放在副作用里并把 page 放进依赖。

6.1 DOM、样式计算、布局、绘制、合成

问题：订单列表从脚本改动变成屏幕上的像素，中间要经过哪些步骤？

约定：把一次更新分成 DOM、样式计算、布局、绘制、合成。脚本在主线程上改 DOM 和样式；布局给出位置和尺寸；绘制把像素写入层；合成把层组合到屏幕，这一步可以和主线程错开。按 60Hz 估算，一帧约 \(1000/60 \approx 16.7\) ms，课程字段 frameBudgetMs 取这个估算，它不是某台设备的保证。达到 longTaskMs 即 50ms，才把这段主线程占用叫做长任务。

DOM节点树。一行订单是元素和文本。
样式计算得出每个节点实际使用的样式。
布局得出位置与尺寸。一行高 48px。
绘制把颜色、文字和边画进层。
合成把层合成到屏幕上。

基准算例：视口行数 viewportRows 为 12，行高 rowHeightPx 为 48。Course.orderMath.visiblePx() 得到 576，这是当前屏要准备的高度。整表 listN 为 10000，Course.orderMath.fullListPx() 得到 480000。一帧里准备的是视口附近的几何，整表高度只作为滚动范围。

一次改字不等于整页重画

改一行草稿，失效的通常是局部样式、布局或某一层。把任何一次 setState 都理解成 10000 行全部重算，会把帧预算用在看不见的行上。

渲染路径上重算整表

在渲染计算里同步排列或测量全部 10000 行，高度按 480000px 整表去跑，很容易超过 16.7ms，并可能达到 50ms 长任务。本章先把整表高度和视口高度分成两个数；虚拟列表的具体做法留到性能一章。

可操作对象：改订单单元格之前，先写下这次改动停在样式、布局还是绘制，以及它碰的是 576px 视口还是 480000px 整表。

6.2 回流与重绘，读布局再写样式会强制同步布局

问题：为什么列表代码读完布局再写样式，主线程会突然变慢？

约定：回流是重新计算布局；重绘是在几何可以不变的情况下重新画像素。浏览器可以把样式写入先攒着。脚本一旦读取 offsetHeight、offsetTop 或 getBoundingClientRect，就必须先把积压的布局算完，这就是强制同步布局。紧接着再写样式，布局又变脏，下一次读取会再算一遍。

rows.forEach(function (row) {
  row.style.minHeight = "48px";
  var height = row.offsetHeight;
});

基准算例：上面的 48 来自行高 rowHeightPx。若 rows 有 listN 即 10000 行，每一行都「写样式、立刻读布局」，读数大多落在视口 576px 之外。当前屏真正用得上的高度仍是 visiblePx() 的 576。

读写布局穿插

在渲染函数或翻页事件里交替写 style 和读 offsetHeight，会把本可攒成一次的布局拆成许多次。本章不把某台机器的毫秒数写成结论；判断标准是它是否挤进 16.7ms 的帧，以及是否长到 50ms。

渲染期间读 offsetHeight

渲染计算只负责描述这一帧。把布局读数写进渲染路径，会在描述还没提交时强迫浏览器算几何。先把要写的样式攒齐，需要读高度时集中读一次容器，而不是在每一行订单上读一次。

可操作对象：在列表渲染代码里搜索 offsetHeight、offsetTop、getBoundingClientRect，标出紧挨着的样式写入。

6.3 函数组件、JSX、props、children、事件

问题：订单页的一块界面用什么来描述？

约定：本章以函数组件为例。函数接收 props，返回这一帧的界面描述。JSX 是描述，构建之后变成创建元素的调用，页面上最终仍是 DOM。写在标签中间的内容经 props.children 进入函数。点击、输入经 props 里的事件函数进入组件。函数在每次渲染时执行，它根据当前 props 和状态算出描述。

function OrderList(props) {
  return layout(props.children, {
    page: props.page,
    size: props.size,
    onPage: props.onPage
  });
}

基准算例：教学订单的 page 默认是 1，size 是 20。列表函数的 props 带上这两个数，以及翻页事件 onPage。工具条、空状态可以放在 children。翻页事件只负责交出下一页的页码；请求留在后面的副作用里，不写在 JSX 求值的过程中。

把函数体当成只会执行一次

函数组件在每次渲染时都会执行。写在函数体里的局部变量，下一次渲染会重新建立。想跨渲染留下草稿或库存，要用状态，而不是指望函数里的普通对象自己刷新。

在函数体里发请求

函数体是渲染计算。渲染次数可以多于用户的一次点击。把 /api/orders 写在这里，每一次渲染都会发起请求。取数放到副作用，见 6.7 与 6.8。

可操作对象：为一个订单函数写下输入 props（至少含 page 与 size）、children 里放什么，以及它向外交出的事件。

6.4 列表 key 用雪花 id，不用下标

问题：翻页之后，为什么第一行刚输入的草稿还留在第一行？

约定：列表子项的 key 是前后两次渲染之间的身份。相同的 key 会沿用这一项已经记下的状态，例如输入框里的草稿。下标跟着数组位置走，两页的第一行都会得到下标 0。订单身份用雪花 id 的字符串：取课程字段 snowflakeText，再拼行号，得到互不相同的教学字符串。雪花数字保持字符串，不写成 JS 数字字面量，也不先转成 Number。

基准算例：演示里第 1 页两行的行号是 1 和 2，第 2 页接着是 3 和 4，id 形如 snowflakeText 加这一个行号。size 仍是 20，这里只画出两行，是为了看清 key，不是把每页改成 2 条。userIdText 为 10001，它在安全整数以内，不能拿来演示精度丢失；列表身份仍用雪花字符串。orderMath.jsonNumberRoundTrip 会让雪花文本少 1，所以 key 使用原来的 snowflakeText，不使用往返之后的文本。

用下标当 key

page 1 与 page 2 的第一行下标都是 0。第一行输入过的草稿会留在下标 0 上，翻页后仍出现在第一行，和这一页自己的订单 id 对不上。

用随机数或渲染序号当 key

每次渲染都变的 key，会让每一行都被当成新行，草稿和焦点保不住。key 要在这一行的整个生命周期里稳定，又要和别的行不同。教学订单用雪花字符串承担这件事。

可操作对象：下面先在第一行输入，再分段翻到另一页。读出第一行当前文本：下标 key 时文字还在；雪花 id 时翻页后第一行是另一条订单自己的草稿。

列表 key：下标或雪花 id分段切换 key 与 page · 在第一行输入
观察要点：① 先在第一行输入草稿，翻页时先不要改字。② 下标作 key 时，两页第一行都用下标 0，第一行当前文本会留在。③ 雪花 id 作 key 时，两页第一行的 key 不同，翻页后第一行当前文本是这一页自己的内容。④ 订单 id 由 snowflakeText 加行号拼成，雪花部分来自课程字符串，不是数字字面量。每页仍按 size 20 理解，这里只显示两行。

6.5 useState，用新对象替换，直接改字段不会重画

问题：代码里改了 stock，界面为什么仍显示 8？

约定：useState 返回当前状态和更新函数。更新函数安排一次新的状态。界面按随后那一次渲染来画。要让订单字段变化出现在界面上，把新对象交给更新函数。直接改原对象的字段，再把同一个引用交回去，这一帧仍用进入这次调用之前的画面。

语义以文档原文为准

useState 与 useEffect 如何比较新旧值、何时跳过渲染、副作用在提交之后的哪一步运行、清理函数相对下一次副作用的次序，以及更新是否合并，都以你所使用版本的 React 文档原文为准。本章只用教学订单页说明常见写法，不把某一小版本的调度写成唯一行为。

var pair = useState({ stock: 8 });
var snapshot = pair[0];
var setSnapshot = pair[1];

function wrong(nextStock) {
  snapshot.stock = nextStock;
  setSnapshot(snapshot);
}

function right(nextStock) {
  setSnapshot({ stock: nextStock });
}

基准算例：教学订单的 stock 是 8。上面的初始状态用这个 8。wrong 把下一个库存写进原对象，再把同一引用交给更新函数，界面仍显示 8。right 交出新对象，下一次渲染才能读到新字段。金额仍以 amountFen 19950 为账，本章不用 199.5 做加减；库存实验也不要把订单库存改成 0，0 是第 3 章输入回退的例子。

原地改 stock

不调用更新函数，或者调用了却仍传入同一个对象，界面都保持原来的 8。字段已经在内存里变过，并不能代替一次新对象替换。

浅层展开留下共享嵌套对象

只复制最外层时，嵌套的列表和详情仍指向同一块对象。一边改嵌套字段，另一边会看见同一次改动。嵌套的订单字段也要换成新对象。

可操作对象：检查每一处会显示出来的订单字段，确认它只通过更新函数进入新对象，初始库存仍是课程数据里的 8。

6.6 同一轮更新会合并

问题：一次点击里连续写了两次状态，界面会渲染几次？

约定：同一次事件处理中的多次更新，通常合并成一次重新渲染。后一次写入的同名字段覆盖前一次。新状态若依赖旧状态，使用更新函数形式，让每一次拿到队列里的前一个值。定时器或 Promise 回调里是否同样合并，随版本和入口变化，以 React 文档原文为准。

function onClick(page, setPage) {
  setPage(page + 1);
  setPage(page + 1);
}

function onClickQueued(setPage) {
  setPage(function (p) { return p + 1; });
  setPage(function (p) { return p + 1; });
}

基准算例：教学订单的 page 从 1 出发。一次点击里若两次都读取这次渲染的 page，两次看到的都是 1，结果停在 2。需要在同一次点击里连续前进时，用函数式更新，每一次接收队列中的前一个页码。同一次点击里同时写下 page 为 2 和「正在加载」，界面按合并后的那一次来画。合并只管状态更新，不管函数体里的请求；请求次数见 6.8。

两次读取同一次渲染的 page

setPage(page + 1) 连写两次，用的是同一次渲染里的 page 1，不能把它当成已经加了两次。页码要连加时，把更新写成函数。

在渲染期间调用更新函数

合并发生在事件处理这类更新入口里。渲染函数执行到一半再去调用更新函数，会再安排渲染。页码和库存的写入放在事件或副作用里。

可操作对象：打开一次翻页点击，数一数里面的更新函数，确认它们应合成同一次界面，并且页码的连加使用函数式更新。

6.7 useEffect、依赖数组、清理函数

问题：请求、订阅和定时器应该挂在组件的哪一段？

约定：useEffect 把副作用安排在这次渲染提交之后。依赖数组列出副作用里用到、并且会变化的值。文档用它规定的比较决定要不要重新执行，比较的措辞以 React 文档原文为准。清理函数在下一次该副作用重新执行之前运行，也在组件卸下时运行，用来取消请求、退订和清除定时器。省略依赖数组，和写上一个空数组，是两种写法：前者按文档在渲染之后核对副作用；后者表示不依赖渲染里的那些值。

useEffect(function () {
  var alive = true;
  request(page, size).then(function (data) {
    if (alive) setList(data);
  });
  return function () { alive = false; };
}, [page, size]);

基准算例：拉订单列表时，依赖里写下 page。页码从 1 变为 2，副作用按新的 page 再请求一次。size 为 20，请求里带着它；size 也会变时，同样放进依赖。清理时放弃尚未写回的结果，离开 /orders 之后不再改库存。课程里的库存事实仍是 8。

依赖里漏掉 page

副作用只在挂载时跑一次，闭包里的 page 停在 1。地址或界面已经是 2，发出的请求仍是 page 1。下一节的演示把这个计数读出来。

清理函数没有卸掉

离开页面后，旧的订阅、定时器或迟到的回调仍调用更新函数，界面上的 stock 会离开 8。每个会写状态的副作用都返回清理函数。

可操作对象：给订单页每个副作用写两列：依赖里有哪些值，清理时取消的是哪一次请求或订阅。

6.8 请求和订阅放副作用

问题：为什么翻页之后请求仍是 page 1，或者每一次渲染都打到订单接口？

约定：请求和订阅是副作用，放在 useEffect 里。渲染函数只根据已经有的状态描述界面。依赖数组包含这次请求真正使用的 page。组件函数每次渲染都会执行，所以写在函数体里的请求会跟着渲染次数增加。订阅库存变化时同样放在副作用里，清理时退订。

基准算例：接口路径用 apiPath，即 /api/orders。查询参数用 page 与 size 20，默认 page 是 1。下面用按钮模拟再渲染一次，读出实际请求的 page 和累计请求次数。依赖含 page 时，翻到 page 2 会再请求一次，单纯再渲染不会加次数。漏掉 page 时，翻页后界面可以是 2，实际请求仍是 1。请求写在渲染里时，再渲染一次，次数就再加一。演示只记账，不访问网络。后返回的旧响应怎样丢掉，留到下一章。

请求写在函数体

函数体里的 request(apiPath) 会在每一次渲染执行。用户只是再渲染了一次，累计请求次数也会增加，重复打到 /api/orders。

空依赖锁住第一次的 page

用空依赖数组让请求「只发一次」，里面却读取会变的 page。那一次请求记住的是挂载时的 page 1，之后的翻页不再发出新请求。

可操作对象：切换三种写法，分段翻 page，再点「再渲染一次」。核对读数里的实际请求 page 和累计请求次数。

请求落在副作用还是渲染分段切换写法与 page · 按钮增加渲染
观察要点：① 依赖含 page：翻到 page 2 时，实际请求的 page 变为 2，累计次数加一；再渲染一次，次数不加。② 漏掉 page：翻到 page 2 后界面 page 是 2，实际请求仍是 1，次数停在挂载那一次。③ 请求写在渲染里：每点一次「再渲染一次」，累计请求次数加一，路径是 apiPath。④ 这里用普通 DOM 记账，没有加载 React，也没有发出网络请求。effect 的时序和清理顺序以 React 文档原文为准。

6.9 路径、参数 page/size、嵌套，路由表不是 Controller

问题：浏览器地址上的订单页，和取数接口各管什么？

约定：前端路由表把路径、参数和嵌套对应到要显示的函数组件。它运行在浏览器里，决定哪一块界面出现。嵌套表示布局组件的子位上再放子页面，子页面仍是组件。页码和每页条数从地址读出，再进入 6.8 的请求依赖。服务端如何接收接口，不在本章展开。

位置教学订单里的值它决定什么
前端 route/orders浏览器里渲染哪一个页面组件
请求 apiPath/api/orders副作用里请求哪一个接口
page 与 size1 与 20地址参数，并写入请求依赖

基准算例：page 为 1，size 为 20，listN 为 10000，Course.orderMath.pageCount() 得到 500。地址可以表达这 500 页中的一页。库存和金额分 19950 由接口负责。页面来源 pageOrigin 是 http://localhost:5173，接口来源 apiOrigin 是 http://localhost:8080，端口不同。路由表选的是组件，不处理这组来源差异。

把路由表写成业务入口

在路由配置里扣库存或计算金额，会把浏览器里的路径表写成业务规则的唯一入口。路径表只选择组件；业务结果来自 /api/orders 的响应。

地址已是下一页，请求仍是 1

只改地址栏或路由状态里的 page，却不把 page 放进副作用依赖。地址可以已经是 2，列表请求仍是 1。路由参数和请求依赖要写在同一条链上。

可操作对象：为 /orders 写一行路由：路径、要渲染的函数组件、从地址读出的 page 与 size，以及副作用里使用的 apiPath。

6.10 状态放哪，Context 只解决传递

问题：草稿、页码和库存各放在哪一层？

约定：只属于这一块界面的状态放在该组件，例如某一行草稿还没提交。两个组件都要读的状态，放到最近的共同父组件。跨页面仍要共享的事实，放外部 store。地址上的 page 以路由为来源，组件读取它，并把它放进请求依赖。Context 把已经决定的值传到深层子组件，省掉一层层手工传递。它不决定这份状态该不该存在，也不承担整表数据。

组件内这一行的草稿、是否展开。刷新后若不必留下，就停在这里。
共同父组件列表和详情都显示的 stock，只留一份，初始为 8。
路由或外部 store页码以地址为来源。跨页面仍要共享的事实放外部 store。
Context传递已经放好的值，例如当前 page。不在 value 里放 10000 条。

基准算例：行内草稿先放列表组件。若刷新后草稿还要在，再写入课程给出的 storageKey，即 order.draft；筛选条件不要顺手放进同一个键。stock 为 8，列表和详情读同一份。整表 listN 为 10000，Context 的 value 里放这 10000 条时，value 一变，消费它的组件都会按文档约定参与更新。

Context 装进整表

Context 解决的是传递。把 10000 条订单放进 value，会让每次列表变化都通知所有消费者。整表放在持有它的那一层，Context 只传页码或当前选中的 id 字符串这类小值。

列表和详情各存一份 stock

两份库存会各自被副作用改写。一边离开 8，另一边仍显示 8。库存只保留一份来源，两边读取它。

可操作对象：给草稿、page、stock 各写一句：谁产生、谁读取、刷新后还要不要，以及它是否只是经 Context 传递。

6.11 组合、受控与非受控、容器与展示、自定义 Hook

问题：订单页怎样拆开，输入框里的值由谁持有？

约定：用组合把页面拼起来：布局组件接收 children，表格接收行和事件。受控输入的 value 与 onChange 指向同一份状态，界面显示的就是那一份。非受控输入使用 defaultValue，提交时再读取 DOM，适合还没成为订单事实的草稿。容器组件持有状态和副作用，展示组件只接收数据和回调。重复的「按 page 请求」可以收进自定义 Hook，名字以 use 开头，里面仍把请求放在副作用、把 page 写进依赖。Hook 的调用位置遵循 React 文档里的规则，精确限制以文档原文为准。

function StockField(props) {
  return renderInput({
    value: props.stock,
    onChange: function (next) { props.onStock(next); }
  });
}

function useOrderList(page) {
  var pair = useState(null);
  var list = pair[0];
  var setList = pair[1];
  useEffect(function () {
    var alive = true;
    request("/api/orders", { page: page, size: 20 }).then(function (data) {
      if (alive) setList(data);
    });
    return function () { alive = false; };
  }, [page]);
  return list;
}

基准算例：件数若表示库存，受控时 value 来自那一份状态，初始显示 8，onChange 写回同一份。展示组件只渲染拿到的行：雪花 id 保持字符串，金额用 Course.orderMath.yuanText(amountFen) 得到 199.50，计算仍用整数分 19950。容器 OrderPage 调用 useOrderList(page)，表格组件只接收 list。请求路径仍是 /api/orders，size 仍是 20。

value 与 onChange 各写一份

value 绑在 stock 这一份，onChange 却写入另一份 draft。界面可以仍显示 8，提交出去的是另一份。受控输入的读和写使用同一份状态。

展示组件里再请求一次

容器的副作用已经按 page 请求过，表格再在函数体或自己的副作用里请求 /api/orders，同一页会打两次。自定义 Hook 可以把请求收走，但调用它的仍是容器，展示组件只画行。

可操作对象：把订单页分成取数的容器和只画表格的展示。请求只出现在容器的副作用或 useOrderList(page) 里，输入框的 value 与 onChange 指向同一份 stock 或同一份草稿。

本章避坑清单

  1. 列表 key 用雪花 id 字符串。用下标时，翻页后第一行输入会留在下一页的第一行。
  2. 更新订单时用新对象替换。直接改 stock 字段，界面仍显示 8。
  3. 请求放在副作用里，依赖数组包含 page。漏掉 page 时，翻页仍请求 page 1。
  4. 请求不要写在组件函数体里，否则每次渲染都会打 /api/orders。
  5. 渲染期间不要读 offsetHeight。写样式和读布局要分开，避免强制同步布局。
  6. Context 只传递已经决定的值，不要把 10000 条订单放进 value。
  7. 受控输入的 value 和 onChange 使用同一份状态。
  8. 离开页面时运行清理函数。没有清理时，离开后仍可能改掉 stock。

本章小结与延伸阅读

函数组件描述教学订单页的一帧。列表 key 使用 snowflakeText 拼成的字符串，下标会让第一行草稿串页。库存要从 8 变成界面上的新值，必须用新对象替换。请求和订阅放在副作用里，依赖包含 page；漏掉 page 时翻页仍请求 1，写在函数体里则每次渲染都打 /api/orders。路由表把 /orders 对应到组件，page 与 size 再进入请求。Context 只传递值。容器取数，展示组件画行，受控输入的读写指向同一份状态。

  • useState、useEffect、列表 key 与 Context 的精确语义，以所用版本的 React 官方文档原文为准。本章不把某一小版本的调度写成唯一行为。
  • 第 2 章给出帧预算 16.7ms 与长任务 50ms；第 3 章给出引用和不可变更新。本章在界面上使用这两件事。
  • 下一章继续同一笔教学订单的样式、请求取消、后到的旧响应和业务 code。把 page 放进依赖，只是把请求放在了正确的位置。
