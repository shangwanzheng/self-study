第 5 章 · 对象与结构

TypeScript：类型在打包后不存在

类型标注、字面量联合和泛型用来在编译前写清教学订单：id 用字符串，金额用整数分，业务 code 能把成功和失败分开。打包进浏览器的是 JavaScript。标注和 as 都不会检查运行时 JSON，缺字段和被数字解析过的雪花 id 要另做校验。

预计学习一段完整专注时间 前置：第 3 章 交互演示 2 个
  • 能给订单 id 用 string、金额用整数分；
  • 能用业务 code 做可辨识联合收窄，并在成功分支取出金额分；
  • 能说明 as 和类型标注都不检查运行时 JSON。

5.1 基础类型、字面量、联合、交叉、可选、只读

问题：教学订单页的字段，怎样在编译前写成可以检查的形状？

约定：Handbook 的 Everyday Types 把 string、number、boolean 称为 primitives。变量上的类型标注叫 type annotation。Literal Types 表示某一个具体的字符串或数字。Union Types 用 | 表示若干类型之一。Object Types 里的 Intersection Types 用 &，表示同时具备两边的成员。Optional Properties 在属性名后写 ?。属性前的 readonly 让类型检查拒绝写入。这些都写在源码里，给编译器看。

基准算例：教学订单的路由字面量是 /orders。业务成功与失败的字面量是 businessCodeOk 与 businessCodeFail，也就是 0 与 40001。金额分 amountFen 是整数 19950。下面这段是类型示意，浏览器不执行它。

type OrderOk = { readonly id: string; amountFen: number; route: "/orders"; }; type Coded = { code: 0 | 40001 }; type Row = OrderOk & Coded; type Draft = { note?: string };
字面量被写成宽类型

把业务 code 标成 number 之后，0 和 40001 以外的数也能通过类型检查。字面量联合只接受这两个课程数据里的 code。

交叉与只读都停在编译期

& 不会在运行时把两段 JSON 合并。readonly 也不会冻结对象。Handbook 说明 readonly 不改变运行时行为，只在类型检查时拒绝赋值。

可操作对象：给教学订单写类型别名时，路由用字面量 "/orders"，业务 code 用 0 | 40001，备注用可选属性。金额字段留到下一节写成整数分。

5.2 订单 id 用 string，金额用整数分

问题：订单 id 和金额，在类型里各该用什么？

约定：雪花 id 的类型标注是 string。金额计算的类型是表示整数分的 number，字段名用 amountFen。展示文本另走 Course.orderMath.yuanText()。类型标注约束的是编译期的赋值，它不改写已经得到的 JSON 值。

基准算例：userIdText 是 10001。Course.orderMath.isSafeId(userIdText) 为真，它在安全整数以内，不能用来演示精度丢失。snowflakeText 是 9007199254740993，isSafeId 为假。jsonNumberRoundTrip(snowflakeText) 得到 snowflakeRoundedText，即 9007199254740992，两者都是字符串。maxSafeText 是 9007199254740991。amountYuan 是 199.5，amountFen 是 19950。yuanText() 得到展示文本 199.50。199.5 这一次转成二进制看不出错，账仍按整数分算。

type OrderMoney = { id: string; amountFen: number; }; // 展示：yuanText(amountFen) → "199.50" // 运算只使用 amountFen，也就是 19950
标注写成 string 就当成运行时也是字符串

源码里写着 id: string，只说明编译器按字符串检查你的 TypeScript。接口若曾把雪花 id 当成 JSON number 解析，运行时留下的是另一串文本。标注不会把它改回去。

用错的数做演示

不用 userId 的 10001 演示精度丢失。不用 199.5 做加减或入账。对外契约写 id: string 与 amountFen: number，展示层再调用 yuanText。

可操作对象：审查订单类型时，确认雪花 id 是 string，金额字段名叫 amountFen，计算式里出现的是 19950 这种整数分。第 5.9 节的演示会把三种 JSON 和这条约定对照。

5.3 typeof、in、可辨识联合（业务 code）

问题：同一次响应里，怎样只在业务成功时取出金额分，而不是在失败分支上也去读？

约定：Handbook 的 Narrowing 把 typeof 检查叫 typeof type guards，把 in 检查叫 The in operator narrowing。可辨识联合的原文是 Discriminated unions：联合里每个成员都有一个共同属性，且该属性是字面量类型时，这个属性叫 discriminant property。手册的例子用字段名 kind。本课的判别属性是业务 code。收窄到没有剩余成员时，类型会变成 never，Exhaustiveness checking 用它检查 switch 是否写全。点到为止即可。

基准算例：businessCodeOk 是 0，这一支有 amountFen，值是 19950，也可以有订单列表 list。businessCodeFail 是 40001，这一支没有金额分，也没有 list。httpOk 是 200。HTTP 200 且业务 code 不是 0，仍然是失败。判别属性用业务 code，不用 HTTP 状态码。

type OrderOk = { code: 0; amountFen: number; list: string[] }; type OrderFail = { code: 40001 }; type OrderResult = OrderOk | OrderFail; function readFen(body: OrderResult): number | undefined { if (body.code === 0) return body.amountFen; return undefined; }

typeof body.amountFen === "number" 和 "amountFen" in body 都能帮助收窄。Handbook 提醒 typeof null 的结果是 "object"，所以不要用 typeof 判断“字段缺了没有”。失败分支上直接写 body.list 或 body.amountFen，在可辨识联合里应被类型检查拒绝。

联合不收窄就读 list

成功成员才有 list 和 amountFen。在 code 收窄之前读取，失败成员上并没有这些字段。先看判别属性，再读金额或列表。

用可选属性代替判别属性

把 amountFen 写成可选，表达不出“code 为 0 才有金额”。Narrowing 一章写明：在 strictNullChecks 之外，可选属性在读取时会被当成一定存在。可辨识联合把 code 分成 0 与 40001 两个成员，成功分支才露出 amountFen。

可操作对象：下面切换业务 code。成功值取自 businessCodeOk，失败值取自 businessCodeFail。读出这一支能否取出金额分。

业务 code 收窄切换 code
观察要点：① businessCodeOk 这一支能取出金额分，数值是订单的 amountFen（19950）。② businessCodeFail 这一支取不出金额分。③ 两段响应的 HTTP 状态都可以是 httpOk（200）；能否取金额只看业务 code 收窄后的那一支。

5.4 泛型函数与约束

问题：读取金额分的函数要能复用，又不能让任意 JSON 混进来。

约定：Handbook 的 Generics 把带类型参数的函数称为 Generic Functions。Generic Constraints 用 extends 写上类型参数必须具备的字段。约束发生在编译期。它不是运行时的 instanceof，也不会解析 JSON。

基准算例：约束要求有 amountFen: number。把教学订单交进去，函数读到的就是 order.amountFen，即 19950。不要另造一个金额。没有 amountFen 的失败响应不满足约束，不能调用这个函数。

function readFen<T extends { amountFen: number }>(row: T): number { return row.amountFen; } // readFen(教学订单) → 19950
泛型不写约束

类型参数放空、或写成能接受 any 时，失败 JSON 也能被拿去读 amountFen。约束要写明整数分字段，调用点才保留订单的形状。

把 extends 当成运行时判断

extends { amountFen: number } 不会在浏览器里检查响应缺了字段没有。缺 amountFen 的 JSON 要由第 5.9 节的运行时校验拒绝，不能靠泛型约束代替。

可操作对象：写读取金额的泛型函数时，把约束写成 T extends { amountFen: number }，返回值直接是这个整数分。列表、分页参数不要塞进这个约束。

5.5 tsconfig 与 strict

问题：可选字段可能缺失时，谁在编译期要求你先判断？

约定：项目配置文件名是 tsconfig.json，开关放在 compilerOptions。TSConfig Reference 的菜单原文是 Type Checking。总开关名是 strict。文档原文：The strict flag enables a wide range of type checking behavior that results in stronger guarantees of program correctness. Turning this on is equivalent to enabling all of the strict mode family options. 该页同时说明，以后的 TypeScript 还可能在这个旗标下加入更严的检查。strict mode family 里、文档 Default 写明 true if strict；false otherwise 的开关有：alwaysStrict、noImplicitThis、strictBindCallApply、strictBuiltinIteratorReturn、strictFunctionTypes、strictNullChecks、strictPropertyInitialization、useUnknownInCatchVariables。noImplicitAny 也在 Type Checking 菜单中，并随 strict 打开。exactOptionalPropertyTypes 同样在这个菜单里，但不随 strict 打开。

基准算例：订单备注若写成 note?: string，在 strictNullChecks 打开时，读取前要处理可能的 undefined。金额分不是可选字段：响应里就应该有 amountFen，值是 19950。用关掉 strict 的办法让“缺金额”不再报错，教学订单的字段约定会被一起放行。

菜单原文开关原文和 strict 的关系
Type Checkingstrict打开整个 strict mode family。
Type CheckingstrictNullChecks随 strict 打开。null 与 undefined 各自成类。
Type CheckingnoImplicitAny随 strict 打开。推断失败时不许静默变成 any。
Type CheckingalwaysStrict随 strict 打开。按 ECMAScript strict mode 解析，并输出 "use strict"。
Type CheckingexactOptionalPropertyTypes不随 strict 打开。不能拿它的名字代替 strict。
没开 strict 时可选字段被当成一定有

strict 关闭则 strictNullChecks 不为 true。TSConfig 对 strictNullChecks 的说明是：此时 null 与 undefined 会被语言忽略。Narrowing 一章写明，在 strictNullChecks 之外，可选属性在读取时会被当成一定存在。

关掉 strict 消掉字段报错

缺 amountFen、把订单响应标成 any，都应保留报错并改类型或补运行时校验。不要把 strict 设为 false，也不要单独关掉 strictNullChecks 来换一个能编译的订单页。

可操作对象：打开 tsconfig.json，确认 Type Checking 的 strict 为 true。订单字段报错时，改标注或补校验，保持 strict mode family 开着。

5.6 路径别名、.d.ts、类型随依赖来

问题：导入路径的简写，以及依赖带来的类型，各自落在哪个开关上？它们会不会检查订单 JSON？

约定：路径映射在 TSConfig Reference 的菜单 Modules 里，开关名是 paths。文档原文：A series of entries which re-map imports to lookup locations relative to the baseUrl if set, or to the tsconfig file itself otherwise. 同一菜单里的 baseUrl 文档写明：它为配合 AMD module loaders 而设计，在其他场合不推荐；自 TypeScript 4.1 起，使用 paths 不再必须设置 baseUrl。声明文件的手册章节叫 Declaration Files，文件是 .d.ts。生成开关在菜单 Emit，名字是 declaration，文档说明它为项目中的 TypeScript 或 JavaScript 文件生成 .d.ts，用来描述模块的外部 API。同菜单还有 declarationDir、declarationMap、emitDeclarationOnly。哪些声明包进入全局作用域，看 Modules 里的 types 与 typeRoots。指定 types 时，只有列出的包进入全局作用域；文档用 import moment 的例子说明，这不影响你在代码里导入的模块如何带上类型。types 的默认值以当前 TSConfig Reference 该条目为准，文档区分了 TypeScript 6.0 之前的行为。

基准算例：订单页可以写 import { readFen } from "app/order"，由 paths 告诉 TypeScript 到哪份源码找类型。依赖若在 package.json 用 types（或 typings）指向声明入口，类型随这份依赖而来；没有自带声明时，再查找 @types 包。无论哪一种，.d.ts 里都是 declare 和类型，没有对 snowflakeText 与 amountFen 的运行时比较。

{ "compilerOptions": { "strict": true, "paths": { "app/*": ["./src/*"] }, "declaration": true } }
把 .d.ts 当成校验器

声明文件给编辑器和 tsc 看。Emit 出的 .d.ts 不会在浏览器里拒绝缺 amountFen 的 JSON，也不会把已经被数字解析过的 id 改回 snowflakeText。

路径别名只改 tsconfig

paths 的文档原文：this feature does not change how import paths are emitted by tsc，所以只应用来告诉 TypeScript：另一个工具在运行时或打包时会使用这套映射。只改 tsconfig.json 的 paths，打包器仍按它自己的配置解析 app/*。

可操作对象：改订单模块的导入前缀时，同时改 Modules 的 paths 和打包器里的同一映射。看依赖时读 package.json 的 types，再看 types 与 typeRoots。订单 JSON 的对错仍交给运行时校验。

5.7 类型在打包后不存在

问题：浏览器执行教学订单页时，还能看到 id: string 吗？

约定：类型标注、接口、泛型约束、as 和 .d.ts 都在编译和打包时被擦掉。浏览器收到的是 JavaScript 值。JSON.parse 的结果是当时文本里的值，不读取源码里的标注。

基准算例：源码可以把雪花 id 标成 string，值是 9007199254740993。打包后的脚本只剩下这个字符串值，没有 : string。若这串文本事先经过 jsonNumberRoundTrip，运行时的 id 是 9007199254740992，标注不会跟着改变。amountFen 的类型同样不会在浏览器里核对是不是 19950。

// 源码 const id: string = "9007199254740993"; // 打包后的脚本 const id = "9007199254740993";
源码里的 string 被当成浏览器里的检查

看到标注写着 string，只说明编译那一次按字符串检查过源码。页面上的响应是后来的 JSON。标注不会留在包里继续核对 id。

密钥写成 string 再打进包

课程数据里的 secretName 是 ORDER_API_SECRET，只是名字，不是密钥值。把它标成 string 不会阻止构建把值写进前端包，打包后这个类型也不存在。名字可以出现在文档里，值不能进入订单页的脚本。

可操作对象：读打包产物时，确认订单脚本里没有类型标注，也没有 ORDER_API_SECRET 的值。id 与金额是否可信，用下一节的断言边界和 5.9 的校验判断。

5.8 as 不检查运行时数据

问题：响应已经是 JSON.parse 的结果时，as 会替你检查订单形状吗？

约定：Everyday Types 的 Type Assertions 使用 as。文档原文：Like a type annotation, type assertions are removed by the compiler and won’t affect the runtime behavior of your code. 同节还写明：Because type assertions are removed at compile-time, there is no runtime checking associated with a type assertion. There won’t be an exception or null generated if the type assertion is wrong. .tsx 以外还可以用尖括号断言，作用相同。类型之间重叠不够时，编译器会拒绝直接断言；经由 any 或 unknown 的两次断言能绕过这道编译期限制，运行时仍然不检查。

基准算例：把一段 JSON 断言成订单，不会让 id 等于 snowflakeText，也不会补上 amountFen 的 19950。断言错误时不会抛异常，也不会自动变成 null。非空断言 ! 同样只存在于编译期，不能用来证明可选的金额字段一定有值。

const body = JSON.parse(text) as { id: string; amountFen: number; }; // 编译器此后按订单使用 body // 浏览器仍拿到 parse 出来的那个值
as 把任意 JSON 当成订单

断言之后，类型检查会允许读取 amountFen。若这段 JSON 的 id 已是数字往返后的字符串，或根本没有 amountFen，as 不会报错，也不会改值。

两次断言绕过重叠检查

先 as any（或 as unknown）再 as 成订单，只是让编译器停止比较两边是否重叠。运行时数据保持原样。订单响应用 5.9 的比较函数接受或拒绝。

可操作对象：代码评审里看到 as 订单类型时，旁边应有运行时校验。校验不看标注，只看值。

5.9 接口响应要有运行时校验

问题：类型在包里已经不存在，页面怎样决定接受这段订单 JSON？

约定：运行时校验读取解析后的值。本课的接受条件是两条同时成立：id === snowflakeText，并且 amountFen === order.amountFen。类型标注保持 id: string，三段 JSON 都如此。标注不参与这个条件。

基准算例：第一段的 id 是 snowflakeText（9007199254740993），amountFen 是 19950，校验通过。第二段的 id 是 Course.orderMath.jsonNumberRoundTrip(snowflakeText) 的字符串，表示它曾被当成 JSON number 解析，结果与 snowflakeText 不同，校验不通过。第三段没有 amountFen，第二条不成立，校验不通过。三段的类型标注都仍写着 string。

只核对标注或只核对一半

标注一直是 string，不能当作校验结果。只比较 id、不比较 amountFen，缺金额的响应会被收下。两条都要成立。

用 HTTP 200 代替字段校验

httpOk 是 200。状态码说明 HTTP 这一层完成了，不说明 id 仍是雪花原文，也不说明金额分仍是 19950。字段校验和业务 code 收窄各看各的值。

可操作对象：切换三种 JSON。读出类型标注是否仍写着 string，以及运行时校验是否通过。

三种订单 JSON切换响应
观察要点：① 三种分段的类型标注都仍写着 string。② 运行时校验通过，仅当 id 等于 snowflakeText 且 amountFen 等于订单的 amountFen。③ 第二段的 id 来自 jsonNumberRoundTrip，表示曾被当成 JSON number 解析，已不是雪花原文。④ 缺 amountFen 时校验不通过，标注不会补上 19950。

5.10 和「类型留在字节码里」只做一句对照

问题：读到姊妹课那句「类型留在字节码里」时，这一章要记住的边界是哪一句？

约定：只对照一句：Java 服务课说类型留在字节码里；这一章的 TypeScript 类型在打包后不存在。

基准算例：仍是同一笔教学订单。浏览器里的脚本没有 id 的 string 检查，也没有 amountFen 的类型检查。接受响应的条件仍是 5.9 的两条：id 等于 snowflakeText，且 amountFen 等于订单的 amountFen（19950）。

用对照句推断浏览器还会复查类型

这句只划定边界。订单页是否收下 JSON，看运行时比较的结果，也看业务 code 能否收窄到金额分。

对照句代替校验

记住这一句之后，回到 5.9 的演示：类型标注仍写着 string，校验另算。id 与整数分的约定不因这句对照而改变。

可操作对象：以后同时读两门课时，前端订单只追问三件事：id 是不是字符串字段，金额是不是整数分，响应用业务 code 收窄之后有没有再做运行时校验。

本章避坑清单

  1. 不用 userId 的 10001 演示精度丢失；雪花 id 的类型用 string。
  2. 金额运算用整数分 19950；199.50 只是 yuanText 的展示文本。
  3. 联合先按业务 code 收窄，再读 amountFen 或 list。
  4. 保持 strict 打开。可选字段在没开 strictNullChecks 时会被当成一定有；不要靠关掉 strict 消掉缺字段报错。
  5. paths 不改变 tsc 发出的导入路径；打包器要有同一套映射。baseUrl 不是使用 paths 的前提。
  6. .d.ts 与 as 都不是运行时校验器。类型标注写成 string，不保证运行时 id 仍是 snowflakeText。
  7. 接受订单 JSON 的条件是 id 等于 snowflakeText，且 amountFen 等于订单的 amountFen。
  8. ORDER_API_SECRET 只是名字。不要把它的值写进前端包。
