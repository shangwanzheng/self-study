7.1 盒模型、层叠、继承与选择器优先级

问题：一行的宽度，算到边框还是只算内容？

约定：盒模型从内到外是 content、padding、border、margin。教学订单页按 border-box 理解指定宽度：padding 和 border 含在这个宽度里面。层叠解决同一元素上多条声明谁生效：优先级高的胜出；优先级相同，后出现的胜出。继承只传递颜色、字号这类属性，宽度和边距不继承。选择器优先级从高到低是内联样式、id、类（含属性选择器和伪类）、元素（含伪元素）。!important 会打断这套比较，业务样式少用。

border 与 padding
content · 一条订单

虚线外的留白是 margin。最里面是 content。

基准算例：一页订单的行数是基准 size（20）。当前页参数是基准 page（1）。盒模型和层叠只决定这一行怎么画，不改请求里的 page 和 size。

后写的元素选择器盖住类

类选择器的优先级高于元素选择器。一条写在后面的 div { } 盖不住写在前面的类。用 content-box 量宽度时，padding 会加在指定宽度之外，行和滚动区域对不齐。

先比优先级，再看顺序

业务样式写在类上。一条声明没生效时，先看是不是被更高优先级划掉，再看同优先级里谁写在后面。

可操作对象：选中列表中的一行，读出 content、padding、border、margin，并指出被划掉的那条声明输在优先级还是输在顺序。

7.2 flex 与 grid：一页 size 行

问题：筛选条横着排、列表竖着排，各用哪种布局？

约定：flex 沿一条主轴分配空间，适合筛选条、一行里的操作按钮。grid 同时划分行和列，适合订单表。一页的行数用基准 size，列用轨道描述，换行后各列仍对齐。

基准算例：基准 page 为 1，size 为 20。翻到下一页时，请求参数里的 page 改变，布局仍是一页 size 行。grid 不负责发请求。

用浮动挤一页列表

浮动离开正常流之后，操作列会在换行时错位。一页 20 行的订单表用 grid 的列轨道对齐。

布局行数和请求各写一个 size

画面上的行数和请求参数 size 都用基准 size。翻页只改 page。

可操作对象：筛选条用 flex，订单表用 grid。对照请求：page 是当前页，size 是一页行数。

7.3 定位

问题：校验提示为什么会跑到页面角落？

约定：static 留在正常流里。relative 相对自己的位置偏移，原来的位置仍占着。absolute 相对最近的、定位不是 static 的祖先。fixed 相对视口。sticky 在滚动容器里粘住。层叠比较发生在定位元素之间；一个新的层叠上下文会把内部的比较圈在内部。

当前页的单元格 校验提示 · absolute

基准算例：提示盖住的是当前这一次列表：page 为 1，一页 size 为 20 行。定位不新发请求，也不改这两个参数。

祖先都是 static

单元格没有形成包含块时，absolute 的提示会相对更外层的包含块定位，看起来像跑到页面角落。

用很大的层叠值压全站

给单元格 position: relative，提示用 absolute，遮罩的层叠留在这一层内部解决。

可操作对象：为订单单元格建立包含块，再把这一格的校验提示放进这个包含块。

7.4 Less、CSS Modules 与全局样式互盖

问题：订单页和组件库都写了同名类，谁盖住谁？

约定：Less 提供变量、嵌套和运算，编译之后仍是普通 CSS，类名默认是全局的。全局样式会互相盖：后进入页面的样式表可以盖住先进入的组件库。CSS Modules 在构建时把局部类名改写成只在当前模块生效的类。要改一处颜色，优先改变量；要改一块订单区域，把类放进模块。

基准算例：样式无论是否隔离，列表请求的参数仍是 page 与 size。全局类名盖住组件库时，变的是控件外观，页码仍是基准 page。

全局类名盖住组件库

一条全局的按钮或表格类会打到组件库控件上，别的页面一起变。Less 嵌套编译出来的仍是全局选择器。

用嵌套代替模块边界

订单列表的类放进 CSS Modules。全局只保留重置和设计变量。组件库的外观改动走下一节的覆盖层次。

可操作对象：指出订单页里哪些类是局部的，哪些选择器编译后仍是全局的，会不会盖到组件库。

7.5 组件库：覆盖层次，不重写基础控件

问题：筛选和表格要自己再做一套输入框吗？

约定：表单和表格用组件库的现成控件。覆盖按层次走：设计变量，组件提供的状态和类名，最后才是当前页面模块里的局部覆盖。业务页不重写一套输入框。基础控件的焦点、键盘和禁用状态留在组件库里。

基准算例：组件库表格展示的一页仍是 size 行，分页控件提交的参数仍是 page 与 size。换一套自己写的输入框不会改变这两个参数，只会拆掉组件库已经做好的行为。

业务页重写一套输入框

订单页再做一套输入、校验和表格，焦点和禁用会和组件库不一致，全局类名也更容易互相盖。

用标签选择器压组件库

间距和颜色用设计变量或订单页模块里的局部类。具体类名以所用组件库的文档原文为准。

可操作对象：筛选表单和订单表格直接用组件库。只在订单页这一块覆盖间距，并检查别的页面没有一起变。

7.6 请求体、超时与取消

问题：翻页请求最多等多少毫秒？离开页面后，这次响应还能改列表吗？

约定：fetch 和 axios 都可以请求订单列表。查询参数使用 page 与 size。浏览器侧等待上限是基准 browserTimeoutMs（3000 毫秒）。到点要取消：fetch 使用 AbortController 或等价的中止信号；axios 同时配置超时和取消。取消方式的字段名以各自文档原文为准。已经取消的响应不写入列表。

基准算例：等待上限只取 browserTimeoutMs。页面所在源是 pageOrigin（http://localhost:5173），接口所在源是 apiOrigin（http://localhost:8080）。超时数值不从这两个地址里读。

超时到了却不取消，旧响应仍回来

界面停止转动，请求仍在路上。响应稍后到达时，会按过期的 page 改写列表。

取消和丢弃是同一道门

翻页、超时和离开页面都中止上一次列表请求。清理函数里执行取消。若响应仍然到达，按下一节判断它是不是最后一次发出的那次。

可操作对象：为列表请求准备中止信号，把等待上限设为 browserTimeoutMs，并在第 6 章的清理函数里调用取消。

7.7 后到的旧响应丢掉

问题：先请求第 2 页、再请求第 1 页，后到的第 2 页还要显示吗？

约定：只保留最后一次发出的那次请求。本场景最后一次发出的是 page=1，也就是基准 page。page=2 只是先发出的那次请求参数，不另起一个 page 常量。后到的 page=2 丢掉。谁先回到浏览器，不改变这条规则。地址栏已经是 page=1 时，列表保持这一页。

基准算例：基准 page 为 1，size 为 20。发出顺序固定为先 page=2，再 page=1。两种到达顺序下，列表应显示的 page 都是 1，被丢弃的 page 都是 2。

旧响应把地址栏 page=1 的列表盖成第 2 页

后返回的响应当成更新的真相时，地址栏仍是 page=1，表格却画出第 2 页。

用到达顺序覆盖列表

响应进入页面前，先对上最后一次发出的 page。对不上就丢弃。超时后的取消和这里一起用：不该生效的响应不能写进列表。

可操作对象：切换谁先回来，读出列表应显示的 page，以及被丢弃的 page。

两次请求谁先返回切换到达顺序
观察要点：① 默认先发出 page=2，再发出 page=1。② 只保留最后一次发出的那次，列表应显示的 page 是基准 page。③ 选「第 2 页先回来」或「第 1 页先回来」，被丢弃的 page 都是 2。④ 到达顺序不能把地址栏 page=1 的列表盖成第 2 页。

7.8 拦截器、业务 code 与两层缓存

问题：HTTP 已经是 200，列表就可以更新了吗？

约定：拦截器统一加上请求头，并作为失败提示的出口。HTTP 状态码与业务 code 分开看。状态为 httpOk（200）且业务 code 为 businessCodeOk（0）时，才更新列表。状态仍是 httpOk、业务 code 为 businessCodeFail（40001）时，给出失败提示，列表保持上一次成功的结果。两层缓存分开：接口列表留在页面内存里，按这一次的 page 与 size 使用；浏览器对入口 html 和构建出的 js、css 的 HTTP 缓存是另一层。两层各写各的失效。

HTTP 状态业务 code列表
httpOk · 200businessCodeOk · 0更新为这一次的 page、size
httpOk · 200businessCodeFail · 40001不更新，走失败提示

基准算例：三个数一起用：httpOk、businessCodeOk、businessCodeFail。只看到 200 还不能更新。内存里的列表键是 page 与 size；它到期或翻页时重新请求。html 和 js 的 HTTP 缓存不由业务 code 清除。

HTTP 200 且 code 40001 仍更新列表

200 只说明 HTTP 这一层完成。40001 是业务失败。把失败体写进表格，页面会留下一份不该展示的订单数据。

两层缓存写成同一条失效

成功之后才更新内存里的列表。静态资源的 HTTP 缓存留在构建和发布那一层处理，不跟业务 code 绑在一起。

可操作对象：为一次列表响应写下四格：HTTP 状态、业务 code、是否更新列表、提示是否出现。再写一句：这份列表在内存，html 与 js 在 HTTP 缓存。

7.9 跨域、预检与凭据

问题：页面和接口端口不同，浏览器为什么会拦住？Cookie 会自动带上吗？

约定：跨域拦截由浏览器执行。页面源 pageOrigin 是 http://localhost:5173，接口源 apiOrigin 是 http://localhost:8080，端口不同，就是不同源。方法、头和正文类型都落在浏览器规定的简单集合里，才是简单请求；超出集合时浏览器先发预检。集合的边界以浏览器文档原文为准。自定义请求头会让订单请求先走预检。凭据 Cookie 的名字是基准 cookieName（sid）。跨源默认不带上它。客户端打开 withCredentials（fetch 里对应携带凭据的模式）之后，服务端还要允许凭据，并回显具体来源。

页面pageOrigin
http://localhost:5173
接口apiOrigin
http://localhost:8080
凭据cookieName
sid

基准算例：从 pageOrigin 上的订单页请求 apiOrigin 的列表，参数仍是 page 与 size。预检没有通过时，响应里还没有业务 code。cookieName 只标识这份会话凭据；secretName（ORDER_API_SECRET）不放进 Cookie，也不进前端包。

端口不同仍当成同源

5173 与 8080 是两个源。浏览器会做跨域检查。服务端程序自己去调 HTTP 时不走这套浏览器规则；本章的调用方是浏览器。

withCredentials 开了服务端未允许凭据

只在客户端打开凭据，浏览器仍会丢掉响应。预检失败时先看允许来源和凭据，而不是先看 businessCodeFail。

可操作对象：先确认发起者是浏览器，再对照 pageOrigin 与 apiOrigin，然后看这次是简单请求还是预检，最后看 cookieName 是否被服务端允许。

7.10 package.json、lock 与语义化版本

问题：依赖写在 package.json 的哪一段？不提交 lock 会装到哪一版？

约定：package.json 记下脚本和依赖声明。dependencies 放运行订单页需要的包，devDependencies 放转译、构建和检查用的包。语义化版本按主版本、次版本、修订版本理解。lock 锁住整棵依赖树已经解析好的版本。lock 开，装到的版本是 semverLocked（1.4.2）。lock 关，同一条允许更新的声明可能装到 semverUnlocked（1.5.0）。lock 文件的具体名字以仓库所用的包管理器为准。

lock装到的版本基准名
开1.4.2semverLocked
关1.5.0semverUnlocked

基准算例：本章只比较这两个版本。1.4.2 是锁住的结果，1.5.0 是不锁时可能装到的结果。不另造第三个版本号。

没交 lock 装到 1.5.0

package.json 里的范围声明可以在以后的安装中解析到 semverUnlocked。没有 lock 时，两台机器或两次安装不必得到 1.4.2。

只改声明不更新 lock

lock 和 package.json 一起提交。要升级时，让安装器改写 lock，再提交这份锁住的结果。

可操作对象：切换 lock 开或关，读出装到的版本是 semverLocked 还是 semverUnlocked。

lock 开或关切换 lock
观察要点：① lock 开，装到的版本是 semverLocked，也就是 1.4.2。② lock 关，装到的版本可以是 semverUnlocked，也就是 1.5.0。③ 运行页面的包在 dependencies，构建和检查用的包在 devDependencies。④ 版本只取这两个基准，不另造一版。

7.11 入口、转译与两种交付

问题：生产环境打开的是源码，还是已经生成的文件？

约定：构建从入口开始。转译把 TypeScript 和 JSX 变成浏览器能执行的脚本；类型留在检查阶段，不留在产物里。loader（或工具里等价的转换）处理 Less 和 CSS Modules。开发服务器按请求现给转换后的文件。生产构建的结果是静态产物：html、js、css。浏览器运行的是产物。工具的配置键以该构建工具的文档原文为准。

基准算例：开发时页面源是 pageOrigin（http://localhost:5173），接口仍是 apiOrigin（http://localhost:8080）。构建不改变 page 与 size 的含义。产物里的列表请求仍要判断 httpOk 和业务 code。内存里的接口数据和这些静态文件的 HTTP 缓存仍是两层。

开发服务器能开就当成生产

开发服务器现给转换后的模块。生产环境交付的是已经生成的静态文件，不会在用户打开时再去转译源码。

用源码类型代替产物

用生产构建核对局部类名是否还在、公开的接口基址是否写对。业务 code 的判断写在运行时，因为类型不会留在产物里。

可操作对象：分开看两样东西：开发服务器正在提供的页面，以及生产目录里的 html、js、css。

7.12 构建期环境变量与密钥

问题：多个环境的接口地址放在哪？密钥能跟着包发布吗？

约定：构建期环境变量在打包时写进产物，用来区分多环境可以公开的配置，例如接口基址。写进产物的字符串，打开页面的人都能看到。密钥不能进前端包。secretName 只是名字，值也不能放进构建变量。多环境替换的是可以公开的 api 基址；需要密钥的调用留在服务端。

基准算例：教学环境的页面是 pageOrigin（http://localhost:5173），接口是 apiOrigin（http://localhost:8080）。secretName 为 ORDER_API_SECRET。在产物里搜索这个名字，对应的秘密不应出现。cookieName（sid）是会话凭据的名字，不能用来代替这份密钥。

ORDER_API_SECRET 写进构建变量

构建变量会进入前端包。类型写成字符串，只说明源码里有个类型，不表示打包之后它是秘密。

密钥不能进前端包

前端包只带可以公开的 api 基址。ORDER_API_SECRET 留在服务端。换环境时替换基址，不把密钥再打进一份新包。

可操作对象：列出会进包的变量：接口基址可以有。再列出不能进包的名字：secretName。用生产产物搜一遍这个名字。

本章避坑清单

  1. HTTP 200 且 code 40001 仍是失败，不能据此更新列表。
  2. 后到的旧响应不能把地址栏 page=1 的列表盖成第 2 页。
  3. 全局类名会互相盖，也能盖住组件库。
  4. 没交 lock，可能装到 1.5.0；lock 锁住的是 1.4.2。
  5. 超时到了却不取消，旧响应仍会回来。
  6. withCredentials 开了，服务端未允许凭据时，浏览器仍不把响应交给页面。
  7. ORDER_API_SECRET 不能写进构建变量，也不能进前端包。
  8. 业务页不重写一套输入框；表单和表格用组件库，按层次覆盖。
