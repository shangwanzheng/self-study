第 4 章 · 对象与结构

异步、模块与页面上的结构

教学订单页要等接口把金额分交出来，也要把这一份事实放进唯一的模块，把菜单和列表放进合适的结构。这一章用同一笔订单看回调、Promise、打包前的文件边界，以及数据量从一页 20 条到整表 10000 条时的数量级。

预计学习 90 分钟 前置：第 3 章 交互演示 2 个
  • 能说出漏写 await 时拿到的是 Promise，而不是 amountFen。
  • 能说出 Promise.all 出现拒绝时要接住。
  • 能用 compareCost 比较 size 为 20 与 listN 为 10000 的线性与 \(n \log_2 n\)，并说明渲染路径不要整表重算。

4.1 回调

问题：点击订单列表之后，金额分 19950 不会在下一行立刻出现。谁在结果回来时接着干活？

约定：回调是稍后被调用的函数。成功回调接收已经到达的金额分；失败回调接收失败原因。请求的路径是 apiPath（/api/orders），页面路径是 route（/orders）。业务成功的 code 是 businessCodeOk（0），业务失败的 code 是 businessCodeFail（40001）。HTTP 状态 200 且业务 code 为 40001，仍然是失败。

基准算例：加载这一笔订单时，成功回调应收到 amountFen 19950，库存仍是 stock 8。失败回调要能看见业务 code 40001，也要能看见传输没有完成。展示用的 199.50 来自 Course.orderMath.yuanText()，回调参数仍用整数分。

loadAmount(function onOk(amountFen) {
  // 成功出口：amountFen 为 19950
}, function onFail(reason) {
  // 失败出口：业务 code 40001，或传输没有完成
});
只留成功回调

只写拿到 19950 的函数时，业务 code 40001 和传输失败都没有出口。页面会停在旧列表上，调用方还以为请求还没结束。

回调里再嵌请求

在成功回调里再请求库存，又在库存回调里再请求金额，失败要从最内层一层层传出来。库存那一层漏掉失败回调时，外层永远等不到 19950，也等不到失败说明。

可操作对象：为金额分写出两个具名函数：成功函数的参数应是 19950，失败函数能分开业务 code 40001 和传输失败。不要把第二次请求写进第一个成功函数的内部。

4.2 Promise 三种状态

问题：回调把成功和失败拆在两个函数里。怎样用一个对象同时记住「还在等、已经兑现、已经拒绝」？

约定：Promise 有三种状态：pending（进行中）、fulfilled（已兑现）、rejected（已拒绝）。兑现和拒绝都叫落定。落定之后状态不再改变。then 走兑现，catch 走拒绝。继续执行排在微任务里，顺序在第 2 章已经排过；本章关心这个对象里装的是什么。

pending请求已发出，页面还在浏览器超时 browserTimeoutMs（3000 毫秒）之内等待。此时还没有 19950。
fulfilled传输完成，并且你把这份响应当成成功。兑现值里可以读到金额分 19950。业务 code 必须是 0。
rejected超时、网络失败，或客户端把失败转成拒绝。拒绝原因要有人接住。

基准算例：页面上这一等，用的是浏览器超时 3000 毫秒。连接超时 500 毫秒和读取超时 2000 毫秒是另外两个数，不要并成一个「网络超时」。HTTP 200 且 body 里的 code 为 40001 时，响应已经到了，这是业务失败：要么在兑现后的函数里检查 code，要么由客户端把它转成拒绝。两种写法都要有人处理，不能把它当成仍在 pending。

把业务失败当成还在等待

HTTP 200 且 code 为 40001 时，Promise 可能已经兑现，只是兑现值里的业务 code 不是 0。若只判断「有没有抛错」，列表会被这份失败响应更新。

落定之后还等它变回去

已经兑现为 19950 的 Promise 不会再变成拒绝，也不会回到 pending。要表达新的一次请求，就创建新的 Promise，而不是对旧的那一个再等一次。

可操作对象：拿一次 /api/orders 请求标三行证据：还在 3000 毫秒内等待；已经能读到金额分 19950 且业务 code 为 0；拒绝已经被 catch 接住，或兑现值里的 code 40001 已经被分支处理。

4.3 async/await 与漏写 await

问题：写成 await 之后，下一行拿到的到底是金额分，还是仍要等待的对象？

约定：async 函数一定返回 Promise。await 暂停这个函数，直到被等的 Promise 落定，然后把兑现值交给下一行。漏写 await 时，这一行的变量里就是那个 Promise 本身。async 函数的调用处如果再漏一次 await，调用方手里同样是 Promise。

基准算例：loadOrder() 兑现为带 amountFen 的对象，金额分是 19950。写了 await 时，got.amountFen 为 19950。漏写 await 时，got 是 Promise，got.amountFen 读不到 19950。展示字符串 199.50 只来自 yuanText()，不是这一行的返回值。

async function readAmount() {
  const got = await loadOrder();
  const amountFen = got.amountFen;
  return amountFen;
}
漏写 await 后去读 amountFen

把 await 去掉之后，got 是 Promise。对它读 amountFen 得不到 19950。后面的加法、列表渲染和分支都会拿着这个 Promise 继续跑。

调用处再漏一次

函数内部写了 await，调用方写 const got = readAmount() 时，got 仍是 Promise。async 函数的返回值要在调用处再 await，或交给 then，下一行才能使用 19950。

可操作对象：切换下面的分段。写了 await 时，读出应是金额分 19950；漏写时，读出应是 Promise。

写了 await 与漏写 await切换分段
观察要点：① 写了 await，兑现后拿到的是 amountFen，读出 19950。② 漏写 await，这一行拿到的是 Promise，读不到 19950。③ 展示用的 199.50 来自 yuanText，不是这一行的返回值。④ 函数内部写了 await 时，调用 async 函数的地方仍要再 await 一次。

4.4 Promise.all 与拒绝要接住

问题：列表、库存和金额分要一起到齐才画页面。其中一条失败时，整组结果怎样交出来？

约定：Promise.all 接收一组 Promise。全部兑现时，它兑现为一个数组，顺序与传入顺序相同。任意一条拒绝，all 返回的那一个 Promise 就拒绝，then 不会执行。拒绝要写 catch，或在 async 函数里用 try/catch 接住。没人接住的拒绝是未处理拒绝。

基准算例：三条分别是：列表（page 1、size 20）、库存（stock 8）、金额分（amountFen 19950）。三条都兑现，then 里才能更新列表。库存这一条拒绝时，all 拒绝，金额分即使已经准备好也不会进入 then。页面应留下失败说明，而不是一直空白。

Promise.all([loadList(page, size), loadStock(), loadAmount()])
  .then(function (parts) {
    // 三条都兑现才到这里；金额分在兑现值里
  })
  .catch(function () {
    // 任意一条拒绝都到这里，要给出失败说明
  });
一条拒绝整页空白

库存请求拒绝、又没有 catch 时，then 不跑，列表区域没有新数据，控制台留下未处理拒绝。看起来像整页空白，其实是拒绝没有人接。

只写 then

成功分支里直接画 19950 和库存 8，失败分支不存在。业务 code 40001 若被转成拒绝，用户看不到失败说明。若三条需要分别保留成败，再查 Promise.allSettled；本章的订单页在三条都成功时才更新列表，用 all 并把拒绝接住即可。

可操作对象：写出 Promise.all 的 then 和 catch。catch 里至少放一句失败说明。确认库存拒绝时，列表不会被半份结果更新。

4.5 import / export

问题：金额分、路径和接口地址要给页面用。打包之前，这些名字从哪个文件的边界出去？

约定：export 声明模块愿意交出的绑定，import 声明本文件使用的绑定。具名导出用花括号对上名字；默认导出一个模块只有一个。没有导出的 let 留在模块内部。本教程页是经典脚本，全局名是 Course，页面脚本里不写 import。工程源码在打包前使用模块语法。

基准算例：订单事实只导出一份：金额分 19950、route /orders、apiPath /api/orders。页面具名导入这些名字。另一文件再写一个数字 19950，就成了第二份事实。

// order-facts.js 只写这一份
export const amountFen = 19950;
export const route = "/orders";
export const apiPath = "/api/orders";

// page.js
import { amountFen, route, apiPath } from "./order-facts.js";
导出方式接错

对方用默认导出，这里用具名导入，amountFen 对不上。页面拿到的绑定是空的，金额分不会变成 19950。

每个文件各写一份

列表页和详情页各自写死 19950、/orders 和 /api/orders。改一处时另一处还是旧的。事实放在一个模块里导出，两边都导入它。

可操作对象：在源码里指出 amountFen、route、apiPath 的那一行 export，以及页面的那一行 import。确认没有第二份金额分字面量。

4.6 ESM 与 CommonJS

问题：同是「一个文件一份订单事实」，为什么有的文件写 import，有的文件写 require？

约定：ESM 使用 import / export，依赖在文件顶部静态写明。CommonJS 使用 require 与 module.exports，这是 Node 的模块写法，浏览器页面不执行 require。本课命令按 nodeMajor 20 来写；项目实际版本以仓库约定和文档为准。同一边界只选一种写法。

基准算例：金额分 19950、路径 /orders、接口 /api/orders 只存在于一份模块里。ESM 文件导出它们，或 CommonJS 文件导出它们，由仓库选定。不要在 .mjs 与 .cjs 里各放一套，让列表读到 19950、详情读到另一份数。

ESMexport 交出金额分，import 按名字取回。浏览器工程的源码常用这一套。
CommonJSmodule.exports 交出同一份事实，require 取回。它跑在 Node 里，不写进浏览器页面脚本。
在浏览器脚本里写 require

页面不是 Node 程序。require 不会在浏览器里解析出 amountFen。打包前的 Node 工具可以用 CommonJS；进浏览器的源码按仓库约定写成 ESM，或只通过打包器交接到产物里。

两套订单事实

同一边界一边 ESM、一边 CommonJS，各写一份 19950。互操作时具名可能落在 default 上，读 amountFen 会落空。选定一种模块，事实只导出一份。

可操作对象：在仓库里搜索金额分和 /api/orders。若同一事实同时出现在 module.exports 和 export 两套文件里，收成一份，让另一套只做转发或删掉。

4.7 循环依赖、打包前的模块边界

问题：文件 A 的初始化要读文件 B，文件 B 的初始化又要读文件 A。金额分什么时候才是 19950？模块顶层的请求又在什么时候发出？

约定：打包前，一个文件是一个模块，作用域停在文件边界，export 是唯一的出口。循环依赖是导入关系成环。CommonJS 在环上先执行到的一方，拿到的 module.exports 可能还是空对象。ESM 的绑定是活的，但 const 导出在初始化前处于暂时性死区，读它会在求值时失败。两种结果都不是稳定的 19950。打包器会把多个文件收成产物，顶层语句的副作用仍在模块被装入时执行。

基准算例：把金额分 19950、route 和 apiPath 放到没有环的 order-facts 模块。列表模块和展示模块都只导入它，它们之间不再互相取这笔事实。请求放在 loadOrders(page, size) 里，参数用 page 1 和 size 20，不要写在模块顶层。

// order-facts.js 不再导入 view 或 api
export const amountFen = 19950;

export function loadOrders(page, size) {
  // 调用时才发请求。模块被 import 时不发。
}
环上读到空导出

展示模块在初始化时读取接口模块再导出的金额分，接口模块又正在等待展示模块。CommonJS 这边常常还是空导出；ESM 这边可能在赋值前就失败。页面都不会稳定拿到 19950。

模块顶层发请求

文件顶层写 fetch(apiPath) 时，任何一次 import 都会把 /api/orders 发出去，测试和打包求值也会碰上。请求放进函数，由页面在需要 page 与 size 时调用。组件里对应的位置是副作用，第 6 章再写。

可操作对象：画出导入箭头。若成环，把订单事实挪到环外的模块，再确认这些文件的顶层没有 fetch。

4.8 Array、Map、Set、JSON、URL

问题：订单页上的当前页、按用户记下的金额、已选 id、接口正文和请求地址，各用标准库里的哪一种？

约定：Array 是有顺序的列表。Map 按键保存值，键保持当初放入的类型。Set 保存不重复的值。JSON 的 parse / stringify 只表达对象、数组、字符串、数字、布尔和 null。URL 用基准地址加路径，再写查询参数。日期和正则也在标准库里：时间的契约用字符串，Date 只负责展示；正则只做形态检查。

基准算例：当前页是 Array，长度按 size 20 这一页来，不是整表 listN 10000。Map 的键用 userIdText（字符串 10001），值是金额分 19950。Set 里放雪花 id 的字符串，不用数字。JSON 正文里的雪花 id 保持字符串；jsonNumberRoundTrip 会把它收成少 1 的文本，这是第 3 章的精度边界，本节不再用它做账。URL 的基准是接口源 apiOrigin（端口 8080），路径是 apiPath，查询带上 page 1 和 size 20。页面源 pageOrigin 在端口 5173，端口不同，不是同一源。

MapuserIdText 对应金额分数字键和字符串键不会被收成同一个
Set已选雪花 id 的字符串重复添加同一个字符串只留一次
JSON接口正文stringify 留不住 Map、Set 和 undefined
URLapiOrigin 加 apiPath，再加 page、size不要拿页面源 5173 去拼接口

JSON.stringify 一个 Map 得到的是空对象文本，里面没有 10001 和 19950。把 Date 放进 JSON 会变成字符串，读回来不再是原来的对象。正则可以检查 userIdText 是否全为数字；金额仍用整数分，不用正则把 199.50 解析成账。

用页面源拼接口

把路径 /api/orders 接到端口 5173 的页面源上，请求打到页面自己的源，而不是端口 8080 的接口源。两个端口不同源。

JSON.stringify 丢掉 Map

草稿若放在 Map 里，JSON.stringify 不会写出 userIdText 到 19950 的条目。要进 localStorage 的键 order.draft 时，先换成普通的可序列化字段，或改用数组条目。Set 同样不会被写进 JSON。

可操作对象：用 Map 记下 userIdText 到 19950；用 Set 记下雪花 id 字符串；用 URL 把 apiPath 接到 apiOrigin，并写入 page 与 size。然后对这个 Map 做 JSON.stringify，确认条目不在结果里。

4.9 对象当字典的键坑，菜单和路由是树

问题：想按用户 id 快速取出金额分，于是写了一个普通对象。键还是当初那个 10001 吗？订单菜单又该放在哪一种结构里？

约定：普通对象的键是字符串或符号。数字会先被收成字符串。查找时还会沿原型链看见对象自带的属性。Map 不把 10001 和 "10001" 收成同一个键，也不把原型上的名字当成你的条目。菜单和路由是树：父节点下面有子节点。沿父节点走到当前 route，而不是假设所有路径排在一个定长格子里。

基准算例：userIdText 是字符串 10001，它在安全整数以内。这里要看的是键的类型，不是雪花 id 的精度。把数字 10001 或字符串 "10001" 放进普通对象，都会落在同一个字符串键上，值若写成金额分，就是 19950。菜单的父节点是订单，子节点一条是列表：路径 /orders，接口 /api/orders，查询用 page 1 和 size 20；另一条是草稿，键名 order.draft。

键被收成字符串

普通对象把 10001 收成字符串 "10001"，和 userIdText 撞在同一格。来路不明的字符串若叫 __proto__ 或 constructor，会碰到原型，而不是新的订单一格。用户 id 到金额分改用 Map。

把原型键当成一条路由

用普通对象存路径时，in 能看见原型上的 toString，读出来是函数，不是 /orders。for-in 会带上原型链上可枚举的名字。键若是 __proto__ 或 constructor，会碰到原型本身。子节点用数组存放，路径索引用 Map。

可操作对象：按上面的树写下父子。索引用 Map，键用 route 字符串。不要把 userIdText 放进普通对象当字典，也不要用 for-in 直接生成菜单。

4.10 线性与 n log n，JS 数组不是定长数组

问题：整表 10000 条和当前页 20 条，差的是常数还是另一个数量级？渲染函数里能不能顺手把整表排序？

约定：线性是与 \(n\) 成正比的一份工作。比较排序的时间数量级是 \(n \log_2 n\)，假设比较排序、按随机比较来估计次数。它是数量级，不是某一次运行的计时，也不是容量承诺。Course.orderMath.compareCost(n) 返回 linear 与 nLogN，其中 nLogN 为 \(n \log_2 n\)。空间上，再复制一整表就是另一份与 \(n\) 成正比的引用。JS 数组的 length 会变，它是列表，不是定长格子；按下标赋值可以撑大 length，中间可以是空位。栈用 push / pop，后进先出。队列从一端进、另一端出；对数组头部 shift 会搬动后面的元素。

基准算例：取 \(n\) 为 size 20，再取 \(n\) 为 listN 10000，两行都只调用 compareCost，读出 linear 与 nLogN。一页的线性是 20 这一档；整表比较排序走 \(n \log_2 n\) 那一档。视口大约 viewportRows 12 行，渲染路径处理这一页或这一屏，不对 10000 条重算。帧预算 16.7 毫秒和长任务 50 毫秒是第 2 章的时间门槛，本章不把 nLogN 换算成毫秒。整表高度和视口高度由 fullListPx、visiblePx 在后面的章使用，这里只记住：排序不要放进每次渲染。

把数量级当成计时

\(n \log_2 n\) 不是毫秒，也不是接口能扛多少请求。compareCost 只比较工作量的阶。滑块上的两个读数用来判断「整表」和「一页」差了哪一阶。

渲染时对 10000 条排序

每次渲染都对 listN 做比较排序，主线程要走完这份 \(n \log_2 n\)。排序放在数据到达时做一次，或只排当前页 size 条。另外，JS 数组不是定长的：把值写到下标 size 上，length 会变成 21，中间的空位不会抛错。撤销草稿用 push / pop 当栈；待发请求若靠 shift 出队，每次搬动后续元素，不要在渲染里对整表这样做。

可操作对象：拖动数据量。停在 20 和 10000，分别读出 linear 与 nLogN。确认渲染函数里没有对整表的排序或整表 shift。

线性与 n log n拖动数据量

观察要点：① 滑块范围覆盖 size 20 到 listN 10000，两端都能落点。② linear 与 nLogN 随滑块变化，都来自 compareCost。③ \(n \log_2 n\) 假设比较排序，是数量级，不是某次计时。④ 停在 10000 时，渲染路径不要整表重算。

本章避坑清单

  1. 漏写 await 时，这一行拿到的是 Promise，读不到 amountFen 19950。
  2. Promise.all 任意一条拒绝，整组拒绝；没人接住时，页面会空白且没有失败说明。
  3. 循环依赖在初始化时会拿到空导出，或在暂时性死区失败，金额分还不是稳定的 19950。
  4. 普通对象会把键 10001 收成字符串，in 和 for-in 还可能碰到原型键。
  5. 不要在模块顶层发请求。导出函数，等到要使用 page 与 size 时再调用。
  6. JSON.stringify 留不住 Map，也留不住 Set。
  7. 同一边界不要让 ESM 和 CommonJS 各写一套订单事实。
  8. 不要在渲染路径上对 10000 条做比较排序，也不要把 JS 数组当成定长数组。
