第 2 章 · 共同语言

浏览器：一帧、事件循环与一次加载

第 1 章留下了教学订单页和页面全局对象 window。这一章用同一页看渲染进程的主线程怎样排一帧、怎样排一次任务，以及一次加载从解析走到同源判断。

  • 能画出一帧里脚本、样式、布局、绘制的排队。

  • 能区分 DOMContentLoaded 与 load，以及 5173 与 8080 不同源。

2.1 浏览器进程、渲染进程、JS 主线程、合成、GPU

问题：地址栏、页面脚本和最后上屏，是不是都在同一个进程里？

约定：进程职责以 Chrome 文档《Inside look at modern web browser》的原文划分为准。浏览器进程负责地址栏、书签、前进与后退，以及网络请求和文件访问这类特权操作；文档把这些放在浏览器进程，较新的 Chrome 也可以把网络服务放到单独的进程。渲染进程负责标签页里的页面。插件进程负责插件，教学订单页不使用插件。GPU 进程把 GPU 任务和其他进程隔开，因为 GPU 要替多个程序往同一块表面上画。站点隔离是同一套文档里的安全模型：一个渲染进程里的文档来自同一个站点（方案加上可注册域），跨站 iframe 可以再进另一个渲染进程。渲染进程内部还有分工：主线程跑大部分 JavaScript，并做 HTML 与 CSS 的解析、样式计算和布局；Worker 有自己的线程，碰不到这份文档的 DOM；合成器线程可以处理一部分滚动和只改合成层的更新；光栅线程把绘制记录变成位图。进程个数以本机这一版的任务管理器为准。Chrome 帮助里的任务管理器同时写了菜单中的“更多工具”和快捷键；开发者工具同样同时有菜单和快捷键。使用文档列出的任一入口即可，不要把某一次点击路径写成唯一做法。

进程 浏览器进程

地址栏、书签、前进后退，以及网络与文件这类特权操作。

进程 渲染进程

订单文档所在的进程。站点隔离按站点拆，不按“整个浏览器一个进程”来记。下面两格是它里面的线程，不是另外两个进程。

线程 · 属于渲染进程 主线程

脚本、解析、样式计算、布局。

线程 · 属于渲染进程 合成器线程

一部分滚动和只改合成层的更新。它不在 GPU 进程里。

进程 GPU 进程

与 GPU 通信，把合成结果送上屏幕。

用教学订单页走一遍：地址栏中的页面源来自 Course.data.order.pageOrigin，也就是 http://localhost:5173，导航落在浏览器进程。订单文档进入渲染进程后，路由 /orders 上的脚本、DOM、样式和布局都在该渲染进程的主线程。列表若只改合成层能表达的属性，合成器线程可以参与，不必每一步都回到主线程重做布局。像素由 GPU 进程送上屏。接口源是 http://localhost:8080。它和页面不同源，但这不自动等于第二个渲染进程：站点隔离看站点，端口不一定单独拆进程。不同源如何限制脚本读取响应，放到 2.9。页面能碰到的全局对象仍是这个文档的 window，它不是操作系统进程的全局袋子。

主线程被记成浏览器进程

订单列表卡在脚本上，是这个文档所在渲染进程的主线程被占住。地址栏所在的浏览器进程并不在算这张表的布局。所有标签页也不共用一个渲染进程。

到页面脚本里找进程句柄

进程模型用来读任务管理器和性能轨迹。页面代码能碰到的是 window、文档和主线程上的任务。这里没有 JVM，也没有一份可以在脚本里枚举的操作系统进程表。

可操作对象：在纸上先画三个进程：浏览器进程、渲染进程、GPU 进程。主线程和合成器线程画在渲染进程里面，不要和进程并列。再在渲染进程旁注明：页面源与接口源端口不同，只说明不同源，不说明一定已经拆成两个渲染进程。

2.2 一帧里脚本、样式、布局、绘制排队，帧预算 16.7ms

问题：这一帧里，脚本、样式、布局、绘制谁先谁后？超过 16.7ms 算不算长任务？

约定：把主线程上的一帧排成脚本、样式、布局、绘制，后面再是合成。脚本包括事件处理和 requestAnimationFrame 回调，发生在这一帧的样式计算之前。样式计算得出每个节点用哪些规则，布局得出位置和大小，绘制把这些记录下来，合成再把图层送到屏幕。合成可以离开主线程，前四步里占主线程的工作共享同一段时间。帧预算按 \(1000/60 \approx 16.7\)（假设 60Hz，单位是毫秒）估算。教学订单页把这个估算放在 frameBudgetMs。它是预算，不是显示器的保证；垂直同步、后台标签和机器负载都会让实际间隔变长。长任务看同一页的 longTaskMs：主线程上的任务达到这个门槛，才称为长任务。超过帧预算只说明这一帧装不下，两道门槛不要写成同一个毫秒数。

1. 脚本 2. 样式 3. 布局 4. 绘制 5. 合成

用教学订单页走一遍：订单列表共 listN 行，基准是 10000 行；接口一页是 size 行，基准是 20；视口大约 viewportRows 行。可见高度用 Course.orderMath.visiblePx()，整表高度用 Course.orderMath.fullListPx()。整表远高于一屏。若在脚本阶段同步重算全部 listN 行，再去改样式、读布局，样式、布局和绘制都排在这段脚本后面，帧预算先被脚本吃掉。可见的那十几行留到后面的章再做虚拟列表，本章先把排队画对。行高 rowHeightPx 只参与这两个高度，不另换一套像素当帧预算。

把帧预算当成设备保证

frameBudgetMs 来自 60Hz 的估算。某台显示器的刷新率、当前标签是否在前台，都会让真实帧间隔偏离它。把估算背成“每帧一定正好这么多毫秒”，读数一对不上就会怀疑公式。

同步重算 10000 行

在渲染路径上同步重算 listN 行，主线程被占住，超过 frameBudgetMs。达到 longTaskMs 才叫长任务。只超过帧预算，还不够称为长任务。不要为了“优化”另写一套毫秒门槛。

可操作对象：拖动下面的滑块，把脚本耗时从 0 ms 调到 80 ms。读数回答两句：是否超过 frameBudgetMs，是否达到 longTaskMs。滑块本身是整数毫秒，比较仍然用订单页里的那两个字段。

脚本耗时与两道时间门槛拖动滑块
观察要点：① 滑块表示主线程上这段脚本的耗时，范围 0–80 ms。② 帧预算来自 frameBudgetMs，即 \(1000/60 \approx 16.7\)（假设 60Hz）；耗时大于它，读数显示超过帧预算。③ 长任务门槛来自 longTaskMs；耗时达到它，读数才显示达到长任务。只超过帧预算并不叫长任务。④ 列表行数是 listN，可见行数是 viewportRows。同步重算整表占的是这段脚本时间，行数本身不是毫秒。

2.3 调用栈

问题：函数还没返回，点击和定时器能插进来吗？

约定：调用栈是主线程上当前正在执行的函数嵌套。外层函数调用内层函数时，内层压栈；内层返回，栈顶弹出。JavaScript 这一趟要跑到栈空，排队的回调才有机会开始。这就是运行到完成。栈描述正在执行的嵌套，任务队列描述还没开始的回调。两者不要画成同一条横线。

用教学订单页走一遍：同步函数先读 page 和 size，拼出 apiPath。展示金额时调用 Course.orderMath.yuanText()，它根据 amountFen 得到展示文本，这次调用也压在同一栈上，返回后栈顶才回到外层。在外层返回之前，用户连点的翻页、已经登记的 Promise.then 和 setTimeout 都还在各自的队列里。它们不会把“读 page”和“拼路径”从中间拆开。金额的小数元 amountYuan 不在这一帧里做账，账务仍用整数分；这里只说明格式化是一次同步调用。

以为定时器能插进栈中间

调用栈不是协作式线程切换。把 setTimeout(0) 写在两行计算之间，只是登记了一个以后的任务。当前函数仍会先返回，定时器回调才可能开始。

栈还没空就去读 then 的结果

then 登记的是微任务。当前函数还在栈上时，这个回调还没执行。若在登记的下一行就读取“列表已经画好”的标志，读到的是登记之前的状态。

可操作对象：给 showOrders 画一层栈：外层读 page、size，内层是 yuanText()。在栈的旁边另画一个等待区，把点击、微任务和定时器放进去，并写上“栈空之后才离开等待区”。

2.4 宏任务与微任务

问题：当前函数跑完后，先执行 Promise 回调，还是先执行 setTimeout？

约定：宏任务是规范里的 task。事件循环从任务队列里一次取一个来执行，例如一次点击、setTimeout 或 setInterval 的回调。这个任务的同步部分跑完，调用栈空了，接着做微任务检查点：把微任务队列清空。清空期间新排入的微任务仍在同一次检查点里执行，检查点结束后才离开。Promise 的 then、catch、finally，以及 queueMicrotask，都进微任务队列。因此微任务紧跟在当前这次任务后面，不排到下一轮宏任务之后。下一轮宏任务是检查点结束之后，事件循环再取到的另一个任务。

登记队列相对当前函数
函数体内的语句调用栈正在执行，直到返回
Promise.then微任务这次任务结束的检查点
setTimeout宏任务检查点之后的另一轮任务

用教学订单页走一遍：点击“下一页”是一个宏任务。处理函数把 page 加一，并登记一个 Promise，准备在行数据就绪后改表格。处理函数返回后，微任务检查点跑这个 then，不用等下一次点击，也不用等一个 setTimeout。若 then 里再 then，新的微任务仍挤在同一次检查点里。用这种方式把 listN 行拆成一万个微任务，主线程在检查点里一直不让出，绘制插不进来，耗时仍可能超过 frameBudgetMs，并达到 longTaskMs。

微任务排到下一轮宏任务之后

看见 then 就把它写成“下一次 setTimeout 之后才执行”，顺序就反了。当前点击任务的同步代码结束之后，微任务先清空，定时器回调是更后面的宏任务。

用微任务链铺完 10000 行

检查点会把新排入的微任务一起跑完。在微任务里为每一行再登记微任务，主线程不会回到事件循环去取绘制。要把工作拆开，得放到后续的任务里，或交给 2.6 的绘制节奏，而不是在同一次检查点里排满 listN。

可操作对象：拿一次翻页点击，标出三段：处理函数里的同步语句、它登记的 then、它登记的 setTimeout。在纸上把 then 画在这次点击的末尾，把 setTimeout 画成下一次取出的任务。

2.5 Promise 回调与 setTimeout(0) 不是并行

问题：setTimeout(0) 会和当前函数一起执行吗？

约定：setTimeout(fn, 0) 把 fn 排进任务队列，成为以后的一个宏任务。0 表示希望尽快入队，不表示当前语句执行到这里时 fn 已经开始，也不表示浏览器为它新开一条线程。当前调用栈，以及随后那一次微任务检查点，都比这个回调优先。Promise.then 是微任务，所以在同一次任务里，它早于这个定时器回调。两者都回到渲染进程的主线程上执行。登记的先后不能单独决定队列种类：先写 setTimeout、后写 then，then 仍在微任务检查点先跑。

function showOrders() { formatAmount(); // 调用栈，含 yuanText() setTimeout(onLater, 0); // 先登记：宏任务 Promise.resolve().then(onRows); // 后登记：微任务，却更早执行 }

用教学订单页走一遍：列表数据到达之后，有人用 setTimeout(0) 把“画出 size 行”推迟，希望浏览器先把表头画出来。回调入队之后，当前函数和已经登记的微任务仍先占着主线程。轮到 onLater 时，它若同步重算 listN 行，主线程再次被占住，订单表在这段时间里同样得不到样式、布局和绘制。延迟参数描述的是排队，不是线程数。页面脚本没有一份 JVM 式的线程池可以并行跑这两段函数。

setTimeout(0) 当成并行

0 毫秒没有第二条主线程。当前函数返回之前，定时器回调不会开始；它开始之后，仍然独占这条主线程，直到自己返回。

用 0 延迟把整表让出主线程

把同步重算 listN 行放进 setTimeout(0)，只改变它在任务队列里的位置。回调真正执行时仍会挡住订单列表的布局和绘制。要缩短的是这一次任务的工作量。

可操作对象：按上面的函数，在纸上写下实际先后：formatAmount，然后 onRows，然后 onLater。下一节把 requestAnimationFrame 插进这张顺序表，用分段控件把四步读出来，并核对“是否并行”一栏。

2.6 requestAnimationFrame

问题：想赶在下一帧绘制之前改列表，回调写在哪？

约定：requestAnimationFrame 的回调在浏览器准备更新画面时运行，位于这一帧的样式计算、布局和绘制之前。它不是微任务，也不进 setTimeout 的任务队列。事件循环在任务之间若决定这是一次绘制机会，就会先跑这些帧回调，再做样式、布局和绘制。绘制机会通常跟着显示器的刷新走；假设 60Hz 时，仍用 \(1000/60 \approx 16.7\)（假设 60Hz）去估一帧，也就是 frameBudgetMs。在“微任务已经清空，且这次绘制机会先于定时器任务被选中”的前提下，四步是：当前函数、Promise.then、requestAnimationFrame、setTimeout(0)。若定时器任务先被选中、这一帧的绘制机会还没到，setTimeout(0) 会落在下一次帧回调之前。两种排法都在同一条主线程上，都不是并行。下面的演示按前一种排队读数，避免把登记顺序当成执行顺序。

用教学订单页走一遍：滚动订单表时，若每一帧要知道视口里大约 viewportRows 行的范围，把计算登记到 requestAnimationFrame，它会和这一帧的样式、布局排在一起。不要用 setTimeout(0) 去赌“差不多一个帧预算之后”。帧回调若同步重算全部 listN 行，脚本阶段仍会超过 frameBudgetMs；时间达到 longTaskMs 就记成长任务。帧回调只提供绘制前的位置，不保证回调本身很短。可见高度继续用 visiblePx()，不要在每一帧对整表高度 fullListPx() 做全量布局。

把 rAF 当成 setTimeout 或微任务

requestAnimationFrame 不在微任务检查点里，也不会因为延迟写成某个毫秒数就变成定时器。把它和 then 画在同一格，样式计算之前的那一次机会就丢了。

在 rAF 里重算整张表

回调位于绘制之前，所以它有多长，这一帧的样式、布局、绘制就晚多久。在帧回调里同步走过 listN 行，帧预算在绘制开始前已经用完。

可操作对象：用分段切换四步。读数给出完整执行顺序、当前是第几步、所在队列，以及是否并行。并行一栏应始终为否。

四步排队切换分段
观察要点：① 四段都在同一条主线程上，切换分段只是查看其中一步，读数里的执行顺序保持不变。② 当前函数占着调用栈时，Promise.then、requestAnimationFrame 和 setTimeout(0) 都还没开始。③ Promise.then 在这次任务结束的微任务检查点跑完，不排到下一轮宏任务之后。④ 演示假定微任务清空后先遇到绘制机会，因此 requestAnimationFrame 在 setTimeout(0) 之前；setTimeout(0) 仍是后续宏任务，写成 0 也不是并行。

2.7 解析 HTML、再要脚本和样式、脚本从上到下

问题：订单表写在 HTML 里，为什么有时要等前面的脚本跑完才进 DOM？

约定：HTML 解析器从上到下建 DOM。遇到没有 async、defer 的经典脚本，解析停住，先取得脚本并执行，再继续往下。脚本按在文档中的出现顺序执行。样式表不按同一方式截断解析，但会挡住渲染；排在未完成样式表后面的、会挡住解析的脚本，还要等那张样式表，因为脚本可能读取样式。带 defer 的脚本下载时不截断解析，文档解析完后按顺序执行，并且早于 DOMContentLoaded。带 async 的脚本下载时不截断解析，一下载完就可以执行，多个 async 脚本彼此不保证顺序。教学订单页先用经典脚本把“从上到下、会挡住后面的标签”看清。

用教学订单页走一遍：文档可以是页头、一段根据 page 和 size 做准备的经典脚本，然后才是订单表的标签。解析器走到脚本时，表的标签还没有进入 DOM，apiPath 对应的那些行也还没有节点。脚本若在这里同步做重活，表的解析继续等。样式表放在前面时，首次绘制这张表之前要先完成样式；样式晚到，绘制排队会变样。这份 HTML 是入口，脚本是随后再取的资源。入口怎样缓存、带内容哈希的脚本怎样缓存，第 1 章已经分开；挡住解析说的是文档内部的顺序，不是缓存秒数。

先解析完整份 HTML 再执行脚本

经典脚本出现在文档中间时，解析就在这里停。写在脚本标签后面的订单表，要等这段脚本执行完才继续解析。标签在源文件里更靠后，并不等于它已经在 DOM 里。

脚本挡住订单列表

把会挡住解析的脚本放在订单表之前，并在脚本里做重计算，表格标记进不了 DOM，主线程又被脚本占住。不必挡解析的脚本用 defer，或把脚本放在表格标记之后。计算量大的工作不要放在这段同步脚本里。

可操作对象：在订单页骨架上画一条竖线，标出经典脚本的位置，以及它下面的表格标记。在脚本返回之前，表格那一格写“尚未解析”。再标一张排在脚本前的样式表，写上“这段脚本要等它”。

2.8 DOMContentLoaded 与 load

问题：HTML 解析完了，图片还没到，这时算加载完成吗？

约定：DOMContentLoaded 在文档解析完成、并且 defer 脚本已经按顺序执行之后触发。它不等待图片。样式表若挡住了还要执行的脚本，会把那些脚本和这个事件一起拖后；这仍然不等于图片已经加载完。window 的 load 还要等文档依赖的子资源，包括样式表和图片。两个事件看两段生命周期。接口响应是另一次网络活动，不属于这两个事件的定义。

用教学订单页走一遍：由 HTML 解析出来的表格和翻页按钮，在 DOMContentLoaded 时已经在文档里，可以在这里查询和绑定。若经典脚本写在表格之前，脚本执行时表格还不存在；那是 2.7 的位置问题，不是这个事件没有触发。订单行里的图片若还没到达，DOMContentLoaded 可以已经发生，load 还没有。要用图片自己的尺寸做布局，就等这张图片的加载完成或窗口的 load。列表数据来自 apiPath，返回时刻由那次请求的回调决定。load 触发只说明文档的子资源这一段结束了，不说明第 page 页的 JSON 已经写进表格。

把两个事件当成同一个

名字不同是因为时机不同。DOMContentLoaded 看解析和延迟脚本，load 还要看图片等子资源。用其中一个监听器代替另一个，按钮绑定和图片尺寸会有一个对不上。

在错误的事件里量订单图或绑按钮

在 DOMContentLoaded 里读取订单图片的布局高度，图片未到时高度还不是最终值。把表格里已经解析出来的按钮一直拖到 load 才绑定，点击会空等图片。接口失败也不要归进这两个事件。

可操作对象：列三行检查表。DOM 查询和按钮绑定对 DOMContentLoaded。图片尺寸对图片自己的加载事件或 load。/api/orders 的返回对请求回调。每一行只填一个时机。

2.9 DNS、TCP、TLS、HTTP 方法与状态码、同源（5173 与 8080）

问题：页面在 5173、接口在 8080，算同源吗？

约定：一次走到 HTTP 的加载按这个顺序理解：DNS 把名字解析成地址，TCP 建立连接，方案若是 https 再做 TLS，然后才是 HTTP 的方法和状态码。前一层没有完成，后一层没有报文。同源比较协议、主机、端口，不比较路径；三者相同才是同源。省略端口时按该协议的默认端口参与比较。教学订单页的两条源都写明了端口，直接比较字段。浏览器按同源政策限制页面脚本如何读取另一源的响应；这不表示服务端一定没有收到请求。预检和凭据在第 7 章。

比较项页面 pageOrigin接口 apiOrigin
源http://localhost:5173http://localhost:8080
协议httphttp
主机localhostlocalhost
端口51738080
路径/orders（route）/api/orders（apiPath）

用教学订单页走一遍：localhost 通常在本机解析，公网权威 DNS 的故障不一定出现，但“名字还没变成地址，TCP 就不会开始”这条顺序仍然成立。连接阶段的等待用 connectTimeoutMs，基准 500 ms。连接建立之后等待响应数据，用 readTimeoutMs，基准 2000 ms。浏览器侧整段等待用 browserTimeoutMs，基准 3000 ms。三个超时不是同一个数。教学用的两条源都是 http，这条练习本身不走 TLS。部署改成 https 而握手失败时，失败停在 TLS：没有 HTTP 状态码，也没有正文里的业务 code。不要把它记成 businessCodeFail（40001），也不要记成 httpOk（200）。HTTP 真正返回之后，才同时看状态码和业务 code：状态是 httpOk 且业务 code 是 businessCodeOk（0）才是这一次业务成功；状态已是 httpOk 但业务 code 为 businessCodeFail 仍是失败。取第 page 页、每页 size 条，用 GET 表达读取。同源结论只看前三行：协议相同，主机相同，端口 5173 与 8080 不同，所以不同源。路径不同不改变这个结论。

端口不同仍当同源

只比较了 localhost 和 http，漏了端口。同源三要素里端口不同，页面脚本与接口就是不同源。路径 /orders 与 /api/orders 再怎么像，也不参与这三项比较。

TLS 失败当成业务 code

业务 code 只出现在已经拿到的 HTTP 正文里。证书或握手失败时，业务日志里还没有这条带着 businessCodeOk 或 businessCodeFail 的响应。先记下失败停在 TLS，再决定要不要看接口实现。

可操作对象：用协议、主机、端口三列抄下 pageOrigin 与 apiOrigin。端口列不同就停笔，结论写不同源。另起一行写 TLS：若失败发生在握手，业务 code 一栏填“无”。

2.10 Node 20、包管理器、环境变量，浏览器里没有 JVM

问题：订单页的脚本里能拿到 Node 的 process 吗？

约定：本课命令示例按 nodeMajor 写，基准主版本是 20。项目实际版本以仓库约定和该版本的文档为准，教程里的主版本不是对每台机器的探测结果。包管理器负责安装依赖和运行脚本；Node 的发行版带有 npm。仓库若约定了别的包管理器，命令以那个仓库的文档为准，不把某一种图形菜单写成唯一做法。环境变量属于启动那个进程时的环境。浏览器里的订单页没有 JVM，没有 Node 的 process，也没有进程级的全局袋子。这个文档的全局对象是 window。secretName 的值是名字 ORDER_API_SECRET，不是密钥本身；这个名字也不该出现在下载到浏览器的脚本里。

用教学订单页走一遍：开发时，页面由监听在 pageOrigin 上的开发服务器提供，列表接口监听在 apiOrigin。这是两个监听端口，不是“浏览器里面跑着 JVM”。终端里的 Node 是另一个进程，process 和环境变量在那个进程里。订单页的脚本下载到渲染进程之后，能当作全局对象使用的是这份文档的 window。构建步骤若把 ORDER_API_SECRET 写进包，秘密会跟着脚本到用户机器上；那是构建泄漏，不是浏览器自带了读取服务器环境的能力。页面需要的公开配置，例如接口源，和密钥是两类东西。

在页面里找 process

在订单页的脚本里读取 process 或 process.env，找的是 Node 进程的对象。浏览器没有这个对象，也没有 JVM。若某个打包结果里出现了它，那是构建时塞进来的代码，要回到构建配置里看塞了什么。

把密钥名字写进前端包

ORDER_API_SECRET 只作为名字出现在课程数据里。把它放进会打进页面脚本的变量，等于把秘密交给每一个打开订单页的人。页面全局对象保持为 window，密钥留在服务端进程。

可操作对象：画两行环境。第一行是终端：Node 主版本按 nodeMajor 写示例，环境变量在这个进程。第二行是订单页：全局对象写 window，process 一栏写“无”，JVM 一栏写“无”。

本章避坑清单

  1. 渲染路径上同步重算 listN（10000）行时，超过 frameBudgetMs 与达到 longTaskMs 是两道门槛。后者才叫长任务。
  2. 会挡住解析的脚本放在订单列表前面，列表标记要等这段脚本执行完才进入 DOM。
  3. TLS 握手失败时还没有 HTTP 正文，不能记成业务 code 40001，也不能记成 HTTP 200。
  4. 页面里没有 process，也没有 JVM。全局对象是 window。ORDER_API_SECRET 不能打进前端包。
  5. setTimeout(0) 仍在主线程上排队，延迟为 0 不是并行。
  6. 微任务在当前任务结束的检查点清空，不要排到下一轮宏任务之后。
  7. load 与 DOMContentLoaded 不是同一个事件。前者还要等图片等子资源。
  8. http://localhost:5173 与 http://localhost:8080 端口不同，是不同源。路径不参与同源判断。

本章小结与延伸阅读

订单页跑在渲染进程的主线程上。一帧按脚本、样式、布局、绘制排队，合成可以再往后、并离开主线程。帧预算是 \(1000/60 \approx 16.7\)（假设 60Hz），记在 frameBudgetMs；长任务另看 longTaskMs。调用栈跑完才进入微任务检查点，setTimeout(0) 是之后的宏任务，不是并行；绘制机会先到时，requestAnimationFrame 排在这个定时器之前，并位于样式计算之前。经典脚本从上到下，会挡住它后面的订单表。DOMContentLoaded 看解析和延迟脚本，load 还要看图片等子资源。页面源 http://localhost:5173 与接口源 http://localhost:8080 不同源。TLS 失败时还没有业务 code。浏览器里没有 JVM，页面全局对象是 window。
