第 8 章 · 现象与判断

排错、测试与协作

订单页的组件、请求和构建已经能串起来。这一章练判断：一个现象先缩到哪个文件、哪一块面板；HTTP 200 里面业务 code 仍可能失败；测试断言用户看见的金额文本，请求用假实现，不连真实的 8080。

预计学习一段完整专注时间 前置：第 6、7 章 交互演示 2 个
  • 能把一个现象缩到文件和面板；
  • 能区分 HTTP 200 与业务失败，并决定下一步看拦截器、运行时校验还是服务端；
  • 能写出测用户看得见的金额：展示文本来自 orderMath.yuanText()，组件测试不打到真实 8080。

8.1 目录职责、命名、组件拆分

问题：金额、列表和样式同时不对，先改哪个文件？

约定：教学订单页按四块职责拆开。页面负责路由 /orders 的组合；展示组件只接收整数分并交给 orderMath.yuanText()；请求模块只面向 /api/orders，返回业务 code 和 amountFen；样式只用局部类名。这是职责约定。仓库若已有目录名，沿用仓库的名字，不要为本章另起一套平行目录。

基准算例：展示组件拿到的金额是 amountFen 19950，屏幕文本由 yuanText 得到 199.50。订单 id 使用字符串 snowflakeText，变量名表达“文本”，不要写成数字字面量。userIdText 是 10001，它在安全整数以内，不能拿来给 id 字段命名当精度反例。草稿键是 order.draft，它不属于请求模块。

页面路径 /orders。组合列表、金额和分页，参数是 page 1、size 20。
展示组件只格式化 amountFen。不发请求，不读 apiOrigin。
请求模块只访问 apiPath。不把分换算成展示文本。
样式行高约定 rowHeightPx 48。不在这里写业务 code。
易错：一个文件包办四块职责

请求函数里顺手把 19950 除成元，展示组件又自己拼 apiOrigin。现象出现时，Console、Elements 和 Network 会同时可疑，缩不到一个文件。

避坑：字段名看不出单位和类型

金额字段写成不含“分”的名字，雪花 id 用数字命名。评审和测试会把 amountYuan 199.5 当成已经核对过账。id 保持 snowflakeText 这一串，金额计算停留在 19950。

可操作对象：给当前订单页画一张四格卡片：页面、展示组件、请求模块、样式。每格只写一个文件职责，以及它允许碰的基准字段。

8.2 ESLint 与格式化

问题：ESLint 过了，屏幕上的金额就一定对吗？

约定：格式化统一空白、引号和换行。ESLint 按仓库配置检查可疑写法，例如意外的相等比较、未使用的绑定。两套配置都进仓库，具体规则名和命令以仓库脚本、ESLint 文档为准。本章不写死某一条规则的开关。命令示例按 Node 主版本 nodeMajor 20 来写，项目实际版本以仓库约定为准。

基准算例：amountYuan 是 199.5。写成 199.5 === 199.5 会成立，ESLint 不会因此知道你没有读 amountFen 19950，也不会知道屏幕文本应当来自 yuanText。lint 通过只说明这条写法没有触发仓库规则。

易错：用 lint 通过代替金额断言

格式化把订单文件排整齐，不改变 19950 和 199.5 的单位。检查绿灯之后，仍要用用户看得见的文本核对分。

避坑：关掉规则来消掉订单文件的报错

整文件关闭 ESLint，或让格式化配置和 lint 配置各写一套却不提交。下一次换机器，同一份订单代码会得到另一套警告。规则放进仓库；业务单位放进断言和接口文档，不要指望规则认识“分”。

可操作对象：在订单展示组件上区分两列：格式化改过的空白，以及 ESLint 没有能力判断的字段（amountFen、字符串形式的雪花 id）。

8.3 Console、断点点到为止

问题：断点停在框架里时，还要不要继续往下点？

约定：Console 用来看未捕获错误、被拒绝的 Promise，以及你有意打印的值。打印要带上能对回文件的事实：page、snowflakeText、amountFen，以及 yuanText 的结果。断点下在 Sources 面板里、订单展示组件调用 yuanText 的那一行。确认这一行拿到的分是 19950，就可以停。这就是“点到为止”：不进入框架或依赖的源码。面板名称以 Chrome DevTools 文档中的 Console、Sources 为准；打开方式和调用栈的菜单位置以当前文档原文为准，本章不写死点击路径。

基准算例：断点处应能读到 amountFen 19950。同一时刻 yuanText(19950) 的文本是 199.50。若这里已经是 19950 而屏幕不是 199.50，下一眼看展示那一行有没有绕过 yuanText。若这里的分已经不是 19950，再往请求和运行时校验退，而不是先步进框架。

易错：断点步进框架源码

栈顶还在框架内部时就单步进入实现，订单组件尚未被确认。先沿调用栈回到自己的展示文件，停在 yuanText 那一行。

避坑：Console 只留一句“出错了”

没有 page、没有字符串形式的订单 id、没有 amountFen，事后无法把这条消息对回某一次教学订单。打印这些基准字段，然后回到断点；不要用一长串对象代替文件名。

可操作对象：准备一次停驻：Sources 里订单展示组件的一个断点，Console 里一行同时含 page 1、雪花 id 字符串和 19950。

8.4 Elements 看盒模型和被盖住的样式

问题：金额数字是对的，行却挤在一起，该看哪？

约定：用 Elements 面板查看选中节点的 DOM，在 Styles 窗格的盒模型图里看内容区、内边距、边框和外边距，并看哪一条声明胜出、哪一条被划掉。窗格的英文名以 Chrome DevTools 文档原文为准。本章只使用文档中的面板和窗格名称，不写从哪个按钮点进去。

基准算例：教学订单行的高度约定是 rowHeightPx 48。盒模型图上胜出的高度若不是 48，先找被划掉的那条高度声明，以及是哪一个局部类名盖过了它。clsShiftPx 也是 48，那是缺高度时布局位移的教学数字，留到第 9 章展开。本章看见 48，先问它是行高还是被挤开的位移，两个 48 不要记成同一次测量。

易错：只读没被划掉的颜色

胜出的声明和被划掉的声明会同时出现。只引用最终颜色，说不出是全局类名盖住了组件库，还是订单页自己的局部类名没生效。

避坑：为压过一条样式去重写基础控件

业务页再做一套输入框，第 7 章已经把这件事标成坑。Elements 里先指出胜出的选择器和被盖住的选择器，再决定改哪一层。不要把行高 48 和位移 48 写成同一个缺陷。

可操作对象：选中订单行，记下盒模型图里的内容高度，以及一条被划掉的声明和胜出它的那条规则。高度期望对照 48。

8.5 Network：状态码、业务 code、内存缓存还是重新下载

问题：Network 里已经是 200，列表为什么还不更新？

约定：在 Network 面板里分三列看同一条订单请求：HTTP 状态码、响应体里的业务 code、资源是从缓存给出还是重新下载。缓存字样以 Chrome DevTools 文档中的 memory cache、disk cache 为准，出现在该资源的大小信息里。页面源是 pageOrigin（http://localhost:5173），接口源是 apiOrigin（http://localhost:8080），端口不同，不同源。静态脚本的缓存字样不解释接口 JSON。

基准算例：业务成功的信封是 HTTP httpOk 200 且 code 为 businessCodeOk 0，响应里仍应有 amountFen 19950。HTTP 200 且 code 为 businessCodeFail 40001 是业务失败，列表不应更新。HTTP 500 时，不要假设正文里一定有 40001。入口 html 的 htmlMaxAgeSec 是 60 秒；带内容 hash 的 js/css 的 assetMaxAgeSec 是 31536000。带 hash 的脚本显示来自内存缓存，只说明这次没有重新下载这份静态资源。

Network 里看见的它说明它不说明

code 为 0业务信封按成功放行amountFen 一定还在
code 为 40001业务失败，列表应保持原样可以当作 HTTP 失败
HTTP 500失败发生在服务端这一侧正文可以当成 code 0

易错：看见 HTTP 200 就更新列表

200 且 code 为 40001 仍是失败。拦截器若把“有响应”当成成功，地址栏上的订单列表会被一次业务失败盖住。

避坑：用静态资源的内存缓存解释接口

内存缓存描述的是 html、js、css 这一层。订单 JSON 来自 8080 的 /api/orders。两层缓存的失效策略不同，第 1 章已经分开；本章在 Network 里也分开看。

可操作对象：选中一次订单请求，抄下状态码、响应体里的 code，以及它是不是静态资源的缓存字样。抄完再进入下一节决定下一步。

8.6 先把现象缩到文件

问题：只说“订单页不对”，下一步该打开哪一块面板？

约定：三种响应各有一个下一步，不要并列猜测。HTTP 200 且 code 为 businessCodeOk：拦截器会按成功放行，下一步做运行时校验，核对 amountFen 等字段还在，再交给 yuanText。HTTP 200 且 code 为 businessCodeFail：下一步看拦截器是否把非 0 当成失败并阻止更新列表。HTTP 500：还没有可按 0 或 40001 分支的成功信封，下一步看服务端。面板仍是 Network；文件分别是校验模块、拦截器、服务端日志。

基准算例：成功信封里的分是 19950，校验通过后展示文本才是 199.50。失败 code 是 40001，对应的列表仍应停在上一次成功的内容。教学用的 qpsTeach 是 50，只表示数量级。页面慢、列表空、金额错，都不能写成“系统就是 50 QPS”。50 不是压测结论，也不是容量承诺。

金额文本不是 yuanText 的结果Sources展示组件里调用 yuanText 的那一行
行高或文字被盖住Elements胜出的那条样式
控制台有异常Console栈里第一个属于订单页的文件
200 且 code 为 40001，列表却变了Network拦截器
200 且 code 为 0，但没有分Network运行时校验
HTTP 500Network服务端
易错：现象不带文件名

“列表不对”可能是金额文本、业务 code 或行高。先从上面六行里选一行，写下面板和文件，再改代码。

避坑：把 qpsTeach 写成性能结论

qpsTeach 等于 50，用来记住这是教学数量级。它不解释 10000 行的渲染，也不证明 8080 上的接口容量。性能测量留在第 9 章，而且要在缩到文件之后。

可操作对象：切换下面三种响应，读出下一步是运行时校验、拦截器还是服务端。不要在这一步写下 QPS。

三种响应，下一步看哪里切换一种响应
观察要点：① HTTP 200 且 code 为 businessCodeOk 时，下一步是运行时校验，核对 amountFen 后再交给 yuanText。② HTTP 200 且 code 为 businessCodeFail 时，下一步是拦截器，列表不应更新。③ HTTP 500 时，下一步是服务端，不要把正文猜成 40001。④ qpsTeach 的 50 不参与这次判断。

8.7 安装、类型检查、lint、构建、产物可复现

问题：我这台机器能打开订单页，流水线上为什么会装出另一版？

约定：流水线按同一顺序重复：安装、类型检查、lint、构建。安装使用仓库提交的 lock，使依赖停在锁定版本。类型检查重跑第 5 章那种字段约束，lint 重跑仓库规则，构建产出静态文件。脚本名以仓库为准。Node 主版本的命令示例按 nodeMajor 20 书写。产物可复现，指的是同一 lock、同一主版本约定下依赖树稳定；字节是否逐位相同，以所用构建工具的文档为准。

基准算例：锁定版本 semverLocked 是 1.4.2。没有 lock 时，解析可能走到 semverUnlocked 1.5.0。流水线应安装到 1.4.2。构建产物是静态文件，不是“开发服务器已经监听 5173”。这四步全绿，仍不表示屏幕文本已经等于 yuanText(19950)。

安装 → 停在 1.4.2 类型检查 → 订单 id 为字符串，金额为整数分 lint → 仓库规则 构建 → 静态产物 可复现 → 同一 lock、同一 Node 主版本约定
易错：把持续集成绿灯当成金额正确

安装、类型、lint 和构建都不读用户看见的 199.50。绿灯说明这四步在锁定的树上跑完，金额断言在下一节的用例里。

避坑：CI 不锁版本，装出 1.5.0

lock 没有进仓库时，流水线可能解析到 1.5.0，与本机曾经安装的 1.4.2 不是同一棵依赖树。密钥名 ORDER_API_SECRET 也不进安装脚本和前端产物，它只是名字。

可操作对象：列出流水线的四步，并在安装那一步旁写下期望版本 1.4.2。若实际是 1.5.0，先补 lock，再谈订单代码。

8.8 测用户看得见的行为、用例、缺陷记录

问题：测试通过了，用户却看不到正确的金额，这条测试在测什么？

约定：用例写成“给定、操作、用户看见”。给定使用教学订单的字段，不另造一套金额。操作是渲染、点击或输入。期望写用户能指着的结果。缺陷记录至少含页面路径、page、字符串形式的订单 id、期望文本和实际文本。只写“失败”无法复现。

基准算例：给定 amountFen 19950，用户应看见 orderMath.yuanText() 得到的 199.50。断言比较的是这个文本。amountYuan 为 199.5，199.5 === 199.5 成立，但比较的是同一个元字段，没有核对分，也不能代替屏幕文本。另一条看得见的行为：控件上输入 0，用户应看见 0；默认回退值才是库存 stock 8。不要把订单库存改成 0。分页用例看见的 page 是 1、size 是 20。

一条缺陷记录

页面 /orders，page 1，size 20，订单 id 为 snowflakeText 的原串。期望金额文本 199.50。实际文本写你看见的那一串。相关文件写展示组件或拦截器，二者先按上一节缩过。

易错：用 199.5 的偶然相等代替分

199.5 === 199.5 没有读取 19950，也没有读取 yuanText 的结果。它不能作为“金额已经正确”的用例。

避坑：缺陷只写失败

缺少 /orders、page 和字符串订单 id 时，下一个人无法打开同一次教学订单。id 保持文本，不要改成 JSON number 之后少 1 的那一串再拿来报缺陷。

可操作对象：写一条用例和一条缺陷，两张都含 page、订单 id 字符串，以及期望的金额文本。金额文本由 yuanText 产生。

8.9 组件测试看渲染、点击和输入，请求用假实现，不测框架内部

问题：组件测试要不要真的去请求 8080？

约定：组件测试只看三件事：渲染结果、点击之后看得见的变化、输入之后控件上的值。请求换成假实现，返回约定好的 code 和 amountFen，不访问 apiOrigin。不读取框架内部的更新队列，不步进 useState 的实现。钩子的语义仍以 React 文档原文为准；测试停在组件呈现给用户的结果上。生产草稿键是 order.draft。用例之间使用单独的键，或在前后清掉该键，避免互相写下这一份草稿。

基准算例：假实现返回 code businessCodeOk 0 和 amountFen 19950，以及字符串 id snowflakeText。渲染断言：屏幕金额文本等于 yuanText(19950)，即 199.50。点击或输入之后，断言仍读页面上的文本，例如输入 0 时看见 0，而不是库存 8。假实现不拼接 apiOrigin 与 apiPath。

易错：组件测试打到真实 8080

请求目标变成 apiOrigin 之后，这条测试看的是端口上的服务，不是金额文本。服务没开、返回 40001 或返回 500 时，失败原因和展示组件无关。

避坑：用例互相污染 order.draft，并去测框架内部

前一条用例把草稿写进 order.draft，后一条会看见别人的输入。清理或换键。断言不要读框架保存状态的内部结构；用户看不见的队列，不是这条测试的对象。

可操作对象：切换下面两种测试，读出这条测试看的是金额文本还是 apiOrigin。

断言看得见的金额，或连上真实接口切换测试在看什么
观察要点：① “断言看得见的 199.50”看的是金额文本，文本由 orderMath.yuanText(amountFen) 得到，请求停在假实现。② “连真实接口”看的是 apiOrigin，金额文本没有被这条测试读取。③ 两种分段都不使用 199.5 === 199.5。④ 假实现不写入共享的 order.draft。

8.10 编辑器、Chrome DevTools、React DevTools、Git、Wiki、评审、接口文档

问题：口头说金额没问题，单位跟接口文档对齐了吗？

约定：编辑器负责打开订单文件，菜单以所用编辑器的文档为准。Chrome DevTools 使用文档中的 Elements、Console、Sources、Network 这几个面板名；打开方式和其余菜单以当前 Chrome 文档原文为准，不把某一次点击顺序写成固定步骤。React DevTools 的 Components 面板用来看展示组件收到的 amountFen；Profiler 留到有测量的第 9 章，本章不靠它下结论。Git 保存 lock 和订单代码的差异。Wiki 只记录决定：金额以分进入页面，展示用 yuanText，HTTP 状态与业务 code 分开。评审核对可见文本、假实现和缺陷里的 page、订单 id。接口文档写出 apiPath、page、size、amountFen 的单位、雪花 id 为字符串、businessCodeOk 与 businessCodeFail，并与运行时校验使用同一组字段名。

基准算例：文档和评审卡上的数字仍是这一套：页面 /orders，接口 /api/orders，源分别是 5173 和 8080，金额分 19950，展示 199.50，成功 code 0，失败 code 40001，锁定版本 1.4.2。密钥只出现名字 ORDER_API_SECRET，值不进 Git、Wiki、接口文档和前端包。qpsTeach 50 可以在 Wiki 里被记成“教学数量级”，不能被记成性能承诺。

Chrome DevToolsElements、Console、Sources、Network 四块面板各看一类证据

接口文档路径、分、字符串 id、code 0 与 40001，和运行时校验同名
易错：评审只看能否编译

编译通过、lint 通过、开发服务器能开，都还没看 199.50，也没看 200 与 40001 的分支。评审清单写上可见文本和业务 code。

避坑：文档把 id 写成 JSON number，或写下密钥的值

本章避坑清单

  1. 不用 199.5 === 199.5 代替对分的断言。用户看见的文本来自 orderMath.yuanText()，基准是 199.50，分是 19950。
  2. 组件测试不打真实的 apiOrigin（8080）。请求用假实现，断言金额文本。
  3. Network 上的 HTTP 200 不等于业务成功。code 为 40001 仍是失败，列表不更新。
  4. 断点停在订单组件里调用 yuanText 的那一行，不步进框架源码。
  5. 持续集成使用 lock，安装停在 1.4.2，避免未锁定时走到 1.5.0。
  6. 缺陷记录写下 /orders、page 和字符串形式的订单 id，不单写“失败”。
  7. qpsTeach 的 50 只是数量级，不是性能结论，也不是容量承诺。
  8. 测试不要互相污染 order.draft。用例使用单独的键或在前后清掉。
