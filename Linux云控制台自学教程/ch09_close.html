第 9 章 · 对上证据

用日志把控制台走通

上一章分清了块设备上的 100 GiB 和文件系统上的 20 GiB。这一章把第 1 章到第 8 章收成一条链：控制台上的一种现象，对应系统里的一处证据。

预计学习 45 分钟 前置：第 1–8 章 分段演示 1 个
  • 能按基准实例把「创建后的身份、登录、放行、服务、磁盘」说成一条链。
  • 能按现象选到证据位置，并调用 Course.linux.evidence。
  • 能说明 /var/log/nginx/error.log 和 journalctl -u nginx 不是同一份记录。

9.1 前置检查

这条链要用到前面每一章。登录回看 第 2 章，两道门回看 第 7 章，磁盘回看 第 8 章。身份、路径、权限、sudo 和服务分别在 第 1 章、第 3 章、第 4 章、第 5 章、第 6 章。

下面 3 题各查一件事：登录、两道门、磁盘。它们单独计分，不计入章末自测。有一题不稳，先回那一章，再往下收这条链。

9.2 为什么学

控制台上同一种「打不开」，系统里可以是完全不同的证据。你要先给现象起名，再打开对应的那一处。

基准实例已经能按数字说完。它在区域 cn-demo-1，名字 web-demo，镜像 Ubuntu 22.04 LTS，登录用户 ubuntu，密钥 demo-key。安全组 sg-web-demo 放行 TCP 22（来源 198.51.100.20/32）和 TCP 80（来源 0.0.0.0/0）。nginx 成功时听在 0.0.0.0:80。数据盘 /dev/vdb 在控制台是 100 GiB；文件系统还没 resize 时，df -h /data 是 20 GiB。

这些数字前 8 章都用过。缺的是一条回头的路：网页一直转、连接被拒绝、ssh 连不上、df 仍是 20 GiB，各自回到哪一处。控制台截图里的「运行中」只说明虚拟机开着，回答不了上面任何一种现象。

这一章不增加新概念

主概念仍是：一种现象，对应一处证据。端口仍是 TCP 22 和 TCP 80。命令只用 Course.linux.commands 里已有的字符串。203.0.113.15 和 198.51.100.20 是文档保留地址，用来教学，不是某台真实服务器，也不是个人信息。

先想一下：实例显示运行中，网页却打不开。你准备继续截控制台的图，还是先把现象分成「一直转」或「连接被拒绝」？想完再看下一节。

9.3 核心概念：现象到证据

先看一个正例。浏览器一直转圈，页面出不来。这种现象的参数是 timeout。证据在安全组有没有放行 TCP 80；若 ufw 已经启用，还要看它有没有放行 80。本课用来看 ufw 的命令是 sudo ufw status。

先想一下：若浏览器直接提示连接被拒绝，你还去看安全组的 TCP 80 吗？

连接被拒绝是另一种现象，参数是 refused。两道门已经放行时，证据改去看 nginx 是否 active，以及是否听在 0.0.0.0:80。查看命令换成 journalctl -u nginx -n 20 --no-pager。一直转和连接被拒绝不共用一处证据。

反例是：无论哪一种打不开，都只刷新控制台的「运行中」，或者把 /var/log/nginx/error.log 和 journalctl -u nginx 当成同一份记录来回看。运行中不指向任何一条规则、任何一个监听或任何一块磁盘。错误日志和单元日志各记各的，看了一份，另一份仍要单独打开。

调用时只传入 ssh、timeout、refused、disk。返回值读三行：title（标题）、where（去哪看）、command（命令）。下表与 Course.linux.evidence 的返回值一致。演示里以函数当场返回的为准。

9.4 逐步走通整条链

上一节给出了失败时的入口。这一节把成功时要能说完的事实按顺序走一遍。数字只来自基准算例：区域 cn-demo-1 的实例 web-demo（ID i-demo0001，可用区 cn-demo-1a）。

身份

创建之后，你先核对三件套：区域是 cn-demo-1，实例名是 web-demo，镜像是 Ubuntu 22.04 LTS。登录用户是 ubuntu，绑定的密钥名是 demo-key。这三件套对上了，后面的命令才是在这台教学实例上执行。区域不同，列表里就没有这台 web-demo。

登录

登录要三条同时成立：用户名 ubuntu，密钥 demo-key，安全组 sg-web-demo 放行 TCP 22，来源仍是 198.51.100.20/32。基准命令是：

ssh -i demo-key.pem ubuntu@203.0.113.15

它使用公网地址 203.0.113.15。私网 10.0.1.15/24 给云里的其他资源用。现象若是 ssh 连不上，evidence('ssh') 的「去哪看」还包含密钥文件权限：/home/ubuntu/.ssh 建议 700，authorized_keys 建议 600，属主是 ubuntu。权限规则留在第 4 章，这里只把它当作 ssh 那一行的核对点。

放行

网页这条路有两道门。安全组 sg-web-demo 的 TCP 80 来源是 0.0.0.0/0。基准成功态里 ufw 未启用。系统里查看 ufw 用：

sudo ufw status

安全组规则在控制台看，不靠这一条命令。ufw 是否启用，用这一条看。两处都要看，才算把「放行」说完。

服务

实例在跑，回答不了 TCP 80 有没有进程在听。服务这一步沿用第 6 章的四条命令，顺序是安装、启动、看状态、看监听：

sudo apt-get install -y nginx
sudo systemctl start nginx
systemctl status nginx
ss -ltn

成功态是 nginx 听在 0.0.0.0:80。只听 127.0.0.1 时，公网仍到不了。包名和单元名在这台 Ubuntu 22.04 教学镜像上都是 nginx，配置文件是 /etc/nginx/nginx.conf。写配置要 sudo，那是第 5 章的事。

现象若已经是「网页连接被拒绝」，本章取证表把命令指到 journalctl -u nginx -n 20 --no-pager。ss -ltn 仍是第 6 章看套接字的那条。两条都在 commands 里，各看各的证据。

磁盘

数据盘设备是 /dev/vdb，挂载在 /data，整盘 ext4、没有分区。控制台容量是 100 GiB。文件系统还没 resize 时，df -h /data 是 20 GiB。你用这条 df 命令看见 20 GiB，那是现象。现象参数 disk 返回的命令是 sudo resize2fs /dev/vdb，因为要处理的证据是：这块盘的文件系统还没变大。

规格里的 4 GiB 是内存。系统盘 /dev/vda 是 40 GiB，挂在 /，不在这条数据盘的扩容里。

先想一下：控制台已经写成 100 GiB，你准备把 df 的结果说成 100 GiB，还是先承认未 resize 时仍是 20 GiB？

未 resize 时说 20 GiB。100 GiB 是块设备已经到达的大小，df 要等文件系统变大之后才会变成 100 GiB。

日志：两处，两份记录

服务和「连接被拒绝」都会把你带到日志。这里有两处，而且不是同一份：

  • nginx 错误日志写在 /var/log/nginx/error.log。这是 nginx 自己的那份文件。路径用绝对路径。登录后的当前目录是 /home/ubuntu，在家目录里用相对路径 error.log，到不了这份文件。
  • systemd 为单元 nginx 保留的记录，用 journalctl -u nginx 查看。本课这一条的完整字符串是 journalctl -u nginx -n 20 --no-pager。

同一时刻两边都可以有字。你看完错误日志，单元日志仍是另一份；看完 journalctl -u nginx，错误日志文件也不会因此被打开。commands 里没有为错误日志再列第二条命令。单元日志只用 commands.journal 这一条。

9.5 示范例题

题目：基准实例上，浏览器提示连接被拒绝。写出要看的位置，以及本课使用的命令。说明为什么这次不去改安全组的 TCP 80。

为什么选 refused

先把身份和两道门按基准数字核对完，连接被拒绝才站得住。

  1. 身份：区域 cn-demo-1，实例 web-demo，镜像 Ubuntu 22.04 LTS，用户 ubuntu，密钥 demo-key。你已经能登录，所以这次不是 ssh。
  2. 放行：安全组 sg-web-demo 的 TCP 80 来源是 0.0.0.0/0。ufw 处于基准成功态，未启用。两道门都放行时，现象不应再是一直转。
  3. 因此参数选 refused。去哪看：nginx 是否 active，以及是否听在 0.0.0.0:80。只听 127.0.0.1 时，公网这边仍是连接被拒绝。
  4. 命令用 commands.journal。磁盘的 100 GiB / 20 GiB 回答不了「连接被拒绝」。

在实例上查看单元日志时，输入下面这一行。它与 commands.journal 逐字相同：

journalctl -u nginx -n 20 --no-pager

同一行写在 examples/ch09/journal.sh。页面摘录与该文件一致，末尾有换行。

看这 20 行的同时，nginx 错误日志仍在 /var/log/nginx/error.log。你要单独按这个绝对路径打开它。两份记录都可能解释「进程为什么没在 0.0.0.0:80 上听」，但它们不是同一份，不能用其中一份代替另一份。

这道题选 journal 这条命令，是因为现象已经定为连接被拒绝。ss -ltn 用来核对套接字还在不在，留在服务那一步，不把取证表改写成另一条命令。

9.6 常见错误

只在控制台截图里找原因

运行中、100 GiB、安全组页面各截一张，就认为原因已经找到。

先选定 ssh、timeout、refused 或 disk，再打开 evidence 给出的那一处。运行中只说明虚拟机开着。

把 nginx 错误日志和 systemd 日志当成同一份

看过 /var/log/nginx/error.log，就认为 journalctl -u nginx 不必再看。

错误日志是 nginx 写入的文件。单元日志是 systemd 为单元 nginx 保留的记录。本课查看后者的命令是 journalctl -u nginx -n 20 --no-pager。

现象和证据错行

网页一直转，却只去读 journal；df 仍是 20 GiB，却去改安全组的 TCP 80。

timeout 看安全组 sg-web-demo 的 TCP 80，以及 ufw 是否被启用，命令是 sudo ufw status。disk 看 /dev/vdb 的文件系统，命令是 sudo resize2fs /dev/vdb。

journalctl 的参数以发行版文档为准

不同发行版文档里，journalctl 的参数写法要以那份文档为准。本课查看命令以 commands.journal 为准，就是 journalctl -u nginx -n 20 --no-pager。做这道教学题时按这一行输入，不在后面自行追加参数。

两处易错（只看截图、两份日志当成一份）和参数这条避坑，都收进章末清单。下一节用四类题检查你能不能自己走这张表。

9.7 四类练习

先做再看解析。解析给出正确结果、关键步骤、常见错法，以及应回看的节。

回忆

合上页面，用一句话说出本章的主概念，并按顺序说出这条链的五段：创建后的身份、登录、放行、服务、磁盘。

回忆的答案

正确结果：控制台上的一种现象，对应系统里的一处证据。链的顺序是身份、登录、放行、服务、磁盘。

关键步骤：现象用 ssh、timeout、refused、disk 四个参数进入 evidence；链用基准实例 web-demo 把前 8 章串起来。

常见错法：把「运行中」说成主概念，或把链说成只剩日志。运行中只说明虚拟机开着；日志是取证时要分开看的两份记录。

回看 9.3 核心概念，以及 9.4 逐步走通整条链。

辨析

有人说：/var/log/nginx/error.log 和 journalctl -u nginx 是同一份记录，看哪一边都可以。这个说法哪里错了？本课查看单元日志时该输入哪一条命令？

辨析的答案

正确结果：这两处不是同一份记录。错误日志是文件 /var/log/nginx/error.log。单元日志用 journalctl -u nginx -n 20 --no-pager 查看。

关键步骤：先指出两边的存放位置不同，再写出 commands.journal 的原文。参数以发行版文档为准，本课这一条以该字符串为准。

常见错法：认为 nginx 单元一旦 active，两份日志就会自动合成一份。active 只说明服务状态，不把两个记录位置合并。

回看 9.3 的反例，以及 9.6 常见错误。

应用

仍是基准实例：区域 cn-demo-1，web-demo，Ubuntu 22.04 LTS。安全组 sg-web-demo 已放行 TCP 80，来源 0.0.0.0/0，ufw 未启用。浏览器提示连接被拒绝。写出 evidence('refused') 的去哪看和命令。

应用的答案

正确结果：去哪看是「nginx 是否 active，以及是否听在 0.0.0.0:80」。命令是 journalctl -u nginx -n 20 --no-pager。

关键步骤：两道门已经按基准放行，ufw 未启用，所以排除 timeout。剩下的现象是 refused。磁盘上控制台 100 GiB、df 20 GiB 对不上连接被拒绝。

常见错法：因为网页打不开，就去删 TCP 80 的来源，或把命令写成一条 commands 里没有的查看命令。ss -ltn 可以另看套接字，但不替换这一行的 journal 命令。

回看 9.5 示范例题。

迁移

现象改成 timeout。实例仍是 web-demo，你已经能登录。要看哪两处？命令用 commands 里的哪一条？做完后用 9.8 的步骤再走一遍。

迁移的答案

正确结果：看安全组 sg-web-demo 的 TCP 80，以及 ufw 是否被启用。命令是 sudo ufw status。

关键步骤：evidence('timeout') 的标题是「网页一直转」。安全组在控制台核对，基准来源是 0.0.0.0/0。ufw 用上面这条命令看；基准成功态是未启用。若 ufw 已被启用，还要看它有没有放行 80。

常见错法：一直转却去读 journal，或只看 TCP 22。TCP 22 属于 ssh 那一行。连接被拒绝才把命令指到 journal。

回看 9.8 迁移。若两道门的差别不稳，再回看第 7 章。

9.8 迁移

上一节的迁移题放在一个完整现场里做一遍。实例仍是区域 cn-demo-1 的 web-demo，镜像 Ubuntu 22.04 LTS，用户 ubuntu，密钥 demo-key。你已经用 ssh -i demo-key.pem ubuntu@203.0.113.15 登录，所以这次不把 TCP 22 当作证据入口。浏览器一直转，没有出现「连接被拒绝」。

参数选 timeout。按返回的「去哪看」做两步：

  1. 在控制台打开安全组 sg-web-demo，核对入方向 TCP 80。基准来源是 0.0.0.0/0。这一条没放行时，网页会一直转。
  2. 在系统里看 ufw 是否被启用。命令只用 sudo ufw status。基准成功态是未启用。若你发现它已被启用，再核对有没有放行 80。启用了却没放行 80，结果同样是一直转。

命令栏只有 ufw 这一条，是因为安全组在控制台看，ufw 在系统里看。两处都对上之后，若现象变成连接被拒绝，再改走 refused：nginx 是否 active，是否听在 0.0.0.0:80，命令换成 journalctl -u nginx -n 20 --no-pager。df 仍显示 20 GiB 时，那是 disk 行，命令是 sudo resize2fs /dev/vdb，与这次一直转无关。

这一节的结果：现象选 timeout 时，你看安全组 sg-web-demo 的 TCP 80，以及 ufw 是否被启用。

本章避坑清单

  1. 只在控制台截图里找原因。运行中只说明虚拟机开着。先选定现象，再打开 evidence 指出的那一处。
  2. 把 nginx 错误日志和 systemd 日志当成同一份。/var/log/nginx/error.log 是 nginx 的错误日志文件；journalctl -u nginx 是单元日志。两处分开看。
  3. journalctl 的参数以发行版文档为准。本课查看命令以 commands.journal 为准：journalctl -u nginx -n 20 --no-pager。
  4. 现象选 timeout 时，要看安全组 sg-web-demo 的 TCP 80，以及 ufw 是否被启用。命令是 sudo ufw status。不要把一直转拿去对磁盘或只对错误日志。
  5. 教学词不是某一家云控制台的固定按钮名。用到自己的账号时，打开该厂商现行文档，把区域、实例、安全组、密钥换成那边现在的按钮名。

本章小结与延伸阅读

一句话：控制台上的一种现象，对应系统里的一处证据；基准实例从身份、登录、放行、服务走到磁盘，失败时回到 ssh、timeout、refused、disk 其中一行。

  • 身份是区域 cn-demo-1、实例 web-demo、镜像 Ubuntu 22.04 LTS，用户 ubuntu，密钥 demo-key。
  • 登录看 TCP 22 来源 198.51.100.20/32，命令是 ssh -i demo-key.pem ubuntu@203.0.113.15。
  • 放行看安全组 TCP 80 来源 0.0.0.0/0，以及 ufw 是否启用。基准成功态 ufw 未启用，nginx 听在 0.0.0.0:80。
  • 数据盘 /dev/vdb 在控制台是 100 GiB；未 resize 时 df 为 20 GiB。
  • /var/log/nginx/error.log 和 journalctl -u nginx 不是同一份记录。
