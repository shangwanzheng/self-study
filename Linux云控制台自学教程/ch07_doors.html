第 7 章 · 跑起来

两道门都要放行

公网要打开基准实例上的 80 端口，包先过安全组，再过系统里的 ufw。两道门都放行、却没有进程在听时，你得到的是连接被拒绝，页面不会一直转。

预计学习 40 分钟 前置：第 6 章 开关演示 1 个
  • 能说明基准实例的 ufw 默认未启用。
  • 能区分「连不上」和「连接被拒绝」。
  • 能判断安全组、ufw、监听三项怎样组合成结果。

7.1 前置检查

第 6 章你已经能判断：实例显示运行中，仍要分开看 nginx 装了没有、是不是 active、听在哪个地址。这一章把绑定地址固定在成功态 0.0.0.0，只新增两道门。先用下面三题确认第 6 章还在。

7.2 为什么学

服务已经听在 0.0.0.0:80，浏览器仍可能打不开。包还要过云上的安全组，和系统里的防火墙。

你在第 6 章把 nginx 放到了监听这一步。刷新 203.0.113.15 时，页面仍可能停住。停住有两种样子，后面要靠它们决定你去改安全组、去看 ufw，还是回到「有没有进程」。

这一章只做这一件事：给定安全组、ufw 和监听三样事实，读出模型的 label 和 reason。label 只会是打得开、连不上、连接被拒绝。

7.3 核心概念

公网访问基准实例的 TCP 80，要过两道门。第一道在云控制台：安全组 sg-web-demo 的入方向 TCP 80，来源 0.0.0.0/0。第二道在系统里：ufw。第三件不是门：有没有进程听在 0.0.0.0:80。

基准成功态三件同时成立：安全组已经放行 TCP 80，ufw 未启用，nginx 听在 0.0.0.0:80。这时 label 是打得开，reason 是「安全组、ufw 和 0.0.0.0:80 都成立」。ufw 未启用，就是第二道门没有拦你，模型把这种情况算进「ufw 成立」。

两道门怎样算放行

安全组放行，是 sg80 为真。ufw 这一道放行，是「未启用」，或者「已启用并且放行了 80」。两道都放行之后，还要有进程听在 0.0.0.0:80，页面才打得开。

反例先记一句：两道门都放行，但没有进程。这时 label 是连接被拒绝。reason 是「两道门都放行，但没有进程监听 80」。下一节把「连不上」和「连接被拒绝」拆开。

绑定地址本章不动

调用时 bind 固定传入 baseline.bind，也就是 0.0.0.0。模型里还有一种拒绝：进程只听 127.0.0.1，reason 是「进程只听 127.0.0.1，公网到不了」。那是第 6 章的失败。本章演示不设这个开关。

先想一下

安全组已经放行 TCP 80，ufw 已启用，却没有放行 80，nginx 仍听在 0.0.0.0:80。你预期 label 是打得开、连不上，还是连接被拒绝？先选一个，再看下一节。

核心概念给出了三件事。这一节按模型的判断顺序走两种失败：门没开时是连不上；两道门都开了、没人听时是连接被拒绝。

绑定地址固定传入 baseline.bind（0.0.0.0）。来源 0.0.0.0/0 写在安全组规则上，不另设开关。203.0.113.15 是文档用地址。

观察要点：① 关掉「安全组放行 80」，label 变成连不上，reason 指向 sg-web-demo。② 安全组开着，只打开「ufw 已启用」、不勾「ufw 放行 80」，仍是连不上，reason 指向 ufw。③ 两道门都放行，关掉「有进程监听」，label 变成连接被拒绝。④ ufw 未启用时，勾不勾「ufw 放行 80」，label 不变。

第一种失败：连不上

模型先看安全组。只要 sg80 为假，就返回 label「连不上」，reason「安全组 sg-web-demo 未放行 TCP 80」。后面的 ufw 和监听不再参与这一次结果。浏览器里页面会一直转。

安全组已经放行时，模型才看第二道门。ufw 已启用，并且没有放行 80，同样返回「连不上」，reason 换成「ufw 已启用且未放行 TCP 80」。nginx 正在听，也改变不了这一步：包还没走到进程。

所以上一节那个问题的答案是连不上。有人在听，只在两道门都放行之后才有意义。

两种原因共用一个 label。你从浏览器看不出是哪一道门。要同时看控制台里 sg-web-demo 的 TCP 80，以及实例上的 sudo ufw status。

第二种失败：连接被拒绝

先想一下

安全组已放行，ufw 未启用，没有进程听 80。页面还会一直转吗？

不会。两道门都放行之后，模型看到 listening 为假，返回 label「连接被拒绝」，reason「两道门都放行，但没有进程监听 80」。页面会很快告诉你拒绝。一直转属于上一小节的「连不上」。

ufw 已启用并且放行了 80，同样算第二道门放行。这时如果没有进程，label 仍是连接被拒绝。基准实例走的是另一条放行路径：ufw 未启用。

模型怎么排这三步

你自己判断时，按这个顺序，中途返回就停：

  1. 安全组放行 TCP 80 了吗？没有，label 是连不上，原因在 sg-web-demo。
  2. ufw 是否已启用？已启用且未放行 80，label 仍是连不上，原因在 ufw。未启用则这道门不拦，进入下一步。
  3. 有没有进程听在 0.0.0.0:80？没有，label 是连接被拒绝。有，label 是打得开。

这是教学模型里的表现

在本课里，安全组未放行，和「ufw 已启用且未放行 80」，label 都是连不上。你自己的云上，安全组默认放行哪些端口，以该厂商现行文档为准。本课只规定教学安全组 sg-web-demo：入方向 TCP 80 的来源是 0.0.0.0/0。ufw 在这台镜像上的具体输出，以你运行的状态命令和发行版文档为准。

7.5 示范例题

两种失败都看过了。把开关拨回基准成功态，核对「打得开」是哪三件事凑出来的。

基准实例 web-demo

实例 web-demo（i-demo0001），区域 cn-demo-1，镜像 Ubuntu 22.04 LTS，公网地址 203.0.113.15。这个地址是文档用地址，用来指这台教学实例，不是某台真实服务器。

安全组用 sg-web-demo。入方向 TCP 80 的来源是 0.0.0.0/0。ufw 未启用。nginx 听在 0.0.0.0:80。绑定地址用 baseline.bind。

代进 reach80 的四个量是：sg80 为真，ufwActive 为假，ufwAllow80 不参与，listening 为真，bind 为 0.0.0.0。顺序走下来：安全组放行了；ufw 未启用，第二道不拦；有进程，并且绑定地址就是成功态。所以 label 是打得开，reason 是「安全组、ufw 和 0.0.0.0:80 都成立」。

选这组数，是因为它就是全课唯一的基准成功态。ufw 写成未启用，是因为这台教学实例就是这样，不是因为「所有镜像都不开防火墙」。有的镜像默认不开 ufw，这台恰好如此；换一台镜像之前，先看状态。

在实例上只看 ufw 时，用这一条命令。前面的 sudo 沿用第 5 章：登录用户是 ubuntu。

sudo ufw status

页面上的命令和 examples/ch07/ufw.sh 逐字相同。基准实例上，你要读到的结论是 ufw 未启用。输出的具体字样以这台镜像的文档为准。本章只用这一条命令，不另给修改防火墙的命令。

有的镜像默认不开 ufw

先跑上面的命令看这台，不要把另一台机器的印象抄过来。基准实例的 ufw 是未启用。未启用时，演示里的「ufw 放行 80」不改变 label。

不要把一家云的默认写成普遍事实

安全组默认放行什么、按钮叫什么，各家控制台不一样，以你所用厂商的现行文档为准。本课能确定的只有教学安全组 sg-web-demo 上的这条 TCP 80。

7.6 常见错误

例题的结果是打得开。下面三种改法会让你以为已经修好，或者修错地方。

只改安全组
sg-web-demo 放行了 TCP 80，网页就该开。 若 ufw 已启用且未放行 80，label 仍是连不上。reason 会写成「ufw 已启用且未放行 TCP 80」。两道门都要看。
只关 ufw，安全组没放行
把 ufw 关掉之后，不管安全组，页面应该打得开。 模型先看安全组。sg80 为假时，label 是连不上，reason 指向 sg-web-demo。关掉 ufw 改变不了这一步。
把连接被拒绝当成安全组丢包
浏览器说连接被拒绝，就去改安全组。 连接被拒绝表示两道门已经放行，没有进程听 80。安全组未放行时，label 是连不上，页面会一直转。拒绝出现后，回到第 6 章看有没有进程听在 0.0.0.0:80。

这三处都会收进章末避坑清单。演示里可以用右侧三个对照按钮各走一遍，读 reason 的主语是安全组、ufw，还是「没有进程」。

7.7 四类练习

错误看过了。这一节做回忆、辨析和应用。第四类迁移放在下一节：只把「有进程监听」关掉。

回忆

合上演示。公网访问这台基准实例的 TCP 80，两道门分别是什么？label 有哪三个？基准实例的 ufw 是启用还是未启用？

解析

正确答案：第一道门是安全组 sg-web-demo 的入方向 TCP 80，第二道门是系统上的 ufw。三个 label 是打得开、连不上、连接被拒绝。基准实例的 ufw 未启用。

关键步骤：先点名两道门，再点名三个 label，最后答 ufw 的基准状态。「一直转」是连不上在浏览器里的样子，不是第四个 label。

常见错误：只答安全组。错因是把云上的那道门当成唯一的门。另一错是说基准实例的 ufw 已启用。错因是把别的镜像的习惯套到这台教学实例上。

回看：只答了一道门，回看 7.3 核心概念。ufw 状态答错，回看 7.5 示范例题。

辨析

下面两句，指出哪句成立。

甲：安全组没放行 TCP 80 时，页面会一直转，label 是连不上。

乙：看到连接被拒绝，就说明安全组把包丢了，应该先改 sg-web-demo。

解析

正确答案：甲成立。乙不成立。

关键步骤：安全组未放行，模型在第一步返回「连不上」。连接被拒绝出现在两道门都放行、且没有进程的时候。丢包那种一直转，对应的 label 是连不上。

常见错误：认为乙成立。错因是把两种失败收成一种，看到拒绝就去改安全组。

回看：7.4 逐步讲解两种失败，以及 7.6 常见错误里的第三条。

应用

仍用基准实例 web-demo，公网地址 203.0.113.15（文档用地址），安全组 sg-web-demo。现在的事实是：安全组已放行 TCP 80，来源 0.0.0.0/0；ufw 已启用，没有放行 80；nginx 仍听在 0.0.0.0:80。绑定地址仍是 0.0.0.0。

label 和 reason 各是什么？你下一步看哪里？

解析

正确答案：label 是连不上。reason 是「ufw 已启用且未放行 TCP 80」。下一步在实例上执行 sudo ufw status，并对照安全组里的 TCP 80。命令和 examples/ch07/ufw.sh 一致，写在 7.5 示范例题里。

关键步骤：安全组已经放行，所以不会得到「安全组 sg-web-demo 未放行 TCP 80」。ufw 已启用且未放行，模型在查看监听之前返回。nginx 在听，参与不了这一次结果。

常见错误：答打得开。错因是只看见有进程。另一错是答连接被拒绝。错因是把「门没开」和「没人听」对调了。

回看：7.4 逐步讲解两种失败。若命令记串了，回看 7.5 示范例题。

7.8 迁移

前三类做完了。换掉一件事：两道门保持放行，把 listening 改成假。

换一组开关

安全组仍放行 TCP 80，来源仍是 0.0.0.0/0。ufw 保持基准实例的未启用。绑定地址仍是 baseline.bind（0.0.0.0）。没有进程听 80。

label 是什么？页面会一直转吗？把演示里的「没人听」按出来，对照你的判断。

解析

正确答案：label 是连接被拒绝。页面不会一直转。reason 是「两道门都放行，但没有进程监听 80」。

关键步骤：安全组放行，第一步过了。ufw 未启用，第二道门不拦，模型把这算作放行。然后 listening 为假，落到连接被拒绝。若把第二道门换成「ufw 已启用且已放行 80」，listening 仍为假，label 同样是连接被拒绝。

常见错误：答连不上，并预期页面一直转。错因是把「没人听」当成安全组丢包。另一错是去关 ufw 或改安全组。错因是两道门已经放行，该回到第 6 章检查有没有进程。

回看：结果答成连不上，回看 7.4 第二种失败。去改已经放行的门，回看 7.6 常见错误。

本章避坑清单

  1. 只改安全组。ufw 已启用且未放行 80 时，label 仍是连不上。
  2. 只关 ufw，安全组却没放行 TCP 80。模型先看安全组，结果仍是连不上。
  3. 把「连接被拒绝」当成安全组丢包。拒绝表示两道门已经放行，没有进程在听；安全组未放行时页面会一直转，label 是连不上。
  4. 有的镜像默认不开 ufw。先用 sudo ufw status 看这台，不要凭别的机器的印象。
  5. 不要把某一家云的默认安全组写成普遍事实。按钮名以该厂商现行文档为准。本课只规定教学安全组 sg-web-demo 的 TCP 80，来源 0.0.0.0/0。
  6. 基准实例的 ufw 是未启用。未启用时，「ufw 放行 80」不改变 label。

本章小结与延伸阅读

公网访问 80，安全组和 ufw 都要放行；两道门都放行但没有进程监听时，结果是连接被拒绝。

  • 基准实例的 ufw 未启用。未启用不拦 80，也不要把它说成所有镜像的默认。
  • 连不上：安全组未放行，或 ufw 已启用且未放行 80。页面会一直转。
  • 连接被拒绝：两道门都放行，没有进程听 80。这不是安全组丢包。
