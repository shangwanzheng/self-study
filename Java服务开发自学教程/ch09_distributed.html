9.1 单体、集群、分布式、微服务各解决什么

问题：同事说「我们是微服务」「这台挂了还有集群」，这四个词说的不是一件事。分不清它们，后面的注册中心、网关、分布式事务就没有附着点。

约定

本章用「进程」指一份独立运行的 Java 程序（一个 JVM）。「服务」指按业务能力划分、可以单独部署的一组进程。图里的份数和服务数都是示意，不是容量结论。

形态解决什么多出来的问题
单体一个进程完成全部业务，部署、调试、本地事务都最简单发布和故障域绑在一起，一个模块出问题拖垮整个进程
集群同一份程序跑多份，前面加负载均衡，解决单机容量和单点内存里的会话、本地缓存、synchronized 各台不共享
分布式不同进程分工，缓存、消息、存储交给专门的进程每一跳都可能超时；同一份数据有多个副本，开始有一致性问题
微服务按业务能力拆服务，各自独立部署和扩缩调用链变长，数据拆到多个库，@Transactional 管不到另一个库

前端也有单体仓库和微前端。微前端解决发布和团队边界，不等于后端拆成了微服务；前端只认网关一个地址时，后面是单体还是十个服务，从浏览器看不出来。

基准算例：查一次教学订单

单体里，查 userId 10001 的订单并显示库存 8，是一个进程里的两次方法调用和一次 SQL。拆成用户、订单、库存三个服务后，同一个页面要经过网关和三个服务，任何一跳超时（第 4 章的连接 500 ms、读 2000 ms）都会让页面失败。

集群不等于微服务

同一个 jar 跑三份是集群，不是微服务。它没有拆业务，只是多了几份；会话和本地锁不共享的问题却已经出现了。

为了「像大厂」先拆服务

教学订单的数据量（listN 10000 条）一个单体加一个 MySQL 就够。拆分的代价是调用链、数据和事务，没有发布边界或团队边界的需要时，先别拆。

四种形态下的一次查询切换形态
观察要点：① 从单体切到集群，服务种类不变，份数变了；② 切到微服务，一次查询经过的服务数变多，扣库存跨了库；③ 右侧「多出来的问题」就是本章后面各节的入口。

9.2 分区时放弃哪一头

问题：两个副本之间的网络断了（分区），此时又来一个写请求。系统要么拒绝它、保住两边一致，要么接受它、让另一边暂时读到旧值。CAP 说的就是这一刻的取舍。

约定

C 一致性：读到的是最近一次成功写入的值。A 可用性：每个请求都得到非错误的响应。P 分区容错：网络分区时系统仍按约定行为。跨机器的系统必须面对 P，所以取舍只发生在 分区期间的 C 与 A 之间。本章不讲 Paxos、Raft 的证明，只用它的结论。

  • 偏 CP：分区时拒绝部分读写，保一致。选主、注册中心的集群元数据常这样做。
  • 偏 AP：分区时继续服务，恢复后再收敛，这叫最终一致。
  • 改昵称可以最终一致；扣库存要更强的保证，通常让库存只有一个写入的地方（一个主库、一个事务）。
基准算例：分区期间在 A 上买 1 件

两个副本 A、B 上的 stock 都是 8。分区期间在 A 上买 1 件：偏 CP 时这次写被拒绝，两边仍是 8，从 B 读到的 8 是当前值；偏 AP 时 A 变成 7，从 B 读到的 8 是旧值，网络恢复后 B 才收敛到 7。

「三选二」不是平时也要丢一个

没有分区时，C 和 A 可以同时满足。CAP 只说分区发生时不能两全，不是说系统平时就必须放弃一致或放弃可用。

刷新后数据「变回去」当成前端缓存问题

前端看到刚提交的值刷新又变回去，常常是读请求落到了还没赶上的副本上。先问后端这个接口读的是主还是从、是不是最终一致，再去清浏览器缓存。

分区时保一致还是保可用切换网络状态与取舍
观察要点：① 网络正常时两种取舍读到的都是 7；② 分区中选 CP，下单失败，从 B 读到的 8 是当前值；③ 分区中选 AP，下单成功，从 B 读到的 8 是旧值；④ 恢复后 AP 收敛到 7。

9.3 缓存教学订单时的三种故障

问题：给「按 userId 查订单与库存」加 Redis 缓存后，接口快了。但有三种情况会让大量请求越过缓存直接打到数据库：击穿、穿透、雪崩。

约定

本节用最常见的旁路缓存：读时先查缓存，未命中再读库并写回缓存；写时先写库，再删缓存。Redis 是服务端共享缓存，和浏览器的 HTTP 缓存不是一回事。持久化（RDB 快照、AOF 命令日志）只需知道宕机可能丢最后一小段。

故障现象常用对策
击穿一个热键过期的瞬间，大量并发请求同时去读库重建互斥重建（只放一个去读库），或逻辑过期
穿透查一个不存在的键，缓存永远不命中，每次都读库缓存空值并给短过期，或布隆过滤器
雪崩大量键同一时刻过期，或 Redis 整体不可用过期时间加随机抖动，准备降级
基准算例：stock 8 的缓存

缓存里存着教学订单 stock = 8。下单扣到 7：先在事务里把库里的 8 改成 7，再删掉缓存。若删缓存失败，之后的读会一直拿到旧的 8，直到这个键过期。所以缓存必须有过期时间，删除失败要重试或记日志。

「库和缓存都写成功才算完成」

写库和写缓存是两个系统，不在一个事务里。库已提交、删缓存之前进程崩溃，就有一段时间缓存是旧值。要接受这个失败窗口并用过期时间兜底，而不是假设两边同时成功。扣库存的判断要以数据库为准，不能以缓存里的 8 为准。

没有过期时间的缓存

不设过期时间，一次删缓存失败就会让旧值永远留下，内存也只增不减。每个键都要有过期时间，批量写入的键再加抖动，免得同一秒一起过期。

同时到达的请求有几个打到数据库切换故障 · 拖动滑块 · 打开对策
观察要点：① 正常命中时打到数据库的是 0；② 击穿和穿透不加对策时，打到库的次数等于并发数；③ 打开对策后击穿、穿透降为 1；④ 雪崩的抖动只是把同一秒的读库摊开，数字是示意。

9.4 Redis 锁的过期

问题：集群里多台机器都能扣库存，synchronized 只锁得住本机。常见做法是在 Redis 里放一把锁。它很快，也最容易用错：锁过期了业务还在跑，或者删掉了别人的锁。

约定

加锁用一条命令同时完成「不存在才设置」和「设置过期」，值里放持有者标识（例如请求 id）。解锁必须先比较值、是自己的才删，两步要原子执行，用 Lua 脚本或客户端库提供的等价操作。Redlock 针对多个 Redis 实例，存在争议，本章不展开。

SET lock:stock:teach  <请求 id>  NX  PX  <过期毫秒>

-- 解锁：值是自己的才删除
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end

业务可能比过期时间长时要续期。Redisson 的看门狗就是在持有期间定时把过期时间往后推；进程挂了就不再续，锁到期自然释放。

基准算例：锁过期后又扣了一次

请求 A 拿锁后读到 stock 8，业务还没写回，锁先过期。请求 B 拿到锁，也读到 8，写回 7。A 结束时写回 7。卖出 2 件，库存却只少了 1 件，超卖 1 件。A 最后若直接 DEL，还会把 B 的锁删掉，让第三个请求也进来。

解锁直接 DEL

锁过期后已经属于别人。不比较值就 DEL，删的是别人的锁。「先 GET 再 DEL」分两条命令也不行，中间可能换了主人。

锁过期后另一个请求又扣 stock

过期时间按「平时多快」估，碰到一次 Full GC 或慢 SQL 就超了。要么续期，要么在数据库上再兜一层：UPDATE ... SET stock = stock - 1 WHERE stock >= 1，以影响行数判断是否扣成功。锁只用来减少冲突，不要把它当成正确性的唯一保证。

锁过期、续期与安全解锁的时序拖动滑块 · 勾选开关
观察要点：① 业务时长短于过期时间时，B 在 A 解锁后才进入，最终 6；② 业务长于过期时间且不续期，B 在 A 仍在跑时进入，最终 7，超卖 1 件；③ 打开看门狗续期后恢复为 6；④ 关闭「比较持有者」时，A 结束会删掉 B 的锁。

9.5 交换机/队列和主题/分区

问题：「订单已创建」要通知库存、邮件、审计。用 RabbitMQ 时你会听到交换机、路由键、队列；用 Kafka 时听到主题、分区、消费组、位移。两套词不能互相套用。

约定

RabbitMQ：生产者发给交换机，交换机按路由键和绑定规则投到队列，消费者从队列取。常用交换机类型是 direct（路由键完全相等）、fanout（广播给所有绑定队列）、topic（* 匹配一个词，# 匹配零个或多个词）。Kafka：主题是逻辑名，分区是并行和顺序的单位；同一分区内有序，一个消费组里一个分区同时只给一个消费者。

要保证的语义倾向无论选谁都要回答
灵活路由、较低延迟的业务消息RabbitMQ重复怎么办、堆积怎么办、能不能回溯、失败进不进死信
高吞吐日志和事件流，需要回放Kafka
事务消息、延迟、顺序这类业务消息RocketMQ（碰到再展开）
基准算例：userId 10001 的三条事件

用户 10001 依次产生「创建、支付、发货」。Kafka 以 userId 为分区键时，三条落在同一个分区，消费顺序和产生顺序一致；用随机键时可能分到不同分区，消费者看到「发货」早于「支付」是可能的。

交换机和队列当成同一个东西

RabbitMQ 的交换机不存消息，只负责转发。没有队列绑定到它，消息发出去就没了。排查「消息丢了」先看绑定，再看消费者。

为了全局有序只开一个分区

Kafka 只在分区内有序。为全局有序只开一个分区，吞吐就只剩一个消费者。通常只需要「同一个用户或同一笔订单有序」，用它做分区键即可。

消息落到哪个队列、哪个分区切换交换机类型、路由键、分区数与分区键
观察要点：① fanout 不看路由键，三个队列都收到；② direct 下绑定键 order.* 只是字面量，匹配不到 order.created；③ Kafka 以 userId 为键时三条事件同分区、有序；④ 改成随机键后分区散开。分区号用的是示意哈希，不是 Kafka 的真实算法。

9.6 至少一次和重复扣库存

问题：消费者收到「订单已支付」去扣库存。网络抖一下、消费者重启一下，同一条消息就可能再来一次。8 件库存会不会被减两次？

约定

消息投递有三种语义：至多一次（可能丢）、至少一次（可能重复）、恰好一次（要靠端到端配合，不是队列单方面能承诺的）。业务消息默认按至少一次设计，消费端必须幂等：同一条消息处理多次，结果和处理一次相同。

  • RabbitMQ：处理成功之后再确认（ack）。先 ack 再处理，处理时崩溃消息就没了。
  • Kafka：先处理后提交位移，崩溃会重复；先提交后处理，崩溃会丢。默认接受重复，把处理做成幂等。
  • 幂等的常见做法：以消息 id（或业务单号）建唯一键去重表，去重记录和扣库存放在同一个本地事务里。
-- 同一个事务
INSERT INTO consumed_msg(msg_id) VALUES (?);          -- 唯一键，重复插入即失败，整笔回滚
UPDATE stock SET stock = stock - 1 WHERE sku = ? AND stock >= 1;
基准算例：同一条消息投递 2 次

stock 8，一条「买 1 件」的消息投递 2 次。不做幂等：扣两次，剩 6，多扣 1 件。做了去重：第二次插入去重表失败、整笔回滚，剩 7。

消费成功和扣库存不是同一时刻

扣完库存、确认之前崩溃：消息会重投，没有幂等就重复扣。先确认、扣库存之前崩溃：消息不会再来，订单已付款而库存没扣。两种顺序各有一种坏结果，「先确认」把重复换成了丢失，不是解决。

消费端不防重复，8 件库存被减两次

只写 WHERE stock >= 1 防不住重复：8 和 7 都满足条件。必须有按消息 id 的去重，且与扣减在同一事务里。也不要指望换一个「号称恰好一次」的队列就不用管消费端。

投递次数与库存被减几次拖动投递次数 · 切换崩溃点 · 打开幂等
观察要点：① 不做幂等时，投递几次就减几次；② 打开幂等后，无论投递几次都只减 1 次，剩 7；③ 「扣后确认前崩溃」至少多投一次；④ 「确认后扣前崩溃」一次都没减，幂等也救不回来。

9.7 注册与配置不要打进包里

问题：订单服务要调库存服务，库存服务有几台、在哪个地址？读超时要从 2000 ms 调一下，难道重新打 jar？注册中心回答前一个问题，配置中心回答后一个。

约定

以 Nacos 为例。注册：实例启动时登记服务名和地址，临时实例靠心跳续约，心跳停了一段时间后被摘除；调用方订阅服务名，在本地缓存实例列表。配置：按 Data ID 和 Group 定位一份配置，变更后标了刷新的 Bean 能更新。心跳间隔、摘除时间等参数以 Nacos 文档为准，本章不列参数表。

  • 前端只访问网关。实例增减应被网关和调用方消化，不需要前端发版改地址。
  • 前端的环境变量在构建时烙进包里；服务端配置可以在运行时改，这是两者的分界。
  • 配置中心地址本身不能只放在配置中心里，它要在启动前就知道，放环境变量。
  • 本地要有一份能启动的默认值，配置中心全挂时进程仍能起来。
基准算例：把读超时放到配置中心

readTimeoutMs = 2000 写在 jar 里的 application.yml，改成 3000 要重新构建发布；放到 Nacos 并标刷新，改值后不重启就生效，jar 里留 2000 作为默认值。注意它不能超过浏览器侧的 3000 ms（browserTimeoutMs），否则前端已经放弃，后端还在等。

进程停了，调用方立刻就不选它

调用方用的是本地缓存的实例列表。心跳刚停、还没被摘除的这段时间，仍可能选到这台，所以调用方要有超时和失败转移，不能只靠注册中心。

把业务数据当配置

stock = 8 是业务数据，在数据库里由事务扣减，不是配置项。数据库密码要放环境变量或密钥管理，有权限和审计，不要放进所有人可读的命名空间，更不要提交进仓库。

这一项放在哪里，实例掉线后谁还会被选中选配置项与位置 · 切换实例状态
观察要点：① 放进 jar 的项，改一次就要重新构建；② 配置中心地址放进 Nacos 会自相矛盾；③ 库存放在哪种配置里都不对；④ 8081 心跳刚停时，调用方本地列表里还有它。

9.8 网关、令牌、过滤链

问题：浏览器报 CORS 错误、接口返回 401 或 403，问题出在网关、令牌，还是服务的过滤链？先知道一次请求依次经过哪几道门。

约定

网关（Spring Cloud Gateway）：前端的 BASE_URL 指向它，按断言匹配路由，用过滤器改请求或响应，目标是注册中心里的服务名。它建立在响应式栈上，过滤器里不要做阻塞的数据库调用。OAuth 2.0：用户在授权服务器登录，客户端拿访问令牌访问资源服务器；有用户登录时用授权码模式，服务之间用客户端凭证模式。Spring Security：一组过滤器，认证（你是谁）在授权（你能不能做）之前。配置项写法以各自文档为准。

  1. 浏览器发预检 OPTIONS：网关放行并返回 CORS 头，否则浏览器根本不发真正的请求。
  2. 网关按路径路由：/api/orders/** 到订单服务。
  3. 资源服务器验令牌的签名、过期时间、受众：没有或无效返回 401。
  4. 授权检查角色：登录了但没有权限返回 403。
  5. 通过后才进 Controller。
基准算例：用户 10001 的两个请求

用户 10001 带有效令牌查自己的订单，返回 200；同一个普通用户发 DELETE /api/orders/{id}，过滤链认证通过、授权不通过，返回 403。未带令牌时两者都是 401。

只在 React 路由里判断角色

前端路由守卫只影响界面。请求可以不经过页面直接发出，接口必须在过滤链里再查一次。浏览器看到 CORS 错误时，真正的原因可能是预检被认证过滤器拦成了 401，而 401 响应里没有 CORS 头。

把 Zuul 当成仍在维护的默认网关

Zuul（1.x）已停更，Spring Cloud 新版本已不再集成它。新项目的网关看 Spring Cloud Gateway，以其文档为准；Zuul 的「请求前、路由、响应后」过滤器模型仍是网关的通用词汇。也不要把用户密码存进 localStorage 再让每个接口转发。

一个请求停在哪一道门选择请求 · 切换预检放行
观察要点：① 关闭「网关放行预检」后，浏览器只报 CORS，看不到 401；② 无令牌和令牌过期停在认证，返回 401；③ 普通用户删除停在授权，返回 403；④ 只有通过全部过滤器才到 Controller。

9.9 限流发生在打满之前，对照池的第 109 个

问题：第 4 章的线程池在第 109 个任务时走拒绝策略，调用方只看到一个异常。能不能在打满之前，就有计划地拒绝多出来的请求，并给前端一个明确的状态？

约定

限流按 QPS 或并发线程数设阈值，超出的请求立即返回明确的错误（例如 HTTP 429 和统一错误体），而不是让浏览器转到超时。熔断看慢调用比例或错误比例，打开后对这个依赖主动失败，冷却后放少量探测（半开）。Sentinel 把这些做成可动态修改的规则，还能按热点参数（例如某个热门 id）单独限流。规则写法以 Sentinel 文档为准。

基准算例：第 109 个从哪来

核心 4、队列 100、最大 8：先占满 4 个核心线程，再放进 100 个队列，再涨到 8 个线程，第 \(4+100+(8-4)+1=109\) 个被拒绝（由 Course.orderMath.rejectTaskNo() 算出）。入口限流的阈值要低于池能接住的 108 个，并由压测定；qpsTeach 50 只是数量级，不是阈值。

回退返回空列表当成成功

熔断或限流后的回退要表达「降级」，例如读缓存或返回明确的暂不可用。返回空列表，前端会画成「没有订单」，和失败是两种画面。

把 Hystrix 当成仍在维护的默认选项

Hystrix 已停止开发，Spring Cloud 新版本已不再集成它。关闭、打开、半开的三态模型仍要懂；新的限流熔断落地看 Sentinel（或 Resilience4j），以各自文档为准。

入口限流与线程池拒绝拖动涌入任务数与放行上限 · 开关限流
观察要点：① 不限流时，第 109 个任务开始被池拒绝，前端只看到异常；② 打开限流，超出放行上限的请求在入口被拒（429），池里的队列不再被打满；③ 放行上限调到 108 以上，限流就形同虚设。

9.10 全局 id 用雪花那一串，而不是单表自增

问题：分库之后，每个库的 AUTO_INCREMENT 都从 1 开始，两边会发出同一个 id。全局 id 要在多台机器上独立生成且不撞，这个 id 还要进 JSON 给前端。

约定

三类方案：UUID 不碰撞但无序，做主键会让索引随机写；数据库号段一次取一段在内存里发；雪花算法由时间戳、机器号、序列拼成一个 64 位整数，要处理时钟回拨。id 对后端可以是 long，对前端一律是字符串。

JS 的 Number 是双精度浮点，能精确表示的最大整数是 \(2^{53}-1\)。雪花 id 通常超过它，以 JSON number 传给浏览器，JSON.parse 会把它舍入到最近的可表示值。

基准算例：差 1

雪花 id 字符串是 9007199254740993，即 \(2^{53}+1\)。以 JSON number 解析得到 9007199254740992，差 1。userId 10001 远在 \(2^{53}\) 以内，不能用来演示这件事。

雪花 id 再走 JSON number

后端字段是 Long，Jackson 默认按数字输出。要在序列化时转成字符串（全局配置或字段注解），前端拿字符串比较、拼接，不做算术。

分库后继续用单表自增

单库自增在一个库里唯一，分库或多写之后就会撞。也不要把 id 拆成两个 32 位数字让前端拼回 Number，拼回去照样丢精度。

id 怎么发、怎么传切换发号方式与 JSON 传法
观察要点：① 两个库各自自增，前三个号全部相撞；② 雪花 id 由时间戳、机器号、序列组成，机器号不同就不撞；③ 以 JSON number 传，浏览器实际解析出的值比原值少 1；④ 以字符串传，原样到达。

本章避坑清单

  1. 为了「像大厂」先拆服务：集群不等于微服务；拆分的代价是调用链、数据和事务。
  2. CAP 当成平时也要丢一个：取舍只发生在分区期间；扣库存只让一个地方写。
  3. 无过期的缓存：删缓存失败后旧的 stock 8 会一直留着；每个键都设过期并加抖动。
  4. 以为库和缓存同时成功：两者不在一个事务里，有失败窗口；判断以数据库为准。
  5. 锁过期后另一个请求又扣 stock：续期，并在库上用条件更新兜底；解锁要比较持有者并原子执行。
  6. 消费端不防重复，8 件库存被减两次：按至少一次设计，去重记录与扣减放进同一本地事务。
  7. 先确认再处理：把重复换成了丢失；处理成功后再确认或提交位移。
  8. 为全局有序只开一个分区：用 userId 或订单号做分区键，只保证需要的顺序。
  9. 配置打进 jar、业务数据当配置：读超时、日志级别放配置中心并留默认值；配置中心地址放环境变量；库存在数据库。
  10. 预检被认证过滤器拦下：浏览器只报 CORS；网关要放行 OPTIONS 并返回 CORS 头。
  11. 只在前端判断角色：接口必须在过滤链里再查；未登录 401、无权限 403。
  12. 限流阈值高于池容量，或拍脑袋定：要低于池能接住的 108 个并由压测定；qpsTeach 50 不是阈值。
  13. Hystrix、Zuul 按仍在维护的默认选项来学：两者已停更；地图指向 Sentinel 与 Spring Cloud Gateway，以各自文档为准。
  14. 雪花 id 以 JSON number 输出：浏览器解析后少 1；id 给前端一律用字符串。

本章小结与延伸阅读

  • 单体、集群、分布式、微服务各解决一件事，也各带来新问题：会话与锁不共享、网络失败、一致性、跨库事务。
  • CAP 只在分区期间取舍：保一致时下单失败、两边仍是 8；保可用时下单成功、另一边读到旧的 8。
  • 缓存三种故障：击穿用互斥重建，穿透缓存空值，雪崩加抖动并准备降级；缓存要有过期，库与缓存之间有失败窗口。
  • Redis 锁：一条命令加锁并设过期，值放持有者，解锁比较后原子删除；业务长于过期要续期，库上再用条件更新兜底。
  • 交换机按路由键投到队列；Kafka 分区内有序。消息按至少一次设计，消费端去重并与扣减同事务，8 件库存只减一次。
  • 注册与配置不进包；网关放行预检，过滤链先认证（401）再授权（403）。
  • 限流要在池的第 109 个之前生效并给出明确状态；Hystrix、Zuul 已停更，看 Sentinel 与 Spring Cloud Gateway。
  • 全局 id 不用单表自增；雪花 id 给前端用字符串，否则会被解析成少 1 的值。
