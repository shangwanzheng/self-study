第 8 章 · 现象与判断

算法代价：怎样判断做对了

用教学订单的数据量看排序、查找、贪心、递归和摊还：不是背谜题，而是判断库与数据结构是否合适。

预计学习 100 分钟前置：第 5 章2D 演示 2 个
  • 用比较次数、空间和边界条件解释代价。
  • 选择线性、哈希或树查找。
  • 识别稳定性、递归基线与均摊代价。

8.1 这章要看懂库，不刷完谜题

问题：为什么服务开发还要懂算法？List.sort、Map.get、索引和分页都在执行算法；要判断调用是否匹配数据，不是在业务里手写竞赛模板。

约定

代价包括比较/访问次数、额外空间、顺序保证和边界条件。大 O 描述增长趋势，不是耗时承诺。

基准算例

教学订单上限 listN=10000；分页固定 page 1、size 20。

易错

把 \(O(n\log n)\) 一概说快，或把 \(O(n^2)\) 一概说不能用。

避坑

不要为 page 1、size 20 的一页数据推荐复杂分治；先确认是否真在内存中全量处理。

可操作对象：集合代码、SQL 执行计划、分页参数、JDK 库方法文档。

8.2 比较次数和稳定性

问题：两笔同额订单金额都对，为什么展示顺序仍可能错？稳定排序保持相等键的原相对次序；不稳定排序没有这个承诺。

约定：A 与 B 的金额均为 \(19950\) 分，原顺序 A 在 B 前，排序键仅为 amountFen。

稳定性：相同金额是否保住先后切换排序性质
观察要点：① 两笔金额始终都是 19950 分；② 选“稳定”时 A 仍在 B 前；③ 选“不稳定”只表示相等键可能换位，不表示每次一定换位。
基准算例

先按次要字段排好，再按金额做稳定排序，同额 A、B 保留前一步顺序；更明确的办法是比较器直接写第二排序键。

易错

把“不稳定”理解为金额会排错或结果随机。

避坑

不要依赖偶然保住的输入顺序；给订单展示定义并列规则。

可操作对象：Comparator、List.sort、相等金额订单、接口并列排序规则。

8.3 10000 条订单按金额排序的数量级

问题：10000 条订单按 amountFen 排序，应先估什么？比较型排序常见数量级是 \(n\log_2n\)，两层扫描式排序是 \(n^2\)。

约定与假设：假设比较成本相近、忽略 I/O 与对象分配：

\[n\log_2n\approx10000\times13.29\approx132877,\qquad n^2=100000000.\quad\text{（假设：比较型实现）}\]
基准算例

10000 条不等于要手写归并或快速排序。优先使用库排序与清晰比较器；查询来自数据库时，先让索引与 ORDER BY 工作。

易错

把平均 \(O(n\log n)\) 当作所有实现的最坏保证。

避坑

不要用 listN 或 qpsTeach=50 推导生产容量和复杂度结论。

可操作对象：金额比较器、JDK 排序 API、排序字段索引、性能测试数据规模。

8.4 线性查找 userId

问题：在普通 List<Order> 里找 userId=10001，要检查多少项？无序列表只能扫描到命中或末尾。

约定与假设：目标存在且位置等可能：

\[E[C]=\frac{n+1}{2}=5000.5.\quad\text{（假设：10000 条、命中位置均匀）}\]
基准算例

10000 条最坏看 10000 项；page 1、size 20 页面最多扫 20 项，通常直接而可读。

易错

把首项命中当成 List 查找就是 \(O(1)\)。

避坑

反复按 id 查同一份 10000 条列表时别重复扫描；只展示 20 条时也不必建复杂树。

可操作对象：List<Order>、循环、分页结果、按 id 查询接口。

8.5 哈希查找

问题：为什么 Map<Long, Order> 能快按 userId 找订单？哈希先定位桶，再在桶内判断相等；分布均匀时平均访问接近常数，但不提供范围顺序。

约定：平均 \(O(1)\) 依赖散列分布与受控负载，最坏碰撞仍可退化；它不等于每次只执行一条指令。

基准算例

10000 条按 userId 构成 Map 后反复查 10001 合适。第 3 章容量 16、负载因子 0.75 的 Map，第 13 个键才扩容，扩容是偶发成本。

易错

认为 HashMap 保持插入顺序，或修改参与 hashCode 的键字段。

避坑

需要范围查询、排序输出时，哈希不是替代有序索引的答案。

可操作对象：HashMap、不可变 userId 键、equals/hashCode、扩容阈值。

8.6 树查找

问题：既要按 userId 找，又要取范围，为什么树更合适？平衡树保留键顺序，点查、插入和边界定位是 \(O(\log n)\)。

约定与假设：假设树平衡，\(\log_2 10000\approx13.29\)；退化成链的普通 BST 不满足此前提。

基准算例

找 10001 约走十余层量级；按 id 或时间范围扫描则有序结构更自然。数据库 B+ 树面向磁盘页，不应等同内存二叉树。

易错

把所有树查找都说成 \(O(\log n)\)。

避坑

别为 8 条库存记录搭复杂树；也不要因点查快忽略范围条件。

可操作对象：TreeMap、数据库 B+ 树索引、范围条件、执行计划。

8.7 贪心什么时候会后悔

问题：“每次选当前最好”的策略何时可信？只有局部选择不会排除全局最优时才可用，需交换论证或不变式；没有条件的“选最大”只是猜测。

约定：贪心正确性来自问题结构，不来自运行速度。题目约束不完整时，不编造竞赛题标准答案。

基准算例

订单“优先处理金额最大者”是否正确，取决于 SLA、创建时间、公平性与库存约束，不能只看金额。

易错

局部最优等同全局最优，或只跑几个样例就宣布证明完成。

避坑

需求规则不完整时，先写目标、约束和并列规则，不要让贪心代码替产品决策。

可操作对象：任务排序键、优先队列、业务 SLA、反例样本、不变式。

8.8 递归拆订单列表的深度

问题：递归不断二分订单列表时栈多深？有基准情形且每次规模减半时是 \(\lceil\log_2n\rceil\)；每次只少一个元素则可到 \(n\) 层。

约定与假设：假设每一步近似对半拆分，空或单元素立即返回：

\[d=\lceil\log_2 10000\rceil=14.\quad\text{（假设：平衡二分，基准情形 }n\le1\text{）}\]
基准算例

平衡拆 10000 条深度约 14；逐条递归可能深到 10000 层，有 StackOverflowError 风险。

易错

漏掉基准情形，或问题规模没有缩小。

避坑

深度 10000 的操作改为循环或显式栈，不要交给生产请求线程。

可操作对象：递归基准条件、规模参数、调用栈、ArrayDeque。

8.9 分治、回溯、摊还对照 ArrayList 扩容

问题：“偶尔很慢”是不是代码错了？不一定。分治是拆分、解决、合并；回溯是选择、递归、撤销；摊还把少数昂贵操作分摊到大量便宜操作。

约定与假设：动态数组按常数倍增长：

\[1+2+4+\cdots<2n,\qquad\frac{\text{总成本}}n=O(1).\quad\text{（假设：按倍数扩容）}\]
基准算例

ArrayList 某次 add 可能搬移很多元素，但连续追加均摊 \(O(1)\)；这不代表每一次 add 都是 \(O(1)\)。已知约 10000 条可预估初始容量。

易错

把均摊 \(O(1)\) 说成最坏 \(O(1)\)，或把回溯与分治混为同一模板。

避坑

不要把教学上限照搬为生产参数；容量应来自实际数据量与内存预算。

可操作对象：ArrayList 初始容量、扩容日志、递归树、回溯路径。

8.10 怎样从曲线判断选错了结构

问题：如何从增长趋势发现结构不匹配？相同规模下，线性随 \(n\) 长，对数随 \(\log n\) 长；曲线是模型，不是压测替身。

查找代价曲线拖动数据量滑块，最大为 listN=10000
观察要点：① 每次拖动滑块，三条曲线和当前竖线都会更新；② 线性扫描在 10000 条接近 10000 次，平衡树约十余层，哈希平均接近常数；③ 曲线不能替代真实压测，也不能从 qpsTeach=50 反推复杂度。

约定：图中哈希曲线用“平均接近 1 次”表达模型；冲突、缓存、网络、数据库 I/O 均未画入。

基准算例

若同一请求反复扫描 10000 条才找到 userId，应考虑 Map 或索引；若仅处理一页 20 条，线性扫描可能正是最简单正确的方案。

易错

把曲线纵轴误当毫秒，或把 qpsTeach=50 当成算法证明。

避坑

优化前先量出热点与数据规模；避免在小页面数据上引入不可维护的结构。

可操作对象：性能剖析、查询计划、数据规模、集合类型、接口分页契约。

本章避坑清单

  1. 不要把最好情况、平均情况和最坏情况混为一谈。
  2. 相等金额 19950 分的显示顺序需要稳定性或明确次键。
  3. 递归必须有基准情形，且不能把 10000 层递归交给请求线程。
  4. 平均 \(O(1)\) 不是单次操作保证。
  5. page 1、size 20 先选简单可读方案。
  6. qpsTeach=50 不是复杂度或压测结论。
