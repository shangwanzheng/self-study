线程、IO 与网络

从请求拿到工作线程开始，依次看线程池、字节与字符、超时、TCP 边界，以及能在框架代码中认出的六个模式。

4.1 请求进池而不是事件循环

问题：两个 HTTP 请求怎样执行？约定：请求提交给服务器工作线程池，不是浏览器单一事件循环。

基准算例

两个教学订单查询可各占一条工作线程；若同时修改共享可变对象，必须同步或取消共享。

易错

Java 中两个请求确实可能同时改同一块内存。

避坑

不要到处 new Thread()。可操作对象是执行器和共享状态。

4.2 四个数

问题：池满不满看什么？约定：教学订单固定 core=4、max=8、queue=100，第四个数是拒绝策略。

对象值作用
核心线程4未满时直接执行
队列100核心线程忙时暂存
最大线程8队列满后再扩张
拒绝策略第 109 个所有位置满后处理
基准算例

先占满 4 条核心线程，再排 100 个任务；队列满后最多新增 4 条线程。

易错

最大线程不是初始线程数。

避坑

可操作对象是构造参数、队列类型和拒绝策略；只加大队列会隐藏延迟。

4.3 第 109 个任务

问题：涌入时谁被拒绝？约定：任务到来期间池仍忙，不能假定已有任务完成。

任务涌入与拒绝
观察要点：① 1–4 占核心线程；② 5–104 入队；③ 105–108 扩至 8 条线程；④ 第 109 个被拒绝，来自 Course.orderMath.rejectTaskNo()。
基准算例

\(4+100+(8-4)+1=109\)，是当前“池仍忙”的假设，不是压测结论。

易错

池满不会无限建线程。

避坑

可操作对象是拒绝响应、指标和重试规则；没人接异常，调用方只会失败。

4.4 同步 JDBC 占住工作线程

问题：慢数据库为何导致请求排队？约定：同步 JDBC 从调用到返回始终占当前工作线程。

基准算例

4 条核心线程都在查询教学订单时，第 5 个请求先入队；等待数据库不等于线程已释放。

易错

异步 API 外形不自动消除底层阻塞。

避坑

可操作对象是 JDBC 连接池、SQL 耗时和活跃线程数，要一起观察。

4.5 字节流与字符流

问题：读取内容时该选什么流？约定：InputStream/OutputStream 是字节，Reader/Writer 是已解码字符。

目标可操作对象理由
复制图片字节流不解释内容
读 UTF-8 JSON字符流 + UTF-8明确解码规则
写 HTTP 响应字节流网络发送字节
基准算例

教学订单 JSON 的中文字段，必须从字节按 UTF-8 变成字符。

易错

“文本”不是编码，文本是字节按字符集解释的结果。

避坑

可操作对象是 charset 参数与响应 Content-Type；不要依赖平台默认编码。

4.6 UTF-8 和谁包着谁

问题：怎样得到正确中文？约定：处理流包在节点流外，InputStreamReader 按 UTF-8 解码。

流的包装与解码
观察要点：① FileInputStream 提供字节；② BufferedInputStream 增加缓冲；③ InputStreamReader 按 UTF-8 变为字符；④ 缓冲包住文件流是装饰，不是模板方法。
new BufferedReader(new InputStreamReader(
  new BufferedInputStream(new FileInputStream(path)),
  StandardCharsets.UTF_8))
基准算例

错误编码会让教学订单中文字段乱码；明确 UTF-8 后恢复。

易错

BufferedInputStream 包住 FileInputStream 是装饰：同为 InputStream，外层转发并增添能力。

避坑

可操作对象是创建顺序和 try-with-resources，不要只关闭内层流。

4.7 连接超时 500ms 与读超时 2000ms

问题：“超时”卡在哪？约定：连接、读取、浏览器等待是不同计时器：500ms、2000ms、3000ms。

超时值等待什么
连接500msTCP 尚未建立
读取2000ms连接后无可读数据
浏览器3000ms调用方总等待
基准算例

300ms 连上、2200ms 才有首字节，先触发的是读超时，不是连接超时。

易错

浏览器 3000ms 不会让服务器自动采用相同读取超时。

避坑

可操作对象是 HttpClient、Socket、前端取消器；日志记录超时阶段和耗时。

4.8 TCP 没有消息边界

问题：为何一次 read() 不能保证完整 HTTP？约定：TCP 是有序可靠字节流，不保留应用发送分段。

请求头字节
请求体字节
read()任意长度
基准算例

教学订单 JSON 可被拆成两次读取，也可与下一段合在一起；HTTP 解析器依靠头部、长度或分块编码划界。

易错

粘包、拆包不是 TCP 出错，是应用层恢复消息的职责。

避坑

可操作对象是协议解析器、长度字段和累计缓冲区，不能猜 read 返回长度。

4.9 六个模式在 IO 和框架里怎么认出

问题：模式怎样帮助读代码？约定：只讲工厂、单例、装饰、策略、模板方法、访问者；表上的“单列”是单例。

模式识别问题对象
工厂谁决定具体实现？按配置建客户端
单例是否只有容器托管的一份？Spring 默认 Bean
装饰同一抽象上是否包一层？BufferedInputStream
策略算法能否替换？重试、拒绝规则
模板方法父类定流程、子类填步骤？模板化执行
访问者操作是否从结构中分离？复杂 AST 遍历
基准算例

教学订单选不同拒绝处理方式是策略，缓冲加到文件输入流外是装饰。

易错

BufferedInputStream 不是模板方法。

避坑

可操作对象是接口、委托、继承和 Bean 作用域；先画关系再命名。

4.10 Netty 只建立地图

问题：为什么有 Netty？约定：它是异步事件驱动网络框架，本章只认 Channel、Pipeline、编解码器和 Handler。

Channel通道
Pipeline处理链
Codec字节/消息
Handler业务
基准算例

教学订单请求由编解码器从 TCP 字节流划出 HTTP 消息，再交给业务 Handler。

易错

Netty 不等于没有线程，而是改变等待和调度方式。

避坑

可操作对象是 Pipeline 边界、编解码器和 Handler；先理解 TCP 无边界再深入 API。

本章避坑清单

  1. 到处 new Thread：改为受监控的执行器。
  2. 最大线程当初始：先看核心线程和队列。
  3. 漏掉拒绝：第 109 个任务要有可见处理。
  4. 默认编码：订单文本显式 UTF-8。
  5. 一次 read 当一条消息：由协议划界。
  6. 混淆模式：BufferedInputStream 是装饰，“单列”是单例。

本章小结与延伸阅读

  • 多个 Java 请求可由不同工作线程并发执行。
  • 本章线程池按 4、100、8 推演，第 109 个拒绝。
  • 文件流给字节，UTF-8 把字节解成字符；缓冲是装饰。
  • 500ms、2000ms、3000ms 分别对应连接、读取、浏览器等待。
  • TCP 无消息边界；Netty 先认 Pipeline 和编解码器。
