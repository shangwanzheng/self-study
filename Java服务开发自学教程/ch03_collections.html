第 3 章 · 对象与结构

集合：List、Set、Map

JS 的数组和对象字面量不能直接换成 List 和 Map。这一章用教学订单的 userId 决定：日志能不能重复、用户名要不要唯一、怎样按 id 取回那一笔，以及 HashMap 在第 13 个键时为什么扩容。

预计学习 90 分钟 前置：第 1 章 交互演示 2 个
  • 按「可重复、要唯一、要按键取出」三选一，给日志、用户名和订单选对容器；
  • 说明 equals 与 hashCode 必须一起写，HashMap 不保证插入顺序；
  • 用容量 16 和负载因子 0.75 算出阈值 12，并看到第 13 个键扩到 32。

3.1 三种容器各回答什么问题

问题：业务代码每天都在选容器。选错以后，重复数据、按键取不到、空指针会叠在一起。

符号或约定：List 保留插入顺序，允许重复。Set 按相等去重。Map 用键取值。表上的笔误 Cellection 指的是接口 Collection；Collections 是工具类，不是这个接口。

对照前端：JS 数组接近 List，Set 接近 HashSet。字段固定的教学订单应写成类，再作为 Map 的值。字段不固定才考虑 Map<String, Object>，订单不是这种数据。

易错

把 HashMap 当成按插入顺序排列。遍历顺序不是「先放进 userId 10001 就一定先出来」。要插入顺序用 LinkedHashMap，以所用 JDK 文档为准。

避坑

把订单塞进 Map<String, Object>。编译器不再检查金额是不是分、库存是不是整数，调用方只能记得键名。

可操作对象：Collection、List、Set、Map、Collections。教学订单的身份是 Course.data.order.userId，值为 10001。

3.2 ArrayList 与 10000 条

问题：按下标取一条订单日志要快。课程用 listN = 10000 表示这种列表的数量级，不是说每次请求都真的返回一万条。

符号或约定：ArrayList 按下标访问是常数时间，尾部追加均摊也是常数时间。中间插入要搬移后面的元素。分页仍是 page = 1、size = 20，一页只有 20 条；10000 是用来看扩容拷贝的上限，不是接口默认页大小。

不指定初始容量时，JDK 会按自己的默认值多次扩容并把旧数组拷贝到新数组，直到装下 10000 条。默认值以所用 JDK 文档为准，不要把文档里的默认容量写成本课的另一套基准。

易错

以为 List 不允许重复。操作日志可以有多条，List 会把它们都留下。

避坑

明明知道要装 10000 条，仍用默认容量。扩容时整表拷贝，延迟会出现在追加的那几次，而不是均匀摊在每一条上。

可操作对象：new ArrayList<>(order.listN)、下标、add。已知条数时把 listN 传进去。

3.3 LinkedList 的代价

问题：链表在已知节点处插入可以少搬移元素，但按下标找到那个节点要沿着指针走。

符号或约定：对长度为 \(n\) 的链表，按下标访问的步数随 \(n\) 增长。这里的 \(n\) 用到课程上限时就是 listN。ArrayList 按下标不随 10000 变长。业务列表默认 ArrayList；LinkedList 的教学意义大于日常订单列表。

易错

以为链表按下标也是常数时间，因为「插入很快」。快的是已经拿到节点之后的改指针，不是 get(i)。

避坑

为了库存只有 8 的一张小表换成链表。指针和缓存上的损失比中间插入那一点好处更大。8 是库存件数，不是必须用链表的理由。

可操作对象：ArrayList、LinkedList、get。第 5 章会把步数再画出来，这里先记住谁回答「按位置取」。

3.4 Set 与 equals、hashCode

问题：用户名要唯一。Set 靠「相等」决定是不是同一个元素，不是靠你觉得它是同一笔订单。

符号或约定：HashSet 无序，TreeSet 排序，LinkedHashSet 记住插入顺序。放进 HashSet 或当作 HashMap 键的对象，必须同时正确实现 equals 和 hashCode。相等的对象哈希必须相同；哈希相同只说明可能相等，还要再比 equals。

字符串 userId 用 equals 比较内容。用 == 比的是是不是同一个对象，两个都写成 "10001" 的字符串不一定通过 ==。

易错

只用 == 比较字符串 id。集合去重走的是 equals 和 hashCode，不走 ==。

避坑

订单对象只写了 equals、没写 hashCode，或只写了其中一个。HashSet 里逻辑上同一笔 userId=10001 的订单会留下两份。可变字段拿去当键也会让它放进去之后再也取不出来。

可操作对象：HashSet、equals、hashCode。用户名用 Set；操作日志用 List。

3.5 HashMap 按 userId 取订单

问题：「这个 id 在不在」和「把这个 id 对应的订单拿出来」不是同一个问题。

符号或约定：键是 Long 型 userId，值是订单对象，不是再套一层 Map。本课的键是 10001。Set 只能回答在不在；List 要扫描；Map 按键取。

Map<Long, Order> byId = new HashMap<>(); byId.put(order.userId, order); Order hit = byId.get(10001L);

代码里的 10001L 就是 Course.data.order.userId，不要改成别的示例 id。

易错

用 HashSet 只放订单，然后期望按 id 取回对象。Set 没有「按另一个字段取出」这一种操作。

避坑

HashMap 允许一个 null 键。订单 id 缺失时放进 null 键，后面的查找会和「没有这笔单」混在一起。没有 userId 就不要 put。

可操作对象：put、get、键的类型 Long。给前端的 JSON 仍用字符串 "10001"，那是第 1 章的边界，Map 里面可以用 Long。

3.6 容量 16 与第 13 个键

问题：HashMap 不是放满 16 个键才扩容。阈值由容量和负载因子相乘得到。

符号或约定：课程里的初始容量 hashCap = 16，负载因子 loadFactor = 0.75。阈值用 Course.orderMath.hashThreshold()，结果是 12。插入第 13 个键时，大小会超过 12，容量从 16 变成 32。不要说成第 16 个键才扩容。

扩容要重新摆放已有的键。这是摊还到多次插入上的拷贝，不是每一个键都同样贵。第 8 章会把「均摊」和「这一次」分开。

易错

用 16 乘 1，认为第 16 个键触发扩容。负载因子 0.75 已经把阈值收成 12。

避坑

知道大概要放多少键，仍从默认过程走一遍扩容。已知规模时把容量传进构造器，算法以所用 JDK 文档为准，课程数字仍是 16 和 0.75 这套。

可操作对象：容量、负载因子、阈值、第 13 次 put。演示里的滑块只数键的个数，不另造一套容量。

3.7 遍历时删除

问题：想从日志列表里去掉某一条时，增强 for 循环里直接 remove 会让迭代器失效。

符号或约定：for-each 使用迭代器。结构被别人改掉时，下一次 next 抛出 ConcurrentModificationException。要删元素，用迭代器自己的 remove，或收集之后再删。这和「两个请求同时改一个 HashMap」不是同一件事，但现象都是容器的结构变了，正在看的那一方不知道。

易错

在 for-each 里调用 List 的 remove。单线程也会失败，不必等到并发。

避坑

捕获这个异常后当成「没有可删的元素」继续跑。异常说的是迭代器失效，不是业务上的库存或 userId。

可操作对象：Iterator.remove、removeIf。方法是否存在以所用 JDK 文档为准。

3.8 日志、用户名、id 各用哪一种

问题：三种容器不要混用在同一种数据上。先问这句话要回答什么。

符号或约定：可重复的操作日志用 List。要唯一的用户名用 Set。userId 到订单用 Map<Long, Order>，键是 10001 这种 Long，值是字段固定的订单，里面的金额是分 19950，库存是 8。

算例

把 userId 10001 放进 List 两次，大小是 2。放进 Set 两次，大小是 1。放进 Map 两次，键仍是一个，后一次覆盖前一次的值。覆盖不会把金额从 19950 分改成别的数，除非第二次 put 的值不同。

易错

用户名用 List，靠人眼保证不重复。Set 才会在放入时按相等去掉第二次。

避坑

id 到对象用 List 再线性扫描。10000 条日志这样扫和按键取不是一个代价，扫描的写法留到第 5 章和第 8 章量化。

可操作对象：日志 List、用户名 Set、订单 Map。选的时候先写「要重复、要唯一、还是要按键取出」。

3.9 并发读写不要用外面一把大锁

问题：两个请求可以同时跑在两条线程上，同时改同一个 HashMap。普通 HashMap 不保证这种用法。

符号或约定：并发读写用 ConcurrentHashMap，而不是在外面套一把锁把整个 Map 的所有操作都串行化。锁的范围越大，线程池里的工作线程越容易堵在这把锁上。池的四个数在第 4 章：核心 4、队列 100、最大 8。

易错

认为单线程里试过的 put/get，在两个请求同时执行时结果一样。HashMap 的结构可能被同时修改。

避坑

用一把锁包住整个 Map，锁里面还去做会等待数据库的调用。等待期间别的请求进不了这张表，池里的线程被占住。数据库那一段不要放在这把大锁里。

可操作对象：ConcurrentHashMap、锁的范围、工作线程。具体分段方式以所用 JDK 文档为准，不要把某一版本的内部表结构背成唯一实现。

本章避坑清单

  1. HashMap 不保证插入顺序；阈值是 12，第 13 个键才从 16 扩到 32。
  2. 字符串 id 用 equals，不用 ==；equals 和 hashCode 一起写。
  3. 不要在 for-each 里直接 remove。
  4. 已知要装 10000 条时指定容量，避免默认容量下的多次拷贝。
  5. 可变对象不要当键；订单不要塞进 Map<String, Object>。
  6. Collection 是接口，Collections 是工具类。
  7. 日志用 List，用户名用 Set，userId 到订单用 Map。
  8. 并发读写用 ConcurrentHashMap，不要用一把大锁包住整张表再去等数据库。

本章小结与延伸阅读
