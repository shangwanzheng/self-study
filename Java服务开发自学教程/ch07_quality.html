第 7 章 · 方法

日志、测试、规范与构建

接口能跑通还不够。别人接手时要能从日志里找到这笔教学订单，用测试锁住扣库存的行为，用同一套 JDK 把编译和测试跑完，并且知道命令是在哪个目录执行的。

预计学习 90 分钟 前置：第 6 章 交互演示 2 个
  • 写一条能还原现场的日志：有 userId，异常带栈，不靠 System.out；
  • 用测试断言扣库存后的剩余件数，并把「连真实库」从单元测试里分开；
  • 说出 Maven 生命周期、流水线变红时不产出可发布包，以及排错命令的顺序。

7.1 一条日志里要有 userId

问题：线上只能靠日志还原「哪一笔订单扣失败了」。只写「失败」时，无法把现场对上教学订单。

符号或约定：业务代码依赖 SLF4J 的 Logger。占位符写成 {}。本课要能对上的身份是 Course.data.order.userId，也就是 10001。金额若出现，用分 amountFen，不用元的小数去对账。

一条够用的 INFO 至少带用户：log.info("reserve stock userId={}", order.userId)。扣减结果再带上剩余库存。没有 userId 的日志，等于把所有用户的失败堆在同一句里。

易错

日志只打「失败」或「success」，不打 userId。检索时只能看到有错误，对不上 10001 这一笔。

避坑

不要把令牌、密码打进同一条日志。身份用 userId 就够，不要为了「信息全」把凭证拼进去。

可操作对象：Logger、userId、日志检索关键字。菜单和配置文件名以所用日志实现的文档为准。

7.2 不要用 System.out 代替日志

问题：System.out.println 能在本机看见，但没有级别，也不能按环境关掉 DEBUG，异常栈还经常被漏掉。

符号或约定：SLF4J 是门面，Logback 或 Log4j 是 classpath 上的实现。业务代码不 new Logback 的类。级别从重到轻：ERROR 要处理，WARN 还能继续，INFO 是关键路径，DEBUG 是排查。异常作为最后一个参数：log.error("reserve failed, userId={}", userId, e)。

字符串拼接发生在调用之前。即使用 DEBUG 级别被关掉，"id=" + userId 也已经付出拼接代价。占位符把格式化留到真正输出时。

易错

把异常写进字符串：log.error("failed " + e)。这样通常没有栈。栈要靠最后一个参数传入的异常对象。

避坑

catch 里空着，或者只 printStackTrace。调用方以为库存没动，日志里也没有 userId=10001。

可操作对象：LoggerFactory.getLogger、级别、异常参数。换实现时以该实现的文档为准，不把某次 IDE 点击路径写成唯一做法。

7.3 JUnit 测扣库存的行为

问题：改一个分支之后，如果只能手点接口，就不知道库存从 8 扣 1 件后是不是 7。

符号或约定：JUnit 5 用 @Test。一个测试只验证一个行为。库存用整数：扣减前 stock = 8，买 1 件，期望剩余 7。金额断言用分 19950，不用 double 和 199.5 做相等比较。199.5 在二进制里恰好能表示，单次转换看不出错，所以不能用它当断言。

@Test void reserveOneLeavesSeven() { int left = Stock.reserve(order.stock, 1); Assertions.assertEquals(7, left); Assertions.assertEquals(19950, order.amountFen); }
易错

断言 amountYuan == 199.5。课程约定账用分。用元的浮点相等，会把「展示正常」误当成「账是对的」。

避坑

测试方法依赖上一个测试留下的库存。每个测试自己准备 stock=8，不从静态字段里继承上一次的 7。

可操作对象：@Test、Assertions.assertEquals、纯函数 reserve。断言库的方法名以所用 JUnit 版本文档为准。

7.4 Mockito 替掉数据库

问题：Service 要证明「会按 userId 去取订单」，但单元测试不应该为了这一句话去连数据库。

符号或约定：Mockito 提供假的 Mapper。成功路径断言剩余库存为 7；失败路径断言库存仍是 8，并且异常被记下来。需要真数据库的是集成测试，不要和几秒内该结束的单元测试放在同一个类里。

对照前端：Jest 的 mock 替掉远程模块。这里替掉的是 Mapper，不是把 Tomcat 拉起来。

易错

测试类里连了真实库，却把类名叫成单元测试。它会随数据、网络和 JDK 以外的环境一起失败。

避坑

Mock 把「扣减」也替掉，然后断言 Mock 被调用过，却从不检查 8 减 1 得 7。行为没有被测到。

可操作对象：Service、假 Mapper、userId = 10001。Mock 的 API 以所用 Mockito 文档为准。

7.5 命名、异常、分层

问题：别人接手时，先看名字和异常能不能读懂，再看 SQL 有没有写在 Controller 里。

符号或约定：包名全小写。类名是名词，方法名是动词。布尔方法读起来像判断。业务异常和系统异常分开。Controller 不写 SQL，Mapper 不写「库存够不够」这种业务分支。入参出参用明确类型，不用 Map<String, Object> 把教学订单传到底。

易错

空的 catch。扣库存失败被吞掉，调用方看到成功，库里仍是 8。

避坑

在 Controller 里直接拼 SQL，或者更新语句没有 WHERE。规范手册的全部条款以团队采用的原文为准；这里先改掉这三处：空 catch、拼接 userId、Controller 访问数据库。

可操作对象：包、类、方法、异常类型、Mapper。安全项同时包括：密钥不进 Git，接口不能只靠前端把按钮藏起来。

7.6 黑盒看接口、白盒看分支

问题：没有期望的操作清单既不是黑盒也不是白盒。黑盒对着契约，白盒对着分支。

符号或约定：按 id 查教学订单，至少覆盖：存在且 userId 为 10001、不存在、id 格式非法、未登录、数据库失败。每条都写期望状态或错误码。白盒则给扣库存的两个分支各一条测试：够扣（8 到 7）和不够扣（库存保持 8）。中级先覆盖关键分支，不把行覆盖率数字当成目标。

算例

买 1 件，stock 从 8 变为 7，这是白盒里的成功分支，也是黑盒里「下单成功」的期望。库存为 0 时拒绝，剩余仍是 0，那是另一条分支；本课基准库存是 8，不够扣的用例要单独准备，不要改掉基准算例本身。

易错

把「点过接口、返回了 200」当成测完。没有写期望剩余库存，200 也可能没扣成。

避坑

缺陷单只有一句「不行」。要有重现步骤、实际结果、期望结果、版本。测试计划写范围和入口标准，不是排期表的别名。

可操作对象：用例、分支、缺陷单。静态检查不运行程序；JUnit 运行起来才是动态测试。

7.7 先定指标，qpsTeach 不是结论

问题：没有指标的压测只是把机器打热。本课给出的 qpsTeach = 50 只用于数量级，不是这台机器或这个接口的容量承诺。

符号或约定：负载测试看预期流量下的延迟和错误率。压力测试加大到系统退化，看它怎么失败、失败后能不能恢复。计划里写清场景、数据量、持续时间、成功标准。一次只改一个因素。要看的四个数：延迟、错误率、CPU、线程池队列。线程池的拒绝点仍是 Course.orderMath.rejectTaskNo()，也就是第 109 个任务，不要从 50 这个教学 QPS 反推出来。

易错

把 50 写成「本服务能承受 50 QPS」。它是教学刻度，没有对应的持续时间、数据量和成功标准。

避坑

压测打到会扣库存的接口，8 件库存在观察结束前就被打成负数或 0。查询和扣减要分开。

可操作对象：压测计划、延迟、错误率、队列长度。工具上的按钮名称以该工具文档为准。

7.8 Maven 生命周期

问题：依赖写在 pom 里之后，还要知道哪一条命令会编译、哪一条会跑测试、哪一条会打出 jar。

符号或约定：生命周期里先记住 compile、test、package。测试失败就停，不要带着失败的测试去 package。依赖冲突看依赖树。私有仓库的地址和凭据放在本机或 CI 的配置里，不提交进仓库。JDK 用课程约定的 17；IDE 里一套、命令行里另一套，测试结果会对不上。

易错

只在 IDE 里点了绿色按钮，就认为命令行的 mvn test 也会用 JDK 17。两边的 JAVA_HOME 要单独看。

避坑

把仓库密码写进 pom 再提交。凭据和 Nexus 的配法以团队文档为准。

可操作对象：pom、生命周期阶段、依赖树、JAVA_HOME。IDE 里从 Controller 跳到 Mapper 的快捷键以所用版本的说明为准。

7.9 提交后编译和测试

问题：本地通过不代表主干还能编译。流水线至少包括：取出代码、用 JDK 17 编译、跑单元测试、打出 jar。

符号或约定：CI 让主干始终能编译、测试能跑。CD 是把同一个产物送到环境，而不是在服务器上再编译一份。测试失败就不产生可发布的包。Jenkins 是表上的一种实现；阶段划分和你已经会的其他 CI 是同一件事。具体阶段名以所用产品的文档为准。

易错

流水线里用了另一套 JDK，不是 17。本地绿、主干红，或相反。

避坑

在服务器上改完代码直接跑。下次发布会盖掉这次修改，也没有和任务、评审对上。

可操作对象：分支、流水线阶段、构建产物、任务状态。评审要看事务和 SQL，不只看格式。

7.10 排错时连起来的几条命令

问题：接口没反应时，先重启会丢掉「进程在不在、端口是不是这个、日志里有没有 userId=10001」。

符号或约定：顺序是：确认目录（pwd）、看进程和端口、用 tail 跟日志并用 grep 滤 userId、在本机用 curl 打进程实际监听的地址。覆盖 jar 之前先备份。rm 之前先列出路径。密钥文件不要所有人可读。

易错

命令在家目录或旧拷贝里执行，看的是另一份日志，里面没有这笔订单。

避坑

本机 curl 打通了，就认为浏览器那条链路也通。浏览器超时仍是 3000 ms，连接超时 500 ms，读超时 2000 ms，三处不是同一个数。

可操作对象：工作目录、进程、端口、日志文件、curl。发行版里命令的参数差异以该系统文档为准。

本章避坑清单

  1. 日志要有 userId；异常作为最后一个参数传入，才能带栈。
  2. 不要用 System.out 或空 catch 代替日志。
  3. 单元测试断言剩余库存 7，并用 Mock 替掉数据库；连真实库的是集成测试。
  4. 金额断言用分 19950，不用 double 和 199.5 比较。
  5. 测试各自准备 stock=8，不依赖执行顺序。
  6. qpsTeach=50 不是容量承诺，也不能用来反推线程池拒绝点。
  7. CI 使用 JDK 17；测试失败就不产出可发布包，不在服务器上临时编译。
  8. 排错先确认目录、进程、端口和日志，再考虑重启。

本章小结与延伸阅读

接手一个接口，先看日志能不能对上 userId=10001，再看测试是否锁住了「8 扣 1 得 7」并且没有连真实库，然后确认流水线用 JDK 17 跑 test，失败时不打发布包。排错时从目录、进程、端口、日志走到本机 curl，而不是先重启。

  • SLF4J、JUnit、Mockito、Maven、Jenkins 或团队所用 CI 的参数和菜单，以各自文档原文为准。
  • 下一章用 listN=10000 看算法代价；50 这个教学 QPS 不要带去当复杂度或容量。
