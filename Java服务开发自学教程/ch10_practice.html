10.1 从代码到可运行的最小闭环

问题：第 6 章的接口在你本机 mvn spring-boot:run 能返回教学订单。要让同事和前端页面访问它，中间少了哪几步？哪几步绝不能在服务器上手工补？

前端工程师对这条链路并不陌生：提交代码，CI 构建，产物上传，Nginx 容器上线。Java 服务的链路形状一样，只是产物从静态目录变成了一个含 JRE 和 jar 的镜像，进程从 Nginx 变成了 java -jar。

  1. 提交代码。第 7 章的流水线用 JDK 17 编译并跑测试，测试不过就停在这里。
  2. 流水线执行 mvn package，在 target/ 下得到可执行 jar。
  3. 流水线用 Dockerfile 把 jar 和 Java 17 JRE 一起做成镜像，标签用提交号。
  4. 镜像推到镜像仓库。从这一刻起，这个标签对应的内容不再改变。
  5. Deployment 引用这个标签，声明要跑几份；Service 给出一个稳定的访问名字。
  6. 在集群里用 curl 查询教学订单，看返回值和日志，闭环完成。
约定

一次提交对应一个不可变的镜像。服务器上只做「拉镜像、按声明运行」，不做编译、不改代码。镜像标签用提交号，不用会漂移的 latest 指代生产版本。

基准算例

闭环最后一步的验收请求，查询的仍是这一笔教学订单：userId 10001，订单 id 以字符串 "9007199254740993" 返回，金额 amountFen = 19950，库存 stock = 8。返回值里只要有一项和基准不一致，就说明链路上某一步换了东西，不能算「部署成功」。

易错

在服务器上拉代码再执行 mvn package，用它代替流水线产出镜像。这样一来，服务器上的 JDK、本地仓库和依赖版本都没人管，出问题时也说不清跑的是哪次提交。

避坑

进容器改完代码或替换 class 文件就当发布。容器一重启，改动就没了；多副本时，只有你进过的那一份被改了。改代码只有一个入口：提交，然后让流水线重新出镜像。

动手

把你所在项目的上线过程写成上面六步，标出哪一步现在是手工做的。下面三条命令验证产物来自哪次提交：

git rev-parse --short HEAD                 # 当前提交号
docker image ls order-api                  # 镜像标签应当就是这个提交号
kubectl get deploy order-api -o jsonpath='{.spec.template.spec.containers[0].image}'

10.2 镜像里要有 JRE 和应用

问题：把 jar 拷到一台装了 Java 的服务器上也能跑，为什么还要做镜像？镜像里该放什么，不该放什么？

镜像把运行 Java 需要的系统依赖固定下来：哪个 JRE、哪个用户、哪个启动命令。容器是镜像的一次运行。宿主机上装的 Java 版本、环境变量，都不再影响你的服务。

和前端镜像相比，差别有两处：进程是 java -jar，而不是 Nginx；暴露的是 Boot 的服务端口，而不是静态目录。

约定

基础镜像用含 Java 17 的 JRE 镜像，运行时不需要编译器。一个容器一个主要进程。镜像里只有 JRE、jar 和启动命令；配置、密码放在容器外面，通过环境变量和 Secret 传进来；日志写到标准输出，由平台收集。

基准算例

jdk = 17 要在三处同时成立：你本机终端（第 2 章的 java -version）、流水线（第 7 章）、镜像的基础层。教学堆 -Xms256m -Xmx512m 只在本地 docker run 时通过环境变量传入，不写进 Dockerfile，它不是生产配置。

FROM eclipse-temurin:17-jre
WORKDIR /app
RUN useradd -r app
COPY target/app.jar app.jar
USER app
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
易错

镜像里用了和本机不同的 JDK。本机是 17，基础镜像却随手拿了别的版本，测试在本机和 CI 都过了，上线才报 UnsupportedClassVersionError 或者行为不一致。基础镜像的标签要写明 17，不要只写一个不带版本的名字。

避坑

COPY application-prod.yml 把含数据库密码的配置文件烤进镜像。镜像会被推到仓库、被很多人拉取，密码也就跟着扩散了；改一次密码还得重新构建。密码走 Secret，普通配置走 ConfigMap 或环境变量（见 10.5）。

动手

在 WSL 里构建并运行。PORT 取你 application.yml 里配置的端口；教学堆通过 JAVA_TOOL_OPTIONS 传入，JVM 启动时会打印一行 Picked up JAVA_TOOL_OPTIONS，可以用来确认它生效了。

mvn -q package
TAG=$(git rev-parse --short HEAD)
docker build -t order-api:$TAG .
docker run --rm --name order-api -p "$PORT:$PORT" \
  -e JAVA_TOOL_OPTIONS="-Xms256m -Xmx512m" order-api:$TAG
docker exec order-api java -version        # 另开一个终端执行，应当是 17
docker logs -f order-api                   # 容器日志在宿主机上就能看到

10.3 声明要跑几份

问题：只跑一份，它一挂接口就不可用；跑多份，第 9 章那些「多个进程同时改同一份数据」的问题就全回来了。副本数从 1 改成多份时，哪些写法会坏？

Kubernetes 里不写「启动几次」，而是写一份声明：Deployment 的 replicas 表示要维持几份 Pod，控制器负责让实际数量等于声明。调用方不记 Pod IP，只访问 Service 这个稳定的名字，由 Service 把请求分给某一个就绪的 Pod。

约定

每个副本都按「随时可能被替换、请求随时可能落到别的副本」来写：副本内存里不保存登录状态，不保存库存这类必须全局一致的数，雪花 id 的 workerId 每个副本各不相同。滚动升级时新旧 Pod 会同时存在，接口要能兼容新旧两个版本。

基准算例

同一笔教学订单买 1 件，stock 从 8 变成 7，不管有几个副本，都只能扣一次。订单 id 仍是 9007199254740993，以字符串输出；多副本时它也必须全局唯一，靠的是每个副本不同的 workerId，而不是单表自增（第 9 章 9.10）。

易错

多副本各自保存登录状态。用户在 Pod 1 登录，下一次请求被 Service 分到 Pod 2，就被要求重新登录。会话要放进共享存储，或者改用每个副本都能独立校验的令牌（第 9 章 9.8）。

避坑

多副本各自扣一次库存。库存放在每个副本的内存里，各副本看到的数就各不相同；如果每个副本都消费同一条下单消息，一单就会被扣好几次。库存只放在数据库里，在事务中做条件更新（第 6 章 6.9）；消费端要防重复（第 9 章 9.6）。

副本数与多副本下的状态拖动副本数滑块 · 切换各项写法
观察要点：① 副本数为 1 时，几乎所有错误写法都看不出来，副本数一大于 1 就暴露；② workerId 写死在镜像里时，所有副本用同一个 workerId，雪花 id 不再保证全局唯一；③ 库存放在副本内存里，各副本看到的数不一致；每个副本各消费一次，一单就扣了副本数那么多次；④ 探针指向扣库存的接口时，每一轮探针都会再扣掉副本数那么多件；⑤ 下方的 Deployment 片段跟着控件变化，replicas 就是滑块上的副本数。
动手

把副本数调大，再查同一笔订单若干次，看每次落到哪个 Pod。--prefix 会在每行日志前标出来自哪个 Pod。

kubectl scale deploy/order-api --replicas=<副本数>
kubectl get pods -l app=order-api -o wide
kubectl logs -l app=order-api --prefix | grep 'userId=10001'

10.4 挂了以后谁拉起来

问题：进程崩溃，谁把它重启？进程还在但已经卡死，谁发现？刚启动、连接池还没建好的 Pod，要不要马上接流量？

进程退出时，kubelet 按重启策略把容器重新拉起来；Pod 所在的机器没了，Deployment 控制器会在别处补一个 Pod，让数量回到声明值。「进程还在但不干活」这种情况进程本身发现不了，要靠探针：

探针回答的问题失败后Boot 里的端点
就绪探针（readiness）现在能不能接请求从 Service 摘掉，不再分流量；不重启/actuator/health/readiness
存活探针（liveness）进程是否已经坏到只能重启重启容器/actuator/health/liveness
约定

探针只打 Actuator 的健康端点。存活探针不依赖数据库等下游：数据库短暂不可用时，重启所有副本解决不了问题，反而会让它们一起重启。「暂时不该接流量」交给就绪探针表达。

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: http
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: http

port: http 引用容器里名为 http 的端口，它的值与 server.port 相同。在 Kubernetes 里运行时，Boot 会自动启用这两个探针分组；在本机想看到它们，可以设置 management.endpoint.health.probes.enabled=true。具体属性以所用 Boot 3 版本的文档为准。

基准算例

假设有人把就绪探针指向「下单扣库存」的接口。探针是周期性的，每个副本每一轮都打一次，教学订单的 stock = 8 会在没有任何用户下单的情况下被探针扣光。在 10.3 的演示里把「探针指向」切到扣库存接口，可以读出每一轮探针再扣掉几件。

易错

以为「进程在」就是「服务好」。进程可能还在，但工作线程全被占住、队列已满（第 4 章），或者连接池耗尽（第 6 章 6.5）。存活探针只回答「要不要重启」，业务是否健康要看日志和指标（10.6）。

避坑

健康检查打到会扣库存的接口，或任何有副作用的接口。健康端点必须只读、轻量、不改业务数据。负载均衡器和监控系统的「拨测」也属于这种请求，同样不能指向写接口。

动手

本地跑起来后，先确认探针端点只读，再在集群里看探针失败的事件：

curl -s http://127.0.0.1:$PORT/actuator/health/liveness
curl -s http://127.0.0.1:$PORT/actuator/health/readiness
kubectl describe pod <pod名> | grep -i -A3 probe
kubectl get pods -l app=order-api -w     # RESTARTS 列在涨：存活探针在失败，或进程在崩

10.5 配置仍在外面

问题：第 9 章说注册与配置不要打进包里。到了容器里，这句话具体落在哪：超时写在哪、密码写在哪、堆参数写在哪？

原则和前端的 .env 一样：同一个产物，在不同环境用不同配置运行。镜像只认环境变量名，值由 ConfigMap（普通配置）和 Secret（密码、密钥）在启动容器时注入。

# application.yml（打进 jar，只有变量名，没有值）
order:
  client:
    connect-timeout-ms: ${ORDER_CONNECT_TIMEOUT_MS}
    read-timeout-ms: ${ORDER_READ_TIMEOUT_MS}

# ConfigMap（在镜像外面）
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-api-config
data:
  ORDER_CONNECT_TIMEOUT_MS: "500"
  ORDER_READ_TIMEOUT_MS: "2000"

# Deployment 的容器片段
envFrom:
  - configMapRef:
      name: order-api-config
  - secretRef:
      name: order-api-db

yml 里不写默认值是有意的：变量没注入时，Boot 启动就失败并报出变量名，而不是悄悄用一个谁也不知道的值跑起来。

约定

超时、下游地址放 ConfigMap；数据库密码放 Secret；教学堆参数只出现在本地运行命令里。浏览器侧的 3000ms 属于前端工程自己的配置，不在这个 Java 服务里。

基准算例

连接超时 connectTimeoutMs = 500、读超时 readTimeoutMs = 2000、浏览器超时 browserTimeoutMs = 3000。三者的关系是 \(500 + 2000 = 2500 \lt 3000\)：服务端调下游即使连接、读取都用满，也会在浏览器放弃之前先失败，并在自己的日志里留下记录。改其中任何一个，都要重新核对这个不等式。

易错

把教学堆参数 -Xms256m -Xmx512m 抄进生产 Deployment。这两个数是为了在笔记本上跑教学订单（第 2 章 2.10），不是容量规划；生产的堆大小要按实际数据量和容器内存限制来定，并写清来源。

避坑

配置打进镜像，改一次超时就要重新构建、重新走一遍流水线。另一个相反的坑：改了 ConfigMap 却不重启 Pod。以环境变量注入的值只在容器启动时读取，正在运行的 Pod 不会自动换值，需要 kubectl rollout restart。

动手

确认运行中的 Pod 拿到的就是 ConfigMap 里的值：

kubectl get configmap order-api-config -o yaml
kubectl exec <pod名> -- env | grep TIMEOUT      # 应为 500 与 2000
kubectl rollout restart deploy/order-api        # 改了 ConfigMap 之后
kubectl rollout status deploy/order-api

10.6 一次排错要看的日志、端口和线程池

问题：前端同事说「接口没反应」。第一反应是重启？重启以后现场就没了，下次还会再来。排错要有一条固定的顺序。

这条顺序来自自学页「Linux 常用命令」卡片的验收标准：进程、端口、日志、本机 curl，相当于把浏览器 Network 面板换成服务器上的一组命令。本课再补上两站：线程池、超时与配置来源。

顺序看什么命令判据
1 进程与端口进程在不在，听的是不是你访问的端口和地址kubectl get pods、ps -ef | grep java、ss -lntpPod 为 Running 且就绪；端口在监听
2 本机 curl绕开网关和浏览器，直接打这个进程curl -m 3 http://127.0.0.1:$PORT/...本机通、外面不通，问题在网络或 Service；本机也不通，问题在进程里
3 日志里的 userId这一笔请求进来没有、走到哪一步tail -f、kubectl logs、grep 'userId=10001'有进入、无结束，就是卡在中间
4 线程池核心线程、队列、最大线程、拒绝日志里的 RejectedExecutionException、jcmd <pid> Thread.print出现拒绝，说明已经满到第 109 个
5 超时与配置来源运行中的值是不是 500 / 2000，来自哪里kubectl exec ... env，对照 ConfigMap值不对或缺失，就回到 10.5

curl -m 3 的 3 秒就是浏览器的 3000ms：用和前端相同的耐心去等，结论才能对上。

约定

先看，后动手。pwd、ls 确认你在发布目录而不是家目录的旧拷贝；rm 之前先 ls 核对路径；覆盖之前先 cp 备份；启动脚本用 chmod 保证可执行，密钥文件不要所有人可读。重启放在保存了日志和线程转储之后。

基准算例

线程池 poolCore = 4、queueCapacity = 100、poolMax = 8。任务涌入时，先占满 4 个核心线程，再放进 100 个队列位置，再涨到 8 个线程，第 \(4 + 100 + (8 - 4) + 1 = 109\) 个走拒绝策略（由 Course.orderMath.rejectTaskNo() 算出）。日志里每条都带 userId=10001 和 amountFen=19950，才能把拒绝和某一笔订单对上。

易错

只盯着浏览器的 3000ms。浏览器超时只说明「3000ms 内没等到响应」，不说明是谁慢。按 10.5 的不等式，服务端的读超时 2000ms 应该先触发；如果浏览器先超时、服务端日志却没有超时记录，就要怀疑服务端的超时配置根本没生效。

避坑

只看进程还在，不看第 109 个请求已被拒绝。拒绝发生在线程池里，进程和健康端点都完好，探针也一切正常。如果拒绝策略没人接、异常没进日志，调用方只看到一个笼统的错误（第 4 章）。拒绝次数要进日志或指标。

按固定顺序排错选择现象 · 切换步骤 · 拖动涌入任务数
观察要点：① 四种现象都从「进程与端口」开始，进程在只排除了最粗的一层；② 「浏览器 3000ms 超时」时，池没满就去看超时，池已拒绝就回到日志里的 userId；③ 把涌入任务数拖到 109，线程池那一站变红，而进程与健康端点那一站仍是绿的；④ 「日志里找不到」常常是只看了一个 Pod，要按标签看全部副本；⑤ 每一步的读数都给出「下一步该看」，排错不靠猜。

10.7 对照基准算例做检查

问题：部署成功、探针变绿，算不算上线完成？怎样用一笔已知答案的订单，快速判断链路上有没有哪一步悄悄换了东西？

基准算例的用处就在这里：每个数都有已知的正确值和出处。部署后拿它逐项比对，比读几百行配置更快发现问题。

基准值部署后在哪核对不一致说明什么回看
订单 id 字符串 "9007199254740993"curl 返回的 JSON变成 9007199254740992：某处按 JSON number 输出或解析第 1 章
userId "10001"返回的 JSON 与日志日志里查不到：日志字段缺 userId第 1、7 章
amountFen = 19950返回的 JSON 与数据库出现 199.5 的 double 运算：金额单位换了第 1、6 章
stock = 8，下单 1 件后为 7数据库多扣：事务、幂等或探针出了问题第 6、9 章，10.4
jdk = 17docker exec ... java -version镜像基础层和本机、CI 不一致第 2、7 章
连接 500、读 2000、浏览器 3000kubectl exec ... env、前端配置值来自镜像而不是 ConfigMap，或缺失第 4 章，10.5
池 4 / 100 / 8，第 109 个拒绝日志或指标中的拒绝计数线程池参数被改，或拒绝没进日志第 4 章
教学堆 -Xms256m -Xmx512m生产 Deployment 里不应出现教学值被当成了生产配置第 2 章
约定

检查只引用 Course.data.order 和 Course.orderMath 里的值。qpsTeach = 50 只是数量级，不进检查表，也不作为容量结论（第 7 章 7.7）。

基准算例

一次完整的验收：查询 userId 10001 的教学订单，返回 id 为字符串 9007199254740993、金额 19950 分；下单 1 件后库存为 7；日志里能用 userId=10001 查到这两条请求；运行中的超时变量是 500 与 2000；镜像里是 Java 17。

易错

用 10001 检查精度丢失。10001 远在 \(2^{53}\) 以内，按 JSON number 传也不会变；能暴露精度问题的只有雪花 id 那一串（第 1 章）。

避坑

只在单副本环境里检查。登录状态、库存扣减、雪花 id 的问题在副本数为 1 时都看不出来（见 10.3 的演示）。检查至少要在多副本下把库存和登录两项再做一遍。

部署检查表：逐项对照基准算例在右侧切换每一项的当前做法
观察要点：① 初始状态故意留了两处错误：超时打进了镜像，教学堆写进了生产 Deployment，先把它们改对；② 订单 id 切成 JSON number 时，左表直接显示前端拿到的 9007199254740992；③ 每一项不合格都标出回看哪一章，这张表就是全课避坑清单在部署时的用法；④ 全部合格，才算「部署成功」。

10.8 全课避坑清单怎么用

问题：前九章每章都有一张避坑清单，加起来几十条。背下来不现实，那么什么时候、按什么顺序去翻？

章末的「本章避坑清单」把前九章和本章的坑按章收在一起。它不是用来背的，而是三种场合下的查表工具：

场合怎么用例子
写代码之前按要写的东西找对应章要写扣库存：先看第 6 章的事务、第 9 章的重复消费
上线之前用 10.7 的检查表逐项过，不合格的回看对应章超时来自镜像：回看第 4 章和 10.5
出了问题按 10.6 的顺序定位到一站，再找这一站对应的坑拒绝异常：第 4 章的线程池；日志查不到：第 7 章的日志字段
约定

每条坑都写成「现象 + 原因 + 回看哪章」。新发现的坑，按同样格式追加到你自己的清单里，并注明它对应教学订单里的哪个数。

基准算例

现象「前端显示的订单号末位少 1」，查清单定位到第 1 章：9007199254740993 被按 JSON number 解析成 9007199254740992。修法是服务端按字符串输出，不是在前端加 1。

易错

把清单当成「都做到了就不会出错」的保证。清单只覆盖本课写死的场景；它帮你少踩已知的坑，不替代测试（第 7 章）和排错（10.6）。

避坑

出了问题直接翻清单逐条试。应当先按 10.6 的顺序定位到一站，再看这一站对应的那几条；否则会在无关的条目上浪费时间。

动手

打开章末清单，挑出与你当前项目最相关的五条，抄到卡片上，每条后面写一行「在我的项目里，这一条对应哪段代码或哪份配置」。

10.9 高级条目什么时候才展开

问题：自学页的高级全表里还有 Jenkins、服务网格、自动扩缩容、链路追踪等很多条目。本课没有为它们单独成章，那什么时候该学？

本课的立场与第 9 章 9.11 一致：先建立地图，碰到再展开。「碰到」要有明确的触发条件，而不是「看起来很重要」：

条目触发条件展开前先确认
Jenkins 等流水线工具的细节你要自己维护流水线，而不只是看它变红变绿10.1 的六步都已自动化，标签用提交号

基准算例

以「要不要上自动扩缩容」为例：如果副本内存里还存着会话、库存，扩缩容只会把 10.3 演示里的错误放大。先让教学订单在多副本下仍然只扣一次、id 仍然唯一，再谈扩缩容。

易错

把 qpsTeach = 50 当成扩缩容的阈值。它只是本课的数量级，不是压测结论；阈值要来自你自己测出来、写明条件的数据。

10.10 本章不再引入新的示例数字

问题：为什么整门课只用一笔教学订单？部署和排错时明明还会碰到端口、副本数、探针周期这些数，为什么本章不给示例值？

一套数贯穿全课，你在任何一章看到 19950，都知道它是那笔订单的金额分；看到 109，都知道它是线程池里被拒绝的那个任务。如果每章另造一套数，读者就要在几套互相矛盾的数之间来回换算，排错时也分不清「这个值不对」还是「这只是另一章的示例」。

约定

端口、副本数、探针周期这类数，本章一律写成「取你 yml 里的端口」「<副本数>」这样的占位，由你的项目给出。演示里的副本数滑块只是控件，不是推荐值。

基准算例

本章出现的派生数都能由上表算出：下单 1 件后库存 \(8 - 1 = 7\)；超时关系 \(500 + 2000 = 2500 \lt 3000\)；拒绝序号 \(4 + 100 + 4 + 1 = 109\)。

易错

为了演示方便临时改基准值，比如把库存改成别的数，好让「扣光」来得更快。这样一来，本章和第 6、9 章的结论就对不上了。要演示更快扣光，改的应该是「有几个副本、探针打了几轮」，而不是库存。

避坑

把自己项目里测出来的数写回教程的基准算例。你的数是测量结果，要单独记录并写清条件（机器、数据量、版本）；models.js 里的基准只服务于教学，不跟着任何一个项目变。

本章避坑清单

按章收录前九章已经写死的坑，最后是本章新增的几条。每条后面注明回看哪一章。

  1. 雪花 id 以 JSON number 输出：9007199254740993 变成 9007199254740992，差 1。服务端按字符串输出。（第 1 章）
  2. 金额用 double 元做账：199.5 单次转换看不出错，累加、比较时才出错。一律用整数分 19950。（第 1、6 章）
  3. 依赖没进 classpath、DTO 直接暴露数据表的行：前者运行时找不到类，后者把内部字段泄露给前端。（第 1 章）
  4. 改完环境变量不新开终端、Windows 与 WSL 路径混用：终端里的 java 不是 17，或者读错了文件。（第 2 章）
  5. 拿 -Xmx512m 跑真实数据量：教学堆不是容量规划。（第 2 章）
  6. 默认容量装 10000 条、可变对象当键：前者多次扩容拷贝，后者改了字段就取不出来。（第 3 章）
  7. 到处 new Thread、拒绝策略没人接：池满到第 109 个时，调用方只看到一个笼统的异常。（第 4 章）
  8. 文本按平台默认编码读订单 JSON：中文乱码。按 UTF-8 解码字符流。（第 4 章）
  9. 索引列用函数包裹、为 8 条库存记录上复杂结构：前者走不到 B+ 树，后者是过度设计。（第 5 章）
  10. 拼接 SQL、用 ${} 拼 userId：SQL 注入。用占位符和 #{}。（第 6 章）
  11. 扣减 stock 不在事务里读改写、连接不归还：并发时多扣；连接池被占满后所有请求都在等。（第 6 章）
  12. catch 后吞掉异常、日志缺 userId：出问题时没有任何线索。（第 7 章）
  13. CI 用另一套 JDK、命令在错误目录执行：本机能过的东西在流水线上失败，或者操作了旧拷贝。（第 7 章）
  14. 把 50 QPS 写成容量承诺、用它反推复杂度：qpsTeach 只是数量级。（第 7、8 章）
  15. 递归深到 10000 层、把均摊 O(1) 说成每次 O(1)：前者栈溢出，后者误判单次延迟。（第 8 章）
  16. 无过期的缓存、锁过期后另一请求又扣 stock：读到旧值，或库存被扣两次。（第 9 章）
  17. 消费端不防重复：至少一次投递下，8 件库存被减两次。（第 9 章）
  18. 把停更组件当默认选项：Hystrix、Zuul 只作地图，指向 Sentinel 与 Spring Cloud Gateway。（第 9 章）
  19. 在服务器上编译、进容器改代码当发布：说不清跑的是哪次提交，重启后改动消失。（本章 10.1）
  20. 镜像 JDK 与本机、CI 不同：基础镜像标签写明 17。（本章 10.2）
  21. 多副本各自保存登录状态、各自扣库存、workerId 相同：被要求重新登录、库存不一致或多扣、id 重号。（本章 10.3）
  22. 健康检查打到会扣库存的接口、存活探针依赖数据库：探针扣光库存；下游一抖，所有副本一起重启。（本章 10.4）
  23. 配置打进镜像、教学堆写进生产 Deployment、改了 ConfigMap 不重启：改超时要重新构建；生产用了教学值；新值没生效。（本章 10.5）
  24. 只看进程还在，不看第 109 个已被拒绝：进程和探针都正常，请求却在线程池里被拒。（本章 10.6）

本章小结与延伸阅读

  • 最小闭环：提交、流水线测试打包、构建镜像（标签用提交号）、推仓库、Deployment 引用、Service 访问、用教学订单验收。服务器上不编译，容器里不改代码。
  • 镜像里只有 Java 17 JRE、jar 和启动命令；配置走 ConfigMap，密码走 Secret，教学堆 -Xms256m -Xmx512m 只在本地运行时传入。
  • 多副本时，登录状态放共享存储或令牌，库存只在数据库事务里条件更新，消费端防重复，workerId 每个副本不同；一单只扣一次，8 变 7。
  • 就绪探针决定接不接流量，存活探针决定要不要重启；两者都只打 Actuator 健康端点，绝不打扣库存的接口。
  • 超时 500 + 2000 小于浏览器的 3000，服务端应当先失败并留下日志；改了 ConfigMap 要重启 Pod 才生效。
  • 排错顺序：进程与端口、本机 curl、日志里的 userId、线程池（第 109 个拒绝）、超时与配置来源。先看后动，重启放在最后。
  • 部署后用基准算例逐项核对；避坑清单按「写代码前、上线前、出问题时」三种场合查表；高级条目等到触发条件满足再展开。
