6.1 Servlet 与 Tomcat

这一节要回答的问题：浏览器发出一个 HTTP 请求后，Java 这边到底是“谁”在处理它？前端熟悉的 Express 是 (req, res) 一个函数，Java 这边对应的东西叫 Servlet，而跑 Servlet 的容器叫 Tomcat。Spring MVC 只是盖在 Servlet 上的一层。

Servlet 的生命周期

Servlet 类似一个极薄的服务端处理函数：URL 进来，写出响应。它的生命周期由容器管理：

  • 加载与实例化：容器（Tomcat）在需要时加载类并 new 出实例，单实例多线程；
  • init：实例化后调用一次，做初始化；
  • service：每个请求进来，容器从线程池取一个工作线程调用 service，由它分发到 doGet/doPost；
  • destroy：容器卸载时调用一次，做收尾。

关键点：一个 Servlet 实例被多个线程并发调用。这和第 4 章讲的“请求进池而不是事件循环”是一回事——Tomcat 自己维护一个线程池，每个请求占用一个工作线程。所以不要在 Servlet 里用实例变量保存“当前请求”的状态，那是典型的线程不安全。

约定

Tomcat 既是 Servlet 容器，也是 Spring Boot 的默认内嵌服务器。一次请求的简化路径是：连接 → 解析 HTTP → 找到 Servlet → 业务 → 写状态码和体。Spring Boot 启动时把 Tomcat 作为 starter-web 带进来的依赖直接内嵌，不需要你单独部署 war。

基准算例 6-1：教学订单落在哪个线程

教学订单 Course.data.order 的 userId = 10001、amountFen = 19950。前端发 GET /api/orders/10001，Tomcat 从工作线程池取一个线程（假设叫 http-nio-8080-exec-3）来处理它。这个线程从请求里读出路径变量 10001，一路把它传到 JDBC，最后用 PreparedStatement 绑定进 SQL。线程名只是观察用的标签，业务代码不要依赖它。

易错：以为 Spring MVC 抛弃了 Servlet
@RestController、@GetMapping 这些注解让人以为请求不再经过 Servlet。 Spring MVC 的入口是 DispatcherServlet——它本身就是一个 Servlet。注解只是让框架替你把 URL 映射到方法、把参数绑定好，底层仍是 service → doGet 那一套。所以 Servlet 的线程模型、Filter 机制对 Spring MVC 同样适用。
避坑：在 Servlet / Controller 里用实例字段存请求状态
写一个 private String currentUserId; 字段，在方法里赋值，下一个方法再用。 实例只有一个，线程有很多个。两个请求并发时，后一个请求会覆盖前一个的字段。请求级别的状态要用方法参数、局部变量或 Request 域传递，绝不放进实例字段。
可操作对象

在本机启动一个 Boot 程序后，用 jstack <pid> 抓一次线程转储，找到名字以 http-nio-8080-exec 开头的线程；并发 curl 同一个接口几次，观察这些线程是否被复用。具体菜单和参数名以所用 Tomcat / Boot 版本的文档为准。

6.2 Filter

问题：跨多个 Controller 的通用逻辑（编码、鉴权、日志、限流）写在哪？前端有服务端中间件，Java 这边对应的是 Filter。Filter 在 Servlet 前后包一层，可以决定是否把请求继续往下传。

Filter 与责任链

多个 Filter 组成一条链（责任链模式）。请求依次经过每个 Filter，到达 Servlet，响应再沿原路返回。每个 Filter 在 doFilter 前做“进入”逻辑，调用 chain.doFilter 把控制权交给下一个，在它之后做“离开”逻辑：

public class LogFilter implements Filter {
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) {
        long t = System.currentTimeMillis();
        chain.doFilter(req, res);              // 进入下一环
        log.info("cost={}ms", System.currentTimeMillis() - t); // 离开
    }
}

Spring Boot 里用 @Component + FilterRegistrationBean 注册 Filter 并指定顺序。Spring 自己的 HandlerInterceptor 作用在 DispatcherServlet 内部，粒度比 Filter 细，但本质都是“在业务前后包一层”。

约定

Filter 是容器级别的，对所有 Servlet 生效；Interceptor 是 Spring MVC 级别的，只对进 DispatcherServlet 的请求生效。鉴权、限流这类“不通过就别进业务”的逻辑放 Filter；和 Controller 强相关的横切逻辑放 Interceptor。具体注册方式和默认顺序以 Boot 文档为准。

基准算例 6-2：给教学订单接口加一个耗时 Filter

给 GET /api/orders/10001 加一个 Filter：进入时记下时间戳，chain.doFilter 之后算出耗时。教学订单的 readTimeoutMs = 2000，如果某次耗时接近或超过它，这条日志就是排查慢请求的入口。Filter 不关心 userId 是 10001 还是别的，它只包一层时间。

易错：忘了调用 chain.doFilter
写了一个 Filter，只做了鉴权判断，没调用 chain.doFilter 就返回了，以为请求会继续。 不调用 chain.doFilter，请求就停在当前 Filter，后面的 Filter 和 Servlet 都不会执行。这是“短路”。鉴权失败时确实要短路，但要主动写好响应（状态码、错误体），不能什么都不返回。
避坑：在 Filter 里吞掉异常
Filter 里 try { chain.doFilter(...) } catch (Exception e) {}，把所有异常静默吃掉。 这样业务里的异常再也传不到全局异常处理，前端只看到 500 却没有线索。Filter 只处理它职责范围内的异常（比如鉴权失败），其余异常让它向上抛，交给容器或 Spring 的异常处理器。
可操作对象

写一个打印请求 URI 和耗时的 Filter，注册到 Boot 程序上；curl /api/orders/10001 后看日志里是否出现这条记录。把它的顺序调到鉴权 Filter 之前和之后各试一次，观察日志先后。

6.3 JDBC 四个对象

问题：业务代码最终怎么把数据写进数据库、又怎么读出来？Java 的标准答案是 JDBC。它有四个核心对象，理解它们的分工，就理解了所有上层框架（MyBatis、JPA）在替你做什么。

四个对象

对象作用谁负责创建/关闭
DriverManager / DataSource建立到数据库的连接（或从连接池借一条）DataSource 由容器/Boot 注入；连接由池管理
Connection一个数据库会话，事务绑定在它上面用完归还连接池，不要手动 new
PreparedStatement一条预编译的 SQL，参数用占位符绑定try-with-resources 自动关闭
ResultSet查询返回的行游标，逐行读列try-with-resources 自动关闭

典型用法（try-with-resources 负责关闭语句和结果集）：

try (PreparedStatement ps = conn.prepareStatement(
        "SELECT user_id, amount_fen, stock FROM t_order WHERE user_id = ?")) {
    ps.setLong(1, userId);                 // 占位符绑定，第 1 个 ? = userId
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            long uid = rs.getLong("user_id");
            int fen = rs.getInt("amount_fen");
        }
    }
}
约定

SQL 参数一律用 ? 占位符，再用 setXxx 绑定。连接从 DataSource（连接池，Boot 默认 HikariCP）借，用完归还，不要自己 DriverManager.getConnection。Statement 和 ResultSet 用 try-with-resources 关闭，避免泄漏。

基准算例 6-3：按 userId 查教学订单

用 userId = 10001 查教学订单。SQL 是 SELECT amount_fen, stock FROM t_order WHERE user_id = ?，ps.setLong(1, 10001L) 绑定。读出 amount_fen = 19950、stock = 8。注意 userId 是 Long，用 setLong；金额是整数分，用 getInt，不要按 199.5 元的 double 读。

易错：把金额按 double 读
数据库列是 DECIMAL，Java 这边用 rs.getDouble 读成 199.5 再做运算。 金额用整数分做运算（amountFen = 19950）。DECIMAL 列读出来用 BigDecimal 或整数分，避免 double 在二进制里的表示误差累积。单次 199.5 看不出错，但加减乘除多了就会差分。
避坑：连接不归还，池被占满
手动 getConnection 后忘了 close，或者把 Connection 存进静态变量复用。 连接池容量有限（HikariCP 默认 10）。泄漏几条连接后，新请求借不到连接就卡住。一律从 DataSource 借、用完 close/归还；让框架或 try-with-resources 管关闭，业务代码不要持有 Connection 的生命周期。
可操作对象

用 JDBC + H2 或本机 MySQL 建一张 t_order 表，完成按 user_id 查询。SQL 必须用 PreparedStatement，userId = 10001 绑定后读出 amount_fen 和 stock。

6.4 占位符与拼接

问题：为什么所有教程都强调“不要拼接 SQL”？这一节用一个开关把“拼接”和“占位符”并排放出来，看 userId 在两种写法里分别被当成什么。这是本章最关键的安全红线。

占位符 vs 字符串拼接

占位符（?）由数据库驱动负责转义和绑定，参数永远只是“一个值”，不可能变成 SQL 的一部分。字符串拼接则把用户输入直接写进 SQL 文本，输入可以变成额外的 SQL——这就是 SQL 注入。

占位符（安全）

String sql = "SELECT * FROM t_order WHERE user_id = ?";
ps = conn.prepareStatement(sql);
ps.setLong(1, userId);   // userId 永远是值

即使 userId 传进来 10001 OR 1=1，它也只是当成一个字符串值去匹配 user_id，不会改变 SQL 结构。

拼接（危险）

String sql = "SELECT * FROM t_order WHERE user_id = " + userId;
ps = conn.prepareStatement(sql);

userId = 10001 OR 1=1 时，SQL 变成 ... WHERE user_id = 10001 OR 1=1，OR 1=1 成了 SQL 代码，全表泄露。

占位符 vs 拼接切换开关 · 修改 userId 试注入
观察要点：① 切到“拼接”，把 userId 改成 10001 OR 1=1，看 SQL 文本里多出来的 OR 1=1 被标红——它成了 SQL 代码；userId 是否被当成 SQL 代码显示“是”。② 切到“占位符”，同样输入 10001 OR 1=1，SQL 仍是 WHERE user_id = ?，整串只是第 1 个参数的值，userId 被当成代码显示“否”。③ 即便输入正常 10001，拼接写法在结构上也是危险的，安全看的是写法而不是某一次输入。
约定

凡是来自用户、参数、请求体的值，一律走占位符。前端校验挡不住直接打到接口上的请求，所以服务端必须自己用占位符。把“绝不拼接用户输入”当成代码评审的硬规则。

基准算例 6-4：教学订单的 userId 绝不拼接

查教学订单 userId = 10001，SQL 是 SELECT amount_fen FROM t_order WHERE user_id = ?，ps.setLong(1, 10001L)。如果有人把 userId 改成 10001; DROP TABLE t_order，占位符写法里它只是匹配不到的字符串值；拼接写法里这条 SQL 就真的会被拼出来。

易错：以为“数字就不会被注入”
userId 是 long，前端只让传数字，所以拼接也安全。 类型只在 Java 这边把关，到 SQL 文本时已经是字符串。只要写法是拼接，任何能影响 SQL 文本的输入都有风险。而且“前端只让传数字”挡不住直接打接口的人。占位符是写法层面的保证，不依赖输入内容。
避坑：用 ${} 拼 userId
在 MyBatis 里图省事，用 ${userId} 直接把 userId 拼进 SQL。 ${} 是字符串拼接，等价于本节的危险写法。userId 这种用户值必须用 #{userId}（6.6 节）。${} 只允许用在你完全控制的列名、表名、排序字段上，且这些值要在服务端用白名单校验。
可操作对象

在上方演示里把 userId 依次改成 10001、10001 OR 1=1、10001; DROP TABLE t_order，切换“拼接 / 占位符”各看一次生成的 SQL，确认占位符写法下 SQL 文本永远不变。

6.5 连接归还

问题：每个请求都要连数据库，难道每次都新建一条 TCP 连接？当然不是。连接池负责复用：请求借一条、用完归还。这一节说清“借”和“还”的边界，以及为什么 try-with-resources 是关键。

连接池的角色

连接池（Boot 默认 HikariCP）维护一组现成的 Connection。请求处理时从池里借一条，处理完归还。新建 TCP + 握手 + 认证很贵，复用让第 4 章讲的“同步 JDBC 占住工作线程”期间不必再等连接建立。事务绑定在一条 Connection 上：开启事务、提交或回滚都发生在借到的这条连接上，框架负责在事务结束后把它归还。

// Spring 事务管理下，业务代码只管用，不管开关连接
@Transactional
public void deductStock(long userId, int buy) {
    int stock = mapper.selectStock(userId);   // 借连接 → 查
    if (stock < buy) throw new BizException("库存不足");
    mapper.updateStock(userId, stock - buy);  // 同一连接 → 改
}  // 方法正常返回 → 提交 → 归还；抛异常 → 回滚 → 归还
约定

业务代码不持有 Connection 的生命周期。用 MyBatis 时，SqlSession 背后就是一条连接；用 Spring 事务时，@Transactional 决定这条连接何时提交/回滚/归还。try-with-resources 关闭的是 Statement、ResultSet 这类“用完即弃”的资源，连接由池收回。

基准算例 6-5：教学订单接口的连接生命周期

请求 GET /api/orders/10001 进来，工作线程从 HikariCP 借一条连接，执行 SELECT ... WHERE user_id = ? 绑定 10001，读出 amountFen = 19950，方法返回后连接归还。下一个请求复用同一条连接查别的 userId。连接数有限，所以慢查询会占住连接，影响其他请求。

易错：以为 close 就是物理关闭
看到 conn.close() 就以为这条 TCP 连接被断开了。 池化连接的 close 是“归还到池”，物理连接还留着给下次复用。所以 close 很快、很便宜。真正昂贵的是从池里借不到连接——那意味着池被占满，新请求要等。
避坑：把 Connection 存进静态变量复用
为了“省连接”，把一条 Connection 存进静态变量，所有线程共用。 Connection 不是线程安全的，多线程并发用同一条连接会错乱。连接就该让池管理：借、用、还。复用由池在内部做，不要在业务层手动复用单条连接。
可操作对象

在 application.yml 里把 HikariCP 的 maximum-pool-size 改成 2，并发 curl 5 次 /api/orders/10001，观察是否有请求在等连接；再把池大小改回默认，对比响应时间。参数名以所用 HikariCP 版本文档为准。

6.6 MyBatis 的 #{} 和 ${}

问题：JDBC 能用之后，手写“取一行、按列名填进对象”很啰嗦。MyBatis 负责把行映射成对象，把 if 写进 XML 或注解。但它的两种参数语法 #{} 和 ${} 长得像，行为却完全相反，这是 MyBatis 最容易踩的坑。

#{} 与 ${} 的本质区别

写法底层参数位置能否被注入适用
#{userId}预编译参数（PreparedStatement 的 ?）值的位置否用户传入的值：条件值、插入值
${userId}字符串拼接，直接拼进 SQL 文本SQL 结构里是你完全控制的列名、表名、排序字段
 
<select id="selectByUser" resultType="Order">
  SELECT amount_fen, stock FROM t_order
  WHERE user_id = #{userId}        <!-- 值，安全 -->
  ORDER BY ${orderCol}             <!-- 列名，只能用 ${}，但必须白名单校验 -->
</select>

动态 SQL 用 <if>、<where>、<foreach>：先把条件拼对，再谈优雅。MyBatis-Plus 让实体加注解、Mapper 继承 BaseMapper，单表增删改查可以不写 SQL，但复杂查询仍要会 XML。Mapper 接口的方法靠 JDK 动态代理在调用时找到对应语句。

约定

规则只有一条：用户值用 #{}，结构名用 ${} + 白名单。列名、表名、ORDER BY 的字段名不能用 #{}（它们不是值），只能用 ${}，但必须在服务端把允许的取值限定成白名单，不能直接透传用户输入。

基准算例 6-6：教学订单的两种参数

按 userId 查教学订单：WHERE user_id = #{userId}，绑定 10001。如果还要支持按金额或库存排序，ORDER BY ${orderCol}，orderCol 只允许取 amount_fen、stock 两个值，服务端校验后再拼。userId 永远是 #{}，绝不用 ${} 拼 userId。

易错：把 #{} 和 ${} 当成风格差异
两种写法都能跑出结果，就当成可互换的风格选择。 #{} 是预编译参数，${} 是字符串拼接，行为完全不同。${userId} 等价于 6.4 节的危险拼接，userId 可被注入。代码评审时看到 ${} 包着用户值就要拦下。
避坑：用 ${} 拼 userId
分页或排序时顺手把 userId 也写成 ${userId}，图省事。 userId 是用户值，必须 #{userId}。排序字段才用 ${orderCol}，且 orderCol 要在服务端用白名单校验。两者不要混用，评审时按“是值还是结构名”判断该用哪种。
可操作对象

同一张 t_order 表，用 XML 写一个带可选金额条件的分页查询（#{minFen}、#{offset}），再用 MyBatis-Plus 写一个按 userId 的更新。对比两份代码里哪一处是 #{}、哪一处如果换成 ${} 会有注入风险。

6.7 一级缓存活不过会话

问题：MyBatis 有缓存，能用来当业务缓存吗？不能。这一节说清一级缓存和二级缓存的范围，以及为什么“默认不要靠它们做跨请求的业务缓存”。

两级缓存的范围

缓存范围默认失效时机
一级缓存SqlSession 级别开启SqlSession 关闭即失效；增删改会清空本会话缓存
二级缓存Mapper（namespace）级别需手动开启跨 SqlSession，但跨节点无效；写操作会刷新

关键结论：一级缓存活不过会话。一次请求通常对应一个 SqlSession，请求结束它就没了。所以一级缓存只在“同一个请求里重复查同一行”时有点用，绝不是跨请求的业务缓存。二级缓存跨 SqlSession，但在多节点部署时各节点各存各的，一致性没人管。业务缓存要用第 9 章的 Redis，不要用 MyBatis 缓存顶替。

约定

把 MyBatis 缓存理解成“框架内部的去重优化”，不要当成业务缓存。需要跨请求、跨节点共享的缓存，用 Redis。一级缓存默认开，基本不用管；二级缓存除非你清楚它的刷新语义，否则不要开。

基准算例 6-7：教学订单的一级缓存

在一次请求里连续两次 mapper.selectByUser(10001)，第二次走的是一级缓存，不查库。但下一个请求再查 10001，是新 SqlSession，重新查库。所以一级缓存对“同一请求里查两次”有效，对“两个请求都查 10001”无效。教学订单的 stock = 8 也不会被缓存到下一次请求。

易错：把一级缓存当成跨请求的业务缓存
以为 MyBatis 缓存了 10001 的订单，下一个请求查 10001 就不用查库了。 一级缓存是 SqlSession 级别，请求结束就清空。跨请求要查同一行，每次都查库。把框架缓存当业务缓存，既得不到加速，又会在多节点下出现各节点数据不一致。
避坑：开了二级缓存却忘了写操作刷新
开启二级缓存后，扣减库存后没注意缓存刷新，读到旧库存。 二级缓存的刷新依赖配置和写操作的 namespace 对齐，稍有不慎就读到旧值。教学订单这种会变的业务数据，不要靠 MyBatis 二级缓存；要缓存就显式用 Redis 并自己管失效。
可操作对象

在同一个 Service 方法里连续两次调用 selectByUser(10001)，开 SQL 日志看第二次是否真的没查库；再发第二个请求，确认它又查了一次。这能直观看到一级缓存的边界。

6.8 IoC 与默认单例 Bean

问题：对象不再在业务代码里 new，那谁负责创建、谁负责传进来？Spring 的 IoC 容器。这一节说清 IoC、DI、Bean 默认单例，以及为什么 Controller / Service / Mapper 都是单例。

IoC、DI 与 Bean 生命周期

  • IoC（控制反转）：对象不再在业务代码里 new，由容器创建并管理。
  • DI（依赖注入）：构造器接收依赖，优先构造器注入。
  • Bean 默认单例：一个 Bean 定义对应一个实例，被多线程并发调用；prototype 是每次获取新实例。
  • 生命周期：创建 → 依赖注入 → 初始化 → 销毁，由容器管。
@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService service;       // 构造器注入
    OrderController(OrderService service) { this.service = service; }

    @GetMapping("/{userId}")
    Order get(@PathVariable long userId) { return service.find(userId); }
}

MVC 这一层：DispatcherServlet 收到请求，按映射找 Controller 方法，参数从路径、查询、体里绑定。AOP 把日志、事务、权限从业务方法里拉出来——有接口时常用 JDK 动态代理，没有接口时用 CGLIB 生成子类。

约定

Controller、Service、Mapper 默认都是单例，所以和 Servlet 一样：请求级状态不能放实例字段。依赖优先用构造器注入（final 字段 + 构造器），它让依赖显式、不可变，也方便单元测试。

基准算例 6-8：教学订单接口的 Bean 装配

OrderController 依赖 OrderService，OrderService 依赖 OrderMapper，全部由容器注入，全是单例。请求 GET /api/orders/10001 时，这一个 OrderController 实例的 get 方法被工作线程调用，userId = 10001 作为方法参数传进去，不存实例字段。多个请求复用同一个 Controller 实例，互不干扰。

易错：在单例 Bean 里放可变实例字段
在 Service 里写 private Map<Long, Order> cache = new HashMap<>(); 当缓存用。 单例 + 多线程，HashMap 并发读写会出错（结构破坏）甚至死循环。要缓存就显式用线程安全结构或 Redis，并想清楚失效。单例 Bean 的实例字段只放不可变或线程安全的东西。
避坑：自调用不走代理
同一个类里方法 a 直接 this.b()，指望 b 上的 @Transactional 生效。 事务是 AOP 代理加上去的，对象内部的 this 调用不经过代理，切面不会执行，b 上的事务注解失效。要让事务生效，得从容器拿到的那个代理对象发起调用——比如把 b 挪到另一个 Bean，或注入自身代理。这是 Spring 事务最经典的坑，6.9 节会再讲。
可操作对象

写一个 UserController → UserService → Mapper 的查询，给 Service 方法加 @Transactional；故意在类内部自调用这个方法，观察事务注解没生效，再改成从另一个 Bean 调用，对比结果。

6.9 事务包住扣库存

问题：扣库存是“读库存—判断—改库存”三步，中间任何一步被打断都会出错。怎么保证它们要么全做、要么全不做？用事务。这一节把扣库存包进事务，并讲清事务传播。

扣库存为什么必须在事务里

教学订单 stock = 8。买 1 件：先读出 8，判断 8 ≥ 1，再写回 7。如果“读”和“写”之间另一个请求也读到了 8，两个请求都写回 7，就超卖了。把这三步放进一个事务，数据库的行锁和隔离级别保证读到的库存到写回之间不被别人改；再靠事务的原子性，万一中间抛异常，扣减回滚，库存回到 8。

@Transactional
public void deductStock(long userId, int buy) {
    int stock = mapper.selectStock(userId);        // 读
    if (stock < buy) throw new BizException("库存不足");
    mapper.updateStock(userId, stock - buy);       // 改
    // 方法正常返回 → 提交；抛异常 → 回滚
}

事务传播

事务传播决定一个事务方法被另一个事务方法调用时怎么办。先掌握两种：

传播行为当前有事务当前无事务
REQUIRED（默认）加入当前事务新建一个事务
REQUIRES_NEW挂起当前事务，另开一个新事务新建一个事务

REQUIRES_NEW 常用于“无论外层成功与否都要记录”的日志/审计：它另开一个事务，外层回滚不影响它。绝大多数业务用默认的 REQUIRED 就够。

事务包住扣库存切事务开关 · 拖购买数量 · 点执行
观察要点：① 事务开 + 不抛异常：扣减提交，库存从 8 变 7，结果“已提交”。② 事务开 + 扣减后抛异常：扣减回滚，库存仍是 8，结果“已回滚”。③ 无事务 + 扣减后抛异常：扣减已经落库，没有回滚，库存变 7 且无法恢复，结果“无事务，扣减已落库”。④ 购买数量超过库存时直接失败，不扣减。
约定

事务加在 public 的 Service 方法上，由 Spring 通过代理织入。读改写三步放一个事务方法里，让数据库保证原子性和隔离。需要独立提交的子操作用 REQUIRES_NEW，其余用默认 REQUIRED。

基准算例 6-9：扣减 stock 8

教学订单 stock = 8，买 1 件。事务方法读出 8、判断 8 ≥ 1、写回 7、提交。若写回后抛异常，回滚，库存仍是 8。没有事务时，写回 7 已经落库，异常也救不回来，库存停在 7。演示里可以切开关对比这两种结局。

易错：事务加在 private 方法上
把 @Transactional 加在 private 方法上，以为只要加了注解就生效。 Spring 事务靠代理，private 方法外部访问不到，代理织不进去，注解不生效。同理自调用的 this.b() 也不走代理。事务加在 public 的、从外部（或代理）调用的方法上。
避坑：扣减 stock 8 时不在事务里读改写
先查库存、再在 Service 里判断、再单独调 update，三步没包在事务里。 三步分开就不是原子的，并发下会超卖。用 @Transactional 把“读—判断—改”包成一个方法，靠数据库行锁和事务保证正确。扣库存是本章把前面所有概念收拢的地方：占位符防注入、连接归还、事务传播都在这里。
可操作对象

在上方演示里：把购买数量设为 1，分别试“事务开 + 不抛异常”“事务开 + 抛异常”“无事务 + 抛异常”三种组合，看最终库存和结果说明；再把购买数量调到 9，确认库存不足时不扣减。

6.10 一个查询教学订单的 Boot 接口

问题：把前面所有概念收拢成一个能跑的接口。这一节用 Spring Boot 3 + Java 17 写出 GET /api/orders/{userId}，从数据库读出教学订单的 JSON，并说清端口、数据源、profile 各写在哪。

分层与一个最小接口

接口按 Controller → Service → Mapper 分层。Controller 只做参数绑定和响应；Service 做业务和事务；Mapper 做数据访问。教学订单的 userId 是 Long，给前端的 JSON 写成字符串 "10001"（第 1 章已讲过雪花 id 用 JSON number 会少 1，这里养成习惯）。

@RestController
@RequestMapping("/api/orders")
class OrderController {
    private final OrderService service;
    OrderController(OrderService service) { this.service = service; }

    @GetMapping("/{userId}")
    OrderVO get(@PathVariable long userId) { return service.find(userId); }
}

@Service
class OrderService {
    private final OrderMapper mapper;
    OrderService(OrderMapper mapper) { this.mapper = mapper; }
    OrderVO find(long userId) { return mapper.selectByUser(userId); }
}

配置写在 application.yml：端口、数据源（url、用户名、密码、驱动）、连接池（HikariCP）。多环境用 application-dev.yml，启动时指定 profile。Actuator 先让 /actuator/health 能打开，高级监控放到后面。

server:
  port: 8080
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/teach
    username: root
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
  profiles:
    active: dev
从 HTTP 到 PreparedStatement 的路径切换阶段 · 看每层拿到什么
观察要点：① 从“浏览器”一路切到“PreparedStatement”，看请求经过的八层；每层只做自己那一段，userId 在路径变量里出现，到 PreparedStatement 才被绑定成参数。② 切到 PreparedStatement 阶段，读出绑定的 userId = 10001、amountFen = 19950，确认金额是整数分。③ 切到 Tomcat 线程，读出当前线程名；切到 Service，确认事务在这里开启。④ 整条路径里 userId 始终是值，没有被拼进 SQL。
约定

starter-web 带来 MVC 和内嵌 Tomcat，starter-jdbc 或 mybatis 带来数据源。自动装配靠条件注解：某个类在 classpath 上就注册一组 Bean。读一个自动配置类的开头即可，不必背全部。前后端分离时页面在前端工程，Boot 只给 JSON，模板引擎（Thymeleaf）知道是服务端渲染的一种即可。

基准算例 6-10：GET /api/orders/10001

请求 GET /api/orders/10001：Tomcat 线程拿到请求 → Filter 链 → DispatcherServlet → OrderController.get(10001) → OrderService.find(10001) → OrderMapper.selectByUser(10001) → PreparedStatement 绑定 userId = 10001，读出 amountFen = 19950、stock = 8。返回的 JSON 里 userId 写成字符串 "10001"，amountFen 是 19950。

易错：把密码写死进 yml 提交
为了省事，把数据库密码直接写进 application.yml 并提交到仓库。 用环境变量占位符 ${DB_PASSWORD}，密码留在运行环境里。profile 区分环境，但任何 profile 的 yml 都不要放明文密码。配置打进镜像会导致改超时就要重新构建，敏感配置尤其要留在外面。
避坑：DTO 直接暴露数据表的行
把 Mapper 查出来的实体直接返回给前端，字段名、内部状态都泄露出去。 用 VO/DTO 隔离：实体是数据库行的映射，VO 是给前端的契约。userId 在 VO 里转成字符串，内部字段不返回。改表结构不会直接破坏前端契约。
可操作对象

用 Boot 3 和 Java 17 做出这个接口：启动后 curl http://127.0.0.1:8080/api/orders/10001，确认返回的 JSON 里 userId 是字符串、amountFen 是 19950。再改 yml 里的端口为 8081 启动一次，确认端口生效。

6.11 jakarta 与 javax

问题：跟着老教程抄代码，import 的是 javax.servlet.*，在 Spring Boot 3 里却编译不过。为什么？因为包名从 javax 迁到了 jakarta。这一节说清分界线，避免在 Boot 3 项目里混用。

包名迁移

Spring Boot 3 / Jakarta EE 9 起，原来 javax.* 下的 Servlet、JPA、Validation 等包名全部迁到 jakarta.*。这是命名权转移的结果，不是 API 大改。所以：

  • Boot 2 的教程里写 import javax.servlet.*;，在 Boot 3 项目里要改成 import jakarta.servlet.*;；
  • javax.persistence → jakarta.persistence；javax.validation → jakarta.validation；
  • Boot 3 需要 Java 17+。不要把 Boot 2 的 javax 示例直接搬进 Boot 3。
约定

认准你用的 Boot 大版本：Boot 3 一律 jakarta.*，Boot 2 仍是 javax.*。一个项目里不要混用——同一个 Servlet 接口在两个包名下是不同的类，混用会导致 ClassNotFound 或类型不匹配。具体包名以所用 Boot / Jakarta 版本文档为准。

基准算例 6-11：教学订单接口的 import

教学订单接口在 Boot 3 里，Filter 写 import jakarta.servlet.*;，参数类型 jakarta.servlet.http.HttpServletRequest。如果照着 Boot 2 老教程写成 javax.servlet.*，编译器会报找不到类。userId = 10001 的业务逻辑没变，变的只是包名。

易错：Boot 3 仍写 javax.*
从 Boot 2 老教程复制 import，没注意项目已经是 Boot 3。 先确认 pom.xml 里 spring-boot-starter-parent 的版本。3.x 用 jakarta，2.x 用 javax。报“找不到 javax.servlet”时，第一反应不是加依赖，而是核对包名是否该改成 jakarta。
避坑：依赖版本与 Boot 大版本不匹配
在 Boot 3 项目里引入还停留在 javax 的旧版第三方库。 第三方库也要选支持 jakarta 的版本，否则它内部 import 的 javax 类在 Boot 3 里不存在。引入依赖前看它的发行说明是否标注支持 Jakarta / Boot 3。版本搭配以各自文档为准。
可操作对象

在 Boot 3 项目里写一个 Filter，故意先写 javax.servlet.* 看编译报错，再改成 jakarta.servlet.* 通过；打开 pom.xml 确认 starter-parent 版本。

6.12 JSP 不是这门课的重点

问题：老 Java Web 教程一上来就讲 JSP，这门课却几乎不提。为什么？因为现在前后端分离，Boot 只给 JSON，页面在前端工程。JSP 知道位置就好，不要把时间花在写 JSP 页面上。

JSP 的位置

JSP / JSTL / EL 是在服务端拼 HTML 的技术：把 Java 代码嵌进 HTML 模板，由容器编译成 Servlet，最终输出 HTML。它和 Servlet 是同一时代的东西，JSP 最后也是被编译成一个 Servlet。对做前端的人来说，它的位置就是“服务端模板渲染的一种”，和 Thymeleaf、Freemarker 同类。

这门课的目标是中级后端交付一个能调试的 JSON 接口，不是写服务端页面。所以 JSP 不作为学习重点：知道它在哪、能看懂老项目里的 JSP 就够了，新项目用前后端分离。

约定

新接口一律返回 JSON，页面留给前端工程。需要服务端渲染时再了解 Thymeleaf。JSP、JSTL、EL 这些词能认出来、知道是服务端拼 HTML 即可，不在本章展开。

基准算例 6-12：教学订单用 JSON 不用 JSP

教学订单接口 GET /api/orders/10001 返回 JSON：userId 是字符串 "10001"、amountFen 是 19950、stock 是 8。前端拿到 JSON 自己渲染。如果用 JSP，就要在服务端把 10001、19950、8 拼进 HTML，那是另一种交付方式，不是本课的重点。

易错：以为学 Java Web 必须先学 JSP
按老教程顺序，花很多时间学 JSP 语法、JSTL 标签，迟迟写不出一个 JSON 接口。 本课直接走 Boot + JSON 路线，JSP 只作为“认识一下”。把时间花在 JDBC、MyBatis、Spring 事务、Boot 配置上，这些才是中级后端的交付能力。
避坑：在新项目里用 JSP 做前后端分离
用 JSP 在服务端渲染页面，再让前端改 JSP 模板。 前后端分离时页面在前端工程，Boot 只提供 JSON。JSP 让前后端耦合在同一个部署单元里，不利于独立迭代。新项目用 JSON 接口 + 前端框架。
可操作对象

把教学订单接口的返回类型设成 JSON（@RestController 默认就是），用 curl 看原始 JSON；不需要写任何 JSP。遇到老项目的 JSP 能指出它是服务端拼 HTML 即可。

本章避坑清单

  1. 拼接 SQL：用 + 或 ${} 拼 userId，输入能变成额外 SQL。一律用占位符 ? / #{}。
  2. Boot 3 仍写 javax.*：Boot 3 / Jakarta EE 9 起包名是 jakarta.*，照抄 Boot 2 老教程会编译不过。
  3. 事务加在 private 方法上：代理织不进 private，注解不生效；加在 public 的、从代理调用的方法上。
  4. 自调用不走代理：同类里 this.b() 不经过 Spring 代理，b 上的 @Transactional 失效。
  5. 一级缓存当业务缓存：一级缓存是 SqlSession 级别，请求结束就没了，跨请求无效；业务缓存用 Redis。
  6. 扣库存不在事务里读改写：三步分开会超卖，用 @Transactional 包成一个方法。
  7. 连接不归还：手动 getConnection 后不 close，或把 Connection 存进静态变量，池被占满后新请求卡住。
  8. 按 199.5 元 double 写 DECIMAL 列：金额用整数分 amountFen = 19950 运算，不要用 double 元做账。
  9. 单例 Bean 放可变实例字段：Controller/Service 是单例多线程，请求级状态放实例字段会串号。
  10. DTO 直接暴露数据表的行：把实体直接返回前端，字段和内部状态泄露；用 VO 隔离，userId 转字符串。
  11. 密码写死进 yml 提交：用 ${DB_PASSWORD} 环境变量占位，配置打进镜像会导致改超时要重新构建。
  12. 花太多时间学 JSP：本课走 Boot + JSON 路线，JSP 知道位置即可，重点放在 JDBC/MyBatis/Spring 事务/Boot 配置。

  • 一次请求从浏览器到 PreparedStatement 经过八层：Tomcat 线程 → Filter 链 → DispatcherServlet → Controller → Service → Mapper → PreparedStatement；每一层只做自己那一段，userId 始终是值。
  • JDBC 四个对象：DataSource/Connection/PreparedStatement/ResultSet。SQL 参数一律用占位符，禁止拼接用户输入；连接用完归还连接池，Statement/ResultSet 用 try-with-resources 关闭。
  • MyBatis 的 #{} 是预编译参数（安全），${} 是字符串拼接（只用于完全控制的列名/表名 + 白名单）。一级缓存活不过会话，业务缓存用 Redis。
  • Spring IoC 容器创建并注入依赖，Bean 默认单例；AOP 靠代理织入事务和日志。事务加在 public 的、从代理调用的方法上；自调用的 this.b() 不走代理，事务失效。
  • 事务传播先掌握 REQUIRED（加入或新建）和 REQUIRES_NEW（总是另开）。扣库存的“读—判断—改”必须包在一个事务方法里，否则并发超卖。
  • Spring Boot 3 + Java 17：配置写 application.yml，数据源用 HikariCP，自动装配按条件注解注册 Bean；包名是 jakarta.*，不要混用 javax.*。
  • 金额用整数分（amountFen = 19950）运算，userId 给前端用字符串 "10001"；DTO/VO 隔离数据库行和前端契约；JSP 知道位置即可，新项目走 JSON + 前端分离。
