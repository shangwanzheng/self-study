01 / 基础概念

一张图看懂：前处理 → 求解 → 后处理

工业软件做的事，本质就三步：把问题描述清楚、交给计算机算、把结果画给人看。

在你的电脑上

前处理PRE-PROCESSING

「把题目出清楚」
  • 导入几何、划分网格
  • 指定材料属性
  • 设定边界条件与载荷
  • 选择要输出哪些结果
上传题目.psc + .psd
在云服务上

求解器SOLVER

「真正动手算」
  • 把物理问题变成方程
  • 调用云端算力反复迭代
  • 算出每个节点的数值
  • 算完写出结果文件
取回答案.psr
在你的电脑上

后处理POST-PROCESSING

「把答案讲明白」
  • 把海量数字变成图
  • 曲线：趋势一眼看出
  • 表格：精确到每个数
  • 动画：过程动起来
生活类比 备菜洗、切、配调料 = 前处理› 开火炒灶台真正做功 = 求解器› 装盘品尝看色香味 = 后处理
02 / 系统架构

谁在本地，谁在云上？

记住一句话：你看得见的都在客户端，算得慢的都放在云上。

客户端（你的电脑）

CLIENT · DESKTOP

前处理

建模、网格、材料、边界条件

后处理

曲线、表格、动画

网 络
control socket
data socket

云服务（远程机房）

CLOUD · SERVER

求解器

吃掉大量算力，把方程解出来

结果数据

算完生成 .psr，等客户端来取

为什么这么分？求解要用到很多 CPU、跑很久，放在云上可以随用随开、算完释放；而画图、拖动视角要求「立刻响应」，放在本地才跟手。
03 / 五个文件

先别背文件名，先看它是怎么拼出来的

所有文件都以 ps 开头，后面那几个字母就是它的「职务说明」。

ps
= Poisson Soft
公司 / 产品的名字前缀。
看到 ps 开头，就是自家文件。
db= database数据库 —— 整个工程的总档案.psdb
pat= patch网格或几何相关的数据.pat
c= control控制信息 —— 告诉求解器「怎么算」.psc
d= data数据本体 —— 告诉求解器「算什么」.psd
r= results结果 —— 求解器算完给你的答案.psr
一句口诀：db 存工程 · pat 存网格 · c 发指令 · d 送数据 · r 收结果。
03 / 五个文件

前处理的四个文件

它们都产生在客户端。其中只有 .psc 和 .psd 会被送上云端。

.psdb

工程总档案PS + DATABASE

你在软件界面里做的每一步操作都存在这里：几何、网格、材料、边界条件、载荷、输出设置……相当于 Word 里的那个「源文件」。

只在客户端使用，不会上传
.pat

网格 / 几何数据PATCH

保存 patch（网格或几何相关的数据）。模型「长什么样、被切成了多少个小块」，这类信息就装在它里面。

前处理阶段的模型数据载体
.psc

控制文件PS + CONTROL

给求解器的「操作说明书」：用什么算法、算多久、步长多大、要输出哪些结果。文件很小，但决定了整场计算怎么跑。

点击求解时上传到云端
.psd

数据文件PS + DATA

给求解器的「原材料」：节点、单元、材料参数、载荷数值等大块数据。模型越大，这个文件通常也越大。

点击求解时上传到云端
03 / 五个文件

后处理的文件：.psr

前面四个是「问题」，这一个是「答案」。

.psr
ps + r = Poisson Soft Results
求解器计算成功后生成的结果文件，
是后处理里所有图表的唯一数据来源。

谁生成它？WHO

云端的求解器。只有当计算正常收敛、求解成功之后，才会产生 .psr。

里面装什么？WHAT

每一个时间步 / 载荷步下，每个节点、单元的计算数值 —— 位移、应力、温度等等。

它在哪里？WHERE

生成在云端。客户端不会一次性把它整个搬回来，而是按需索取其中的一部分。

谁来读它？WHY

客户端的后处理模块。你看到的每一条曲线、每一格表格、每一帧动画，数据都来自这里。

05 / 后处理

后处理有三种形态：曲线、表格、动画

同样一堆数字，换三种方式讲给你听。

曲线

CURVE

看趋势。某个点的位移随时间怎么变、力随位移怎么涨，一眼就能看出拐点和峰值。

表格

TABLE

看数值。曲线上那个峰到底是 3.21 还是 3.28？要写进报告的精确数字在这里。

动画

ANIMATION

看过程。整个模型随时间怎么变形、云图颜色怎么扩散，一帧一帧播给你看。

05 / 后处理

重点：曲线和表格是「一路」，动画是「另一路」

这一点在新人排查问题时特别有用 —— 曲线不对，表格通常也不对；但动画可以单独出问题。

曲线 ＋ 表格

同一套数据，两种呈现

同一批取数请求→ 同一份返回数据→ 画成曲线 列成表格
本质是「某几个点在各个时刻的数值序列」，画出来是线，列出来是表。

动　画

独立的一条处理路径

单独的取数请求→ 逐帧全模型数据→ 渲染成连续帧
要的是「整个模型在每一帧的样子」，数据量远大于曲线，所以单独走一套流程。
记忆方式：曲线和表格问的是「几个点、很多时刻」；动画问的是「所有点、每一帧」。问的问题不一样，要的数据自然不一样。
06 / 通信机制

后处理怎么把云端的数据拿回来？两条 Socket

客户端通过 control socket 和 data socket 两条通道，向云服务请求后处理数据。

客户端

CLIENT · 后处理模块
›我要第 12 步的位移曲线
›我要第 3 帧的整模型云图
›收到数据后画图给用户看
›››
control socket客户端 → 云服务：发出「我要什么数据」的请求
‹‹‹
data socket云服务 → 客户端：回传求解器算出来的结果数据（.psr 的内容）

云服务

CLOUD · 求解器
›收到请求，去 .psr 里翻
›取出对应那段结果
›从数据通道送回客户端
为什么要分成两条？请求「又小又频繁」，数据「又大又连续」。分开走，大数据传输就不会把小请求堵住，界面点哪响哪。

从建模到看图，完整走一遍

08 / 动画后处理

三种分支，各走各的路

三选一、互斥执行。它们的差别其实就一句话：云图这活儿，是云端干还是客户端干。

客户端做的事 云服务做的事 云服务返回的数据 客户端本地计算（关键差异）
01

刚体后处理

1请求动画数据
2云端解析 .psr
3一次请求，按帧依次下发
本分支到此结束 · 没有云图
最省事的一支：只要动画数据，没有云图环节，走完三步就直接进入图例生成。
02

有限元柔性体后处理

1请求动画数据
2云端解析 .psr、轻量化
3一次请求，按帧依次下发
4再请求云图数据
5云端解析、计算、轻量化
6按帧下发，含云图 + 热点
7云图动画数据落盘
解析、计算、轻量化全在云端做，由 C++ 动态库 cloudvtk 完成。
03

模态柔性体后处理

1请求动画数据
2云端解析 .psr
3一次请求，按帧依次下发
4动画数据落盘
5本地计算云图：应力 / 应变 / 热点
6云图动画数据落盘
这一支不向云服务要云图：云服务只负责下发动画数据，云图留给客户端自己算。

09 / 代码里的后处理

代码里，「去云端拿数据」被拆成了三层

对应模块 PSPostData。上层只管「我要什么」，底下两层负责「怎么要到」。

▲  后处理界面 / 业务逻辑　只要调用一句 fetchData(要什么, 拿到后干什么)
框架层

PSPostData

缓存 + 回调
先看这份数据是不是已经拿过了，拿过就直接给；没拿过才往下走。数据回来后负责拼装分块，再通知所有在等它的人。
分发层

PSMessageDispatcher

通道分配 + 消息路由
给每个请求分一个通道号 opno，记住「这个号的数据回来后该交给谁」。号占满了就先排队，有空号了自动补发。
传输层

PostDataClient

两条 WebSocket
真正连网的一层：ctrl 通道发出文本请求、data 通道收回二进制数据，顺带管连接、断线重连和心跳保活。
▼  云服务　Post Data Server
分层的好处：写业务的人不用关心通道号和 WebSocket，只需要说清楚「我要什么」；换了网络实现，上层代码一行都不用改。
09 / 代码里的后处理

通道号 opno：像去银行取个号

同一时间会有很多请求在飞。靠一个小小的号码，每份回来的数据都能找到自己的主人。

一共 126 个号（1 ~ 126）

每个格子就是一个通道。亮着表示正被某个请求占用，用完就熄灭、把号还回号池。

1 ~ 64　　直接发出去的请求 65 ~ 126　排队后补发的请求
opno…… 这一帧 / 这一段的数据 ……
回包的第一个字节就是号码，分发层照着它把数据交给对的处理函数。
1
取号

发请求之前先申请一个空闲 opno，同时登记好「这个号的数据回来后由谁处理」。

2
带号出门

请求里塞上 opNo 和 messageId，从 control 通道发给云服务。

3
认号回家

data 通道收到二进制数据，首字节就是 opno，分发层照号找到登记的处理函数。

4
用完还号

数据收全后释放通道。号被占满时新请求不会丢，先进队列，有号了自动补发。

09 / 代码里的后处理

要回来的数据，都暂存在哪？

三个地方各管一段。理解了它们，就明白「为什么第二次点同一个结果会秒开」。

LAYER 1

成品数据缓存

已经解析好、可以直接拿去画图的业务数据。同一份数据再要一次，直接从这里给，不再打扰云服务。

所以：第二次切回同一条曲线、同一帧，几乎是瞬间出来的。
LAYER 2

请求排队队列

还没连上网、或者 126 个号全被占满时，请求不会被丢掉，而是先排进队列等着。

一旦连上了、或者有请求还了号，队列里的请求会被自动补发出去。
LAYER 3

轻量化数据

从压缩包里解出来的几何 + 物理量：点、边、面，以及位移、应力、应变、速度等等，按零件分开存。

动画每一帧长什么样、什么颜色，最后都是从这里取的。

大数据会分块回来

CHUNKED RESPONSE

收到第 1 块→ 合并进已有数据→ 继续收下一块→ 收到最后一块才回调
一次「取数」在日志里可能对应好几条回包，只有最后一块到齐，界面才会刷新。
09 / 代码里的后处理

一次「我要这段数据」的完整旅程

把三层串起来，八步就走完了。

1
开口要

界面调用 fetchData，说清楚要什么、拿到后干什么

2
先翻缓存

要过的直接给，一个网络请求都不用发

3
领一个号

没要过，就向分发层申请一个空闲 opno

4
没号就排队

没连上网或号被占满时，请求先进队列，不会丢

5
从 ctrl 发出

请求带着 opNo 和 messageId 走控制通道上云

6
从 data 收回

二进制数据回来，首字节就是 opno

7
认号 + 拼块

按号找到处理函数，解析数据并把分块合并起来

8
收齐 · 回调 · 还号

存进缓存、通知所有等待的人、把通道号释放掉
